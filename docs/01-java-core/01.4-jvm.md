## 模块一：运行时内存区域与对象

### 1. 核心原理

- **线程私有**：程序计数器（字节码行号，唯一无 OOM 区域）、虚拟机栈（栈帧=局部变量表/操作数栈/动态链接/返回地址，`StackOverflowError`/OOM）、本地方法栈（Native 方法）。
- **线程共享**：堆（对象实例 + 数组，GC 主战场，分新生代 Eden/S0/S1 + 老年代）、方法区/元空间（类元数据、运行时常量池；JDK8 起用**元空间（本地内存）**替代永久代，`-XX:MaxMetaspaceSize` 控制）、字符串常量池（JDK7+ 移入堆）。
- **对象创建**：`new` → 类加载检查 → 分配（指针碰撞/空闲列表，TLAB 线程本地分配缓冲减少竞争）→ 零值初始化 → 设置对象头 → 执行 `<init>`。
- **对象头**：Mark Word（hash、GC 年龄、锁状态）、类型指针；数组对象多一个 length 字段。
- **可达性分析**：GC Roots（栈帧局部变量、静态属性、常量、JNI 引用）不可达即回收；`finalize` 只执行一次且不保证执行，**生产禁止依赖**。

### 2. 生产落地

- **堆布局（生产常用）**：`-Xms` = `-Xmx`（避免动态扩容抖动）；`-Xmn` 或 G1 直接 `-XX:MaxGCPauseMillis=200`；元空间 `-XX:MaxMetaspaceSize=512m`（防无限吃本地内存）。
- **内存dump 预案**：`-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/logs/`，OOM 时自动留证据。

```bash
# 生产 JVM 启动参数模板（JDK8，G1）
java -Xms4g -Xmx4g -Xss512k \
  -XX:MaxMetaspaceSize=512m \
  -XX:+UseG1GC -XX:MaxGCPauseMillis=200 \
  -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/logs/dump/ \
  -XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/data/logs/gc.log \
  -jar app.jar
```

### 3. 踩坑规避

| 现象 | 根因 | 对策 |
|------|------|------|
| `Metaspace` 持续增长不释放 | 动态类生成频繁（CGLIB/脚本引擎/反射）或类加载器泄漏 | 排查 ClassLoader 泄漏；设 `MaxMetaspaceSize` 兜底 |
| 老年代增长缓慢但 Full GC 频繁 | 大对象直接进老年代 / 晋升失败 | 调 `-XX:PretenureSizeThreshold`；排查大数组/大 JSON |
| GC 后吞吐骤降 | `-Xms != -Xmx` 反复扩容 / 容器内存 limit 被 K8s OOMKill | 容器内感知 limit（JDK10+ `UseContainerSupport`） |
| `Direct buffer` OOM | NIO/Netty 堆外内存无 GC 管理 | `-XX:MaxDirectMemorySize` 显式限制 |

### 4. 优化进阶

- **G1 调优路径**：先设 `MaxGCPauseMillis` 目标 → 观察 GC 日志（`-Xlog:gc*:file=...` JDK9+）→ 调整堆大小/Region 大小，**不要一上来堆一堆细粒度参数**。
- **ZGC/Shenandoah（JDK11+/JDK12+）**：暂停时间亚毫秒级（TB 级堆），适合大堆低延迟；吞吐略降，需实测。

### 5. 选型对比

| 回收器 | 停顿 | 吞吐 | 适用 |
|--------|------|------|------|
| Serial/Serial Old | 长 | 高 | 客户端、小堆 |
| Parallel Scavenge | 中 | **最高** | 后台计算型批处理 |
| CMS（JDK9 废弃，14 移除） | 短 | 中 | 历史老系统 |
| **G1（JDK9+ 默认）** | 可设目标 | 中 | **通用服务端首选** |
| ZGC | 亚毫秒 | 中 | 大堆低延迟 |

## 模块二：类加载机制

### 1. 核心原理

- **生命周期**：加载 → 验证 → 准备（静态变量零值）→ 解析 → 初始化（`<clinit>`，静态变量赋真值）→ 使用 → 卸载。
- **双亲委派**：`Bootstrap → Extension → Application → Custom`，向上委派查找，避免核心类被篡改、保证唯一性。**破坏案例**：JDBC SPI（`Thread.contextClassLoader` 回插）、Tomcat（WebApp 隔离）、OSGi。
- **类初始化时机（主动引用）**：`new/getstatic/putstatic/invokestatic`、反射、初始化子类先初始化父类、主类；接口默认方法不初始化接口本身（JDK8 起）。

### 2. 生产落地

- **自定义类加载器场景**：插件化、热部署、类隔离（同一 JVM 跑多版本 SDK）；加密 class 字节码加载。
- **SPI 机制**：`META-INF/services/` + `ServiceLoader`，面向接口编程的标准解耦手段（JDBC、SLF4J 均如此）。

### 3. 踩坑规避

1. **`ClassCastException` 但"明明是同一个类"**：不同 ClassLoader 加载的同类在 JVM 中是**两个类**，互相不能强转。检查 Web 容器/模块化场景的加载器层级。
2. **静态块异常导致 `NoClassDefFoundError`**：类初始化失败一次后**后续引用都抛 `NoClassDefFoundError`**（不会重试初始化），定位要看首次失败堆栈。
3. **元空间 OOM**：反复生成新类（Groovy 脚本、LambdaMetafactory 高并发、大量代理类），GC 不会回收"无用类加载器"引用的类。

### 4. 优化进阶

- **类加载耗时优化**：`-Xverify:none`（关闭验证，仅开发期用）、CDS/AppCDS（JDK10+ 类数据共享，加速启动）、AOT 编译（Spring AOT）。

### 5. 选型对比

| 加载模型 | 隔离性 | 灵活性 | 场景 |
|---------|--------|--------|------|
| 双亲委派（默认） | 弱 | 低 | 普通应用 |
| 打破委派/线程上下文 | 强 | 高 | SPI、插件 |
| 完全自定义层级 | 极强 | 极高 | Tomcat、OSGi |

## 模块三：GC 算法与回收器

### 1. 核心原理

- **对象存活判定**：引用计数（无法解决循环引用，Java 不用）→ **可达性分析（GC Roots 追溯）**。
- **回收算法**：标记-清除（碎片）、复制（Eden 幸存者，浪费一半空间）、标记-整理（老年代，无碎片但移动开销）。
- **分代假说**：绝大多数对象朝生夕死 → 新生代复制算法；老年代标记-整理。
- **GC 类型**：Minor GC（新生代，频繁快）、Major/Full GC（全堆/老年代，慢，STW）。
- **晋升规则**：对象熬过 Minor GC 次数 ≥ `MaxTenuringThreshold`（默认 15）晋升老年代；大对象直接进老年代。

### 2. 生产落地

- **GC 日志（必开）**：JDK8 `-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:gc.log`；JDK9+ 统一 `-Xlog:gc*=info:file=gc.log:time,uptime,level,tags:filecount=5,filesize=100m`。
- **常用分析工具链**：`gceasy.io` / `GCViewer` 看趋势；`jstat -gcutil <pid> 1s` 实时；`arthas` 在线诊断。

```bash
# 生产值班常用命令
jstat -gcutil <pid> 1000        # 各区域使用率 + GC 次数/耗时
jmap -histo:live <pid> | head -20   # 对象分布 Top（先触发一次 Full GC）
jstack <pid> > thread.dump      # 线程快照
```

### 3. 踩坑规避

1. **`System.gc()` 误用**：业务代码调用触发 Full GC（可用 `-XX:+DisableExplicitGC` 禁止）；RMI/NIO 内部也可能触发。
2. **晋升失败导致 Full GC 风暴**：新生代 Survivor 放不下存活对象 → 提前晋升/担保失败。看日志 `promotion failed`。
3. **频繁 CMS concurrent mode failure**：CMS 并发标记期间老年代被填满 → 退化为 Serial Old。降级方案：调 `CMSInitiatingOccupancyFraction` 提前触发、减小新生代大对象直接晋升。
4. **GC 日志不轮转**：默认不轮转 → 磁盘打满 → 服务宕。务必配 `filecount/filesize`。

### 4. 优化进阶

- **调优顺序**：先确认目标（延迟优先/吞吐优先）→ GC 日志量化（停顿 P99、吞吐 = GC 时间/总时间）→ 再调参；**每次只调一个参数并观察**。
- **代码层减少 GC 压力**：对象池化（谨慎，大对象才值得）、减少临时大对象（大 `String` 拼接用 `StringBuilder`、避免一次性 `toArray` 巨量数据）、堆外内存复用（Netty `PooledByteBuf`）。

### 5. 选型对比

| 回收器组合 | 停顿 | 吞吐 | 内存 | 生产建议 |
|-----------|------|------|------|----------|
| Parallel GC | 秒级 | 最高 | 中 | 批处理/离线任务 |
| CMS | 百 ms 级 | 中 | 中（浮动垃圾） | 仅存量 JDK8 维护 |
| G1 | 百 ms 级可调 | 中 | 略高（RememberSet） | JDK8 后期+JDK11/17 默认 |
| ZGC | <10 ms | 中 | 高（着色指针） | 大堆低延迟（JDK17 生产可用） |

## 模块四：JVM 参数与线上排查 SOP

### 1. 核心原理

- **关键参数三区**：内存（`-Xms/-Xmx/-Xmn/-XX:MaxMetaspaceSize/-XX:MaxDirectMemorySize`）、GC（`-XX:+UseG1GC/-XX:MaxGCPauseMillis`）、诊断（`HeapDumpOnOutOfMemoryError`、GC 日志、`-XX:+PrintGCApplicationStoppedTime`）。
- **排查工具**：`jps`（进程）、`jstat`（GC 统计）、`jmap`（内存 dump/直方图）、`jstack`（线程）、`jinfo`（动态查看/修改参数）、Arthas（**生产在线诊断首选**：`trace/watch/monitor/thread -b`）。

### 2. 生产落地（排查 SOP）

| 症状 | 第一步 | 第二步 | 第三步 |
|------|--------|--------|--------|
| CPU 飙高 | `top -Hp <pid>` 找线程 | `printf %x tid` → `jstack` 定位 | 定位到代码/死循环 |
| 内存 OOM | HeapDump 已自动落盘 | `jhat`/MAT/JProfiler 分析**支配树** | 找泄漏引用链 |
| 频繁 Full GC | `jstat -gcutil` 看老年代趋势 | `jmap -histo` 看对象 | 代码/配置定位 |
| 接口 RT 毛刺 | GC 日志看停顿点 | `arthas trace` 看方法耗时 | 锁竞争/外部依赖 |
| 线程死锁 | `jstack` 搜 deadlock / `arthas thread -b` | 修复加锁顺序 | — |

### 3. 踩坑规避

- **生产慎用 `jmap -dump:live`（无 format 参数的老版本）**：会触发 Full GC 导致服务 STW 秒级；改用 `-XX:+HeapDumpOnOutOfMemoryError` 或 Arthas `heapdump`（同样注意影响）。
- **`jstack` 多次采样**：一次快照可能错过，至少间隔 10s 采 3 次对比。
- **容器环境内存误判**：JVM 看到的 `-Xmx` 之外还有堆外；K8s limit = 堆 + 堆外 + 元空间 + 线程栈 + JVM 自身，按 limit 分配。

### 4. 优化进阶

- **JDK17+ 新诊断**：`-Xlog:gc+heap=debug` 免费看堆详情；JFR（Java Flight Recorder）低开销持续采集，`jfr` 分析延迟热点。
- **Arthas 常用三板斧**：`thread -b`（谁阻塞了别人）、`watch`（观测返回值/异常）、`trace`（方法内部耗时分布），做到**不改代码不停机定位线上问题**。

### 5. 选型对比

| 工具 | 侵入性 | 功能 | 场景 |
|------|--------|------|------|
| jstat/jstack/jmap | 低 | 单点统计 | 命令行值班 |
| GCViewer/gceasy | 无 | 日志可视化 | GC 趋势复盘 |
| MAT/JProfiler | 无（离线） | 深度内存分析 | OOM 事后分析 |
| Arthas | 低（在线） | 动态诊断 | **生产在线排障首选** |
| JFR | 极低 | 持续画像 | 性能基线/延迟分析 |

## 模块五：垃圾回收深度

### 核心原理

- **可达性分析**（主流）：从 GC Roots（虚拟机栈/本地方法栈引用、方法区静态属性与常量、同步锁持有对象、JNI）向下搜索，无引用链即回收；引用计数法因循环引用缺陷被主流 JVM 弃用；
- 四种引用：强（永不回收）→ 软（**OOM 前回收**，缓存场景）→ 弱（**下次 GC 即回收**）→ 虚（跟踪回收，须配 ReferenceQueue）；
- **finalize() 已过时**（JDK 9 弃用、18 待移除），资源清理用 `try-with-resources` / Cleaner，别赌 Finalizer 线程；
- 分代依据：新生代"朝生夕死"适合**复制**；老年代存活率高适合**标记-整理/清除**；ZGC 早期即非分代设计——**分代不是必须，是工程折中**。

### 生产落地

| 算法 | 思想 | 适用 |
|------|------|------|
| 标记-清除 | 标死亡统一回收 | 老年代（有碎片） |
| 标记-复制 | 存活拷至另一块，**可用内存减半** | 新生代（Eden+S0/S1） |
| 标记-整理 | 存活移向一端 | 老年代（无碎片） |
| 分代收集 | 各代选算法 | 整堆 |

晋升规则：Eden → Minor GC 幸存进 Survivor（年龄 1）→ 每次 Minor GC 年龄 +1 → 达 `-XX:MaxTenuringThreshold`（Parallel 15 / CMS 6）或 Survivor 同年龄对象超 50%（`-XX:TargetSurvivorRatio`）→ 老年代；大对象直接进老年代。

### 踩坑规避

- **CMS 已死**：JDK 9 弃用、**JDK 14 移除**。新应用不要选，历史系统升级 JDK 时注意默认收集器从 Parallel 变 G1 的行为差异；
- CMS 三坑：CPU 敏感（并发线程抢核）、**浮动垃圾**（并发标记期间新垃圾本次不清，可能晋升失败触发 Full GC）、空间碎片（标记-清除）；
- G1 的"可预测停顿"（`-XX:MaxGCPauseMillis`）是**软目标**，不保证每次达标，不要当 SLA 承诺；
- 超过半个 Region 的对象是 **Humongous**，直接进老年代连续 Region——大对象（大 List/Map 缓存）滥用会拖垮 G1；
-晋升年龄调大（Survivor 区增大）可减少老年代增长，但 Survivor 过小会导致对象提前晋升。

### 优化进阶

- **收集器选型**：吞吐优先（离线计算/批处理）→ Parallel Scavenge；低延迟（在线业务）→ **G1（JDK 9+ 默认）**；超大堆/亚毫秒停顿 → **ZGC**（JDK 11 可用，21 分代化，最大 16TB，停顿与堆大小几乎无关）；
- G1 调优入口：Region 大小（`-XX:G1HeapRegionSize`，1~32MB，Humongous 阈值 = Region/2）、暂停目标、IHOP（`-XX:InitiatingHeapOccupancyPercent` 并发标记启动水位）；
- GC 日志：JDK 9+ 统一 `-Xlog:gc*:file=...:time,uptime,level,tags`（无需排列组合参数）；
- 大促前预案：预估峰值对象分配速率 → 反推 Survivor 容量与晋升阈值 → 灰度验证 Full GC 频率。

### 选型对比

| 收集器 | 线程模型 | 老年代算法 | 优势 | 适用 | 生命周期 |
|--------|----------|-----------|------|------|----------|
| Serial | 单线程 | 标记-整理 | 简单 | Client 模式 | 长期 |
| Parallel Scavenge | 多线程 | 标记-整理 | 吞吐量最高 | 后台计算 | JDK 8 默认 |
| CMS | 并发 | 标记-清除 | 停顿最短（有代价） | 低延迟旧系统 | JDK 14 移除 |
| **G1** | 并发+并行 | 标记-整理（整体） | 可预测停顿 + Region 化 | **大堆在线业务** | **JDK 9+ 默认** |
| ZGC | 并发 | 标记-复制 | 亚十毫秒、与堆大小无关 | 超大堆/极致低延迟 | JDK 11+（21 分代） |

**决策口诀**：新应用直接 G1；堆 ≥ 16G 且要求亚十毫秒 → ZGC；老系统在 CMS 上别恋战，规划迁 G1/ZGC。
