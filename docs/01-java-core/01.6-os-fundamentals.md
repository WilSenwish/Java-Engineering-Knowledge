## 模块一 · 用户态/内核态与系统调用

### 1. 核心原理

**用户态/内核态是 CPU 特权级别**，不是进程类型。进入内核态的三类事件：

| 事件 | 触发方式 | 同步性 | 典型场景 |
|------|----------|--------|----------|
| 系统调用（Trap） | 当前指令主动触发（`syscall`/`ecall`） | 同步 | `read()`、`send()` |
| 硬件中断 | 外部硬件触发，与当前指令无关 | 异步 | 定时器、网卡、磁盘 |
| 同步异常 | 当前指令触发 | 同步 | 除零、Page Fault（可能是可恢复的懒分配/COW） |

**系统调用 vs 库函数**：库函数（如 glibc `read()`）在用户态按 ABI 准备系统调用号和参数，再执行特权指令进入内核——不是一个层次的概念。

### 2. 生产落地

**Java 视角的系统调用映射**：文件 IO（`FileInputStream` → `read` 系统调用）、网络 IO（`Socket` → `send`/`recv`）、线程阻塞唤醒（`park` → `futex`）、内存分配（`mmap`/`brk`）。性能剖析（async-profiler/arthas）看到的系统态耗时即内核态时间。

**用户态/内核态切换 ≠ 线程上下文切换**：只有调度器切换到另一个执行实体才是上下文切换。系统调用很快返回时无上下文切换——这是「频繁系统调用开销大」与「线程切换开销更大」的辨析关键。

### 3. 踩坑规避

- 把 Page Fault 一律当程序错误：**正常场景也会触发**（懒分配、COW、缺页调页），只有内核无法修复时才投递 SIGSEGV；
- 误判 load 高 = CPU 忙：load 统计的是 **R（可运行）+ D（不可中断睡眠）** 任务数，D 状态高说明在等块设备/网络存储/Swap，此时 CPU 可能空闲——需结合 `vmstat` 的 wa/b/`pidstat` 一起看；
- 连接数爆了只看应用层：先查 `ulimit -n`（进程 fd 上限）与内核内存。

### 4. 优化进阶

**系统调用批量化的本质**：一次系统调用的固定成本（特权切换 + 内核入口/出口 + 权限检查）远高于多带几个参数，所以有 `readv/writev`（聚合 IO）、`io_uring`（共享环形缓冲批量提交，Linux 5.1+）等批量接口——与 Redis Pipeline、MySQL 组提交是同一种思想。

### 5. 选型对比

| 机制 | 成本量级 | 适用 |
|------|----------|------|
| 普通函数调用 | 纳秒级 | 用户态内部计算 |
| 系统调用 | 百纳秒~微秒级 | 必须内核服务的 IO/内存/进程操作 |
| 线程上下文切换 | 微秒级（同进程）/ 数十微秒（跨进程含 TLB 失效） | 并发调度 |
| 进程创建 fork | 毫秒级 | 隔离性要求高的场景（Worker 进程） |

## 模块二 · 进程/线程模型与调度

### 1. 核心原理

- **进程 = 资源分配与隔离单位**（独立地址空间、文件句柄）；**线程 = CPU 调度执行单位**（共享堆/方法区，私有栈/PC/寄存器）；
- **PCB/TCB**：Linux 不严格拆分，统一 `task_struct`，靠资源结构是否共享区分——**地址空间/文件表是资源边界，栈/寄存器/PC 是执行现场**；
- **调度算法谱系**：FCFS（护航效应）→ SJF（饥饿）→ RR（时间片权衡）→ 优先级（饥饿）→ MLFQ（按行为升降级）；Linux 主线 CFS（vruntime 公平）+ Linux 6.6+ EEVDF；
- **同步原语**：互斥锁/读写锁/信号量/屏障/条件变量——Java `synchronized`、`ReentrantLock`、`Semaphore`、`CyclicBarrier`、`Condition` 分别是 OS 层的封装。

### 2. 生产落地

- **JVM 线程数规划**：`-Xss`（默认 1MB）决定单线程栈占用，万级线程仅栈就 GB 级——高并发用线程池 + 异步化（见 [01.3 并发 · 线程池模块](01.3-concurrency.md)）；
- **CPU 密集型 vs IO 密集型**：线程数 ≈ CPU 核数（前者）/ CPU 核数 × (1 + 等待/计算比)（后者）；
- **Java 死锁检测**：`jstack -l <pid>` 或 `ThreadMXBean.findDeadlockedThreads()`——对应 OS 层的资源分配图环检测。

### 3. 踩坑规避

- **僵尸进程**：父进程不 `wait()` 回收已退出子进程，内核残留 PCB 占内存——Java 中表现为 `Process.waitFor()` 未调用；
- 多线程一定更快？线程数远超核数后，上下文切换 + 缓存失效 + 锁竞争使吞吐延迟双降；
- 跨进程共享状态图省事用共享内存：忘了配信号量/`futex` 同步就是数据竞争。

### 4. 优化进阶

**线程模型与 GC 的联动**：JVM 并行 GC 线程数、G1 并发标记线程都吃 CPU 配额；容器化环境下 `-XX:ActiveProcessorCount` 按 cgroup 限额设置，避免按宿主机核数超配。

**上下文切换的缓存视角**：同进程线程切换保留 TLB 与 L1/L2 缓存局部性，跨进程切换几乎全部失效——这就是「线程池优于进程池」的硬件层根因。

### 5. 选型对比

| 通信/并发方式 | 隔离性 | 开销 | 数据共享 | Java 场景 |
|--------------|--------|------|----------|-----------|
| 多进程 + IPC | 强 | 高 | 需序列化/共享内存 | 多 JVM 部署、Worker 隔离 |
| 多线程 | 弱（互相影响） | 低 | 直接共享堆 | **服务内并发默认形态** |
| 协程/虚拟线程 | 弱 | 极低 | 直接共享堆 | JDK 21 虚拟线程高 IO 并发 |
| 事件循环（epoll） | 单线程顺序 | 最低 | 无竞争 | Redis/Netty/Node 模型 |
