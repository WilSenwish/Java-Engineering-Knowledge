## 模块一 · 设计原则：SOLID 与补充法则

### 1. 核心原理

**七大原则总表**（SOLID 五条 + 补充两条）：

| 原则 | 一句话定义 | 违反的典型信号 |
|------|------------|----------------|
| SRP 单一职责 | 一个类只承担一个引起变化的原因 | 一个类同时改需求 A 和需求 B |
| OCP 开闭 | 对扩展开放，对修改封闭 | 加功能就改老代码，回归风险高 |
| LSP 里氏替换 | 子类能完全替代父类不出错 | 子类重写后抛异常/空实现 |
| DIP 依赖倒置 | 高层与低层都依赖抽象，面向接口编程 | 业务代码直接 new 具体实现 |
| ISP 接口隔离 | 客户端不依赖不需要的方法 | 实现类大量 `throw new UnsupportedOperationException` |
| LoD 迪米特 | 对象对其他对象了解最少 | `a.getB().getC().doSomething()` 链式跨层调用 |
| CARP 合成复用 | 优先组合/聚合，少用继承 | 继承树过深，为复用强行继承 |

### 2. 生产落地

**依赖倒置的工程形态**：Spring 的依赖注入即 DIP 的标准实践——Controller/Service 依赖接口，容器启动时装配具体实现；MyBatis 的 Mapper 接口 + SqlSession 模板同理（见 [02.3](../02-backend-components/02.3-spring-mybatis.md)）。

**合成复用的工程形态**：Ragent 项目中大量"接口 + 多实现 + 策略工厂"结构——如 LLM 客户端 `AiClient` 接口 + 多 Provider 实现，通过组合注入而非继承扩展（见 [07.1](../07-business-cases/07.1-projects.md) 设计模式映射表）。

### 3. 踩坑规避

- **为用模式而用模式**：简单 if-else 能解决的不要上策略工厂——模式的价值在"变化被隔离"，没有变化就是过度设计；
- **接口爆炸**：ISP 走到极端给每个方法建接口——按"客户端视角"拆接口，不是按方法拆；
- **继承滥用**：CARP 的实践底线——"is-a" 才继承，"has-a" 用组合。

### 4. 优化进阶

**原则冲突时的裁决顺序**：OCP > DIP > SRP > 其余。开闭是目标，依赖倒置是手段，单一职责是拆解依据。评审中争论"要不要拆类"时，用 SRP 的"引起变化的原因"计数法裁决：数一数这个类有几个独立的修改理由。

### 5. 选型对比

| 维度 | 继承 | 组合 |
|------|------|------|
| 耦合时机 | 编译期静态绑定 | 运行期动态装配 |
| 扩展性 | 受父类约束 | 自由替换部件 |
| 适用 | 稳定的 is-a 关系 | 多变的 has-a 关系 |

## 模块二 · 单例模式深度：写法、破坏与防护

### 1. 核心原理

单例三要点：私有构造、静态访问点、线程安全。五种经典写法的本质差异在**初始化时机**与**同步代价**的取舍：

| 写法 | 初始化时机 | 线程安全机制 | 懒加载 |
|------|------------|--------------|--------|
| 饿汉式 | 类加载时 | JVM 类初始化保证 | ❌ |
| 静态内部类 | 首次 getInstance | JVM 类初始化保证 | ✅ |
| DCL | 首次 getInstance | volatile + 双重检查 | ✅ |
| 懒汉式（synchronized 方法） | 首次 getInstance | 方法级锁 | ✅（每次调用都同步，性能差） |
| 枚举 | 类加载时 | JVM + final | ❌ |

### 2. 生产落地

**静态内部类（懒加载首选）**：

```java
public class CacheManager {
    private CacheManager() {}
    
    private static class CacheManagerHolder {
        private static final CacheManager INSTANCE = new CacheManager();
    }
    
    public static CacheManager getInstance() {
        return CacheManagerHolder.INSTANCE;  // 触发内部类初始化，JVM 保证同步
    }
}
```

**DCL（需兼容老代码或需在构造中持有参数时）**：

```java
public class ServiceRegistry {
    private volatile static ServiceRegistry instance;  // volatile 不可省
    
    private ServiceRegistry() {}
    
    public static ServiceRegistry getInstance() {
        if (instance == null) {                       // ① 无锁快路径
            synchronized (ServiceRegistry.class) {
                if (instance == null) {               // ② 防重复创建
                    instance = new ServiceRegistry();
                }
            }
        }
        return instance;
    }
}
```

**volatile 的必要性**：`new` 的三步（分配内存 → 初始化 → 引用指向地址）可被重排，无 volatile 时另一线程可能看到"非空但未初始化"的引用（详见 [01.3 模块四 JMM](../01-java-core/01.3-concurrency.md) 的 happens-before 分析）。

**枚举（最安全）**：

```java
public enum GlobalConfig {
    INSTANCE;
    private String appName = "MyApplication";
    // GlobalConfig.INSTANCE.getAppName();
}
```

### 3. 踩坑规避

**两条破坏路径与防护**：

| 攻击 | 机理 | 防护 |
|------|------|------|
| 反射 | `setAccessible(true)` 绕过私有构造 | 构造函数内判空抛异常 |
| 序列化 | ObjectInputStream 经 Unsafe 创建新对象 | 定义 `private Object readResolve() { return instance; }` |

**DCL 的 volatile 遗漏**：面试与生产审查高频错误——去掉 volatile 在高并发下有 50% 概率拿到半初始化对象。

### 4. 优化进阶

**CAS 无锁单例**：`AtomicReference` + `compareAndSet(null, instance)` 自旋获取，无锁但高并发下可能创建多个临时对象（GC 压力）——仅性能极端敏感且低并发初始化时考虑。

### 5. 选型对比（最佳实践裁决）

1. **首选枚举**：简洁 + 天然防反射/序列化破坏（Effective Java 推荐）；
2. **需要懒加载**：静态内部类；
3. **老代码改造/构造需参数**：DCL + readResolve + 构造检查三件套；
4. **性能敏感且初始化并发低**：CAS 方案（评估自旋与临时对象开销）。
