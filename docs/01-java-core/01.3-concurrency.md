## 模块一：线程与进程基础

### 1. 核心原理

- **进程 vs 线程**：进程是资源分配基本单位（独立地址空间）；线程是 CPU 调度基本单位（共享进程内存，私有栈/程序计数器）。一个进程可含多线程。
- **线程创建**：继承 `Thread` / 实现 `Runnable`（无返回值）/ 实现 `Callable`+`FutureTask`（有返回值、可抛异常）/ 线程池（**生产唯一推荐方式**，避免频繁创建销毁）。
- **六种状态**：NEW → RUNNABLE → BLOCKED / WAITING / TIMED_WAITING → TERMINATED（JDK `Thread.State`）。

```java
// 生产标准：Callable + 线程池 + Future 超时控制
ExecutorService pool = Executors.newFixedThreadPool(8);
Future<Result> future = pool.submit(() -> doQuery());
try {
    Result r = future.get(3, TimeUnit.SECONDS);  // 超时快速失败，避免无限阻塞
} catch (TimeoutException e) {
    future.cancel(true);
    // 降级逻辑
}
```

### 2. 生产落地

- **线程数标定**：CPU 密集型 ≈ `N(cpu) + 1`；IO 密集型 ≈ `N(cpu) / (1 - 阻塞系数)`，阻塞系数 0.8~0.9 时 ≈ `N(cpu) × 2`~`N(cpu) × 10`，需压测校准。
- **线程命名**：自定义 `ThreadFactory` 按业务命名（`biz-order-worker-1`），出问题时 `jstack` 一眼定位。
- **上下文切换成本**：约 1~10 μs/次 + 缓存失效开销；无谓地"一请求一线程"在 C10K 下不可用。

### 3. 踩坑规避

| 现象 | 根因 | 对策 |
|------|------|------|
| `jstack` 大量 BLOCKED | 锁竞争（synchronized 块过大） | 缩小临界区；分段锁；无锁结构 |
| CPU 100% 但负载不高 | 死循环（如 JDK7 HashMap 并发死循环） | `top -H` 定位线程 → `jstack <pid>` 多次对比 |
| 请求偶发超时无规律 | 频繁 GC 或线程上下文抖动 | 看 GC 日志 + 线程状态分布 |
| `OutOfMemoryError: unable to create new native thread` | 线程数超限（`ulimit -u` / 堆外内存） | 有界线程池 + 拒绝策略 |

### 4. 优化进阶

- **`ThreadLocal`**：线程封闭，注意 **`remove()`**（线程池复用场景不清理会导致：① 内存泄漏 ② 脏数据串号）。`InheritableThreadLocal` 跨线程传递有局限（线程池场景失效），用 `TTL`（TransmittableThreadLocal）封装。
- **虚拟线程（JDK21）**：`Thread.ofVirtual()`，挂起时不占平台线程，适合**高并发 IO 密集型**；CPU 密集/临界区加锁密集场景收益有限。Spring Boot 3.2+ 可 `spring.threads.virtual.enabled=true` 开启。

### 5. 选型对比

| 方式 | 开销 | 返回值 | 异常 | 场景 |
|------|------|--------|------|------|
| 继承 Thread | 高 | 无 | 难捕获 | 不推荐 |
| Runnable | 高 | 无 | 内部吞 | 简单任务 |
| Callable+Future | 高 | 有 | 可捕获 | 需要结果/超时 |
| 线程池 | 低（复用） | 有 | 可捕获 | **生产默认** |
| 虚拟线程 | 极低 | 有 | 可捕获 | 高并发 IO（JDK21） |

## 模块二：线程协作与通信

### 1. 核心原理

- **`wait`/`notify`**：必须在 synchronized 块内（否则 `IllegalMonitorStateException`）；`wait` 释放锁并进入等待队列，被 `notify` 唤醒后重新竞争锁。JDK5+ 优先用 `java.util.concurrent` 的 `Condition`/`LockSupport`。
- **`sleep` vs `wait`**：

| 维度 | sleep | wait |
|------|-------|------|
| 所属类 | Thread 静态方法 | Object 实例方法 |
| 锁 | 不释放 | 释放（进入等待前必须持有锁） |
| 唤醒 | 超时自动 | notify/notifyAll/超时 |
| 用途 | 暂停执行 | 线程间通信 |

- **`join`**：等待目标线程终止（内部基于 `wait`）；`interrupt` 是协作式中断（置标志位，需目标线程响应，如抛 `InterruptedException` 或检查 `isInterrupted`）。

### 2. 生产落地

- **优雅停机**：`@PreDestroy` 中先置"停止接收"标志 → 等待存量任务完成（`executor.shutdown()` + `awaitTermination`）→ 再销毁。Spring Boot `server.shutdown=graceful`。
- **中断响应规范**：可中断方法捕获 `InterruptedException` 后**恢复中断状态**再退出：`Thread.currentThread().interrupt(); return;`——不可默默吞掉。

```java
// 规范的中断处理
public void run() {
    while (!Thread.currentThread().isInterrupted()) {
        try {
            Task t = queue.poll(1, TimeUnit.SECONDS);
            if (t != null) t.execute();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt(); // 恢复中断标志，退出循环
        }
    }
}
```

### 3. 踩坑规避

1. **`notify` 唤醒"错误"的等待者**：多个条件共用一个对象锁时，`notify` 随机唤醒一个可能不满足条件的线程。用 `ReentrantLock` + 多个 `Condition`（如"不满"、"不空"分离）。
2. **`wait` 未在循环中检查条件**：虚假唤醒（spurious wakeup）会导致提前执行。**必须 `while (!condition) wait();`**。
3. **`synchronized` 方法与 `wait` 的锁对象**：`synchronized` 方法锁的是 `this`，`wait` 也必须针对 `this`，别在同步块里对别的对象 `wait`。

### 4. 优化进阶

- **AQS 体系**：`ReentrantLock`（可中断、可超时、可公平）、`Semaphore`（限流）、`CountDownLatch`（等待 N 个完成）、`CyclicBarrier`（相互等待）均基于 AQS（state + CLH 队列）。
- **`CompletableFuture`**：异步编排（`thenApply`/`thenCombine`/`allOf`），注意默认线程池 `ForkJoinPool.commonPool()` 的争用——生产指定业务线程池。

### 5. 选型对比

| 协作工具 | 语义 | 场景 |
|---------|------|------|
| wait/notify | 底层 | 不直接用 |
| ReentrantLock + Condition | 显式锁 + 多条件 | 生产者消费者（有界阻塞队列内部即此实现） |
| CountDownLatch | 一次性等待 N 完成 | 主线程等分片任务汇总 |
| CyclicBarrier | N 方互相到达屏障 | 并行计算分阶段 |
| Semaphore | 许可限流 | 接口并发度控制 |

## 模块三：死锁与并发问题排查

### 1. 核心原理

- **死锁四必要条件**（缺一不可）：互斥、持有并等待（请求新资源时不释放已有）、不可剥夺、循环等待。**破坏任一即可预防**（如按固定顺序加锁破坏循环等待）。
- **活锁与饥饿**：活锁=线程互相"礼让"持续重试无进展；饥饿=某线程长期得不到资源（优先级不合理）。

### 2. 生产落地

- **加锁顺序规范**：跨多个锁的操作按全局约定顺序（如按资源 ID 升序）获取；code review 卡点。
- **锁超时**：`tryLock(timeout)` 替代无限 `lock()`，失败走降级/重试。

```java
// tryLock 超时模式
if (lock.tryLock(100, TimeUnit.MILLISECONDS)) {
    try {
        // 临界区
    } finally {
        lock.unlock();
    }
} else {
    // 降级：返回默认值 / 入重试队列
}
```

### 3. 踩坑规避

- **`jstack` 查死锁**：输出含 `Found one Java-level deadlock` 块，直接给出互相等待的线程栈；无此提示时搜 `BLOCKED` + `waiting to lock` 交叉比对。
- **`jvisualvm`/Arthas `thread -b`**：一键定位阻塞其他线程的"罪魁祸首"线程。
- **数据库死锁**：与 JVM 死锁排查同思路（`SHOW ENGINE INNODB STATUS` 看 LATEST DETECTED DEADLOCK），根因多为行锁顺序不一致 + 间隙锁。

### 4. 优化进阶

- **锁细化粒度**：锁范围=数据范围（如 `ConcurrentHashMap` 桶级锁）；读写分离用 `ReentrantReadWriteLock`（读多写少）。
- **无锁化**：`AtomicInteger`/`LongAdder`/`AtomicReference`；`LongAdder` 在高竞争计数场景比 `AtomicLong` 快数倍（Cell 分段，牺牲强一致性读）。

### 5. 选型对比

| 并发安全手段 | 粒度 | 吞吐 | 场景 |
|--------------|------|------|------|
| synchronized | 对象级 | 中（JDK6 后偏向/轻量/重量级演进） | 简单临界区 |
| ReentrantLock | 显式 | 中 | 需超时/中断/多条件 |
| ReadWriteLock | 读写分离 | 读高 | 缓存类读多写少 |
| Atomic/CAS | 变量级 | 高 | 计数器、状态机 |
| 线程封闭 | 无共享 | 最高 | ThreadLocal、不可变对象 |

## 模块四：JMM、volatile 与锁机制

### 1. 核心原理

- **JMM（Java 内存模型）**：定义多线程下共享变量的读写规则。核心手段：**happens-before**（程序顺序、volatile 变量、传递性等规则）+ 可见性/有序性保证；
- **volatile 语义**（两条）：① 可见性：volatile 写 happens-before 于后续读（**是 JMM 语义，不是"绕过 CPU 缓存"**）；② 有序性：通过插入**内存屏障**禁止指令重排序；
- **四种内存屏障**：LoadLoad（读序）/ StoreStore（写序）/ LoadStore / **StoreLoad（全能屏障，开销最大）**。保守策略：volatile 写前 StoreStore、写后 StoreLoad；volatile 读后 LoadLoad + LoadStore；
- **volatile 写-读组合 ≈ 锁的释放-获取语义**：写前的所有普通写对读后的操作可见（`flag` 状态标志位模式的原理）；
- **CAS（Compare And Swap）**：三操作数 V（当前值）/E（预期值）/N（新值），V=E 才原子更新。CPU 原子指令，`Unsafe.compareAndSwapInt` 实现；`AtomicInteger.getAndAddInt` = **do-while 自旋重试**（自旋锁机制）。

### 2. 生产落地

- **DCL 单例必须 volatile**：`new Singleton()` 三步（分配内存→初始化→赋值引用），无 volatile 可能重排为 1→3→2，T2 拿到未初始化对象：

```java
private volatile static Singleton instance;  // 禁止 2/3 重排 + 保证可见
public static Singleton get() {
    if (instance == null) {
        synchronized (Singleton.class) {
            if (instance == null) instance = new Singleton();
        }
    }
    return instance;
}
```

- **锁选型落地**：简单临界区 `synchronized`；需超时/中断/多条件 → `ReentrantLock`；读多写少 → `ReentrantReadWriteLock`（或 StampedLock）；单变量 → CAS 原子类。

### 3. 踩坑规避

1. **volatile 不保证原子性**：`inc++` 是读-加-写复合操作，5 线程各 500 次结果 < 2500。必须 synchronized/原子类；
2. **CAS 三大问题**：① **ABA**（A→B→A 误判未修改，用 `AtomicStampedReference` 加版本号）；② 自旋长时间不成功烧 CPU（`pause` 指令缓解）；③ 只能保护单个变量（多变量封装 `AtomicReference` 或加锁）；
3. **锁膨胀死磕**：`synchronized(String)` 锁字符串常量池缓存对象——不同业务可能锁到同一字符串，严禁；
4. **静态/实例 synchronized 混用**：两者锁的是不同对象（Class vs 实例），**不互斥**，以为互斥就会出并发 bug；
5. **StampedLock 写锁不可重入**：同线程再获取写锁 = 自我死锁；且不支持 Condition、中断不友好（不当使用 CPU 飙升）——用前读官方文档案例。

### 4. 优化进阶

- **synchronized 锁升级（JDK6+）**：无锁 → 偏向锁 → 轻量级锁 → 重量级锁，只升不降。**偏向锁 JDK15 默认关闭、JDK18 彻底废弃**（收益不明显 + 撤销需全局安全点开销大 + JVM 维护复杂）；
- **乐观锁 vs 悲观锁选型**：读多写少/低冲突 → CAS 乐观锁（无阻塞无死锁，失败重试）；写多高冲突 → 悲观锁（开销固定，避免重试烧 CPU）。**`LongAdder` 以空间换时间（Cell 分段）解决高冲突下的重试问题**，是计数场景首选；
- **锁消除/锁粗化**：JIT 自动优化——逃逸分析发现锁对象不会逃逸则消除锁；相邻同步块合并减少加锁次数。写热点代码避免阻碍这些优化。

### 5. 选型对比

| 方案 | 可见性 | 原子性 | 有序性 | 阻塞 | 场景 |
|------|--------|--------|--------|------|------|
| volatile | ✅ | ❌ | ✅ | 否 | 状态标志、DCL |
| synchronized | ✅ | ✅ | ✅ | 是 | 通用临界区 |
| ReentrantLock | ✅ | ✅ | ✅ | 可中断/可超时 | 需高级功能 |
| ReentrantReadWriteLock | ✅ | ✅（写） | ✅ | 读写分离 | 读多写少 |
| StampedLock | ✅ | ✅（写） | ✅ | 乐观读 | 读极多写少（慎用） |
| CAS 原子类 | ✅ | ✅（单变量） | ✅ | 否 | 计数器/状态机 |

## 模块五：线程池工程化（ThreadPoolExecutor 全解）

### 核心原理

七参数模型：`corePoolSize` / `maximumPoolSize` / `keepAliveTime+unit` / `workQueue` / `threadFactory` / `rejectedHandler`。执行流程四步：**① 运行线程 < core → 新建核心线程；② ≥ core → 入队；③ 入队失败且 < max → 新建非核心线程；④ ≥ max → 拒绝策略**。预热：`prestartCoreThread()` / `prestartAllCoreThreads()`。

核心线程默认不回收（`allowCoreThreadTimeOut=false`）；置 true 后按 keepAliveTime 回收。`getTask()` 中 `timed = allowCoreThreadTimeOut || wc > corePoolSize`：timed 用 `poll(timeout)`（超时退出 TERMINATED），否则 `take()`（WAITING 常驻）。

### 生产落地

- **阿里手册强制**：线程资源必须走线程池；**禁止 Executors 工厂**（Fixed/Single 的 LinkedBlockingQueue 默认无界、Cached 的 maximumPoolSize=Integer.MAX_VALUE、Scheduled 的 DelayedWorkQueue 无界 → 均 OOM 风险）；
- 必须显式命名线程（`ThreadFactoryBuilder.setNameFormat("biz-%d")` 或自实现 ThreadFactory），默认 `pool-1-thread-n` 无法定位问题；
- 队列选型：生产用**有界** ArrayBlockingQueue / 自定义有界 LinkedBlockingQueue；
- 异常语义差异：`execute()` 未捕获异常 → 线程终止并替补新线程；`submit()` 异常封装进 Future，线程复用——**生产优先 submit + Future 统一处理异常**；
- 动态调参：`setCorePoolSize/setMaximumPoolSize/setKeepAliveTime`；队列不可直接改（美团方案：去掉 capacity 的 final）。开源：**Hippo4j**、**Dynamic TP**。

### 踩坑规避

| 坑 | 后果 | 规避 |
|----|------|------|
| CallerRunsPolicy + 耗时任务 | 任务回退主线程执行，阻塞主线程恶性循环甚至 OOM | 评估调用线程承受力；改任务持久化方案 |
| 无界队列 | 任务堆积 OOM | 有界队列 + 合理容量 |
| 核心线程过大 | 上下文切换开销（OS 中最耗 CPU 的操作） | 按公式设定 |
| 自定义优先级队列无界 | OOM + 低优先级饥饿 | 重写 offer 限长；任务老化提升优先级 |
| 共用 ForkJoinPool.commonPool() | CompletableFuture 大量任务时线程饥饿 | 异步编排必须传自定义线程池 |

### 优化进阶

- 线程数公式：CPU 密集型 **N+1**（多 1 防偶发缺页中断）；I/O 密集型 **2N**；严谨公式 **N × (1 + WT/ST)**（WT/ST 可用 VisualVM 观测）；
- 任务持久化兜底：自定义 RejectedExecutionHandler 把拒绝任务入库 + 混合 BlockingQueue（take 时优先取库中最早任务）——服务器资源极限时不丢任务；
- 框架实践参考：Netty NewThreadRunsPolicy（临时线程执行）、ActiveMQ（限时 offer 60s 争取入队）。

### 选型对比

| 拒绝策略 | 行为 | 适用场景 |
|----------|------|----------|
| AbortPolicy（默认） | 抛 RejectedExecutionException | 关键任务不可静默丢失 |
| CallerRunsPolicy | 调用线程自己执行（isShutdown 后丢弃） | 可接受反压、尽量不丢 |
| DiscardPolicy | 直接丢弃 | 允许丢失（如日志上报） |
| DiscardOldestPolicy | 丢弃最老任务再入队 | 喜新厌旧场景 |

## 模块六：ThreadLocal 与线程上下文传递

### 核心原理

值存放在**当前线程的 ThreadLocalMap**（Thread 的成员变量），不在 ThreadLocal 对象上。Entry：`key` 是 ThreadLocal 的**弱引用**、`value` 是**强引用**；定位 `key.threadLocalHashCode & (len-1)`。

### 生产落地

```java
// 阿里手册【强制】：必须回收自定义 ThreadLocal，尤其线程池场景
private static final ThreadLocal<UserContext> CTX = new ThreadLocal<>();

public void handle(HttpServletRequest req) {
    try {
        CTX.set(buildContext(req));   // ① static final 防重复创建实例
        doBusiness();                 // ② try 内使用
    } finally {
        CTX.remove();                 // ③ finally 必清理
    }
}
```

### 踩坑规避

- **内存泄漏机理**：key 弱引用被 GC 后变 null，value 仍被 Entry 强引用 → stale entry 无法回收；ThreadLocalMap 仅在 get/set/remove 时**被动清理**，不完全可靠。泄漏放大条件：ThreadLocal 实例失去强引用 + 线程长期存活（线程池核心线程）；
- **弱引用只是兜底不是免死金牌**：key 若为强引用，忘 remove 就彻底无法回收；弱引用至少给了 GC+自清理的机会；
- **数据污染比泄漏更致命**：美团线上事故——线程池复用的线程残留上一个请求的用户上下文，导致用户 A 读到用户 B 的身份信息；
- 父子线程传递别用 InheritableThreadLocal：只在**线程创建时**复制一次，线程池复用线程时拿到的是脏数据。

### 优化进阶

**TransmittableThreadLocal（TTL）**：装饰器模式把传递时机从"线程创建时"延迟到"任务提交与执行时"，CRR 三阶段：
- **Capture**：`execute()` 瞬间捕获父线程所有活跃 TTL 值存入快照；
- **Replay**：工作线程 run() 前把快照 set 进去并备份旧值；
- **Restore**：任务结束后按备份恢复线程，防污染。

接入：显式包装（`TtlRunnable.get()` / `TtlExecutors.getTtlExecutorService()`）或 Java Agent 字节码增强（默认修饰 ThreadPoolExecutor、ScheduledThreadPoolExecutor、ForkJoinTask 体系、TimerTask）。场景：Trace ID 透传、压测流量标记、用户上下文。

### 选型对比

| 方案 | 传递时机 | 线程池支持 | 风险 |
|------|----------|-----------|------|
| ThreadLocal | 不传递 | — | 泄漏 + 污染（需规范 remove） |
| InheritableThreadLocal | 线程创建时一次性复制 | ❌ | 复用线程脏数据 |
| TransmittableThreadLocal | 任务提交/执行/结束（CRR） | ✅ | 需引入依赖 + 代理开销 |

## 模块七：AQS 与 JUC 并发工具

### 核心原理

AQS（AbstractQueuedSynchronizer，JDK1.5）为同步器提供通用框架：`volatile int state` 表示同步状态 + **CLH 变体队列**（双向链表，自旋+阻塞）完成线程排队；子类重写模板方法实现具体获取/释放逻辑。

CLH 变体的两点优化：① 自旋 → 自旋+阻塞（失败再 `LockSupport.park`）；② 单向 → 双向（释放时需唤醒后继）。

### 生产落地

| 同步器 | AQS 模式 | state 语义 | 典型场景 |
|--------|----------|-----------|----------|
| ReentrantLock | 独占 | 0 无锁，重入累加，减到 0 才释放 | 通用临界区 |
| Semaphore | 共享 | permits 许可证数，acquire 减 1/release 加 1 | 单机限流 |
| CountDownLatch | 共享 | 初始 N，countDown 减 1，归零唤醒 await | 多任务汇总等待 |
| CyclicBarrier | ReentrantLock+Condition | count 到 0 执行 barrierCommand 后重置 | 分阶段并行计算 |

- **Semaphore 无所有权约束**：获取与释放线程可不同（区别于锁）；
- **CountDownLatch 一次性**；CyclicBarrier 可循环（Generation 机制）；
- CyclicBarrier 中断/超时 → `BrokenBarrierException` 屏障破损。

### 踩坑规避

- 锁**获取几次就要释放几次**，finally 中 unlock 配对（ReentrantLock）；
- Semaphore 公平模式下无参 `tryAcquire()` 仍可能插队（不遵守公平设置）；
- 同步器只是原语，**分布式互斥必须用 Redis/ZooKeeper/etcd**（见 [02.2 Redis 工程化](../02-backend-components/02.2-redis.md) 分布式锁选型）。

### 优化进阶

- `ReentrantLock` 优先非公平模式（减少线程切换，吞吐更高）；需要防饥饿才用公平锁；
- 复杂协作优先 `CompletableFuture` 替代 CountDownLatch（函数式编排 + 异常链处理），注意 `whenComplete`/`exceptionally`/`handle`/`allOf` 语义差异，且必须传自定义线程池；
- 锁竞争激烈场景：缩短临界区、锁粗化/细化的权衡、读写分离（ReentrantReadWriteLock / StampedLock 乐观读）。

### 选型对比

| 需求 | 首选 | 备选 |
|------|------|------|
| 一段代码等待多任务完成 | CompletableFuture.allOf | CountDownLatch |
| 一组线程互等同步点 | CyclicBarrier | Phaser（多阶段） |
| 控制并发访问数 | Semaphore | 信号量 + 超时 acquire |
| 单机互斥 | ReentrantLock | synchronized |
