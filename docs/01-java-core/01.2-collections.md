## 模块一：集合框架总览与选型

### 1. 核心原理

- **两大根接口**：`Collection`（单一元素，子接口 List/Set/Queue）+ `Map`（键值对）。
- **四者区别**：List 有序可重复；Set 无序不可重（`HashSet` 基于 `HashMap`）；Queue 按排队规则有序可重复；Map key 无序不可重（`HashMap` 无显式顺序，`LinkedHashMap` 插入/访问序，`TreeMap` 排序）。
- **底层速查**：`ArrayList`=Object[]；`LinkedList`=双向链表；`HashMap`=数组+链表+红黑树；`TreeMap`=红黑树；`LinkedHashMap`=HashMap+双向链表。

### 2. 生产落地

- **默认选型口诀**：单机普通 Map → `HashMap`；需要顺序 → `LinkedHashMap`；需要排序/范围查询 → `TreeMap`；并发 → `ConcurrentHashMap`。
- **初始化容量**：`new HashMap<>(expectedSize / 0.75f + 1)`，避免扩容；`Map<String, X> map = Map.of(...)` 用于不可变常量（JDK9+）。

### 3. 踩坑规避

- **作为字段的集合**：POJO 中的集合字段初始化（`new ArrayList<>()`），避免 NPE；返回内部集合前 defensive copy（`Collections.unmodifiableList` 或 `List.copyOf`）。
- **`Arrays.asList` 陷阱**：返回的是 `Arrays$ArrayList`（定长，`add` 抛 `UnsupportedOperationException`），用 `new ArrayList<>(Arrays.asList(...))` 或 `List.of`。
- **`subList` 是视图**：对原列表结构性修改会使子列表 `modCount` 失效，遍历抛 `ConcurrentModificationException`。

### 4. 优化进阶

- **fail-fast 机制**：迭代时 `modCount != expectedModCount` 即抛 CME（`ArrayList`/`HashMap` 迭代器）；并发场景要么加锁遍历、要么用并发集合（`CopyOnWriteArrayList`/`ConcurrentHashMap`，fail-safe）。
- **`HashMap` 大 Key 场景**：value 是巨型对象时，考虑按需懒加载，避免内存驻留。

### 5. 选型对比

| 容器 | 随机访问 | 插入/删除 | 有序 | 并发安全 | 典型场景 |
|------|---------|----------|------|---------|----------|
| ArrayList | O(1) | O(n) | 插入序 | 否 | 读多写少、列表 |
| LinkedList | O(n) | O(1)* | 插入序 | 否 | 队列/栈（少用，ArrayDeque 更优） |
| HashSet | — | O(1) | 无 | 否 | 去重 |
| TreeSet/TreeMap | O(log n) | O(log n) | 排序 | 否 | 范围查询、TopN |
| LinkedHashMap | O(1) | O(1) | 插入/访问序 | 否 | LRU 缓存 |
| ConcurrentHashMap | O(1) | O(1) | 无 | 是 | 高并发缓存/计数器 |

## 模块二：List — ArrayList vs LinkedList

### 1. 核心原理

- **ArrayList**：动态数组，扩容 `grow()` = 旧容量 1.5 倍（`oldCapacity + (oldCapacity >> 1)`），`System.arraycopy` 拷贝。
- **LinkedList**：双向链表，节点前后驱指针，头尾插入 O(1)。
- **关键结论**：ArrayList 顺序遍历（内存连续，缓存友好）实际常快于 LinkedList 随机访问；LinkedList 按索引访问要 O(n) 定位，**" LinkedList 插入快"只在已知节点位置时成立**。

### 2. 生产落地

- **预设容量**：已知元素量级时 `new ArrayList<>(n)`，一次分配避免多次扩容拷贝。
- **批量操作**：`ensureCapacity` + `addAll` 优于循环 add（减少边界检查与 modCount 变更）。

### 3. 踩坑规避

- **`ArrayList` 并发修改**：多线程 add 丢数据/越界；用 `CopyOnWriteArrayList`（读多写少）或 `Collections.synchronizedList`。
- **`removeAll`/`retainAll` 语义**：按 equals 移除/保留，自定义对象忘写 equals 会"删不掉"。

### 4. 优化进阶

- **读多写少**：`CopyOnWriteArrayList` 读无锁；写时复制整数组，**写操作 O(n)**，仅适合配置表、监听器列表这类低频写场景。
- **`ArrayList` 缩容**：长期占用大数组可用 `trimToSize()` 释放（注意并发安全）。

### 5. 选型对比

| 场景 | 选择 | 理由 |
|------|------|------|
| 默认列表 | ArrayList | 缓存友好、随机访问 O(1) |
| 高频头插/删除且已知节点 | LinkedList | 指针操作 O(1) |
| 并发读多写少 | CopyOnWriteArrayList | 无锁读 |
| 双端队列/栈 | ArrayDeque | 循环数组，无 LinkedList 的节点开销 |

## 模块三：HashMap 深度原理（JDK1.7 → 1.8）

### 1. 核心原理

- **结构**：数组 + 链表 + 红黑树；`hash(key)` = `h = key.hashCode(); h ^ (h >>> 16)`（高 16 位异或低 16 位，减少冲突）；桶索引 `(n - 1) & hash`（n 为 2 的幂）。
- **put 流程**：计算 hash → 定位桶 → 空桶直接放 → 桶首节点 key 相等则覆盖 → 链表尾插（JDK8）→ 长度 ≥ 8 且容量 ≥ 64 树化 → `size > threshold`（容量×0.75）扩容。
- **扩容**：容量翻倍；JDK8 **高低位分离**（`e.hash & oldCap == 0` 留低位，否则迁到 `原索引+oldCap`），省去逐节点 rehash；JDK7 需逐个重算 hash。
- **树化阈值**：`TREEIFY_THRESHOLD=8`、`UNTREEIFY_THRESHOLD=6`、`MIN_TREEIFY_CAPACITY=64`。

**为什么是 8/6/64（泊松分布推导）**：理想 hash 分布下桶长度服从泊松分布（λ≈0.5，负载因子 0.75）：

```
0: 0.60653066   1: 0.30326533   2: 0.07581633
3: 0.01263606   4: 0.00157952   5: 0.00015795
6: 0.00001316   7: 0.00000094   8: 0.00000006（千万分之六）
```

- **8**：正常分布下几乎不可能达到，达到即说明 hash 极度异常，必须用红黑树兜底（防哈希碰撞攻击把查询退化成 O(n)）；
- **6**：与 8 留缓冲带，避免在临界点反复"树化↔退化"抖动（若阈值是 7，增删一个元素就触发一次结构转换）；
- **64**：容量 < 64 时优先扩容（分散冲突）而非树化——小表树化内存收益差。

**TreeNode 保留双向链表的原因**：① 退化时直接沿链表 O(n) 转回普通节点，无需中序遍历；② 删除中间节点维护 prev 指针 O(1)。

**不可比较 key 的红黑树**：比较顺序 `Comparable → 类名 → System.identityHashCode`（`tieBreakOrder`），保证通用性。

### 2. 生产落地

- **初始化容量公式**：`Map<String, Object> map = new HashMap<>((int)(expected / 0.75) + 1)`。
- **key 设计**：不可变对象做 key（缓存 hash）；正确实现 `hashCode`/`equals`；字符串 key 优先。

```java
// 哈希碰撞攻击防护：自定义 key 时保证 hashCode 分散
public final class BizKey {
    private final String bizType;
    private final long bizId;

    public BizKey(String bizType, long bizId) {
        this.bizType = bizType;
        this.bizId = bizId;
    }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof BizKey)) return false;
        BizKey other = (BizKey) o;
        return bizId == other.bizId && Objects.equals(bizType, other.bizType);
    }

    @Override public int hashCode() {
        return Objects.hash(bizType, bizId);
    }
}
```

### 3. 踩坑规避

1. **JDK7 并发扩容死循环**：头插法 + 并发扩容导致环形链表，`get` 死循环（CPU 100%）。JDK8 尾插法已修复死循环，但**并发 put 仍可能丢数据**——`HashMap` 始终非线程安全。
2. **hashCode 返回常量**：所有 key 落同一桶，JDK8 靠红黑树把查询控制在 O(log n)，但插入/内存仍劣化；恶意构造的 key（碰撞攻击）会让服务 CPU 飙高。
3. **resize 阈值误解**：容量 16、负载因子 0.75 → 第 13 个元素触发扩容；树化还要看容量是否 ≥ 64，否则先扩容。
4. **`key` 可变**：put 后修改参与 hash 的字段，再 get 找不到（hash 变了，桶位置错）。

### 4. 优化进阶

- **JDK1.8 相比 1.7**：尾插法（解决死循环）、1 次扰动（`h ^ h>>>16`，红黑树降低对 hash 质量依赖）、高低位分离扩容（免重算 hash）。
- **大 Map 调优**：预设容量减少 resize；`-XX:+UseCompressedOops` 下对象头压缩让指针 4 字节；超高并发场景评估 `ConcurrentHashMap`。

### 5. 选型对比

| 特性 | JDK 1.7 | JDK 1.8 |
|------|---------|---------|
| 结构 | 数组+链表 | 数组+链表+红黑树 |
| 插入 | 头插法（并发死循环） | 尾插法（安全） |
| hash | 4 次扰动 | 1 次扰动 |
| 扩容 | 全量 rehash | 高低位分离 |
| 查询最坏 | O(n) | O(log n) |

## 模块四：Queue / Deque

### 1. 核心原理

- `Queue`：FIFO，`offer/poll/peek`（失败返回 null/false，不抛异常——**生产首选**）；`add/remove/element` 失败抛异常。
- `Deque`：双端队列（`ArrayDeque` 循环数组实现 / `LinkedList`），可当头尾栈/队列用。
- `PriorityQueue`：二叉堆，默认小顶堆，`offer/poll` O(log n)；**非线程安全**。
- `BlockingQueue`：`ArrayBlockingQueue`（有界数组）/`LinkedBlockingQueue`（可选有界）/`PriorityBlockingQueue`/`DelayQueue`（延迟任务）/`SynchronousQueue`（不存元素，直接手交手，`ThreadPoolExecutor` 的 `Executors.newCachedThreadPool()` 在用）。

### 2. 生产落地

- **线程池任务队列**：`ThreadPoolExecutor` 默认 `LinkedBlockingQueue` **无界** → 高并发下任务堆积 OOM。生产定制：有界队列 + `CallerRunsPolicy` + 监控队列深度告警。
- **生产者-消费者解耦**：本地缓冲用 `ArrayBlockingQueue`（有界天然限流）；跨进程用 MQ。

```java
// 生产级线程池定制（有界队列 + 拒绝策略 + 监控）
ThreadPoolExecutor executor = new ThreadPoolExecutor(
        Runtime.getRuntime().availableProcessors(),
        Runtime.getRuntime().availableProcessors() * 2,
        60L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(1000),
        new NamedThreadFactory("biz-worker-"),
        new ThreadPoolExecutor.CallerRunsPolicy());
// 注册 gauge：executor.getQueue().size() / getActiveCount() / getCompletedTaskCount()
```

### 3. 踩坑规避

- `PriorityQueue` 的 `iterator()` **不保证顺序**，要排序输出得 `poll` 或先 `toArray` + `Arrays.sort`。
- `ArrayDeque` 不支持 null 元素。
- `BlockingQueue` 的 `add` 满时抛 `IllegalStateException`，用 `offer` 系。

### 4. 优化进阶

- 有界队列深度 = 突发流量缓冲能力，配合压测标定（队列深度 × 单任务处理时长 × 消费速率 < 生产流量）。
- `SynchronousQueue` 适合"任务轻、要求立即执行"的场景；`DelayedWorkQueue` 适合定时关闭超时订单。

### 5. 选型对比

| 队列 | 有界 | 阻塞 | 排序 | 典型场景 |
|------|------|------|------|----------|
| ArrayDeque | 是 | 否 | 否 | 单机栈/队列 |
| PriorityQueue | 是 | 否 | 是 | 任务优先级调度 |
| ArrayBlockingQueue | 是 | 是 | 否 | 线程池队列 |
| LinkedBlockingQueue | 可选 | 是 | 否 | 大吞吐生产者消费者 |
| DelayQueue | 是 | 是 | 到期时间 | 延迟任务、超时关单 |

## 模块五：ConcurrentHashMap 深度（JDK1.7 → 1.8）

### 1. 核心原理

- **设计目标**：线程安全 + 高并发，锁粒度尽可能细。Hashtable 用全表锁（put 时读写全阻塞）被淘汰；
- **JDK1.7 分段锁（Segment）**：表分 16 段，每段继承 `ReentrantLock` 独立加锁 → 支持 16 线程并发写不同段；
- **JDK1.8 节点锁**：摒弃 Segment，改为 **Node 数组 + CAS + synchronized（锁桶首节点）**：
  - 桶为空 → `CAS`（`casTabAt`）无锁插入；
  - 桶非空 → `synchronized (f)` 只锁**当前桶首节点**，不同桶完全无锁；
  - `putVal` 四场景：未初始化（`initTable`，sizeCtl CAS 竞争）/ 空桶 CAS / `hash==MOVED` 协助扩容（`helpTransfer`）/ 加锁插入；
  - 扩容：每线程分 ≥16 桶任务，`transferIndex` CAS 分配，已迁移桶挂 **ForwardingNode**；
- **Node 的 `val`/`next` 用 volatile**：保证读线程无需锁即可看到最新值 → **get 几乎无锁**。

### 2. 生产落地

- **并发 Map 默认选 CHM**：`ConcurrentHashMap<String, AtomicLong>` 计数器模式：

```java
// 高并发计数：computeIfAbsent 原子初始化 + incrementAndGet 原子自增
ConcurrentHashMap<String, AtomicLong> counters = new ConcurrentHashMap<>();
public void record(String module) {
    counters.computeIfAbsent(module, k -> new AtomicLong()).incrementAndGet();
}
```

- **size 的语义**：CHM 的 `size()` 是**近似值**（高并发下无绝对准确的计数，需准确计数用 `AtomicLong`/`mappingCount` 或业务统计表）；
- **null 禁止**：key/value 都不能为 null（`null` 与"不存在"在并发下无法区分，会抛 NPE）。

### 3. 踩坑规避

1. **复合操作非原子**：`if (!map.containsKey(k)) map.put(k, v)` 是两次操作，并发下重复 put。用 `putIfAbsent` / `computeIfAbsent` / `compute`（整体原子）；
2. **迭代器弱一致**：`keySet()` 遍历反映某一时刻状态，不抛 CME 但不保证全量——遍历期间要绝对一致快照，先 `copyOf` 再遍历；
3. **JDK1.8 仍有并发上限**：单桶冲突时退化为串行；热 key（同 key 高频写）需业务层打散（key 加后缀分段）；
4. **弱引用 key 误用**：CHM 不支持弱引用 key（用 `Collections.synchronizedMap(new WeakHashMap<>())` 场景极少，评估 Guava Cache）。

### 4. 优化进阶

- **JDK1.8 为何用 synchronized 不用 ReentrantLock**：① 桶级锁冲突概率低，synchronized 大多停在前两态（JDK15 前）；② JVM 锁消除/锁粗化/自适应自旋优化；③ 每个节点继承 ReentrantLock 内存开销大，synchronized 靠对象头 Mark Word 零额外对象；④ 自动释放无死锁风险；
- **树化与 HashMap 同参数**：链表 ≥8 且容量 ≥64 转红黑树（TreeBin 包装，`lockState` 管读写等待）；
- **热 key 优化**：本地缓存挡一层 + CHM 分段 key，把单桶竞争降为多桶。

### 5. 选型对比

| 维度 | JDK 1.7 | JDK 1.8 |
|------|---------|---------|
| 锁策略 | Segment 分段锁（ReentrantLock） | 桶首节点 synchronized + CAS |
| 锁粒度 | 段级（默认 16） | 桶级（= 数组长度） |
| 并发度 | ≤16 | 理论 = 桶数 |
| 读性能 | 段锁 | volatile 无锁读 |
| 冲突解决 | 链表 | 链表 + 红黑树 |
| 内存 | Segment 开销 | 更紧凑 |

**与 Hashtable 对比**：Hashtable 全表 synchronized（读写互斥，已淘汰）；CHM 读无锁、写锁桶。
**与 synchronizedMap 对比**：`Collections.synchronizedMap` 任一操作锁全表，仅适合低并发。
