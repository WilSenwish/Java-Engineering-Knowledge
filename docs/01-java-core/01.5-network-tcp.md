## 模块一：TCP 连接管理（三次握手与四次挥手）

### 1. 核心原理

- **四元组唯一确定连接**：源 IP + 源端口 + 目的 IP + 目的端口。
- **三次握手**：① 客户端 SYN（client_isn）→ ② 服务端 SYN+ACK（server_isn, ack=client_isn+1）→ ③ 客户端 ACK（ack=server_isn+1，**可携带数据**）。
- **为什么是三次**（三个原因，按重要性）：
  1. **阻止重复历史连接初始化**（RFC 793 首要原因）：旧 SYN 先到时，客户端通过确认号不匹配回 **RST** 终止历史连接；两次握手服务端无中间态可阻止，直接进入 ESTABLISHED 白白建立连接；
  2. **同步双方初始序列号 ISN**：双向都要"我发 SYN、你 ACK 确认"，一来一回才能可靠同步；
  3. **避免资源浪费**：两次握手时服务端每收到一个 SYN 都要先建连接，滞留 SYN 会造成大量冗余连接。
- **四次挥手**：每方向要"FIN + ACK"两个报文，服务端 ACK 与 FIN 通常分开发（可能还有数据要发）→ 四次；主动关闭方进入 **TIME_WAIT（2MSL）**。
- **ISN 随机化**（RFC 793）：`ISN = M + F(src_ip, src_port, dst_ip, dst_port)`，M 为 4μs 递增时钟（防历史报文错收 + 防伪造）。

### 2. 生产落地

- **内核参数速查（Linux）**：

```bash
# SYN 相关
net.ipv4.tcp_max_syn_backlog      # 半连接队列大小（默认 128/256）
net.core.somaxconn                # 全连接队列上限（listen backlog 上限）
net.ipv4.tcp_syncookies           # 1 = 半连接队列满时用 cookie 保连接（抗 SYN 攻击）
net.ipv4.tcp_syn_retries          # 客户端 SYN 重传次数（默认 5，总耗时约 63s）
net.ipv4.tcp_synack_retries       # 服务端 SYN+ACK 重传次数（默认 5）
# 连接关闭相关
net.ipv4.tcp_fin_timeout          # FIN_WAIT_2 超时（默认 60s）
net.ipv4.tcp_orphan_retries       # 本地 FIN 重传次数（默认 0 实际按 8 次）
net.ipv4.tcp_tw_reuse              # 复用 TIME_WAIT（仅客户端安全）
net.ipv4.tcp_max_tw_buckets        # TIME_WAIT 总量上限（默认 18000）
# 保活
net.ipv4.tcp_keepalive_time=7200  # 2h 无活动启动探测
net.ipv4.tcp_keepalive_intvl=75
net.ipv4.tcp_keepalive_probes=9
```

- **高并发服务端调优**：`tcp_max_syn_backlog` 提到 8192+、`somaxconn` 128→4096、`tcp_syncookies=1`；`netdev_max_backlog` 1000→10000（网卡堆积）。
- **Nginx 长连接**：`keepalive_timeout 75;` `keepalive_requests 1000;`（高 QPS 场景调大避免频繁关闭产生 TIME_WAIT）。

### 3. 踩坑规避

| 现象 | 根因 | 定位与对策 |
|------|------|-----------|
| 服务端大量 **TIME_WAIT** | 服务端主动关闭连接（HTTP 短连接、长连接超时、`keepalive_requests` 达上限） | `ss -s` 统计各状态；排查客户端/服务端 Keep-Alive 是否都开启；调大 `keepalive_requests` |
| 服务端大量 **CLOSE_WAIT** | 服务端**程序没调用 close**（socket 未注册 epoll、accept 后未加入事件循环、读事件后未 close） | `ss -tan \| grep CLOSE-WAIT` + `lsof -p pid`；代码审查 fd 生命周期，典型：Netty handler 异常未释放 |
| 客户端端口耗尽 | 客户端 TIME_WAIT 占满 32768~61000 端口 | `tcp_tw_reuse=1`（配合 tcp_timestamps）；连接池化（HTTP keep-alive / RPC 长连接） |
| 偶发 `Connection reset` | 收到 RST：对端崩溃重启无连接记录 / 防火墙 / 服务端 accept 队列满（`tcp_abort_on_overflow=1` 时） | 服务端扩容 accept 能力；`ss -lnt` 看 Recv-Q/Send-Q 堆积 |
| SYN  Flood 攻击 | 半连接队列被打满，正常 SYN 被丢弃 | `tcp_syncookies=1` + `tcp_max_syn_backlog` 调大 + 防火墙 SYN 代理 |

### 4. 优化进阶

- **TIME_WAIT 治理原则**：**TIME_WAIT 是主动关闭方的正常状态，不要"消灭"它，而是让对端关**——"永远不要主动断开连接，让客户端断开，由分布在各处的客户端承受 TIME_WAIT"（UNIX 网络编程）。服务端要避免大量 TIME_WAIT，核心是**长连接化 + 连接池**。
- **`tcp_tw_reuse` 安全性**：依赖 TCP 时间戳（`tcp_timestamps=1` 默认开启），时间戳过期的新数据包会被丢弃，因此复用安全；但**仅限客户端（connect 方）**。
- **`SO_LINGER` 暴力关闭**：`l_onoff=1, l_linger=0` 时 close 立即发 RST，跳过 TIME_WAIT——会丢数据、破坏优雅关闭，不提倡。

### 5. 选型对比

| 机制 | 作用 | 代价 | 生产建议 |
|------|------|------|----------|
| 长连接（Keep-Alive） | 消除重复握手 | 连接保活资源 | HTTP 服务端开启；客户端配连接池 |
| 连接池（OKHttp/HikariCP/Druid） | 复用 + 限流 | 池参数需标定 | **默认做法** |
| `tcp_tw_reuse=1` | 客户端复用 TIME_WAIT | 依赖时间戳 | 客户端机器开启 |
| `tcp_max_tw_buckets` | 强制清理超限 TIME_WAIT | 粗暴，可能误杀 | 兜底手段 |
| `tcp_syncookies` | 队列满时仍可建连 | 关闭部分 TCP 选项 | 服务端=1 常开 |

## 模块二：TCP 可靠性机制与 UDP 对比

> 本模块在面试题骨架基础上，随小林《TCP 重传、滑动窗口、流量控制、拥塞控制》深化为全参数版本（sources/xiaolincoding/network/tcp-reliability.md）。

### 1. 核心原理

- **序列号 + 确认应答**：seq 累加已发字节数，ack = 期望收到的下一个字节 → 去重 + 按序 + 确认交付；**累积确认**（ACK 700 意味着 700 之前全部收到，中间 ACK 丢了没关系）。
- **重传四机制**：
  - 超时重传：RTO 动态计算，RFC6289 `RTO = SRTT + 4×DevRTR`（Linux α=0.125、β=0.25），**超时间隔加倍**（一次超时说明网络差，不宜频繁重发）；
  - 快速重传：**数据驱动**，收到 3 个重复 ACK 立即重传，不等超时；
  - SACK：选项字段告知已收到的数据范围，**只重传丢失段**；
  - D-SACK：告知发送方**哪些数据被重复收到**——区分「数据包丢了 / ACK 丢了 / 网络延迟 / 网络复制」。
- **流量控制（滑动窗口）**：接收方通过 ACK 的 Window 字段通告剩余缓冲，发送窗口 = `min(cwnd, rwnd)`；发送方三指针（SND.UNA / SND.NXT / SND.WND），可用窗口 = `SND.WND - (SND.NXT - SND.UNA)`；收发窗口**约等于**相等（通告存在时延）。
- **拥塞控制四算法**：

| 算法 | 条件 | 规则 |
|------|------|------|
| 慢启动 | cwnd < ssthresh | 每 ACK，cwnd+1（**指数**） |
| 拥塞避免 | cwnd ≥ ssthresh | 每 ACK，cwnd + 1/cwnd（**线性**） |
| 拥塞发生 | 超时重传 | ssthresh = cwnd/2，cwnd = 1 重慢启动 |
| 快速恢复 | 快速重传 | cwnd = cwnd/2，ssthresh = cwnd，cwnd = ssthresh+3；重复 ACK 则 +1；新数据 ACK 后 cwnd = ssthresh 回拥塞避免 |

- **MSS vs MTU**：MTU=链路层最大包（以太网 1500）；MSS=TCP 数据最大段 = MTU - IP头 - TCP头。TCP 层按 MSS 分片，丢包只重传一个 TCP 段；若交给 IP 层分片，丢一片要重传**整个 IP 报文的所有分片**。

### 2. 生产落地

- **内核参数基线**：`net.ipv4.tcp_sack=1`、`net.ipv4.tcp_dsack=1`（默认开，D-SACK 是排查「假丢包」的利器：抓到 D-SACK 说明是延迟不是丢包）；交互式服务按连接设 `TCP_NODELAY`。
- **UDP 适用面**：DNS、SNMP、QUIC/HTTP3、音视频、广播。基于 UDP 实现可靠传输 = QUIC（TLS1.3 + 自定义重传 + 多路复用无队头阻塞）。
- **Java 网络编程**：BIO（一连接一线程，C10K 不可用）→ NIO（Selector 多路复用）→ Netty（Reactors 主从模型，**生产默认**）；JDK NIO 直接裸用易踩坑（空轮询 bug 等），直接用 Netty。
- **排查工具**：`ss -nli` 看每连接的 cwnd（Linux 初始值 10）；`nstat/sar -n ETCP` 看重传率；`tcpdump` 抓 D-SACK 判定丢包性质。

### 3. 踩坑规避

- **TCP 是字节流无边界**：应用层必须自定义协议（长度前缀 / 分隔符 / TLV），否则粘包半包解析错乱——这是自研 TCP 服务第一课。
- **窗口关闭死锁**：窗口为 0 时通告窗口的 ACK 丢失 → 双方死等。TCP 用**持续定时器 + 窗口探测报文**（3 次、每次 30-60 秒，仍为 0 发 RST）破解。
- **糊涂窗口综合症**：接收方腾出几字节就通告、发送方就发几字节——40 字节头给几个字节数据打工。接收方策略：窗口 < min(MSS, 缓存/2) 时通告 0；发送方策略：Nagle 算法。**两端都满足才有效**；对端 ACK 很快时 Nagle 仍会发小包。
- **Nagle + 延迟确认 40ms 抖动**：请求-响应式小包交互（如 Redis 客户端、MySQL 协议）同时开 Nagle 和延迟确认会出现 40ms 级延迟——`TCP_NODELAY` 必开。
- **`ServerSocket` backlog 误解**：Linux 2.2+ backlog = **全连接队列**大小，上限为 `min(backlog, somaxconn)`；accept 慢于握手速率 → 队列满 → 丢 SYN/ACK。
- **accept 时机**：客户端 `connect()` 返回在第二次握手；服务端 `accept()` 返回在三次握手后——压测时连接建立耗时主要花在服务端 accept 调度。

### 4. 优化进阶

- **拥塞控制的成本直觉**：超时重传 → cwnd 一夜回到 1（「紧急刹车」），高丢包网络吞吐崩塌；快速重传 → cwnd 只减半（「点刹」）。这就是弱网下 QUIC 换 UDP 自研拥塞控制的动机之一。
- **TCP_NODELAY**：关闭 Nagle 算法，小包立即发送（游戏/IM/交易系统开启；大文件传输默认开 Nagle 更好）。
- **零拷贝**：`FileChannel.transferTo`/`sendfile`（Kafka、Nginx、RocketMQ 均用），避免用户态-内核态 4 次拷贝。
- **QUIC/HTTP3**：0-RTT 建连、无队头阻塞的多路复用、连接迁移（换网不断连）——对移动端/弱网收益显著。

### 5. 选型对比

| 维度 | TCP | UDP |
|------|-----|-----|
| 可靠性 | 确认/重传/排序 | 尽力交付 |
| 连接 | 面向连接（握手开销） | 无连接 |
| 首部开销 | 20 字节起 | 8 字节 |
| 流量/拥塞控制 | 有 | 无 |
| 分片层级 | 传输层（按 MSS） | IP 层（丢一片全重传） |
| 场景 | HTTP/RPC/DB 连接 | DNS/音视频/QUIC |

## 模块三：HTTP / HTTPS / HTTP 演进

### 1. 核心原理

- **HTTP 定义**：在计算机世界里专门在「两点」之间「传输」文字、图片、音视频等「超文本」数据的「约定和规范」。**双向协议**，允许中间人中转接力（A <-> N <-> M <-> B）；
- **解决 TCP 粘包**：回车换行符 = header 边界，`Content-Length` = body 边界；
- **GET vs POST（RFC 语义）**：GET 获取资源（安全 + 幂等 + 可缓存，参数在 URL 限 ASCII）；POST 依 body 处理资源（不安全 + 非幂等 + 不缓存，body 任意格式不限大小）。**实际开发不一定按 RFC 实现**（GET 做删除的事故事故）；
- **缓存两级**：**强制缓存**（`Cache-Control` 相对时间优先 / `Expires` 绝对时间，浏览器本地判断）+ **协商缓存**（`If-None-Match`+`ETag` 优先 / `If-Modified-Since`+`Last-Modified`，服务端 304 判断）。协商字段必须配合强制缓存使用；
- **HTTP/1.1**：长连接 + 管道（请求可流水但**服务端按序响应 → 响应队头阻塞**；且管道实际未被浏览器支持）；
- **HTTP/2**：① HPACK 头部压缩（索引表消重）② 二进制分帧（Headers/Data Frame，状态码 200 从 3 字节变 1 字节）③ **Stream 多路复用**（一个 TCP 多 Stream，帧乱序收发，客户端奇号/服务端推送偶号）④ 服务端主动推送。**缺陷：TCP 层队头阻塞仍在**（丢一个包，全部 Stream 等重传）；
- **HTTP/3 = QUIC over UDP**：① 流级丢包只阻塞该流（无队头阻塞）② QUIC 内置 TLS 1.3，1-RTT 建连、会话恢复 0-RTT ③ **连接 ID 替代四元组**，4G 切 WIFI 无缝迁移；
- **HTTPS = HTTP + TLS**：混合加密（非对称交换会话密钥 + 对称加密数据，机密性）+ 摘要算法 + 数字签名（哈希指纹验完整性 + 私钥签名验来源）+ **数字证书**（CA 证明公钥身份，防冒充）。TLS 1.2 握手 2-RTT（4 次通信），TLS 1.3 优化为 1-RTT。

### 2. 生产落地

- **Nginx 静态资源缓存策略**：带 hash 的静态资源 `Cache-Control: max-age=31536000`（强缓存一年）；HTML `no-cache`（每次都协商缓存）；接口按数据时效性设 `max-age` 或 `no-store`；
- **证书信任链**：申请的证书由中间 CA 签发（如 baidu.com ← GlobalSign G2 ← Root CA），客户端逐级验证到 OS/浏览器预置根证书。**Root CA 不直接签发的目的：根证书隔离越严，失守影响越小**；
- **TLS 版本**：服务端只开 TLS 1.2+（禁用 SSLv3/TLS1.0/1.1，防 POODLE/BEAST）；优先 ECDHE 套件（**前向安全：私钥泄露不危及历史会话**，RSA 密钥交换无此特性）。

```nginx
# Nginx 缓存策略示例
location ~* \.(js|css|png)$ {
    expires 1y;
    add_header Cache-Control "public, immutable";
}
location = /index.html {
    add_header Cache-Control "no-cache";  # 每次都协商缓存
}
```

### 3. 踩坑规避

| 现象 | 根因 | 对策 |
|------|------|------|
| 资源更新后用户仍拿旧缓存 | 强缓存 + 文件名不带 hash | 构建产出 content-hash 文件名 + HTML 走 no-cache |
| HTTPS 被抓包明文看到 | 客户端导入了抓包工具根证书（中间人） | 不点证书警告；关键 App 用**双向认证** + SSL Pinning |
| 接口数据被 CDN 缓存 | 未设 Cache-Control | API 默认 `no-store`；CDN 按后缀/路径配置缓存规则 |
| 移动端弱网卡顿 | TCP 层队头阻塞（HTTP/2） | HTTP/3（QUIC）或降低单连接并发度 |
| 大文件传输中断重传代价高 | 单连接 | Range 分段下载 + 断点续传（206） |

### 4. 优化进阶

- **HTTP/1.1 优化手段**（存量系统）：域名分片（多 TCP 并行，HTTP/2 时代废弃）、资源合并（雪碧图/打包，HTTP/2 时代反优化）、内联关键 CSS；
- **HTTP/2 服务器推送的坑**：推送了浏览器已缓存的资源 = 浪费带宽 → 现代实践（HTTP/2 103 Early Hints / HTTP/3）替代；
- **0-RTT 风险**：QUIC 0-RTT 数据无前向安全、可被重放 → **只用于幂等 GET**，写操作等 1-RTT。

### 5. 选型对比

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|------|----------|--------|--------|
| 传输 | TCP | TCP | UDP（QUIC） |
| 头部 | 明文重复 | HPACK 压缩 | QPACK |
| 并发 | 多 TCP（6~8） | 单 TCP 多 Stream | 单连接多 Stream 无队头 |
| 建连 | TCP 1-RTT | TCP 1-RTT + TLS 1-2RTT | QUIC+TLS 1-RTT（恢复 0-RTT） |
| 移动网络 | 切换断开重连 | 同左 | **连接迁移不断连** |
| 生产建议 | 存量兼容 | 主流 | 弱网/移动端优先 |

## 模块四 · I/O 多路复用与高并发网络模型

> 加工来源：小林coding《I/O 多路复用：select/poll/epoll》（sources/xiaolincoding/os/io-multiplexing.md）

### 1. 核心原理

**演进路线**：BIO 一对一 → 多进程/线程模型（C10K 扛不住）→ I/O 多路复用（单进程管万级 Socket）。

- **select/poll**：用户态/内核态 **2 次遍历 + 2 次拷贝** fd 集合，O(n) 复杂度；select 用 BitsMap 受限 `FD_SETSIZE=1024`；poll 用动态数组突破数量限制但本质相同；
- **epoll**：① 内核**红黑树**管理全部待检测 fd（`epoll_ctl` 增删改 O(log n)，免每次全量拷贝）；② **就绪链表 + 回调**，`epoll_wait` 只返回有事件的 fd，不轮询全量；
- **触发模式**：LT（水平触发，条件满足持续通知，安全默认）/ ET（边缘触发，只通知一次，必须**非阻塞 IO + 循环读到 EAGAIN**，效率更高）。

### 2. 生产落地

- Netty/JRedis/nginx 的事件循环均基于 epoll：Boss 线程 accept + Worker 线程 epoll_wait 处理读写；
- 单机连接上限：文件描述符 `ulimit -n`（默认 1024，生产调 100万+）+ 内核内存（每连接约数 KB）；
- Java NIO Selector 是 epoll 的上层封装，`SelectionKey` 对应事件类型。

### 3. 踩坑规避

- **epoll_wait 不用共享内存**（网传误区）：内核 `__put_user` 照样拷贝，只是拷的是就绪链表而非全量集合；
- 多路复用返回的事件**不一定真可读写**（如校验和错误被丢弃），阻塞 IO 下 read/write 可能卡死——必须配 `O_NONBLOCK`；
- ET 模式下没读到 EAGAIN 就结束 = 丢数据；LT 忘处理完 = 忙循环 CPU 100%。

### 4. 优化进阶

C10K → C100K → C10M 的演进本质是**每连接成本的战争**：进程/线程模型每连接数 MB 栈 + 重上下文切换；IO 多路复用把每连接成本压到内核级数据结构；C10M 还需内核调优（tcp_mem、somaxconn、中断多队列）。

### 5. 选型对比

| 接口 | 数据结构 | 遍历 | 拷贝 | 上限 | 触发模式 | 场景 |
|------|----------|------|------|------|----------|------|
| select | BitsMap | 2 次 O(n) | 2 次 | 1024 | 仅 LT | 跨平台兼容（Windows） |
| poll | 链表 | 2 次 O(n) | 2 次 | 系统限制 | 仅 LT | 突破 1024 的遗留场景 |
| epoll | 红黑树+就绪链表 | 1 次 O(就绪) | 1 次 | 系统限制 | LT + ET | **Linux 高并发事实标准** |

## 模块五 · 网络体系结构与协议全景

> 加工来源：javaguide《计算机网络常见面试题总结(上)》（sources/javaguide/cs-basics/network-questions-01.md）

### 1. 核心原理

**分层思想**：OSI 七层（理论完整但不实用）vs TCP/IP 四层（应用/传输/网络/网络接口，事实标准）。分层三理由：各层独立（接口调用）、灵活可替换（高内聚低耦合）、大问题化小。

**协议地图**：

- 应用层：HTTP(S)、SMTP/POP3/IMAP、FTP/SFTP、SSH、RTP、DNS（UDP 53，响应过大/区域传送走 TCP）；
- 传输层：TCP（可靠）、UDP（尽力）；
- 网络层：IP、ARP（IP→MAC）、ICMP（Ping/诊断）、NAT、OSPF/RIP（IGP）、BGP（域间）。

**输入网址到渲染七步**：URL → DNS 解析 → TCP 握手 → HTTP 请求 → 响应 → 解析 HTML 并发起子资源请求 → 关闭/保活连接。

### 2. 生产落地

- **HTTPS 握手选型**：RSA 静态（PreMasterSecret 传过去，**无前向安全**）vs ECDHE（临时密钥协商，证书私钥只签名不解密，**有前向安全**）——生产一律 ECDHE；
- **HTTP vs RPC 选型**：对外接口用 HTTP（通用、好调试）；内部服务互调用 RPC（服务发现/超时/重试/负载均衡/链路追踪一体）——「HTTP 没那么弱，RPC 也没那么神」；
- **用户状态方案**：Cookie+Session（Session 存 Redis）主流；JWT 适合前后端分离/微服务；URL 重写仅 Cookie 禁用时兜底。

### 3. 踩坑规避

- **Ping 通 ≠ TCP 通**：ICMP 与 TCP 由中间设备按协议/端口/策略分别处理（防火墙策略、端口未监听、NAT/负载均衡、TLS SNI 拦截）。排查顺序：DNS → ping → `nc` 测端口 → `curl`/`openssl s_client` 看 TLS；
- **GET 参数进日志**：GET 参数在 URL，网关/中间件日志全量记录，敏感数据必须走 POST body + 脱敏；
- **队头阻塞层次混淆**：HTTP/1.1 是应用层队头阻塞（多 TCP 连接缓解），HTTP/2 是传输层 TCP 队头阻塞（丢一个包阻塞所有 Stream）——HTTP/3 QUIC 才根治。

### 4. 优化进阶

DNS 根服务器逻辑上 13 个标识（a~m.root-servers.net），12 个独立运营组织，Anycast 多物理实例——这是「去中心化 + 任播」在基础设施层的经典工程实践。

### 5. 选型对比

| 模型 | 层数 | 特点 | 现状 |
|------|------|------|------|
| OSI 七层 | 7 | 理论完整、功能重复 | 教学/排障思维框架 |
| TCP/IP 四层 | 4 | 精简实用 | **事实标准** |
