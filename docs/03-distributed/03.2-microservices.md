## 模块一：服务拆分与领域边界

### 1. 核心原理

- **拆分方法论**：① **DDD 限界上下文**（聚合根/领域边界，最正统）；② 业务能力（"能独立变化的部分"）；③ 组织结构（康威定律：系统结构反映沟通结构）。
- **拆分粒度权衡**：太粗=单体（部署耦合）；太细=分布式单体（一次业务调用 10+ 次 RPC，延迟与故障率叠加）。**经验值：团队 5~10 人维护一个服务，服务间调用链 ≤ 5 跳**。
- **拆与不拆的信号**：独立伸缩需求（秒杀服务 vs 普通服务）、发布频率差异大、技术栈异构需求、故障隔离要求高。

### 2. 生产落地

- **服务分层（阿里规范）**：

```
网关层（流量接入/鉴权/限流）
  → 聚合层/BFF（页面/端侧适配）
    → 基础服务层（用户/商品/库存/订单，按领域拆分）
      → 平台层（消息/存储/搜索/支付通道）
```

- **一个服务的标准目录**：`api`（对外契约，DTO + Feign 接口）/ `domain`（领域模型）/ `infrastructure`（外部适配）/ `application`（用例编排）/ `bootstrap`（启动装配）。
- **契约先行**：接口 DTO 定义在独立的 api 包（或 IDL），消费方只依赖契约不依赖实现，避免 jar 传染式升级。

### 3. 踩坑规避

| 现象 | 根因 | 对策 |
|------|------|------|
| 改一个字段要发 5 个服务 | 共享 jar / 数据库共享 | 契约独立版本化；**一服务一库** |
| 调用链绕地球 | 拆分过细 | 领域合并；聚合层裁剪响应 |
| 联调环境互相踩踏 | 共享测试环境 | 每人一套 Namespace（K8s）/ Mock（WireMock） |
| 服务循环依赖 | 领域边界不清 | 引入领域事件解耦（A → 事件 → B） |

### 4. 优化进阶

- **防腐层（ACL）**：与遗留/外部系统对接时，用适配层把外部模型翻译为内部领域模型，防止外部模型渗透污染核心域。
- **演进式拆分**：单体 → 模块化单体（先拆包不拆进程）→ 抽离边缘服务 → 核心域服务化。**不要一次性重写**。

### 5. 选型对比

| 拆分依据 | 稳定性 | 实施难度 | 适用 |
|---------|--------|----------|------|
| 技术分层（controller/service） | 低 | 低 | 反模式 |
| 业务能力 | 中 | 中 | 中小团队 |
| DDD 限界上下文 | 高 | 高 | 复杂业务/大团队 |
| 组织团队 | 中 | 低 | 多团队并行 |

## 模块二：服务通信与治理

### 1. 核心原理

- **同步 vs 异步**：同步（HTTP/RPC，实时结果、耦合强）/ 异步（MQ/事件，削峰解耦、最终一致）。
- **服务治理清单**：注册发现、负载均衡（随机/轮询/一致性哈希/最小活跃）、路由（版本/标签/灰度）、限流（QPS/并发数/线程数）、熔断（错误率/慢调用比例）、降级（兜底数据/简化流程）、超时（分层设置）、重试（仅幂等）。
- **熔断三态**：Closed（正常）→ Open（失败达阈值，直接拒绝）→ Half-Open（放少量试探，成功则 Closed）。

### 2. 生产落地

- **Sentinel 规则配置化**：热点参数限流（`@SentinelResource(value="queryOrder", blockHandler="fallback")` + 参数索引）、系统自适应保护（Load1/CPU/RT 多维度）、规则持久化到 Nacos（动态生效）。

```java
// Sentinel 熔断 + 降级示例
@SentinelResource(
    value = "createOrder",
    blockHandler = "createOrderBlocked",   // 限流降级
    fallback = "createOrderFallback",      // 异常降级
    exceptionsToIgnore = {BizException.class})
public OrderVO createOrder(OrderCreateCmd cmd) {
    return orderService.create(cmd);
}

// 降级方法签名需与原方法一致 + 最后一个参数 Throwable
public OrderVO createOrderBlocked(OrderCreateCmd cmd, BlockException e) {
    return OrderVO.busy("系统繁忙，请稍后重试");
}
```

- **超时分层配置（铁律）**：网关 3s → BFF 2s → 服务 1.5s → DB 500ms。**下游超时必须 < 上游超时**，否则上游等超时了下游还在跑（资源泄漏）。
- **链路追踪**：SkyWalking Agent 零侵入接入；业务日志打 traceId（MDC）；慢调用分析定位真实瓶颈（常是下游 DB 而非当前服务）。

### 3. 踩坑规避

| 现象 | 根因 | 对策 |
|------|------|------|
| 限流只挡外部不挡内部 | 只配了网关限流 | **分层限流**：网关 + 服务 + 依赖方 |
| 熔断阈值形同虚设 | 阈值设太高（如错误率 90%） | 错误率 50% / 慢调用比例 60% 起步压测标定 |
| 降级逻辑把 DB 打挂 | 降级回调里查全量数据 | 降级=本地缓存/静态兜底，**禁止再查重依赖** |
| 重试导致下游雪崩 | 无退避重试 + 重试风暴 | 指数退避 + 抖动 + 熔断内不重试 |

### 4. 优化进阶

- **自适应限流**：Sentinel 系统规则（LOAD1 > CPU 核数×2.5 触发）比固定 QPS 更抗突发。
- **隔离策略**：舱壁模式（线程池隔离：不同依赖不同池，一个慢不拖垮全部）/ 信号量隔离（轻量，无排队，适合短依赖）。
- **混沌工程**：故障注入（ChaosBlade）验证熔断/降级链路是否真实生效——**规则不演练 = 不存在**。

### 5. 选型对比

| 治理能力 | Sentinel | Hystrix（停更） | Resilience4j | Istio |
|---------|----------|----------------|-------------|-------|
| 限流 | ✅ 强（热点/系统） | 弱 | 中 | ✅ |
| 熔断降级 | ✅ | ✅ | ✅ | ✅ |
| 侵入性 | 注解/API | 注解 | 注解 | 零侵入 |
| 生态 | Spring Cloud Alibaba | Netflix | Spring | K8s |

## 模块三：数据一致性与事务

### 1. 核心原理

- **微服务数据一致性原则**：放弃跨服务强事务，用**最终一致 + 补偿 + 对账**；每个服务**独立数据库**（防耦合），跨服务数据只能通过接口/事件。
- ** Saga 编排式 vs 协同式**：编排式（Orchestration，中央协调器推进，易观测）/ 协同式（Choreography，事件驱动，松耦合但难追踪）。
- **幂等三件套**：唯一业务号、状态机约束、去重存储（Redis SETNX + DB 唯一索引双保险）。

### 2. 生产落地

- **订单主链路最终一致设计**（典型五服务）：

```
订单服务(创建: 本地事务+outbox)
  → MQ → 库存服务(预占, 幂等: 唯一索引 order_id)
  → MQ → 优惠券服务(核销, TCC 或消息+补偿)
  → MQ → 支付服务(发起支付)
  → MQ → 履约服务(发货)
任何一步失败 → 反向补偿消息 → 各服务回滚
```

- **对账兜底**：每日定时任务比对订单/库存/支付流水，发现不一致进人工工单 + 自动重试。

### 3. 踩坑规避

1. **消息无序**：同订单的"创建"晚于"取消"到达 → 用版本号/状态机过滤（只接受状态合法流转的事件）。
2. **消息重复**：MQ at-least-once 语义必然重复 → 消费端幂等（`INSERT ... ON DUPLICATE KEY` 或状态机）。
3. **补偿失败**：补偿接口本身不可用 → 补偿任务重试 + 死信队列 + 人工介入面板。**补偿必须先于业务失败发现，而不是等用户投诉**。
4. **分布式事务中间件单点**：Seata TC 挂了全局事务全卡 → TC 高可用 + 本地事务兜底。

### 4. 优化进阶

- **事务消息表合并扫描**：outbox 表量大后按状态分区 + 批量拉取（`LIMIT 500`）+ 索引 `(status, next_retry_time)`。
- **事件溯源（Event Sourcing）**：关键账务用事件流代替状态快照，天然可追溯/可回放；复杂度高，慎用于非核心域。

### 5. 选型对比

| 方案 | 一致性时延 | 复杂度 | 可观测性 | 场景 |
|------|-----------|--------|----------|------|
| Saga（编排式） | 秒级 | 中 | 好 | 长流程业务 |
| Saga（协同式） | 秒级 | 低 | 差 | 简单解耦 |
| TCC | 实时 | 高 | 中 | 资金/库存强一致 |
| 本地消息表 | 秒级 | 低 | 好 | **通用** |
| 事务消息 | 秒级 | 低 | 中 | RocketMQ |

## 模块四：稳定性与可观测性

### 1. 核心原理

- **稳定性三板斧**：限流（保护自己不挂）、熔断（保护自己不拖垮）、降级（牺牲非核心保核心）。
- **可观测性三支柱**：Metrics（指标聚合，`订单创建成功率 P99 < 99%` 告警）、Logging（结构化日志 + traceId）、Tracing（分布式链路）。

### 2. 生产落地

- **上线 Checklist**（稳定性视角）：
  1. 接口是否有限流/熔断/降级规则
  2. 下游依赖是否标注超时 + 配置熔断
  3. 慢查询/慢 RPC 是否治理
  4. 日志是否含 traceId、无敏感信息
  5. 核心指标是否配 Grafana 看板 + 告警（成功率/RT/错误码分布）
  6. 回滚方案（配置回滚/镜像回退/DB 回滚脚本）是否就绪
- **告警分级**：P1（核心链路故障，电话+值班）/ P2（部分受损，IM）/ P3（趋势恶化，邮件）。**告警必须可执行**（没人看的告警=没有）。

### 3. 踩坑规避

| 现象 | 根因 | 对策 |
|------|------|------|
| 告警风暴 | 阈值敏感 + 无收敛 | 分组聚合 + 抑制规则（故障期间静默衍生告警） |
| 挂了监控不知道 | 只监控服务自身，没监控依赖 | 依赖方健康度纳入告警（DB/Redis/MQ） |
| 日志查不到 | 无 traceId 串联 + 日志级别混乱 | MDC 注入 traceId；ERROR 才进告警管道 |
| 压测才暴露瓶颈 | 无常态化基线 | 定期小规模压测；核心链路容量水位看板 |

### 4. 优化进阶

- **全链路压测**：流量染色（压测标打标）→ 影子库/表隔离 → 核心链路（下单/支付）定时演练 → 容量规划（预估大促水位）。
- **SLO 驱动**：定义核心接口 SLO（可用性 99.95%、P99 RT < 200ms），错误预算（Error Budget）内允许发布，超预算冻结需求修稳定性。

### 5. 选型对比

| 能力 | 方案 | 特点 |
|------|------|------|
| 指标 | Prometheus + Grafana | 云原生标准，Pull 模型 |
| 日志 | ELK / EFK / Loki | ELK 功能全；Loki 轻（与 Grafana 一体） |
| 链路 | SkyWalking / Zipkin / Jaeger | SkyWalking Java 生态最强（探针零侵入） |
| 告警 | Alertmanager / PagerDuty | 分级 + 值班轮转 |
