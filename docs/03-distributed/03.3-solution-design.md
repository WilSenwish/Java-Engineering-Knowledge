## 模块一 · 秒杀系统：流量分层过滤与库存扣减

### 1. 核心原理

秒杀的数学本质：**把 N 倍于容量的瞬时流量，在到达最终存储前逐层削减**。核心理念是"层层过滤"——每一层只放行它有把握处理的量，绝大多数请求在到达核心服务前就被拒绝。

**超卖根源**：并发下"查库存 → 判断充足 → 扣减"三步非原子——两个线程同时读到剩余 1 件，均通过判断，均扣减成功，库存变 -1。**对策方向只有两个：把三步合成一个原子操作（DB 乐观锁 / Redis 原子命令），或把并行串行化（队列削峰 + 异步下单）**。

### 2. 生产落地

**五层过滤架构**：

```text
① 客户端层   ：前端随机丢弃，服务端压力大时直接返回"系统繁忙"
② CDN        ：秒杀页静态资源全部 CDN 化，动态接口才回源
③ Nginx      ：IP 限流（单 IP ≤5 次/秒）、黑白名单、连接数限制
④ 网关层     ：Sentinel 动态限流（按实时负载调阈值）+ 业务前置校验
               （登录态/活动时间窗口/资格判断）
⑤ 缓存层     ：热点数据本地缓存（Caffeine）+ Redis 集群双级
```

**热点数据三板斧**：

| 策略 | 做法 | 解决 |
|------|------|------|
| 数据拆分 | 1000 件库存拆 10 个子库存各 100，请求均匀路由 | 单 Key 热点 |
| 多级缓存预热 | 活动前 Redis 预热 + 本地缓存预热 | 冷启动击穿 |
| 多副本 | 热 Key 在多个 Redis 节点建副本，读扩散 | 单节点带宽瓶颈 |

**库存扣减方案矩阵**（详见关联文档）：

| 方案 | 原子性保证 | 适用 |
|------|------------|------|
| DB 乐观锁 `UPDATE stock SET n=n-1 WHERE id=? AND n>0` | 单行更新原子 | 中低并发 |
| Redis `DECR`/Lua 预扣 + MQ 异步落库 | 单线程原子 + 最终一致 | 高并发主流 |
| 库存分段 + 分段锁 | 分段内串行 | 极端热点 |

### 3. 踩坑规避

- **缓存与 DB 库存不一致**：Redis 预扣成功但订单创建失败——必须回补库存（补偿消息/对账），否则"少卖"；
- **限流阈值一刀切**：预热期/进行期/结束期容量不同——阈值应可动态调整（Sentinel 热点参数/规则推送）；
- **前端按钮置灰依赖服务端**：服务端超时后前端自动恢复可点，用户疯狂重点——置灰需客户端定时器强制保持；
- **同步下单直连 DB**：瞬时流量全部打到 MySQL，连接池打满引发雪崩——入口必须排队（MQ/令牌桶）。

### 4. 优化进阶

**令牌桶预发放**：活动前发放限量令牌（= 库存数），抢购转化为"抢令牌"——无令牌请求在任何计算前被拒，把业务判断前置到内存级。

**库存分段扣减 + 合并落库**：子库存扣减成功先记分段流水，异步任务合并写 DB 总库存，降低单行竞争。

**压测基线**：按目标 QPS × 安全系数（3~5 倍）设计各层容量，Nginx/网关/服务/DB 每层都要有压测报告——最短板决定系统容量。

### 5. 选型对比

| 方案 | 一致性 | 复杂度 | 典型场景 |
|------|--------|--------|----------|
| DB 乐观锁直扣 | 强一致 | 低 | 内部秒杀/低并发 |
| Redis 预扣 + 异步下单 | 最终一致 | 中 | 互联网秒杀主流 |
| 令牌桶 + 全异步 | 最终一致 | 高 | 超级热点（整点抢购） |

## 模块二 · 雪崩防护：高可用系统设计

### 1. 核心原理

**雪崩传导链**（真实故障复盘）：流量 10 倍 → 评论服务变慢 → 详情页调用线程全部阻塞等待 → 详情服务线程池满 → 推荐服务调详情超时 → 首页不可用，全程不到 5 分钟。

**关键洞察**：雪崩不是被"压垮"的，是被"等垮"的——**同步阻塞型调用是传导介质**。一个服务慢 3 秒，上游线程就被占 3 秒，线程池耗尽后，上游对它的上游也变成慢服务。防护的核心是**切断传导介质**（超时/隔离/熔断）+ **入口削减流量**（限流）+ **提供降级出口**（兜底）。

**可用性度量**："几个 9"——99.9%（年停机 8.76h）/ 99.99%（52.6min）/ 99.999%（5.26min）。

### 2. 生产落地

**防护四层矩阵**：

| 手段 | 作用点 | 典型实现 |
|------|--------|----------|
| 超时 | 切断等待 | Feign/HTTP 连接/读取超时必须显式设置，且**下游超时 < 上游超时** |
| 限流 | 入口削峰 | Sentinel 网关流控（QPS/线程数/热点参数）、Nginx limit_req |
| 隔离 | 故障不扩散 | 线程池隔离（每个依赖独立池）/信号量隔离（低延迟场景） |
| 熔断 | 快速失败 | 熔断器状态机：Closed→Open（错误率/慢调用率超阈值）→Half-Open 试探恢复 |
| 降级 | 兜底体验 | 返回缓存值/默认值/静态页，静默失败优于空白错误 |

**舱壁模式（Bulkhead）**：线程池按下游依赖划分（评论服务池、推荐服务池互不侵占）——一个依赖故障最多耗尽自己的池，不拖垮整个 Tomcat 线程。

### 3. 踩坑规避

- **无超时或超时过长**：下游挂了上游线程无限等——所有外部调用必须设超时，且逐层递减；
- **重试风暴**：超时后无脑重试，把半死服务彻底打死——重试必须有限次 + 退避 + 仅对幂等操作；
- **熔断阈值不合理**：错误率 1% 就熔断（抖动误熔）/50% 才熔断（慢半拍）——按 SLO 反推，配合半开状态试探；
- **降级链路也走故障依赖**：降级逻辑去查同一个挂掉的 Redis——降级必须是本地缓存/静态数据；
- **健康检查误导**：进程活着但线程池全满—— readiness 探针要检查核心依赖连通性，不只查进程。

### 4. 优化进阶

**容量水位自动化**：按 CPU/线程池利用率/队列深度多维水位自动扩容 + 限流阈值联动（HPA + 自适应流控）。

**故障演练（Chaos Engineering）**：定期注入下游延迟/错误/进程杀死，验证熔断降级是否真生效——没演练过的预案等于没有预案。

**异步化解耦**：非核心链路（通知、积分、统计）全面 MQ 化，主链路只做最少的事——从根本上减少同步等待面。

### 5. 选型对比

| 防护组件 | 形态 | 特点 |
|----------|------|------|
| Sentinel | 流量治理全家桶 | 动态规则推送、热点参数限流、系统自适应保护，国产主流 |
| Resilience4j | 轻量函数式 | 与 Spring Cloud Circuit Breaker 集成，代码简洁 |
| Hystrix | 线程隔离鼻祖 | **已停更**，仅遗留系统参考——新项目不选 |
