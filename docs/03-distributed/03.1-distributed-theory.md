## 模块一：分布式理论基础

### 1. 核心原理

- **CAP**：一致性（C，所有节点同一时刻看到相同数据）、可用性（A，非故障节点在合理时间内响应）、分区容错（P，网络分区时仍能工作）。**分布式系统 P 必须成立，实际是在 C 与 A 之间按场景权衡**（CP：ZooKeeper/etcd/Consul；AP：Eureka/Nacos 默认、大多数缓存）。
- **BASE**：基本可用（Basically Available）、软状态（Soft State，允许中间态）、最终一致性（Eventually Consistent）。是 AP 的工程化落地思想：**用最终一致换取可用性与性能**。
- **一致性模型谱系**：强一致（线性一致）→ 顺序一致 → 因果一致 → 最终一致。业务按"错的代价"选层级：库存扣减要强一致（DB 行锁）， Feed 计数可最终一致。

### 2. 生产落地

- **一致性决策表**：

| 业务动作 | 一致性要求 | 实现 |
|---------|-----------|------|
| 下单扣库存 | 强一致 | DB 事务/行锁、Redis Lua（可接受对账补偿） |
| 支付回调更新订单 | 最终一致 | 幂等 + 状态机 + 对账 |
| 积分/等级 | 最终一致 | MQ 异步 |
| 缓存/榜单 | 最终一致 | 异步刷新 |

- **注册中心选型落地**：Nacos（注册+配置一体，AP/CP 可切，**国内主流**）/ Consul（CP）/ Eureka（AP，已停更）/ ZooKeeper（CP，强一致但运维重）。

### 3. 踩坑规避

- **"CAP 三选二"是误导**：P 发生时不是"关掉 C 或 A"，而是设计**降级策略**（分区期间：限流排队 vs 返回旧数据）。
- **把最终一致当口头承诺**：无补偿机制的"最终一致"= 永久不一致。必须有**对账 + 补偿任务**兜底（如定时比对订单与支付流水）。
- **时钟假设**：分布式下各节点时钟不完全同步（NTP 抖动），**不要把物理时钟当全局时序**，用逻辑时钟/版本号/向量时钟。

### 4. 优化进阶

- **Quorum NWR**：`W + R > N` 保证强一致读；`W=1, R=1` 最高性能。Cassandra/Dynamo 风格系统的核心旋钮。
- **一致性哈希**：节点取余环 + 虚拟节点，扩缩容只迁移 1/N 数据（一致性哈希是**负载均衡策略**，不解决一致性，名称易误导）。

### 5. 选型对比

| 协调系统 | 协议 | 一致性 | 延迟 | 场景 |
|---------|------|--------|------|------|
| ZooKeeper | ZAB | CP（线性一致） | 写 ms 级 | 配置、选主、分布式锁 |
| etcd | Raft | CP | 写 ms 级 | K8s 生态、元数据 |
| Consul | Raft | CP | 写 ms 级 | 服务发现 + KV |
| Nacos | Raft/Distro | CP/AP 可切 | 亚秒 | 注册+配置中心（国内） |
| Eureka | Peer2Peer | AP | 秒级 | 历史系统 |

## 模块二：RPC 与网关

### 1. 核心原理

- **RPC 核心链路**：客户端 Stub（序列化）→ 网络传输 → 服务端 Stub（反序列化 → 调用 → 回包）→ 动态代理屏蔽细节。
- **主流 RPC 框架**：Dubbo（Java 生态，SPI 完善）/ gRPC（HTTP2 + Protobuf，跨语言）/ Thrift（Facebook）/ OpenFeign（HTTP 声明式，微服务网关内）。
- **网关职责**：路由转发、统一鉴权、限流熔断、灰度/流量染色、协议转换（HTTP → RPC）、监控埋点。

### 2. 生产落地

- **Dubbo 生产要点**：`timeout` 显式设置（默认 1s 太长）、`retries=0`（**写操作禁止重试**，读可 1 次）、`check=false`（启动不检查提供方）、`serialization=hessian2/kryo`、泛化调用慎用、`token` 鉴权。
- **Spring Cloud Gateway 要点**：`RequestRateLimiter`（Redis + Lua 令牌桶）、`CircuitBreaker` 过滤器、全局 filter 注入 traceId、超时分层（连接/读/写分开配）。
- **灰度发布**：网关按 header/cookie/uid 维度染色 → 转发到灰度实例组（配合注册中心元数据或 K8s Ingress）。

### 3. 踩坑规避

| 现象 | 根因 | 对策 |
|------|------|------|
| 超时风暴（雪崩） | 下游 RT 升高 → 线程池占满 → 上游连锁超时 | 超时 < 重试超时 < 调用方超时；熔断（Sentinel）快速失败 |
| 写操作重试放大 | 网络超时但服务端已执行 | **写操作 retries=0 + 业务幂等** |
| 序列化不兼容 | 新增字段/改字段名，老消费者反序列化失败 | 字段只加不删不改类型；Protobuf 保留 tag |
| 网关单点 | 无集群/限流自身被打挂 | 网关多实例 + 自身限流 + 快速失败 |

### 4. 优化进阶

- **异步化 RPC**：Dubbo 异步调用（`CompletableFuture`）+ 泛化/事件驱动，削峰填充；回调地狱用 `CompletableFuture` 编排。
- **服务网格（Istio/Envoy）**：流量治理下沉 sidecar，业务零侵入；代价是延迟增加（~2ms）+ 运维复杂度，大规模微服务再上。

### 5. 选型对比

| 框架 | 协议 | 生态 | 跨语言 | 场景 |
|------|------|------|--------|------|
| Dubbo | TCP 自定义 | Java 最强 | 多语言版 | 国内 Java 微服务 |
| gRPC | HTTP/2+Protobuf | 云原生标准 | ✅ 强 | 跨语言、流式 |
| OpenFeign | HTTP | Spring Cloud | — | 内部服务轻量调用 |
| Thrift | TCP 自定义 | 一般 | ✅ | 遗留系统 |

## 模块三：分布式 ID / 锁 / 事务

### 1. 核心原理

- **分布式 ID 方案谱系**：UUID（无序、长）、DB 自增（单点、连续）、号段模式（批量取一段，如美团 Leaf）、Redis 发号（INCR）、**雪花算法 Snowflake**（时间戳 41bit + 机器 10bit + 序列 12bit，单机 ms 级 4096 个，趋势递增）。
- **分布式锁谱系**：DB 唯一索引（最简单）、Redis SETNX（高性能、有主从切换风险）、ZooKeeper 临时顺序节点（强一致、性能中）、etcd 租约。
- **分布式事务谱系**：2PC（XA，强一致但阻塞/单点）→ TCC（Try-Confirm-Cancel，业务层补偿）→ SAGA（长事务，每步有补偿）→ 本地消息表（最终一致，**互联网最常用**）→ 事务消息（RocketMQ 半消息）→ Seata AT 模式（无侵入、靠 undo_log）。

### 2. 生产落地

- **雪花 ID 生产要点**：机器 ID 分配（IP/MAC/配置中心，防容器重启后漂移）；**时钟回拨处理**（等待/拒绝/备用 workerId）；不要用时间戳高位做业务含义。
- **本地消息表（outbox）落地**：业务写与消息写在**同一个本地事务**；定时任务扫消息表投递 MQ；消费方幂等（唯一索引/状态机）；失败重试 + 告警 + 死信。

```java
// 本地消息表模式核心（业务与消息同事务）
@Transactional(rollbackFor = Exception.class)
public void pay(PayCmd cmd) {
    // 1. 业务写
    payService.executePay(cmd);
    // 2. 同事务写 outbox
    outboxService.save(OutboxEvent.of("PAY_SUCCESS", cmd.getOrderId()));
}
// 3. 独立定时任务扫描 outbox -> 投递 MQ -> 消费者幂等处理
```

### 3. 踩坑规避

1. **TCC 空回滚/悬挂/幂等**：Try 未执行就收到 Cancel（空回滚）→ 需记录 Try 状态；Cancel 先于 Try 到达（悬挂）→ Try 时检查是否已 Cancel。**TCC 三惑必须处理**。
2. **SAGA 无补偿隔离**：中途失败回滚时，后段事务已提交的数据被"补偿"而不是隔离——对外可见脏数据窗口。设计上把**不可逆操作放最后**。
3. **Seata AT 的全局锁**：大并发下全局锁竞争 + 脏写检查失败回滚；分库分表 + 热点行场景慎用 AT。
4. **消息丢失三环**：生产方未确认 → broker 丢 → 消费方未确认。逐环配置：`acks=all` + 副本 + 消费手动 ACK。

### 4. 优化进阶

- **幂等设计五法**：唯一索引（最可靠）、状态机（只允许合法流转）、Token 机制（防重复提交）、乐观锁版本号、去重表（TTL 清理）。
- **事务消息 vs 本地消息表**：RocketMQ 事务消息免建表但绑定中间件；本地消息表通用（任意 MQ）但需自建扫描任务。

### 5. 选型对比

| 方案 | 一致性 | 侵入性 | 性能 | 场景 |
|------|--------|--------|------|------|
| 2PC/XA | 强 | 低（协议级） | 低（阻塞） | 传统 DB 间 |
| TCC | 最终 | 高（三接口） | 中 | 资金/核心交易 |
| SAGA | 最终 | 中 | 中 | 长流程业务 |
| 本地消息表 | 最终 | 中 | 高 | **通用首选** |
| 事务消息 | 最终 | 低 | 高 | RocketMQ 体系 |
| Seata AT | 最终 | 低 | 中 | CRUD 型快速接入 |

## 模块四：配置中心与服务注册发现

### 1. 核心原理

- **注册中心职责**：服务注册（心跳保活）、健康检查、服务发现（推/拉）、故障剔除。
- **配置中心职责**：配置集中管理、动态推送（长轮询/Gossip）、环境隔离、版本回滚、敏感配置加密。
- **推拉模型**：注册信息变更推送（长轮询）+ 客户端定时拉取兜底；配置同理。

### 2. 生产落地

- **Nacos 落地**：命名空间（环境隔离：dev/test/prod）→ 分组 → DataID（`服务名-profile.yaml`）；配置变更监听 `@NacosConfigListener` 或 Apollo `@ApolloConfigChangeListener`；敏感配置（DB 密码）用 Jasypt/配置加密插件，**禁止明文提交 git**。
- **健康检查分层**：注册中心心跳（进程活）+ 业务探活（`/health` 自定义检查依赖）——DB 挂了不能把整个服务标记为不可用（扩大故障面），除非确认不可服务。
- **配置版本化**：所有配置变更走发布流程（谁/何时/改了什么），支持一键回滚。

### 3. 踩坑规避

| 现象 | 根因 | 对策 |
|------|------|------|
| 服务批量下线又上线（抖动） | 心跳超时阈值太短 + 网络抖动 | 合理 `preserve.ip.healthy.time`；客户端重试与缓存实例列表 |
| 配置推送延迟/丢失 | 长轮询中断 + 无兜底 | 客户端本地快照 + 定时全量拉取 |
| 配置误改全环境 | 无环境隔离/无审核 | 命名空间隔离 + 变更审批 + 灰度推送 |
| 注册中心雪崩 | 全服务同时重连 | 客户端缓存 + 退避重连（指数退避 + 抖动） |

### 4. 优化进阶

- **配置即代码（GitOps）**：配置存 git → CI 校验 → 发布到配置中心；结合 Apollo 的集群/灰度维度实现"配置发布=代码发布"。
- **多活容灾**：注册中心跨机房部署；客户端**就近接入** + 跨机房容灾（本机房全挂才切远程）。

### 5. 选型对比

| 产品 | 注册 | 配置 | 一致性 | 生态 |
|------|------|------|--------|------|
| Nacos | ✅ | ✅ | CP/AP | Spring Cloud Alibaba / Dubbo |
| Apollo | ❌ | ✅ | 实时推送强 | 携程开源，配置功能最全 |
| Consul | ✅ | ✅ | CP | K8s/VM 混合 |
| ZooKeeper | ✅ | 弱 | CP | 传统 Dubbo |
| etcd | ✅ | ✅ | CP | K8s 原生 |
