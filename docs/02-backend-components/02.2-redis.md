## 模块一：高性能原理与基础架构

### 1. 核心原理

- **为什么快（六因子）**：① 纯**内存**操作；② 高效数据结构（SDS/ziplist/quicklist/intset/skiplist）；③ **单线程**命令处理（无锁、无上下文切换，6.0+ IO 多线程仅用于网络读写）；④ **IO 多路复用** epoll；⑤ 协议简单（RESP）；⑥ 全局哈希表 O(1) 定位。
- **SDS（Simple Dynamic String）**：len 字段 O(1) 取长度、空间预分配 + 惰性释放、二进制安全（`\0` 截断问题解决）。
- **单线程的边界**：单线程指**命令执行**单线程；持久化/异步删除有子进程/后台线程；**慢命令**（`KEYS *`、`HGETALL` 大 Hash、`SMEMBERS` 大集合）会阻塞整个实例。

### 2. 生产落地

- **Jedis/Lettuce 选型**：Spring Boot 默认 **Lettuce**（Netty、异步、线程安全共享连接、集群友好）；Jedis 直连需池化。生产配置连接池 + 超时 + 重试。

```yaml
spring:
  redis:
    lettuce:
      pool:
        max-active: 16      # 按并发压测标定
        max-idle: 8
        min-idle: 2
        max-wait: 3000ms
    timeout: 3000ms
```

- **Key 命名规范**：`业务:模块:唯一标识`，如 `order:detail:20261018xxxx`；禁止无前缀裸 key（难以管理/统计/清理）。
- **大 Key 治理**：value > 10KB 或元素数 > 5000 即警惕；拆分为 hash 分片（`order:{id}:{shard}`）；用 `redis-cli --bigkeys` 扫描。

### 3. 踩坑规避

| 现象 | 根因 | 对策 |
|------|------|------|
| Redis CPU 100% 但 QPS 不高 | 慢命令/大 Key 阻塞单线程 | `SLOWLOG GET` 定位；`--bigkeys` 治理 |
| 内存持续增长不释放 | 惰性释放策略 + 大量过期 Key 堆积 | 监控 `mem_fragmentation_ratio`；开启 active-expire-effort 10 |
| `redis-cli` 生产误操作 `KEYS *`/`FLUSHALL` | 无保护 | rename-command 禁用危险命令；`--scan` 替代 `KEYS` |
| 缓存与 DB 不一致 | 更新顺序错误（先删缓存后写 DB，读请求回填旧值） | Cache-Aside + 延迟双删 / binlog 监听（Canal）异步删 |

### 4. 优化进阶

- **批量操作三选型**：① 原生命令（MGET/HMGET）——原子但不可混搭，Cluster 下 key 可能不在同 slot；② **Pipeline**——N 条命令 N×RTT → 1×RTT，非原子，需自行维护 key-slot 关系；③ **Lua 脚本**——原子+混搭+逻辑，Cluster 下无法保证跨 slot 原子性。命令间有依赖 → Lua；无依赖求吞吐 → Pipeline；同 key 批量 → 原生命令；
- **Redis 事务定位**：功能鸡肋（无原子性/无回滚/无持久性保障），生产用 Lua 替代；
- **大量 key 集中过期**：随机过期时间 + `lazy-free`（4.0+ 异步释放）防定期删除阻塞主线程；
- **内存优化**：`maxmemory-policy` 前先 `INFO memory` 看 `used_memory` vs `used_memory_rss`；碎片 > 1.5 时 `activedefrag yes`（4.0+）或重启整理。

### 5. 选型对比

| 方案 | 延迟 | 吞吐 | 持久化 | 数据结构 | 场景 |
|------|------|------|--------|----------|------|
| Redis | 亚 ms | 10万+ QPS | RDB/AOF | 丰富 | **缓存/分布式锁/排行榜** |
| Memcached | 亚 ms | 10万+ QPS | 无 | 纯 KV | 纯缓存、多线程模型 |
| KeyDB/Tair | 亚 ms | 高 | 强 | 丰富 | 多线程改造/云托管 |

**Redis 阻塞原因清单（排查对照）**：O(n) 命令 / `SAVE` 同步 RDB / AOF 写日志与 fsync 刷盘 / AOF 重写缓冲区追加 / 大 Key 操作 / `flushdb`/`flushall` / 集群迁移同步阻塞 / 内存不足触发 Swap（灾难性）/ CPU 竞争与网络延迟。

## 模块二：数据结构与典型场景

### 1. 核心原理

- **String（SDS）**：缓存对象、计数器（`INCR` 原子）、分布式锁 value。SDS 二进制安全、**取长度 O(1)**、无缓冲区溢出。
- **Hash（ziplist/listpack ↔ hashtable）**：对象属性存储（`HGETALL` vs 多次 `GET`）；field 少时用 listpack 省内存。
- **List（quicklist = ziplist 双向链表）**：最新 N 条（`LPUSH` + `LTRIM`）、简单队列（**生产队列用 MQ，List 仅轻量**）。
- **Set（intset/hashtable）**：去重、交并差（共同关注 `SINTER`）。
- **ZSet（skiplist + hashtable）**：排序榜（score + 排名 `ZRANGE`）、延迟队列（score=时间戳，`ZRANGEBYSCORE` 轮询）。
- **周边结构**：Bitmap（签到/布隆过滤器雏形）、HyperLogLog（UV 统计，~12KB 0.81% 误差）、Geo（LBS）、Stream（5.0+ 消息队列，支持消费组）。

**底层结构版本演进**（建索引/评估内存时必知）：List 从 LinkedList+ZipList → **QuickList（3.2+）** → **ListPack（7.0+ 取代 ZipList）**；ZSet 小数据用 ZipList/ListPack、大数据用 SkipList+Dict。Redis 官网数据结构文档是版本行为的第一权威。

### 2. 生产落地（场景映射表）

| 业务场景 | 数据结构 | 用法 | 注意 |
|---------|---------|------|------|
| 对象缓存 | String（JSON） | `SETEX key 600 json` | 序列化协议（JDK/Kryo/JSON） |
| 计数器/限流 | String | `INCR` + `EXPIRE` | Lua 保证 check-and-set |
| 最新列表 | List | `LPUSH`+`LTRIM 0 99` | 有序要求高用 ZSet |
| 标签/共同好友 | Set | `SADD`/`SINTER` | 大集合 SINTER 慢 |
| 排行榜/TopN | ZSet | `ZINCRBY`/`ZREVRANGE` | 分页深翻页成本 |
| 签到/在线状态 | Bitmap | `SETBIT`/`BITCOUNT` | 大用户量按天分 key |
| UV 统计 | HyperLogLog | `PFADD`/`PFCOUNT` | 不能取单元素 |
| 延迟任务 | ZSet | `ZADD score=执行时间` | 轮询间隔 vs 时效 |

### 3. 踩坑规避

1. **缓存穿透**（查不存在的数据，绕过缓存打库）：布隆过滤器 / 空值缓存（短 TTL）/ 参数校验。
2. **缓存击穿**（热点 key 过期瞬间高并发打库）：互斥锁重建（`SETNX`）/ 逻辑过期（永不过期 + 异步更新）/ 热点 key 预热。
3. **缓存雪崩**（大量 key 同时过期或 Redis 宕机）：过期时间加随机偏移；多级缓存（本地 Caffeine + Redis）；熔断降级（Sentinel）；Redis 高可用（哨兵/集群）。
4. **大 Key 删除阻塞**：`DEL` 大集合阻塞单线程 → 4.0+ `UNLINK` 异步删；Hash/Set 用 `HSCAN`/`SSCAN` 分批。
5. **`HGETALL` 大 Hash**：改 `HSCAN` 游标分批 或拆 key。

### 4. 优化进阶

- **批量操作聚合**：Pipeline 或 `MSET`/`MGET`；Spring Cache `@Cacheable(sync=true)` 防缓存击穿。
- **热 key 拆分**：`hot_key` → `hot_key_1..N`，读时随机后缀 + 本地缓存聚合（读写都放大 N 倍，权衡）。
- **集群模式约束**：key 的 hash tag `{user}:profile` 保证同 slot；跨 slot 事务/Lua 不支持；`MULTI` 有限支持。

### 5. 选型对比

| 场景 | String | Hash | ZSet | 专用结构 |
|------|--------|------|------|----------|
| 存整对象 | ✅ 首选 | 字段多时 | — | — |
| 存对象字段 | — | ✅ | — | — |
| 计数 | ✅ INCR | HINCRBY | — | — |
| 排序/范围 | — | — | ✅ | — |
| 海量去重 | — | — | — | Bitmap/HLL |

## 模块三：持久化、高可用与集群

### 1. 核心原理

- **RDB**：某时刻内存快照（`SAVE` 阻塞 / `BGSAVE` fork 子进程 + Copy-On-Write）。恢复快、可能丢最后一次快照后的数据。
- **AOF**：命令日志（always/everysec/no，**everysec 平衡最好**，最多丢 1s）；`AOF` 重写压缩体积；混合持久化（4.0+，RDB 头 + AOF 增量）。
- **主从复制**：全量同步（RDB）+ 增量同步（命令传播 + 复制缓冲区）；**主从延迟**来源：网络、主库写压力、从库 IO。
- **哨兵（Sentinel）**：监控 + 自动故障转移 + 配置中心（客户端经哨兵拿主节点地址）；**不解决分片**。
- **Cluster**：16384 slot 数据分片；Gossip 协议；客户端直连分片节点；`-c` 模式；槽迁移扩容。

### 2. 生产落地

- **部署选型建议**：缓存为主 → 主从 + 哨兵；数据量大/吞吐高 → Cluster（3 主 3 起）；单实例 > 10GB 或有强一致需求 → 评估云托管或代理层（Codis/Twemproxy）。
- **持久化策略**：`appendonly yes` + `appendfsync everysec`；RDB 作为冷备（`save 900 1` 等）；**备份文件异地存储**。
- **监控必看指标**：`used_memory`、`mem_fragmentation_ratio`、`connected_clients`、`instantaneous_ops_per_sec`、`keyspace_hits/misses`（命中率 < 90% 告警）、`master_repl_offset` 延迟、`rdb_last_bgsave_status`。

```bash
# 值班常用
redis-cli --stat                  # 实时 QPS/内存/连接
redis-cli INFO memory | grep -E 'used_memory_human|fragmentation'
redis-cli SLOWLOG GET 10          # 慢命令
redis-cli --bigkeys               # 大 Key 扫描(从库跑!)
```

### 3. 踩坑规避

| 现象 | 根因 | 对策 |
|------|------|------|
| 主从频繁全量同步 | 复制缓冲区溢出 / 网络抖动 | 调大 `repl-backlog-size`；检查网络与从库负载 |
| 故障转移期间写丢失 | 异步复制（默认） | 关键业务 `WAIT 1 0` 同步写或用 Redlock（权衡性能） |
| 集群某槽卡住 | 大 Key 迁移 / 热 slot | 避免超大 value；slot 均衡预热 |
| `OOM command not allowed` | 达 `maxmemory` 且 no-eviction | 预留内存；改 `allkeys-lru`；治理大 Key |

### 4. 优化进阶

- **内存淘汰策略**：`noeviction`（默认，写报错）/ `allkeys-lru`（**缓存首选**）/ `volatile-lru` / `allkeys-lfu`（4.0+，频率比时间新，防突发流量冲掉老热点）/ `allkeys-random`。
- **读写分离注意**：从库读有延迟；"写后立即读"走主库或加版本号校验。
- **Pipeline + 事务区分**：Pipeline 非原子（服务端可交错其他客户端命令）；`MULTI/EXEC` 原子但无回滚。

### 5. 选型对比

| 维度 | 主从+哨兵 | Cluster |
|------|-----------|---------|
| 数据分片 | 无（单机容量上限） | 有（16384 slots） |
| 容量 | ≤ 单机内存 | 水平扩展 |
| 高可用 | 自动故障转移 | 自动故障转移 + 槽迁移 |
| 客户端复杂度 | 中（Sentinel 发现） | 高（smart client） |
| 事务/Lua | 支持 | 限同 slot |
| 适用 | 中小规模缓存 | 大规模缓存/高吞吐 |

## 模块四：缓存一致性与分布式锁

### 1. 核心原理

- **Cache-Aside 标准流程**：读 = 先缓存 → miss 读 DB → 回填（带 TTL）；写 = **先更新 DB → 再删缓存**（非更新缓存：缓存可能被并发写覆盖成旧值；非先删缓存：写 DB 期间读回填旧值）。
- **延迟双删**：更新 DB 前删一次 → 更新 DB → 休眠（≈ 主从延迟/读耗时）→ 再删一次。低成本缓解，非绝对。
- **最终一致工程化**：Canal/Debezium 监听 binlog → MQ → 消费删缓存（可靠，链路长）。
- **分布式锁**：Redis 实现核心 = `SET key uuid NX PX 30000`（NX 互斥 + PX 防死锁 + uuid 防误删）；释放 = Lua 比对 value 再 DEL（原子）。

### 2. 生产落地

```java
// Redisson 风格锁（生产直接用 Redisson，勿裸写 SETNX）
RLock lock = redissonClient.getLock("order:pay:" + orderId);
try {
    if (lock.tryLock(3, 30, TimeUnit.SECONDS)) {  // 等待3s 持锁30s(看门狗续期)
        // 临界区
    }
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();
}
```

- **Redisson 看门狗**：持锁期间后台线程每 10s 续期（`lockWatchdogTimeout/3`），业务超时自动释放防死锁。

### 3. 踩坑规避

1. **锁过期但业务未完成**：NX+PX 固定超时 → 业务卡顿超时后锁释放，第二个线程进入 → 互斥失效。用看门狗续期（Redisson）或分段续期。
2. **释放了别人的锁**：value 不用唯一标识，A 的锁过期后被 B 获取，A 执行完 DEL 删了 B 的锁。**Lua 比对 value 再删**。
3. **主从切换丢锁**：主节点加锁未同步就宕机，从库升主 → 锁"消失"，两个客户端同时持有。强互斥用 RedLock（多节点，性能代价大）或 ZooKeeper/etcd。
4. **锁粒度过大**：全局锁串行化所有请求；锁到业务 ID 级别，缩短临界区。

### 4. 优化进阶

- **分段锁**：库存分 N 段，`stock:{id}:{segment}`，锁冲突降 1/N（最终一致性对账）。
- **本地锁 + 分布式锁二级**：先 JVM 内 `ReentrantLock` 挡住单机并发，少量穿透再到 Redis，降低 Redis 压力。

### 5. 选型对比

| 实现 | 一致性 | 性能 | 复杂度 | 场景 |
|------|--------|------|--------|------|
| Redis SETNX | 最终（主从切换风险） | 高 | 低 | 大多数业务互斥 |
| RedLock | 强（多节点多数派） | 中 | 高 | 金融强互斥 |
| ZooKeeper（临时顺序节点） | 强（会话机制） | 中 | 中 | 配置/协调型锁 |
| etcd（租约） | 强 | 中 | 中 | K8s 生态 |
| 数据库唯一索引 | 强 | 低 | 低 | 低频兜底 |

## 模块五：AOF 持久化深度

### 核心原理

AOF 记录**写命令**（读命令不记），重启时顺序重放恢复数据。写入三步：命令执行完 → 追加 `server.aof_buf` → `write()` 到内核 page cache → 由 `fsync()` 时机决定落盘。**先执行后记录**两个好处：无需语法检查（记录即可执行）、不阻塞当前写命令。

### 生产落地

**appendfsync 三策略选型**：

| 策略 | 机制 | 可靠性 | 性能 | 选用 |
|------|------|--------|------|------|
| Always | 每次写入后立即 fsync | 最高 | 最低 | 金融等零丢失场景 |
| Everysec | BIO 后台线程每秒异步 fsync | 最多丢 1 秒 | 高 | **生产常用** |
| No | 永不 fsync，OS 决定 | 丢失量不定 | 最高 | 可容忍丢失的缓存场景 |

**AOF 重写**：读全量键值对，每个 key 用一条命令写新文件后替换——压缩命令数量、加速重启恢复。先写新文件再覆盖：**重写失败不污染现有 AOF**。

**后台重写 bgrewriteaof**：fork 子进程遍历数据，主进程继续服务。一致性靠 **AOF 重写缓冲区**：重写期间主进程写命令同时进 AOF 缓冲区 + 重写缓冲区；子进程完成后信号通知，主进程把重写缓冲区追加进新文件再改名覆盖。

**Redis 7.0 MP-AOF**：`manifest`（清单）+ `base`（RDB 格式全量）+ `incr`（AOF 格式增量）。重写时新命令直接进新 incr，子进程写 RDB 格式 base，完成后**原子更新 manifest**——免除管道同步与重写缓冲区，主进程压力更小。

### 踩坑规避

- **fork + COW 的两个阻塞点**：① fork 复制页表（页表越大越久）；② 写时复制物理页——重写期间修改 **bigkey** 会触发大页拷贝，阻塞主进程。规避：避免 bigkey、用 `INFO` 监控 `latest_fork_usec`、大实例用 Redis 7 MP-AOF；
- 内存紧张时无论 AOF/RDB，缓存数据都可能被淘汰（见模块六后台更新方案）；
- **AOF 恢复慢**：单线程顺序重放命令，文件越大重启越久——重写阈值要合理（默认 64M 触发、100% 增长），灾难恢复可先用 RDB 再追 AOF。

### 优化进阶

- 混合持久化（aof-use-rdb-preamble=yes，Redis 4.0+）：重写生成的 AOF 前半段用 RDB 二进制格式，恢复更快；
- 磁盘 I/O 隔离：AOF 文件放独立磁盘/分区，避免与 RDB、日志争抢 I/O；
- no-appendfsync-on-rewrite=yes：重写期间主进程不 fsync（避免重写磁盘竞争阻塞主进程），代价是重写期间丢数据窗口变大。

### 选型对比

| 维度 | RDB | AOF |
|------|-----|-----|
| 内容 | 某一时刻内存快照（二进制） | 写命令流（文本，可阅读） |
| 恢复速度 | 快（直接加载） | 慢（逐条重放） |
| 数据安全性 | 丢一个周期 | everysec 最多丢 1 秒 |
| 文件体积 | 小（压缩） | 大（重写后可控） |
| 对性能影响 | fork 阻塞（大数据集） | 写盘竞争（重写期） |
| 生产实践 | 冷备/灾难恢复 | 主力持久化（everysec + 重写） |

## 模块六：缓存异常三难题（雪崩/击穿/穿透）

### 核心原理

- **缓存雪崩**：大量 key 同时过期**或 Redis 宕机** → 请求全量打到数据库，压力骤增连锁崩溃；
- **缓存击穿**：**单个热点 key** 过期 → 高并发直击数据库（雪崩的子集）；
- **缓存穿透**：数据**既不在缓存也不在数据库** → 无法构建缓存，请求永远打到数据库。

### 生产落地

**雪崩（大量同时过期）**：① 过期时间加**随机数**打散；② **互斥锁**回源（同一 key 只允许一个请求查库重建，必须设锁超时防死锁）；③ 后台线程更新缓存（永久有效 + 定时重建），顺带实现**缓存预热**——上线前主动缓存而非等用户触发。

**雪崩（Redis 宕机）**：① 服务**熔断**（暂停缓存访问直接返回错误保数据库）+ **限流**（只放少量请求到 DB，恢复预热后解除）；② 事前构建**主从高可用集群**（事前防护优于事后熔断）。

**击穿**：互斥锁；热点 key 不设过期时间后台异步更新；过期前主动通知后台刷新。

**穿透**：① API 入口**参数校验**挡恶意请求；② **缓存空值/默认值**（短 TTL）；③ **布隆过滤器**——写库时标记，请求先判存在性，不存在直接返回，不碰 DB。

**布隆过滤器**：位图 + N 个哈希函数；标记=各位置 1；查询=全 1 才认为存在。**说"不存在"一定不存在，说"存在"可能误判**（假阳性来自哈希冲突）。

### 踩坑规避

- 互斥锁**不设超时**：持锁线程异常不释放 → 全局无响应；
- 缓存空值不设 TTL：新写入的正常数据被空值挡住；
- 后台更新方案的"淘汰窗口"：内存紧张被淘汰后到下次定时更新之间，业务读到空值——高频检测（毫秒级，体验一般）或 **MQ 通知更新**（更及时）两种补救；
- 熔断/限流是**止损不是根治**：Redis 恢复后必须**预热**再放开流量，否则恢复瞬间二次打垮 DB。

### 优化进阶

- 多级缓存（本地 Caffeine + Redis）：Redis 故障时本地缓存顶住部分流量；
- 热点 key 发现与治理：客户端统计/Proxy 层发现热 key，本地缓存 + 读写分离；
- 限流算法按业务选（令牌桶/漏桶/滑动窗口），与熔断（Sentinel/Hystrix）组成完整降级链路。

### 选型对比

| 问题 | 直接原因 | DB 有数据 | 核心方案 |
|------|----------|-----------|----------|
| 雪崩 | 大量 key 同时过期 / Redis 宕机 | 有 | 随机过期、互斥锁、后台更新、熔断限流、高可用集群 |
| 击穿 | 单个热点 key 过期 | 有 | 互斥锁、热点不过期、过期前主动刷新 |
| 穿透 | key 在缓存与 DB 均不存在 | 无 | 入口校验、缓存空值、布隆过滤器 |

## 模块七：RDB 快照与混合持久化

### 核心原理

RDB = **某一瞬间内存数据的二进制全量快照**；恢复时直接读入内存，**远快于 AOF 的命令重放**。

两个命令：`save`（主线程生成，**阻塞主线程，生产禁用**）/ `bgsave`（fork 子进程生成，不阻塞）。RDB 加载在服务启动时自动执行。自动触发配置 `save 900 1 / save 300 10 / save 60 10000`（满足任一即 bgsave）。

### 生产落地

**bgsave 与 COW**：fork 复制页表不复制物理内存，父子共享（只读）；主线程修改时触发写保护中断复制该页，子进程继续写原数据 → **快照期间主线程的修改进不了本次 RDB**，只能等下次。

- 混合持久化（Redis 4.0+，`aof-use-rdb-preamble yes`）：AOF 重写时子进程先把内存数据以 **RDB 格式**写入 AOF 文件，重写期间增量命令以 **AOF 格式**追加 → **前半 RDB 全量 + 后半 AOF 增量**；
- **生产推荐组合：AOF everysec + 混合持久化 + 定期 bgsave 冷备**。

### 踩坑规避

- **快照频率的两难**：太高 → fork + 全量写盘性能损耗；太低 → 宕机丢一个周期数据（通常 ≥5 分钟一次即最多丢 5 分钟）；
- **COW 内存翻倍**：写密集期间所有共享页都被修改 → 内存占用趋近 2 倍 → **快照期间 OOM**。写多场景预留内存余量、错峰（低峰期）触发；
- **fork 阻塞**：复制页表阻塞主线程，内存越大越久——监控 `INFO stats` 的 `latest_fork_usec`，超大实例评估；
- 别用 `save`：阻塞主线程直到 RDB 写完，大实例 = 长时间服务不可用。

### 优化进阶

- 主从全量同步同样 fork bgsave 生成 RDB 传输——fork 开销是主从切换/扩容时的延迟源，错峰执行；
- 恢复优先级设计：启动时混合 AOF 先加载 RDB 段（快）再重放 AOF 段（增量），缩短故障恢复时间；
- 云环境关注磁盘 I/O：RDB/AOF 与业务争抢 I/O 时考虑独立磁盘或降级策略。

### 选型对比

| 维度 | RDB | AOF | 混合（RDB+AOF） |
|------|-----|-----|-----------------|
| 恢复速度 | 最快（直接加载） | 慢（重放命令） | 快（RDB 段直接加载） |
| 数据丢失 | 一个快照周期（分钟级） | everysec 最多 1 秒 | 同 everysec |
| 性能影响 | fork + COW 内存翻倍风险 | 重写期写盘竞争 | 兼顾 |
| 文件体积 | 小 | 大（重写后可控） | 中 |
| 定位 | 冷备/灾恢/主从同步 | 主力持久化 | **生产推荐** |

## 模块八：主从复制与高可用

### 1. 核心原理

**读写分离**：主库读写，从库只读执行主库同步的命令。第一次同步（全量复制）三阶段：
1. **协商同步**：从库 `psync ? -1` → 主库 `FULLRESYNC <runID> <offset>`；
2. **同步数据**：主库 `bgsave` 生成 RDB（子进程不阻塞主线程）→ 从库清空旧数据载入；三个间隙期（生成/发送/加载 RDB）的写命令进 **replication buffer** 保一致；
3. **命令传播**：从库加载完回复确认，主库补发 buffer 中写命令。

**长连接命令传播**：第一次同步后维护 TCP 长连接，主库收到写命令即传播。

**增量复制（2.8+）**：断线恢复后 `psync <runID> <offset>` → `CONTINUE` → 补发断线期间命令。依赖 **repl_backlog_buffer**（环形，默认 1MB）+ **replication offset** 差值判定增量 or 全量。容量公式：`second × write_size_per_second`，建议 2 倍（`repl-backlog-size 10mb`）。

### 2. 生产落地

- **级联复制**：从库可带自己的从库（"经理"角色），分摊主库 fork() 与 RDB 传输压力；
- 监控 `INFO replication` 的 master/slave offset 差值，超阈值摘除该从库读流量；
- 主库每 10s ping 从库（`repl-ping-slave-period`）；从库每 1s `replconf ack{offset}` 上报；
- 过期 key 由主库模拟 `del` 命令同步删除，从库不自主过期。

### 3. 踩坑规避

**replication buffer vs repl_backlog_buffer**：

| 维度 | replication buffer | repl_backlog buffer |
|------|-------------------|---------------------|
| 阶段 | 全量 + 增量复制 | 仅增量复制 |
| 分配 | 每个从库连接一个 | 全局只有一个 |
| 满的行为 | 连接断开 → 重新全量复制 | 环形覆盖旧数据 |

**异步复制丢失**：主库返回 ok 后未同步即宕机。方案：`min-slaves-max-lag 10s`（从库延迟超 10s 拒写）+ 客户端降级写 Kafka/本地，恢复后回放。

**脑裂丢失**：主库网络分区仍可写，哨兵误判下线选新主；网络恢复旧主降级为从，**全量同步清空本地 → 脑裂期间写入丢失**。方案：`min-slaves-to-write 1` + `min-slaves-max-lag 12s` + `down-after-milliseconds 10s` 组合——原主卡住时无从库能 ACK，自动拒写，脑裂期不产生新数据。

### 4. 优化进阶

调大 `repl-backlog-size` 降低断线全量同步概率；监控复制延迟（`master_repl_offset - slave_repl_offset`）纳入告警；从库设为只读（`replica-read-only yes`）防误写；大从库集群用级联结构控制主库连接数。

### 5. 选型对比

主从+哨兵（高可用自动切换，哨兵选主通知应用方）vs Cluster（数据分片 + 写入扩展 + 去中心化）：数据量单机可容、只读扩展需求 → 主从+哨兵；数据量超单机内存、需要水平写扩展 → Cluster。

## 模块九：数据库与缓存一致性工程方案

### 1. 核心原理

四种更新顺序的并发分析结论：
- 「更新数据库 + 更新缓存」双向都有并发不一致窗口 → 仅适合命中率敏感场景，需分布式锁或短过期兜底；
- 「先删缓存 + 更新数据库」读+写并发时缓存被回填旧值 → 缓解手段**延迟双删**（删缓存 → 更新 DB → sleep N → 再删），睡眠时长是玄学；
- **「先更新数据库 + 再删除缓存」为生产首选**——理论仍有极小窗口（A 读旧值未写缓存时 B 删了缓存，A 才回写），但缓存写入远快于数据库写入，实际概率极低。

**为什么是删除缓存而不是更新**：删除更轻量；缓存常是多表/多系统聚合数据（商品详情关联商品/价格/库存表），更新代价极高；Lazy Loading 思想——下次命中再填充。

### 2. 生产落地

**Canal + MQ 异步删缓存**（阿里方案）：业务只更新数据库 → binlog 变更 → Canal 伪装从库订阅解析 → MQ → 消费者删缓存。**必须先删成功再 ACK**，否则提前 ACK 导致删除失败无法重试。优点：零业务代码入侵。

### 3. 踩坑规避

「更新 DB + 删缓存」第二步失败 → 缓存长期旧值（客户投诉「数据过一会才生效」）。三层防护：过期时间兜底（最终一致）→ 消息队列重试（代码入侵）→ Canal 订阅 binlog（低侵入，运维成本换一致性）。

### 4. 优化进阶

结合本地缓存（Caffeine）+ Redis 二级结构时，删缓存要同时清本地；热点 Key 删除用异步/分段删除防缓存击穿；对一致性敏感业务可加分布式锁串行化「更新 DB + 删缓存」。

### 5. 选型对比

| 方案 | 一致性 | 侵入性 | 运维成本 | 适用 |
|------|--------|--------|----------|------|
| 先更新 DB 再删缓存 + 过期兜底 | 最终一致 | 无 | 无 | 大多数场景 |
| MQ 重试删除 | 最终一致（强保障） | 高 | 低 | 删除失败不可接受 |
| Canal + MQ | 最终一致（强保障） | 无 | 高（引入组件） | 团队有运维能力 |
| 更新缓存 + 分布式锁 | 近实时一致 | 中 | 低 | 命中率极敏感 |

## 模块十：哨兵与故障转移

### 1. 核心原理

哨兵（Sentinel，2.8+）是特殊模式的 Redis 进程，负责**监控、选主、通知**：

- **主观下线**：每 1s 发 PING，超 `down-after-milliseconds` 未响应；
- **客观下线**：仅主节点适用。一个哨兵发起 `is-master-down-by-addr` 投票，赞同票达 `quorum` 即判定（多哨兵集群部署避免单点误判）；
- **Leader 选举**：候选者需同时满足「半数以上赞成票」+「≥ quorum」；每哨兵仅一票，先到先投；
- **故障转移四步**：① 选新主（过滤下线/网络差从节点 → 三轮考察：`slave-priority` 小者 → `slave_repl_offset` 最接近 master → ID 小者；发 `SLAVEOF no one`）② 所有从节点改指向新主 ③ Pub/Sub `+switch-master` 频道通知客户端 ④ 旧主回归后降为从；
- **集群自发现**：哨兵经主节点 `__sentinel__:hello` 频道互相发现；每 10s `INFO` 获取从节点列表。

### 2. 生产落地

- 哨兵至少 **3 个**（挂 1 个仍可选出 Leader）、数量奇数；**quorum = 哨兵数/2 + 1**（3 个设 2，5 个设 3）；
- quorum 不宜过小：quorum=2 而 3 个故障时能判客观下线却无法完成切换，白做功；
- 按服务器性能设 `slave-priority`（内存最大的从节点优先级最高）；
- 客户端订阅哨兵频道自动感知切换。

### 3. 踩坑规避

- 主节点压力大/网络拥塞会被误判 → 集群部署 + 合理 quorum；
- 选出网络差的从节点当新主 → 很快二次故障转移，靠断连次数过滤（阈值 `down-after-milliseconds × 10`）；
- 与脑裂防护联动：`min-slaves-to-write 1` + `min-slaves-max-lag 12s` + `down-after-milliseconds 10s`（见模块八）。

### 4. 优化进阶

哨兵自身高可用：哨兵数量 3-5 个跨机部署；监控哨兵 `INFO sentinel` 的 master flags；结合 `down-after-milliseconds` 与业务超时权衡（太灵敏误判、太迟钝恢复慢）。

### 5. 选型对比

哨兵（主从+自动故障转移，数据全量，写单点）vs Cluster（16384 槽分片、去中心化、写可扩展、客户端重定向）：数据量单机可容 + 高可用需求 → 主从+哨兵；数据量超单机 + 水平扩展 → Cluster。

## 模块十一：分布式锁工业级方案

### 1. 核心原理（从 SETNX 到工业级七层加固）

1. **原子加锁**：`SET key uuid EX 30 NX`（value 必须是全局唯一 ID）；
2. **等待**：轮询（总等待 ≈ 锁平均持有时间，如 P99 800ms → 1s）或 Pub/Sub 订阅 DEL 事件（检测与订阅需原子有序防漏通知）；
3. **重试幂等**：超时后 `GET` 判定——nil 重试 / 本 UUID 则重置 TTL / 他人 UUID 则本轮失败；
4. **过期**：P999 + buffer；主职责是防宕机死锁，正常应主动 DEL；
5. **看门狗续约**：后台线程周期（如 50s/60s）重置 TTL，预留窗口容忍单次失败；
6. **原子释放**：Lua 脚本「GET 比对 UUID 一致才 DEL」；
7. **续约失败**：保守策略——中断业务回滚（中断信号依赖业务代码在循环/步骤间检测）。

### 2. 生产落地

Redisson 已封装上述全部机制（看门狗、原子释放）；自研注意 value 唯一 ID + Lua 查删 + 续约线程优雅退出（业务结束停线程，见「续约线程检查到锁已释放则退出」）。

### 3. 踩坑规避

- SETNX 与 EXPIRE 分两步 → 间隙宕机死锁，必须原子命令；
- 释放不校验 value → 误删他人锁（GC 停顿场景经典事故）；
- 只依赖主从异步复制的高可用 → 主从未复制即宕机，两客户端同时持锁 → Redlock 或接受单点风险；
- 续约失败仍执行业务 → 排他性破坏，必须中断或接受不一致风险。

### 4. 优化进阶

**Singleflight**：同 key 加锁请求实例内只放 1 个线程竞争，其余本地等结果（竞争越激烈收益越大）；**乐观锁替代**：version 字段 UPDATE 影响行数=0 重试，全程无锁；**一致性哈希**：同 ID 请求固定路由同实例退化为单机 `ReentrantLock`。

**Redlock**（严格互斥场景）：N=5 独立主库多数派加锁（每实例 50ms 超时），有效时间 = 初始 TTL - 加锁总耗时；释放向所有实例发 Lua。**争议要点**（Martin vs antirez）：时钟跳变/GC 暂停/网络延迟使基于时间的锁无严格互斥，强一致需资源侧 fencing token。**结论：资金强一致选 ZooKeeper/etcd + fencing token；性能去重类选 Redis 锁足够**。

### 5. 选型对比

| 方案 | 一致性强度 | 性能 | 运维 | 适用 |
|------|-----------|------|------|------|
| 单实例 Redis + UUID + Lua + 看门狗 | 最终互斥（时钟依赖） | 最高 | 零 | 绝大多数去重/防重场景 |
| Redlock 5 节点 | 更强（多数派） | 中（5 次 RTT） | 高 | 不能容忍单点故障 |
| ZooKeeper/etcd + fencing token | 强一致 | 中 | 高 | 资金/库存强一致 |
| DB 乐观锁 | 最终一致 | 高 | 零 | 读-改-写短事务 |
| 一致性哈希 + 本地锁 | 强（退化单机） | 最高 | 中 | 可按 ID 路由 |

## 模块十二：大 Key 与热 Key 治理

### 1. 核心原理

**定义**：bigkey = String > 1MB 或复合类型元素 > 5000；hotkey = 访问频次显著高于其他 key。

**bigkey 对持久化的影响**：
- AOF **always**：主线程 `fsync()` 大 Key 数据量耗时 → 阻塞久；**everysec** 显著减轻（BIO 异步），但主线程 `write()` 仍耗时且上次 fsync 未完成会被强制等待；
- **fork 两阶段阻塞**：① fork 复制页表（内存大→页表大→阻塞，`latest_fork_usec` 观测，>1s 需优化）；② fork 后写共享大 Key 触发 **COW** 拷贝物理内存阻塞；
- **内存大页陷阱**：透明大页（2MB）使 COW 拷贝单位放大 512 倍 → 必须 `echo never > /sys/kernel/mm/transparent_hugepage/enabled`。

### 2. 生产落地

- bigkey 发现：`redis-cli --bigkeys -i 3`、`SCAN`+`STRLEN/HLEN/LLEN/SCARD/ZCARD`、`MEMORY USAGE`、RDB 工具分析；
- hotkey 发现：`redis-cli --hotkeys`（前提 `maxmemory-policy` 为 `allkeys-lfu`/`volatile-lfu`）、MONITOR（临时）、京东 hotkey 开源、业务预估；
- 删除大 key 用 **`UNLINK`**（4.0+ 异步）或 `SCAN`+分批 DEL，**禁用 DEL**；
- 单实例内存 < 10GB；调大 `repl-backlog-size` 防频繁全量同步触发 fork。

### 3. 踩坑规避

- 大 Hash 一次性 HGETALL → 拆分为 field 级小 key（二次哈希）；
- 热点 key 打挂 Redis → DB 雪崩：本地二级缓存（Caffeine）+ 从节点读 + Cluster 分散；
- 设计阶段不控制 → 运维阶段还债：建 key 规范（单 value 上限、复合类型元素数上限）+ 上线前扫描。

### 4. 优化进阶

UV 统计用 HyperLogLog（~12KB 固定）、状态用 Bitmap 替代大 Set；lazy-free 系列参数（`lazy-free-lazy-expire`/`lazy-free-lazy-server-del`）全开；热点 key 本地缓存 + 短 TTL（1-5s）平衡一致性与性能。

### 5. 选型对比

bigkey 拆分（根治，需改结构）vs UNLINK 缓解（治标）；本地缓存抗热点（引入一致性窗口）vs 从节点读（复制延迟）；HyperLogLog（0.81% 误差省 90%+ 内存）vs Set（精确）。
