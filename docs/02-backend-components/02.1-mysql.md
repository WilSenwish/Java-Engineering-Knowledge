## 模块一：架构与存储引擎

### 1. 核心原理

- **分层架构**：连接层（连接处理/鉴权）→ 服务层（解析器/优化器/缓存）→ 存储引擎层（InnoDB/MyISAM，插件式，**引擎层才真正操作文件**）。
- **InnoDB vs MyISAM**：

| 维度 | InnoDB | MyISAM |
|------|--------|--------|
| 事务 | 支持（ACID） | 不支持 |
| 行锁/表锁 | 行锁 + MVCC | 表锁 |
| 外键 | 支持 | 不支持 |
| 崩溃恢复 | redo/undo | 无 |
| 聚簇索引 | 有（数据即索引） | 无（索引与数据分离） |
| count(*) | 遍历统计 | 内置计数器直接返回 |
| 场景 | **绝大多数业务** | 只读/历史归档 |

- **Buffer Pool**：InnoDB 以 16KB 页为单位缓存数据页/索引页/undo/自适应哈希；`innodb_buffer_pool_size` 建议物理内存 50%~75%（专用 DB 服务器）。

### 2. 生产落地

- **连接池参数（HikariCP）**：`maximumPoolSize` 按 `(CPU核数 × 2) + 有效磁盘数` 起步压测标定；`connectionTimeout=3000`、`maxLifetime < MySQL `wait_timeout``（1800s）、`connectionTestQuery=SELECT 1` 或 `keepalive`。
- **字符集**：统一 `utf8mb4`（真 UTF-8，4 字节；`utf8` 是 MySQL 的 3 字节阉割版，emoji 存不下）+ 排序规则 `utf8mb4_general_ci`（或 `0900_ai_ci` 区分大小写需求场景评估）。
- **基础规范**：所有表 InnoDB、主键 `bigint`（雪花/发号器）、`NOT NULL` + 默认值、每表必备 `create_time`/`update_time`。

```sql
-- 生产建表示范（规范落地）
CREATE TABLE `t_order` (
  `id` bigint unsigned NOT NULL COMMENT '雪花ID',
  `user_id` bigint unsigned NOT NULL COMMENT '用户ID',
  `amount` decimal(18,2) NOT NULL COMMENT '金额(分→元, 禁止float)',
  `status` tinyint NOT NULL DEFAULT '0' COMMENT '状态: 0待付 1已付 2取消',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_user_create` (`user_id`, `create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单表';
```

### 3. 踩坑规避

1. **隐式类型转换导致索引失效**：`WHERE phone = 13800000000`（int 列与 string 比，MySQL 8 前）/ `WHERE varchar_col = 123` → 全表扫描。**保证查询条件类型与列类型一致**。
2. **前导模糊查询**：`LIKE '%abc'` 无法用 B+树索引；`LIKE 'abc%'` 可用。海量文本搜索上 Elasticsearch。
3. **函数/运算包裹索引列**：`WHERE DATE(create_time)='2026-10-18'` 索引失效 → 改范围查询 `create_time >= '2026-10-18' AND create_time < '2026-10-19'`。
4. **深分页**：`LIMIT 100000, 10` 要扫描 100010 行丢前 10 万行。优化：延迟关联（子查询先查 ID）+ 游标（`WHERE id < last_max_id LIMIT 10`）。
5. **大事务**：一次事务操作几万行 → undo 膨胀、锁持有久、主从延迟。拆批（每批 500~1000 行，批间休眠）。
6. **`utf8mb4` 索引长度超限**：单列索引 191 字符（3072 字节限制）；超长字段用前缀索引或 Hash 列。

### 4. 优化进阶

- **覆盖索引**：查询列全部在索引中 → 不回表（Extra 出现 `Using index`）。高频查询按此设计联合索引。
- **索引下推（ICP，MySQL 5.6+）**：`WHERE age > 18 AND name = 'x%'`，联合索引 `(name, age)` 在引擎层先过滤 age 再回表。
- **MRR + Batched Key Access**：离散 IO 转顺序 IO，适合范围扫描多的场景。
- **执行计划必读字段**：`type`（至少 range，杜绝 ALL）、`key`（实际用的索引）、`rows`（扫描行数）、`Extra`（Using filesort/temporary 是大坑）。

### 5. 选型对比

| 方案 | 适用 | 注意 |
|------|------|------|
| 单库单表 | 数据量 < 500 万行、QPS < 2000 | 先别急着分库分表 |
| 读写分离 | 读远大于写 | 主从延迟导致"写完读不到"（读主库兜底） |
| 分库分表（ShardingSphere） | 单表 > 千万级 | 分片键选择 > 技术实现；跨片 JOIN/分页/ID 全局唯一 |
| NewSQL（TiDB/OceanBase） | 海量 + 强一致 + 弹性 | 运维成本、生态成熟度评估 |

## 模块二：索引原理与优化

### 1. 核心原理

- **B+树（InnoDB）**：非叶子节点只存 key（一页存更多索引 → 树高 3~4 层即可支撑千万级）；叶子节点双向链表（范围查询高效）。**树高决定 IO 次数**，3 层 B+树 ≈ 3 次磁盘 IO。
- **聚簇索引 vs 二级索引**：聚簇索引叶子 = 整行数据（按主键组织）；二级索引叶子 = 主键值 → 回表查聚簇。`SELECT *` 走二级索引要回表，**覆盖索引免回表**。
- **联合索引最左前缀**：`(a, b, c)` 可用于 `a`、`a,b`、`a,b,c`；跳过多列失效；`a=1 AND c=3` 只用 a。范围列之后的列无法用于索引定位（但可参与 ICP 过滤）。
- **索引下推**：见模块一。
- **Hash 索引**：Memory 引擎/自适应哈希（InnoDB 内部），等值查询 O(1) 但不支持范围/排序。

### 2. 生产落地

- **索引设计三问**（建索引前）：① 有没有 SQL 支撑（`EXPLAIN`）② 区分度高不高（`COUNT(DISTINCT col)/COUNT(*)` > 0.3 才值得）③ 是否冗余（`(a,b)` 与 `(a,b,c)` 只需后者）。
- **EXPLAIN 实战**：关注 `type`（const > eq_ref > ref > range > index > ALL）、`Extra`。

```sql
EXPLAIN SELECT id, user_id FROM t_order
WHERE user_id = 123 AND create_time >= '2026-10-01';
-- 期望: type=ref/range, key=idx_user_create, Extra=Using index(覆盖索引)
```

### 3. 踩坑规避

- **索引不是越多越好**：每个索引 = 一棵 B+树，写放大 + 优化器选错索引（`ANALYZE TABLE` 刷新统计信息，或 `FORCE INDEX` 干预）。
- **隐式转换 + 排序规则不一致**：JOIN 两表字符集/排序规则不同（`utf8mb4_general_ci` vs `utf8mb4_0900_ai_ci`）→ 索引失效。
- **`OR` 导致索引失效**：`a=1 OR b=2` 若 b 无索引 → 全表；改 `UNION ALL` 分别走索引。
- **`IN` 列表过长**：优化器可能改走全表；超 1000 项分批或用临时表 JOIN。

### 4. 优化进阶

- **慢查询治理闭环**：`slow_query_log=ON` + `long_query_time=1` + `pt-query-digest` 聚合 → 按 `总耗时`（不是次数）排序治理 → `EXPLAIN` 验证 → 线上对比 RT。
- **Count 优化**：`COUNT(*)` InnoDB 也要扫（无 MyISAM 计数器）；近似值用 `SHOW TABLE STATUS` / `EXPLAIN` 的 rows；精确值走缓存或汇总表。
- **Online DDL**：`ALTER TABLE ... ALGORITHM=INPLACE, LOCK=NONE`（MySQL 5.6+ 支持大部分 DDL 不锁表），大表变更用 `pt-online-schema-change`/`gh-ost`。

### 5. 选型对比

| 索引类型 | 等值 | 范围 | 排序 | 场景 |
|---------|------|------|------|------|
| B+树（默认） | ✅ | ✅ | ✅ | 通用 |
| Hash | ✅ 最快 | ❌ | ❌ | 精确查找缓存表 |
| 全文索引 | — | — | — | 已被 ES 替代 |
| 前缀索引 | ✅ | 部分 | ❌ | 超长字符串降开销 |
| 覆盖索引 | ✅ 免回表 | ✅ | ✅ | 高频查询目标形态 |

## 模块三：事务、MVCC 与锁

### 1. 核心原理

- **ACID**：原子性（undo log）、一致性（目标）、隔离性（锁 + MVCC）、持久性（redo log，WAL：先写日志再写页）。
- **隔离级别与问题**：读未提交（脏读）< 读已提交（RC，不可重复读）< 可重复读（RR，幻读）< 串行化。MySQL 默认 **RR**（PG/SQLServer 默认 RC）。
- **MVCC（快照读）**：每行隐藏字段（`trx_id` 最近修改事务 + `roll_pointer` undo 链）；ReadView 判定可见版本 → **读写不互斥**，RR 下普通 SELECT 走快照读无锁。
- **锁体系**：记录锁（行）、间隙锁（GAP，RR 下防幻读）、临键锁（Next-Key = 记录+间隙，默认加锁单位）、意向锁（表级标记，加速行锁兼容判断）。
- **当前读**：`SELECT ... FOR UPDATE`/`LOCK IN SHARE MODE`、`UPDATE`/`DELETE`/`INSERT` 读最新版本并加锁。

### 2. 生产落地

- **事务边界**：`@Transactional` 只加在**写方法**上（查询方法开事务纯属浪费连接）；`rollbackFor = Exception.class`（默认只回滚 RuntimeException/Error）；事务内**禁止 RPC/IO 等待**（长事务占连接）。
- **RR 下防幻读手段**：间隙锁（默认）+ 唯一索引冲突检查；业务幂等（唯一索引/状态机）双保险。
- **乐观锁**：`UPDATE t SET stock = stock - 1, version = version + 1 WHERE id = 1 AND version = 5`，失败重试（适合低竞争）；悲观锁 `SELECT ... FOR UPDATE` 适合高竞争短事务。

```java
// 事务规范示例
@Transactional(rollbackFor = Exception.class, timeout = 3)
public void createOrder(OrderCreateCmd cmd) {
    // 1. 本地计算
    Order order = OrderAssembler.toDO(cmd);
    // 2. DB 写（无 RPC）
    orderMapper.insert(order);
    // 3. 事务消息表/outbox（保证最终一致）
    outboxMapper.insert(OutboxEvent.of("ORDER_CREATED", order.getId()));
}
```

### 3. 踩坑规避

| 现象 | 根因 | 对策 |
|------|------|------|
| `@Transactional` 不生效 | 自调用（同类内 `this.method()` 不走代理）/ 非 public / final / 抛了检查异常未配 rollbackFor | 拆分类/注入自身代理；配 `rollbackFor` |
| 事务回滚了但日志显示成功 | 方法内 try-catch 吞掉异常 | 异常必须抛出或在 catch 里手动 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()` |
| 锁等待超时 `Lock wait timeout exceeded` | 死锁/长事务持锁 | `innodb_lock_wait_timeout=10`；缩短事务；固定加锁顺序 |
| 主从数据不一致 | 主从延迟 + 强制走从库 | 关键读走主库；`sec-msr` 半同步复制；读己之写策略 |

### 4. 优化进阶

- **大事务拆分**：批量 insert 拆批 + 批间提交；定时任务扫全表改状态 → 分批（`LIMIT 1000` 循环 + 主键推进）。
- **死锁预防**：多行更新按主键升序；避免先读后写之间隔太久；`innodb_deadlock_detect=OFF`（超高并发写场景，靠超时重试）。
- **隔离级别降级**：纯读接口把连接切 RC（减少间隙锁）——金融强一致场景除外。

### 5. 选型对比

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能 | 场景 |
|---------|------|-----------|------|------|------|
| RU | 可能 | 可能 | 可能 | 最高 | 几乎不用 |
| RC | 无 | 可能 | 可能 | 高 | 互联网默认（多数框架）/只读 |
| RR | 无 | 无 | InnoDB 基本无 | 中 | **MySQL 默认，金融核心** |
| Serializable | 无 | 无 | 无 | 低 | 强一致账务 |

## 模块四：性能优化与生产规范

### 1. 核心原理

- **SQL 执行链**：客户端 → 解析器（语法树）→ 优化器（基于成本的执行计划 CBO，统计信息驱动）→ 执行器 → 引擎。
- **慢 SQL 根因分布**（生产经验）：索引缺失/失效（~60%）、深分页/大结果集（~15%）、大事务/锁竞争（~10%）、SQL 写法（隐式转换、函数包裹、`SELECT *`）（~15%）。

### 2. 生产落地

- **表设计规范**：单表 < 1000 万行预估；冷热分离（归档表）；`text/blob` 拆附表（主表瘦身）。
- **字段规范**：`decimal` 存金额；`tinyint` 存状态；IP 存 `int unsigned`（`INET_ATON`）或 `varchar(39)`（IPv6）；时间用 `datetime`（带时区语义则 UTC + 应用层转换）。
- **备份与高可用**：xtrabackup 物理备份 + binlog 增量；主从（一主一从半同步）+ MHA/Orchestrator 故障切换；**定期恢复演练**（备份不可用等于没有）。

### 3. 踩坑规避

- **`SELECT *`**：回表数据量放大 + 无法覆盖索引 + 字段变更引发兼容问题。按需取列。
- **`UPDATE ... WHERE` 无索引**：行锁升级表锁（RR 下全表间隙锁），阻塞全库写入。
- **自增 ID 暴露**：爬虫遍历 + 业务量泄露；用雪花 ID 或号段。
- **`NULL` 参与索引**：可索引但语义模糊（"未设置" vs "空"）；显式 `NOT NULL DEFAULT` 更优。

### 4. 优化进阶

- **读写分离 + 缓存层级**：Cache-Aside（先读缓存→未命中读库→回填）规避脏读（删缓存而非更新缓存）。
- **批量写入**：`INSERT ... VALUES (...),(...)` 多值 / `LOAD DATA` / 批量 executor（`rewriteBatchedStatements=true`）。
- **分区表**：范围分区按时间归档（`PARTITION BY RANGE`），DROP 旧分区瞬间回收空间；注意分区键必须含在主键/唯一索引中。

### 5. 选型对比

| 优化手段 | 生效点 | 成本 | 优先级 |
|---------|--------|------|--------|
| SQL + 索引优化 | 单条 SQL | 低 | ⭐⭐⭐ 先做 |
| 连接池/慢日志治理 | 连接与观测 | 低 | ⭐⭐⭐ 常开 |
| 缓存 | 读路径 | 中（一致性成本） | ⭐⭐ 读热点 |
| 读写分离 | 架构 | 中（延迟） | ⭐⭐ 读扩散 |
| 分库分表 | 架构 | 高 | ⭐ 最后手段 |
| NewSQL | 架构 | 运维成本 | 特定场景 |

## 模块五：索引深度补充（图解来源）

> 加工来源：sources/xiaolincoding/mysql/index-interview.md，补全模块二未覆盖的工程细节。

### 1. 核心原理（增量知识点）

- **索引四维分类**：数据结构（B+Tree/Hash/Full-text）× 物理存储（聚簇/二级）× 字段特性（主键/唯一/普通/前缀）× 字段个数（单列/联合）；
- **范围查询的精确匹配规则**（面试高频）：联合索引最左匹配遇到 **`>`、`<` 停止匹配**（其后字段无序）；但 **`>=`、`<=`、`BETWEEN`、`LIKE 'j%'` 前缀匹配不停止**——因为边界值处后续字段仍有序（`a>=1` 被优化器拆成 `a=1`（ab 有序）+ `a>1`（b 无序）两段）；
- **key_len 判定法**：执行计划 key_len = 用于形成扫描区间的字段字节数之和。int 非 NULL 每字段 4 字节（可 NULL +1）；`varchar(30)` utf8mb4 = 30×4+2 = 122（变长字段统一按 2 字节计）。**key_len=4 只有 a 走索引，key_len=8 则 a+b 都走**；
- **区分度 ≠ 排最前**：区分度是参考因素，但**随机 UUID 作主键 → 页分裂 + 二级索引膨胀**；排序/过滤需求与最左前缀复用优先于纯区分度；
- **索引列 NOT NULL**：NULL 使索引统计/比较更复杂（count 省略 NULL 行）+ 行格式至少 1 字节存 NULL 列表。

### 2. 生产落地

- **建索引前三问**：① 有没有 SQL 支撑（EXPLAIN 验证）② 区分度（`COUNT(DISTINCT col)/COUNT(*)`，性别这类低区分度字段单列索引基本无用——优化器发现占比高直接忽略索引走全表）③ 是否冗余（`(a,b)` 与 `(a,b,c)` 只建后者）；
- **排序优化**：`where status=1 order by create_time` → 建 `(status, create_time)` 联合索引，利用索引有序性**免 filesort**；
- **主键设计**：自增主键（追加写无页分裂）+ 主键尽量短（二级索引叶子存主键值）；UUID 作业务唯一键另建二级索引。

### 3. 踩坑规避

1. **误以为"用了联合索引=所有字段都走了索引"**：`where a>1 and b=2` 只 a 走索引定位，b 仅过滤（不回表前不生效）——看 key_len 确认；
2. **前缀索引局限**：`order by` 不能用前缀索引、不能作覆盖索引；
3. **OR 一侧无索引**：`a=1 OR b=2`（b 无索引）→ 索引失效，改 `UNION ALL`；
4. **`BETWEEN` 边界语义**：MySQL 含两端值（`>= and <=`），有的数据库不含——跨库移植 SQL 时注意。

### 4. 优化进阶

- **索引下推（ICP）判据**：EXPLAIN Extra 出现 `Using index condition` → 5.6+ 在索引遍历时先过滤再回表；
- **自增 vs 非自增主键量化差异**：自增 = 顺序追加（页满开新页）；随机主键 = 插入页中 → 页分裂（数据移动 + 碎片 + 空间利用率降）；
- **大表加索引**：`ALGORITHM=INPLACE, LOCK=NONE`（5.6+）或 `pt-osc`/`gh-ost`，避免锁表。

### 5. 选型对比（type 访问方式，效率递增）

| type | 含义 | 生产态度 |
|------|------|----------|
| ALL | 全表扫描 | **必须消灭**（小表除外） |
| index | 全索引扫描 | 避免 |
| range | 索引范围（< > in between） | **底线** |
| ref | 非唯一索引 | 良好 |
| eq_ref | 唯一索引（多表 JOIN） | 优秀 |
| const | 主键/唯一索引 = 常量 | 最优 |

Extra 判据：`Using filesort`/`Using temporary` = 必须优化；`Using index` = 覆盖索引，优。

## 模块六：事务隔离与 MVCC 深度

### 核心原理

四大特性实现分工：**原子性 → undo log；持久性 → redo log；隔离性 → MVCC 或锁；一致性 → 前三者共同保证**。

MVCC 两个构件：
- **Read View（读视图）**：m_ids（活跃事务列表，不含创建者自身）、min_trx_id（m_ids 最小值）、max_trx_id（**全局事务 id 计数器当前值，不是 m_ids 最大值**）、creator_trx_id；
- **聚簇索引隐藏列**：trx_id（最近修改的事务 id）+ roll_pointer（指向 undo log 旧版本，串成**版本链**）。

可见性判定三规则：① `trx_id < min_trx_id` → 创建前已提交 → 可见；② `trx_id >= max_trx_id` → 创建后才启动 → 不可见；③ 区间内看 m_ids：在 → 创建时仍活跃 → 不可见，不在 → 已提交 → 可见。沿 roll_pointer 向下找第一个可见版本。

### 生产落地

**RC 与 RR 的唯一本质区别：Read View 创建时机**——RC 每次读都重新生成；RR 事务启动时生成一次、全程复用。这就是不可重复读的成因与解法。

事务启动时机陷阱：`begin/start transaction` 之后**第一条 select 才是事务真正启动**；`start transaction with consistent snapshot` 才立即启动。

源码对应（MySQL 8.0 `ReadView::changes_visible()`）：`m_up_limit_id`=概念上的 min_trx_id（低水位），`m_low_limit_id`=概念上的 max_trx_id（高水位）——**命名与数值大小直觉相反**；m_ids 有序，判定用 `std::binary_search` **O(log N)**，这是 MVCC 支撑高并发的关键。

### 踩坑规避

- **RR 不是彻底无幻读**：普通 select 靠 MVCC 快照读规避；`select ... for update` 当前读靠 **next-key lock**（记录锁+间隙锁）规避；仍有边界场景，不要迷信；
- 不要为了解决幻读升到**串行化**：读写全加锁，并发性能雪崩，易锁等待/死锁；
- 大事务持有 Read View 过久 → 版本链越拉越长，undo 无法清理（purge 受阻），查询遍历版本链变慢；
- RC 下"两次读不一致"是正常语义，业务代码里**先查后改**的校验逻辑要放事务内或改用当前读/乐观锁。

### 优化进阶

- 长事务监控：`information_schema.innodb_trx` 查 `trx_started`；
- 降低 RR 下版本链扫描成本：控制事务时长、避免大事务；
- 快照读不加锁是 RR 高并发的根基——**能用普通 select 就别用 for update**；
- 需要"读到最新已提交"语义（如库存校验）→ 当前读 + 行锁，或乐观锁版本号。

### 选型对比

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能 | 选用建议 |
|----------|------|-----------|------|------|----------|
| 读未提交 | √ | √ | √ | 最高 | 生产禁用 |
| 读提交（RC） | × | √ | √ | 高 | 互联网默认（阿里改造）；主从/ Binlog 场景友好 |
| 可重复读（RR，InnoDB 默认） | × | × | 很大程度上避免 | 中 | 金融、账务等强一致场景 |
| 串行化 | × | × | × | 最低 | 几乎不用 |

## 模块七：索引失效案例集与 SQL 编写规约

### 核心原理

B+ 树索引按索引值**有序存储**，一切失效场景的本质：**查询条件无法利用有序性定位**，或**比较对象不是索引原始值**。

### 生产落地（六大失效场景速查）

| 场景 | 示例 | 根因 | 规避 |
|------|------|------|------|
| 左/右模糊 | `name like '%林'` | 无法定位前缀起点 | `'林%'`；或全文索引/ES |
| 索引用函数 | `length(name)=6` | 索引存原始值 | 改写；或函数索引（8.0+）`add key idx ((length(name)))` |
| 索引表达式 | `id + 1 = 10` | 同上 | 移到等值另一边 `id = 10 - 1` |
| **隐式类型转换** | `phone = 1300000001`（phone varchar） | 字符串↔数字比较时 MySQL **把字符串转数字** → 等于对索引列 CAST | 参数类型与列类型严格一致 |
| 联合索引非最左 | `(a,b,c)` 上 `where b=2` | 排序仅从最左列开始 | 按最左前缀设计查询 |
| OR 跨非索引列 | `id=1 or age=18` | 单边索引无意义 | 全建索引走 index_merge 或改 UNION |

**团队规约建议**：① 字符串字段查询必须传字符串参数（Java 侧防 int 透传）；② LIKE 一律前缀匹配；③ 联合索引按查询频次与选择性设计最左序列；④ Code Review 检查索引列上的函数与运算。

### 踩坑规避

- 隐式类型转换**方向性陷阱**：字符串列 vs 数字参数 → 失效；整型列 vs 字符串参数 → 不走失效（CAST 作用于参数）。别记反；
- `where a=1 and c=3` 在联合索引 `(a,b,c)` 上是索引截断：5.6+ 靠 **ICP 索引下推**在引擎层过滤 c（`Using index condition`），减少回表——但依然建议补全 b；
- explain 判读：`type=ALL` 全表、`range` 索引范围、`index` 全索引扫描（比 ALL 好但仍是全扫）、`Extra` 出现 `Using index` 才是覆盖索引。

### 优化进阶

- 覆盖索引设计：查询字段全部在索引内 → 不回表（`select id, name from t where name='林%'`）；
- 函数索引（MySQL 8.0+）兜底历史遗留 SQL：`alter table t add key idx_len ((length(name)))`；
- 慢查询日志 + pt-query-digest 定期复盘，把新 SQL 的失效场景消灭在测试环境。

### 选型对比

| 方案 | 适用 | 代价 |
|------|------|------|
| 改写 SQL | 首选，零成本 | 需开发配合 |
| 调整/新增索引 | 高频查询 | 写放大 + 空间 |
| 函数索引（8.0+） | 无法改写的函数条件 | 维护成本 |
| 全文索引/ES | 模糊搜索场景 | 架构复杂度 |

## 模块八：锁体系与死锁治理

### 核心原理

按范围分三级：**全局锁**（`flush tables with read lock` 全库只读）/ **表级锁**（表锁、MDL、意向锁、AUTO-INC 锁）/ **行级锁**（Record Lock 记录锁、Gap Lock 间隙锁、Next-Key Lock 临键锁、插入意向锁）。

关键认知：
- **普通 select 是快照读不加锁**；`lock in share mode`（S 锁）/ `for update`（X 锁）才是锁定读，且**必须在事务中**；
- 意向锁（IS/IX）只为**快速判断表里是否有行被锁**，避免加表锁遍历全表；
- **间隙锁之间互相兼容**（都是防插入）；插入意向锁与区间上的间隙锁互斥；
- MDL：CRUD 自动加读锁，DDL 加写锁，**事务提交才释放**；MDL 写锁等待会阻塞后续所有 CRUD（写优先级高于读）。

### 生产落地

- 全库备份：`mysqldump --single-transaction`（RR + MVCC，业务不阻塞）替代全局锁；MyISAM 只能全局锁；
- **AUTO-INC 锁**：`innodb_autoinc_lock_mode=2`（申请即释放）性能最高，但 **必须搭配 `binlog_format=row`**——statement 格式下主库并发分配 id 不连续、从库顺序执行连续 → 主从不一致；
- 防幻读组合：RR 下快照读靠 MVCC，当前读靠 next-key lock（关联模块六）。

### 踩坑规避

- **MDL 长事务 + DDL 事故链**：长事务持 MDL 读锁 → DDL 等写锁 → 后续 CRUD 全堵 → 连接池打满。DDL 前必查 `information_schema.innodb_trx` 长事务，设 `lock_wait_timeout`（默认 31536000s！必须调小，如 10~50s）；
- **update 无索引锁全表**：UPDATE/DELETE 的 where 无索引 → 行锁退化为**锁全表**（每条记录都加 Gap/Next-Key），必现批量阻塞；
- 大事务长持锁：事务内做 RPC、大循环 → 持锁时间拉长，连锁阻塞。事务只包数据库操作；
- 死锁处置：`SHOW ENGINE INNODB STATUS` 看 LATEST DETECTED DEADLOCK；`innodb_lock_wait_timeout`（默认 50s）是兜底不是方案。

### 优化进阶

- 死锁预防四原则：① 相同顺序访问表与行；② 事务拆小、持锁时间最短化；③ 范围条件精确化（缩小 Gap 范围）；④ 高并发更新行分散（热点行拆分为多行求和）；
- 热点行更新：库存扣减用单行原子 `UPDATE stock SET n = n - 1 WHERE n >= 1`（利用行锁天然串行），避免应用层查改；
- 锁监控：`SHOW STATUS LIKE 'Innodb_row_lock%'` 关注 `Innodb_row_lock_waits`/`time_avg`。

### 选型对比

| 需求 | 方案 | 说明 |
|------|------|------|
| 一致性读不加锁 | MVCC 快照读 | 普通 select |
| 读到并锁住 | for update / lock in share mode | 事务内 |
| 并发扣减 | 单行原子 UPDATE | 行锁串行化 |
| 跨库互斥 | Redis/ZK 分布式锁 | 关联 [02.2 模块四](../02-backend-components/02.2-redis.md) |

## 模块九：三大日志与两阶段提交

### 核心原理

| 日志 | 层级 | 内容 | 保证 |
|------|------|------|------|
| **redo log** | InnoDB | 物理日志（页+偏移+修改），**循环写** | 持久性（crash-safe） |
| **undo log** | InnoDB | 修改前数据，版本链 | 原子性 + MVCC |
| **binlog** | Server 层 | 逻辑/行记录，**追加写全量** | 备份 + 主从复制 |

- **WAL**：先写 redo log 更新即完成，脏页后台刷盘；顺序写远快于随机写——redo log 的本质收益；
- redo log 文件组循环写：write pos 与 checkpoint 之间可写；**write pos 追上 checkpoint → 所有更新阻塞**，强制刷脏页推进 checkpoint。

### 生产落地

**双 1 配置**（安全基线）：`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`——每事务 2 次 fsync。

| 参数 | 值 | 行为 | 风险 |
|------|----|------|------|
| innodb_flush_log_at_trx_commit | 1（默认） | 提交即 fsync | 性能最低 |
| | 2 | write 到 OS page cache | OS 崩丢数据 |
| | 0 | 每秒后台刷 | MySQL 进程崩丢 1 秒 |
| sync_binlog | 1 | 每次提交 fsync | 最安全 |
| | N（100~1000） | 攒 N 个事务 fsync | 掉电丢 N 个事务 binlog |

**binlog 格式**：`row`（推荐，无动态函数问题）；statement 有 `now()/uuid()` 主从不一致风险；mixed 自动选择。

**组提交**（性能优化）：commit 阶段拆 flush（多事务一起 write）/ sync（合并 fsync）/ commit（顺序提交）三阶段队列化；调优参数 `binlog_group_commit_sync_delay` / `binlog_group_commit_no_delay_count`；MySQL 5.7+ redo log 也支持组提交。

### 踩坑规避

- **两阶段提交不可砍**：redo log 与 binlog 各自刷盘，任一先写后崩溃 → 两份日志不一致 → **主从数据不一致**。2PC 流程：redo log 置 prepare 刷盘 → binlog 写 XID 刷盘 → redo log 置 commit（**binlog 写盘成功 = 事务成功标志**）；
- 崩溃恢复判定：重启扫描 redo log，遇 prepare 拿 XID 查 binlog——**有则提交，无则回滚**；
- redo log 可能在提交前被后台线程刷盘（没事，binlog 未写重启照样回滚）；**binlog 必须提交后才刷盘**；
- **误删数据恢复只能用 binlog**（redo log 循环写已覆盖）：全量备份 + binlog 增量恢复是标准灾备流程；
- 从库不是越多越好（主库 log dump 线程消耗 + 带宽），一般 1 主 2~3 从；复制延迟敏感场景用半同步（5.7+，任一从库 ACK 即返回）。

### 优化进阶

- 大事务是日志系统公敌：redo log buffer 打满、binlog cache 溢出、组提交效果差、MDL 持锁久——**大事务必须拆**；
- 磁盘 I/O 高时的调优优先级：组提交参数 → sync_binlog=N → flush_log_at_trx_commit=2（安全性递减，业务认可再动）；
- 灾备组合拳：每日全量（XtraBackup/RDB 式）+ binlog 增量 + 定期恢复演练（**不演练的备份等于没有备份**）。

### 选型对比

| 场景 | redo log | binlog |
|------|----------|--------|
| 崩溃恢复（已提交不丢） | ✅ 唯一手段 | ❌（仅归档） |
| 误删数据恢复 | ❌（循环覆盖） | ✅ 全量保留 |
| 主从复制 | ❌ | ✅ 唯一载体 |
| 写入方式 | 循环写 | 追加写 |

## 模块十：Buffer Pool 深度（缓存引擎内核）

### 1. 核心原理

InnoDB 以 **16KB 页**为磁盘与内存交互单位，Buffer Pool 启动时申请连续内存（默认 128MB，生产设为物理内存 60%~80%）。除索引页/数据页外还缓存 undo 页、插入缓存、自适应哈希、锁信息。每个缓存页配**控制块**（表空间、页号、地址、链表节点），置于池前部，之间可能有碎片。

**三链表管理**：Free 链表（空闲页）、Flush 链表（脏页，后台遍历刷盘）、LRU 链表（脏页+干净页）。脏页同时在 LRU 和 Flush 两链表，刷盘后变干净页。

### 2. 生产落地

- `innodb_buffer_pool_size` = 物理内存 60-80%；
- 读路径：索引定位到页 → 整页加载进 Buffer Pool → 页目录定位记录；
- 写路径：改 Buffer Pool 页 → 标脏 → 后台线程刷盘；WAL 保证崩溃恢复。

### 3. 踩坑规避

**简单 LRU 的两个坑**：
- **预读失效**：预读的相邻页永不被访问却占 LRU 前排，淘汰热页；
- **Buffer Pool 污染**：`like "%x%"` 全表扫描（即使结果集几条）把大量一次访问页涌入 young 区，热数据全灭 → 大量磁盘 IO → 性能急剧下降。

**InnoDB 的三重解法**：
1. **young/old 分区**（`innodb_old_blocks_pct` 默认 37，young:old=63:37）：新页只进 old 头部，真正被访问才进 young → 预读页快速淘汰不污染；
2. **时间门槛**（`innodb_old_blocks_time` 默认 1000ms）：只有「被访问」且「old 区停留超 1 秒」才进 young → 挡掉批量扫描；
3. young 区前 1/4 被访问不移动，减少链表调整。

**脏页刷盘抖动**：慢 SQL 监控中**偶尔**出现的长 SQL 可能是刷脏导致；频繁出现 → 调大 Buffer Pool 或 redo log。刷盘触发：redo log 满 / 淘汰脏页 / 空闲期定期 / 正常关闭前。

### 4. 优化进阶

多实例 Buffer Pool（`innodb_buffer_pool_instances`）减少锁竞争；监控 `Innodb_buffer_pool_read_requests` 与 `Innodb_buffer_pool_reads`（物理读）比值评估命中率；`SHOW ENGINE INNODB STATUS` 看 Free/LRU 链表长度判断容量压力。

### 5. 选型对比

Buffer Pool vs 查询缓存（MySQL 8.0 已移除 Query Cache）：Buffer Pool 是页级通用缓存且随数据自动失效，Query Cache 粒度太粗、任何表更新即全失效、大并发下互斥锁成为瓶颈——生产只依赖 Buffer Pool。

## 模块十一 · SQL 执行全链路（Server 层解剖）

> 加工来源：小林coding《执行一条 select 语句，期间发生了什么？》（sources/xiaolincoding/mysql/sql-execution-flow.md）

### 1. 核心原理

一条 select 的完整链路（8 步，Server 层 + 存储引擎层两层架构）：

```text
客户端 → 连接器 → 查询缓存(8.0已删) → 解析器(词法/语法→语法树) → 预处理器(表/字段存在性检查)
      → 优化器(基于成本选执行计划) → 执行器(与存储引擎按记录交互) → InnoDB(Buffer Pool/B+树/磁盘)
```

- **连接器**：TCP 握手 + 鉴权 + **读取权限快照**（连接中途改权限不影响已存连接）；`wait_timeout` 默认 8 小时回收空闲连接，`max_connections` 默认 151；
- **查询缓存**：key-value 形式，**任何表更新即全表缓存失效**，鸡肋，MySQL 8.0 直接删除（注意删的是 Server 层 Query Cache，不是 InnoDB Buffer Pool）；
- **解析器**：只做词法 + 语法分析构建语法树；**表/字段存在性不在解析器**（源码验证：8.0 在 prepare 阶段 `get_table_share()` 报错）；
- **预处理器**：检查表/字段存在、`select *` 展开为全部列；
- **优化器**：基于成本选索引（覆盖索引优先，避免回表）；
- **执行器**：`read_first_record` / `read_record` 双函数指针模型，以记录为单位与存储引擎交互。

### 2. 生产落地

- **长连接必须治理内存**：连接对象临时内存只在断开时释放，长连接累积会撑爆 MySQL 被 OOM kill。两种解法：① 定期断开长连接；② 执行大操作后调 `mysql_reset_connection()`（不重连、免鉴权、恢复到初始状态）；
- **索引下推（ICP，5.6+）**：联合索引 `(age, reward)` 遇范围查询 `age > 20` 后 reward 无法走索引，ICP 把 `reward = 100000` 的过滤**下推到存储引擎**，先在二级索引层过滤再回表，执行计划 Extra 出现 `Using index condition`；
- **连接数规划**：高并发服务按 `max_connections` + 连接池（Druid/HikariCP）双限流，避免 Too many connections。

### 3. 踩坑规避

- 权限修改不生效？—— 已建立连接用的是**连接建立时读取的权限快照**，需重连；
- 「表不存在报错在解析器」是过时结论（《MySQL 45 讲》旧版说法），**实际在 prepare 阶段**；
- 短连接风暴：每次执行 SQL 都走三次握手/四次挥手，高并发下把 MySQL 连接器打满，必须用连接池；
- 全表扫描时 Server 层**逐条**发给客户端，客户端只是等查询结束后统一显示——不要误以为有批量发送。

### 4. 优化进阶

**覆盖索引判定**：`select id from product where id > 1 and name like 'i%'` 两索引可选时，优化器选二级索引 name（覆盖索引，叶子即主键值，免回表），执行计划 `key=name` + `Extra=Using index`。

**执行器双指针模型**（源码级）：第一次查 `read_first_record`（按访问类型 const/index/all 绑定不同引擎接口），循环查 `read_record`；const 类型第二次即返回 -1 退出循环。理解该模型即可看懂 explain 的 type 字段本质。

### 5. 选型对比

| 阶段 | MySQL 8.0 行为 | 生产含义 |
|------|----------------|----------|
| 查询缓存 | 已删除 | 缓存一律用 Redis，不依赖 MySQL 层 |
| 解析/预处理 | 拆分为两阶段 | 报错定位看错误码阶段（1064 语法 vs 1146 表不存在）|
| 优化器 | 基于成本 CBO | explain 看 type/key/rows/Extra 四核心字段 |
| 执行器 | 双函数指针 | type=const > ref > range > index > ALL 性能阶梯 |
