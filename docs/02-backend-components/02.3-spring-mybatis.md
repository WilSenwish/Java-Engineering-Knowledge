## 模块一：Spring IoC 容器

### 核心原理

IoC 是**思想**而非技术：对象创建与管理权从类内 `new` 反转交给容器。Bean 声明：类上 `@Component`/`@Repository`/`@Service`/`@Controller`（类路径扫描），方法上 `@Bean`（可写复杂逻辑，**第三方库类只能这样注册**）。

三层框架关系：**Spring**（底层，Core/IoC）→ **Spring MVC**（Web 模块，天生集成）→ **Spring Boot**（简化配置，MVC 开发仍基于 Spring MVC）。

### 生产落地

- **注入方式官方推荐构造器注入**：依赖完整性（创建时即注入，避免 NPE）、不可变性（线程安全）、测试便利（无需容器传 mock）；Setter 注入留给可选依赖；
- `@Autowired` 先 byType 再 byName（多实现配 `@Qualifier`）；`@Resource` 先 byName 再 byType——按名注入语义更清晰、减少 Spring 强耦合；
- 单例 Bean 无状态化是并发安全根基（Dao/Service 天然无状态）；有状态单例用 ThreadLocal 或锁（关联 [01.3 模块六](../01-java-core/01.3-concurrency.md)）；
- Bean 生命周期四阶段：**实例化 → 属性赋值 → 初始化（Aware → postProcessBefore → afterPropertiesSet/init-method → postProcessAfter，AOP 代理在此生成）→ 销毁**。

### 踩坑规避

- 字段注入（@Autowired 直接加在字段上）导致**依赖不直观、无法 final、测试需起容器**——统一改构造器注入；
- 循环依赖：Spring Boot **2.6 起默认禁止**。仅部分单例的 Setter/字段注入可解；**构造器注入、原型 Bean 的循环依赖三级缓存也救不了**——只能在设计上拆；
- `@Bean` 方法在同类内调用不会走代理（自注入失效）——事务/缓存注解自调用不生效，经典坑；
- 循环依赖应急方案 `spring.main.allow-circular-references=true` 只是掩盖设计问题，别当常规手段。

### 优化进阶

- 启动加速：`@Lazy` 延迟非首屏 Bean、排除无效自动配置、Spring Boot 3 GraalVM 原生镜像；
- 作用域收敛：Web 层用 request 作用域 Bean 时注意代理方式（JDK 代理要求接口）；
- Bean 定义去重：`spring.main.allow-bean-definition-overriding=false`（默认已禁）防止意外覆盖。

### 选型对比

| 对比项 | @Component（类扫描） | @Bean（方法定义） |
|--------|---------------------|-------------------|
| 目标 | 类 | 方法 |
| 第三方库类 | ❌ 无法使用 | ✅ 唯一方式 |
| 逻辑复杂度 | 简单注册 | 可写条件逻辑 |
| 适用 | 业务自有类 | 中间件配置类、条件化 Bean |

## 模块二：Spring AOP 与动态代理

### 核心原理

AOP 把横切逻辑（事务、日志、权限、缓存）抽成切面，降低重复与耦合。Spring AOP 基于**动态代理**：目标实现接口 → **JDK Proxy**；未实现接口 → **CGLIB**（生成子类）。

术语链：JoinPoint（所有可拦截方法）→ Pointcut（实际拦截的连接点）→ Advice（增强逻辑）→ Aspect（Pointcut+Advice）→ Weaving（织入生成代理）。

### 生产落地

- 通知类型：Before / After / AfterReturning / AfterThrowing / **Around**（唯一能控制目标方法是否执行、修改返回值的）；
- 多切面顺序：`@Order`（**值越小优先级越高**）或 `Ordered` 接口——事务切面要包在最外层（order 最小）；
- 典型切面落位：`@Transactional`（事务）、`@Cacheable`（缓存）、日志脱敏、接口幂等、权限校验；
- 切面方法签名纪律：`ProceedingJoinPoint.proceed()` 的返回值必须原样返回（Around 吞返回值是隐蔽 bug）。

### 踩坑规避

- **同类内自调用不走代理**（AOP 失效第一因）：注入自身代理（`AopContext.currentProxy()`）或拆分类；
- **private/final/static 方法无法增强**：Spring AOP 仅方法级、不支持 final/static；
- 代理对象只走 Spring 容器：`new` 出来的对象没有任何增强；
- CGLIB 代理对象**无法被强转为原类型以外**，注意 `instanceof` 判断；
- 切面内异常处理不当：Around 中 try-catch 后不 rethrow 会**吞掉目标方法异常**，事务回滚失效。

### 优化进阶

- 需要增强 final/字段/构造器或零代理开销 → **AspectJ**（编译期/类加载期织入）；
- 切入点表达式精确化（`execution` 限定包名+类名+方法名），避免过宽匹配拖慢全应用；
- 大量切面场景评估代理链深度，必要时用 AspectJ 或手工装饰器替代。

### 选型对比

| 特性 | Spring AOP | AspectJ |
|------|-----------|---------|
| 织入时机 | 运行时代理 | 编译期/类加载期 |
| 切入点 | 仅 Spring Bean 方法级 | 方法/字段/构造器/静态方法 |
| final/static | ❌ | ✅ |
| 性能 | 有代理开销 | 运行时无代理开销 |
| 复杂度 | 低，开箱即用 | 高 |
| 选用 | 90% 业务场景 | 特殊增强/高性能要求 |

## 模块三：Spring 事务

### 核心原理

`@Transactional` 本质是 AOP：开启事务 → 执行业务 → 提交/回滚。传播行为控制事务边界（默认 **REQUIRED**：有则加入，无则新建）。

### 生产落地

| 传播行为 | 语义 | 生产场景 |
|----------|------|----------|
| REQUIRED（默认） | 有则加入，无则新建 | 绝大多数业务方法 |
| REQUIRES_NEW | 挂起当前事务建新事务 | 操作日志独立提交（主业务回滚日志不丢） |
| NESTED | 嵌套事务（savepoint） | 部分失败需部分回滚 |
| NOT_SUPPORTED | 非事务运行，挂起当前 | 大批量查询不占事务连接 |

**回滚规则**：默认仅 RuntimeException/Error 回滚，**Checked Exception 不回滚**——业务异常统一用 RuntimeException，或显式 `rollbackFor = Exception.class`。

### 踩坑规避

- **自调用失效**（同类方法互调不走代理）→ 事务不生效第一坑；
- **吞异常不回滚**：catch 后不 rethrow，代理层看不到异常 → 提交了本应回滚的数据；
- 数据库引擎必须 InnoDB（MyISAM 无事务）；
- REQUIRES_NEW 与主事务**嵌套提交**：子事务提交后主事务才回滚，数据不一致——设计时明确补偿；
- 事务内做**远程调用/耗时 IO**：长事务占连接池 + 锁，拖垮 DB（关联 [02.1 模块六](../02-backend-components/02.1-mysql.md) 长事务危害）；
- `@Transactional` 加在 private 方法上静默无效。

### 优化进阶

- 编程式事务（TransactionTemplate）用于复杂分支/循环事务控制；
- 事务传播 + 业务分层规范：Controller 不开事务，Service 方法开事务，Mapper 不加事务；
- 大事务拆分：能拆尽拆，只把必须一致的DB操作圈进事务；非DB操作移出。

### 选型对比

| 方式 | 控制力 | 侵入性 | 适用 |
|------|--------|--------|------|
| 声明式（@Transactional） | 中 | 低 | 标准 CRUD 业务 |
| 编程式（TransactionTemplate） | 高 | 中 | 复杂事务边界/动态决策 |

## 模块四：Spring MVC 与统一异常

### 核心原理

链路：DispatcherServlet → HandlerMapping 匹配 → HandlerAdapter 执行 → ModelAndView → ViewResolver 解析 → 渲染 → 响应。**前后端分离后返回 JSON（@RestController），ViewResolver 不再使用**。

### 生产落地

- 统一响应体：`ApiResponse<T>`（code/message/data）贯穿全部接口；
- 统一异常：`@ControllerAdvice` + `@ExceptionHandler`——原理**不是 AOP 代理**，而是 Spring MVC 的 `HandlerExceptionResolver` 处理链，按匹配深度取最匹配方法；
- 分层异常体系：业务异常（BizException，带错误码）/ 系统异常 / 参数校验异常（MethodArgumentNotValidException），全局异常处理器统一转 ApiResponse。

### 踩坑规避

- `@ExceptionHandler` 方法签名错误（返回值/参数不合法）导致静默不生效；
- 异常处理链中被更宽泛的 handler 先拦截——**异常类按精确程度排序注册**；
- 拦截器（HandlerInterceptor）与过滤器（Filter）职责混淆：Filter 管编解码/安全，Interceptor 管登录态/日志；
- 404/405/参数错误等 Spring MVC 内置异常也要在 `@ControllerAdvice` 覆盖（`ErrorController` 或 `ResponseEntityExceptionHandler`）。

### 优化进阶

- `ResponseEntityExceptionHandler` 统一处理 Spring MVC 内置异常；
- 参数校验：JSR-303（@Valid/@Validated）+ 分组校验，全局处理器转业务错误码；
- 大对象响应：`@JsonInclude`、字段脱敏（Jackson 自定义序列化器，比在 Service 逐个 set 更不易漏）。

## 模块五：MyBatis 执行链路与参数安全

### 核心原理

半自动 ORM：封装 JDBC 样板代码，SQL 与映射控制权留给开发者。启动期解析注册 `MappedStatement`/`ResultMap`/`SqlSource`；运行期：Mapper 代理 → BoundSql → Executor（先查一级缓存）→ StatementHandler + ParameterHandler → JDBC → ResultSetHandler 映射。

### 生产落地

- **`#{}` 必须，`${}` 白名单**：`#{}` 生成 JDBC 占位符防注入；`${}` 文本替换仅可用于服务端预定义的列名/排序方向（ORDER BY 动态字段用 Java 层映射白名单，**永远不要直接透传请求参数**）；
- 驼峰映射 `mapUnderscoreToCamelCase=true`，复杂 Join 用 `resultMap` 显式映射（重名列必须别名）；
- 动态 SQL：`<if>/<choose>/<where>/<set>/<foreach>/<bind>`，底层 SqlNode 组合 + OGNL 求值；
- 批量操作：`<foreach>` 批量插入 + `rewriteBatchedStatements=true`（JDBC 层批量）。

### 踩坑规避

- `${}` 拼接 = SQL 注入漏洞（OWASP Top 级）；
- `selectOne()` 查多条抛 `TooManyResultsException`，不会取第一条——唯一性靠唯一约束保证，别用 LIMIT 1 掩盖脏数据；
- **一级缓存在 Spring 无事务时不生效**：每次 Mapper 调用后 SqlSession 关闭，同一 Service 方法两次调用不共享缓存——别把它当性能手段；
- 二级缓存生产慎用：namespace 粒度、跨 Mapper 改同表互不感知、多实例不同步、外部 SQL 修改无法感知——**跨实例共享一律走 Redis**（关联 [02.2 模块六](../02-backend-components/02.2-redis.md)）；
- 延迟加载的 N+1：访问集合属性触发 N 次查询，DTO 返回场景在 Service 一次查齐。

### 优化进阶

- 插件（JDK 动态代理包裹四大组件）：分页插件、SQL 审计、数据权限——注意多插件同时改写 SQL 的组合测试，插件代码必须轻量；
- 大结果集：流式查询（`ResultHandler`）/ 游标，避免一次加载全量入内存；
- SQL 调优闭环：开启 SQL 日志（带最终参数）→ 慢 SQL 收集 → EXPLAIN 分析（关联 [02.1 模块二](../02-backend-components/02.1-mysql.md) 索引体系）。

### 选型对比

| 对比项 | MyBatis | JPA/Hibernate |
|--------|---------|---------------|
| SQL 控制 | 开发者手写，可精确优化 | 框架生成，难精细控制 |
| 开发效率 | 映射/SQL 代码多 | 常规 CRUD 快 |
| 适用 | 复杂查询、报表、SQL 优化密集 | 领域模型稳定、CRUD 为主 |
| 主要风险 | SQL 分散、映射错误、拼接注入 | N+1、抓取过大 |

## 模块六：Spring Boot 自动配置原理

### 1. 核心原理

**入口注解三件套**：`@SpringBootApplication` = `@SpringBootConfiguration`（本质 `@Configuration`）+ `@EnableAutoConfiguration`（核心）+ `@ComponentScan`。

**加载链**：`@EnableAutoConfiguration` 通过 `@Import(AutoConfigurationImportSelector.class)` 导入配置类选择器（`DeferredImportSelector`，延迟到用户配置类解析后执行，保证用户 Bean 优先）；选择器从 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`（2.7+）读取全部候选自动配置类，逐个经 `@Conditional` 体系判定后生效。

**配置文件格式演变**：spring.factories（≤2.6）→ AutoConfiguration.imports（2.7+，3.0 移除前者）。动机是云原生——spring.factories 运行时扫描对 GraalVM 原生镜像不友好；imports 支持编译期（APT）确定配置类，启动 3-5s→0.1-0.5s、内存 200-500MB→50-100MB。

### 2. 生产落地

**条件注解速查**：

```java
@ConditionalOnClass(RedisOperations.class)      // 类路径有才生效（starter 存在的意义）
@ConditionalOnMissingBean(DataSource.class)     // 容器没有才生效（用户覆盖的钩子）
@ConditionalOnProperty(prefix = "spring.redis", name = "enabled", havingValue = "true", matchIfMissing = true)
@ConditionalOnWebApplication(type = Type.SERVLET)
```

**覆盖自动配置的标准姿势**：自定义同类型 `@Bean`（如自己的 Druid 数据源）——自动配置类的 `@ConditionalOnMissingBean` 检测到即退场，无需 exclude。

**排除自动配置**：`@SpringBootApplication(exclude = XxxAutoConfiguration.class)` 或 `spring.autoconfigure.exclude`（yml）。

**调试三板斧**：`debug: true` 启动打印 Positive/Negative matches 报告；`/actuator/conditions` 端点看条件评估；IDE 直接搜 `AutoConfiguration.imports` 文件。

### 3. 踩坑规避

- **starter 依赖传递黑洞**：引入一个 web starter 带来十几个传递依赖，类路径"意外"满足某自动配置条件而生效——用 actuator conditions 报告核对每个生效配置是否预期内；
- **@ConditionalOnBean 的顺序陷阱**：同类自动配置内部 Bean 定义顺序影响条件评估，官方大量用 `@AutoConfigureBefore/After/Order` 显式排序——自定义 starter 必须标注顺序；
- **@ConditionalOnClass 的类缺失静默失败**：条件类不在类路径时配置类整体跳过，症状是"Bean 没注入"而非报错——先查 import 文件与依赖；
- **配置属性绑不上**：忘加 `@EnableConfigurationProperties(XxxProperties.class)` 或类缺 setter——yml 值静默丢失。

### 4. 优化进阶

**自定义 starter 标准结构**：`XxxAutoConfiguration`（@AutoConfiguration + 条件注解 + @EnableConfigurationProperties）+ `XxxProperties`（`spring.xxx` 前缀元数据）+ `AutoConfiguration.imports` 注册 + `spring-configuration-metadata.json`（IDE 提示）。大厂内部中间件（监控、动态线程池、RPC）均以此形态交付，业务方零配置接入。

**原生镜像适配**：Spring Boot 3.x + GraalVM 时确保自动配置全部走 imports 路径，避免自研 starter 仍在用 spring.factories。

### 5. 选型对比

| 配置方式 | 适用 | 风险 |
|----------|------|------|
| 自动配置（imports + 条件注解） | 约定优于默认场景 | 条件误判需 conditions 报告核对 |
| @Bean 显式配置 | 需要精细控制 | 样板代码多 |
| 混合（自动 + 覆盖） | **生产主流** | 覆盖点需文档化 |
