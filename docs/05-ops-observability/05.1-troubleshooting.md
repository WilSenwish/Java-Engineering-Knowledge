## 模块一 · 线上问题排查方法论与 SOP

### 1. 核心原理

**反直觉第一原则**：不要被监控最显眼的曲线带着走——CPU 高抓线程栈、Full GC 查堆、发布后回滚都是「现象驱动」。**故障是跨层传导的**：慢 SQL 占连接 → 业务线程阻塞连接池 → 线程池队列堆积 → 上游超时重试 → CPU/延迟/错误率齐升。根因只有一个，先变化的指标才是入口。

**排查三步框架**：

```text
① 确认影响面：用户侧异常？单实例 vs 全服务？排除监控误报/采集延迟/下游传导
② 止血 vs 留证：故障扩大先按预案止损；留证要抓「时间线」而不是单点快照
③ 按现象选入口：用 现象→检查项 速查表定位，再沿引用链/耗时对账验证
```

**留证清单**（重启/回滚前）：告警前后监控时间范围、应用/访问/GC 日志、**1~3 份间隔数秒的线程栈**（单份会错过真相）、Trace 慢调用、进程 CPU/RSS/堆/线程数/fd/连接、DB 慢查询/锁等待、Redis 慢命令、MQ 积压。

### 2. 生产落地

**提前埋好的防线**（故障后补不开的）：

```bash
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/path/with/enough/space
-XX:NativeMemoryTracking=summary     # NMT 必须启动时开，故障后补无效
-Xlog:gc*:file=gc.log:time,uptime     # JDK9+ 统一 GC 日志
```

**监控口径对齐**：容器环境 `top`/`vmstat` 看的是宿主机口径，`/sys/fs/cgroup` 看容器限额——CPU 高不高先确认观察口径，再看 cgroup 限流是否触发。

**线程栈抓取规范**：`top -H` 的 tid 是十进制，线程栈 `nid` 是十六进制，先 `printf '%x\n' <tid>` 转换再对照；连续抓 3 份间隔 5s，**同一代码位置多次出现才是热点**。

### 3. 踩坑规避

| 坑 | 后果 | 正确做法 |
|----|------|----------|
| 带流量实例直接 Heap Dump | 转储阻塞 + 磁盘打满，故障扩大 | 先摘流量，或依赖 OOM 自动转储 |
| `jmap -dump:live` 当无风险命令 | 触发 Full GC | 生产慎用，评估堆大小/磁盘/停顿 |
| CPU 打满时并行多个诊断 | 诊断本身抢占资源 | 一次一个，选异常实例取证 |
| 线上 `KEYS *` / 高峰期 `--bigkeys` | Redis 阻塞 | 低峰期/从节点/受控采样 |
| 只抓一份线程栈 | 采样巧合误判 | 连续多份对照 |
| 重启即「恢复」不留证 | 现场丢失，无法复盘 | 先留证再重启（除非止损优先） |
| 测试库验证通过即上线 | 执行计划随数据分布变化 | 生产参数 + 接近生产数据分布验证 |

### 4. 优化进阶

**耗时对账思想**：一次慢请求的总耗时必须能和各阶段（连接池等待/DNS/TCP/TLS/服务端处理/响应读取）对上——对不上的「空白段」就是监控盲区，补埋点比猜更有价值。Trace 只记业务方法耗时时，连接池等待和线程池排队是两大常见黑洞。

**修复验证标准**：对比故障前/中/后同一组指标（请求量、P95/P99、错误率、业务成功率、CPU、内存、GC、线程池、连接池、依赖延迟）；涉及资金/库存/订单的补数据对账；性能改动要在相近数据量、流量模型、机器配置、缓存状态下比较——**单接口单次压测不代表链路恢复**。

### 5. 选型对比

| 工具 | 类型 | 用途 | 生产注意 |
|------|------|------|----------|
| `top`/`pidstat` | 命令行 | 进程/线程 CPU、I/O | 确认容器 vs 宿主机口径 |
| `vmstat`/`iostat` | 命令行 | 运行队列/内存/磁盘 | 结合趋势看 |
| `jcmd` | 命令行 | 线程栈/堆信息/JFR/类直方图 | 部分命令开销高 |
| `jstat` | 命令行 | GC 与内存区变化 | 连续采样 |
| JFR/JMC | 事件记录 | CPU/分配/锁/I/O 事件 | 低开销持续采集，**生产首选** |
| Arthas | 运行时诊断 | 方法耗时/watch/trace | 高流量方法限制范围 |
| MAT/VisualVM | 离线分析 | Heap Dump | 看引用链与 GC Roots |
| Prometheus + Grafana | 指标监控 | 全指标时序 + 看板 | 采集口径统一 |
| SkyWalking/Pinpoint | APM | 链路追踪 | 采样率与开销权衡 |

## 模块二 · JDK 命令行工具矩阵

### 1. 核心原理

| 工具 | 全称 | 一句话用途 |
|------|------|-----------|
| `jps` | JVM Process Status | 列 Java 进程（主类 + LVMID） |
| `jstat` | JVM Statistics Monitoring | 类/内存/GC/JIT 运行数据 |
| `jinfo` | Configuration Info | 查看/动态调整 JVM 参数 |
| `jmap` | Memory Map | 堆转储 dump |
| `jstack` | Stack Trace | 线程快照 |
| `jcmd` | 诊断命令接口 | Thread.print/GC.heap_info/VM.native_memory/JFR（**现代首选，整合多工具**） |

**关键细节**：`jps -l/-v/-m/-q` 分别输出主类全名/JVM 参数/main 参数/仅 LVMID；`jstat -gcutil <pid> 1000 10` 每秒采样 10 次看 GC；`kill -3`（SIGQUIT）得的是**线程转储不是堆转储**；`jhat` 在 JDK9 已移除（JEP 241），堆分析用 MAT/VisualVM。

### 2. 生产落地

- **jcmd 优先**：`jcmd <pid> Thread.print`（线程栈）、`jcmd <pid> GC.heap_info`（堆概况）、`jcmd <pid> VM.native_memory summary`（本地内存）、`jcmd <pid> JFR.start`（低开销采集）；
- **jinfo 调参边界**：仅「可管理」参数支持运行时修改，改完 `VM.flags` 确认；
- **JMX 远程（JConsole）**：`-Dcom.sun.management.jmxremote.port=60001`，生产**必须开认证 + SSL + 网络访问控制**（示例中关闭认证的配置仅限隔离测试环境）。

### 3. 踩坑规避

- `jstat -gcpermcapacity` 在 JDK8 后不存在——永久代→元空间，用 `-gcmetacapacity`；
- GC 日志参数 JDK8 (`-XX:+PrintGCDetails`) 与 JDK9+ (`-Xlog:gc*`) 不通用，`jinfo -flag PrintGC` 对 JDK9+ 无效，用 `jcmd VM.log`；
- Major GC / Full GC 术语各资料用法不一——读日志结合具体收集器和事件判断，不要拿固定倍数和 Minor GC 比停顿。

### 4. 优化进阶

**工具链组合拳**：JFR 常开低开销采集（分配/锁/IO 事件）→ 告警触发时 `jcmd Thread.print` 抓现场 → MAT 离线分析 dump → Arthas 对生产问题热诊断（`trace`/`watch` 限流）。**命令行的价值是现场还在，可视化工具的价值是看得全**。

### 5. 选型对比

| 场景 | 首选 | 备选 |
|------|------|------|
| 快速看进程/GC | jps/jstat/jcmd | JConsole |
| 线程死锁/停顿 | jcmd Thread.print（多次）| jstack |
| OOM 根因 | MAT 分析 dump | VisualVM |
| 持续性能画像 | JFR + JMC | Arthas trace |
| 远程监控 | JMX（认证+SSL）| Prometheus exporter |
