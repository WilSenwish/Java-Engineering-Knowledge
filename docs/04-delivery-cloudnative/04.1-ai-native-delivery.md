## 模块一 · Coding Agent 工程化能力栈

### 1. 核心原理

**从「用 AI 写代码」到「工程化用 AI」**：Coding Agent 的价值不取决于模型多强，而取决于**给它搭的工作环境（Harness）**——上下文怎么供、工具怎么给、规则怎么约束、结果怎么验证。

**六件设施**（Claude Code / Codex 同构）：

| 设施 | 作用 | 本质 |
|------|------|------|
| 项目记忆（`CLAUDE.md` / `AGENTS.md`） | 跨会话的项目上下文锚点 | 声明式规则文件（架构/规约/常用命令/禁区） |
| Skills | 按需加载的领域知识 | 带触发条件的 Markdown 指令集 |
| Subagents | 子 Agent 隔离上下文 | 独立窗口干专责（检索/评审/测试），结果回传 |
| MCP | 外部工具/数据协议 | 统一工具接口（DB/浏览器/内部系统） |
| Hooks | 生命周期自动化 | 工具调用前后自动执行（格式化/lint/测试） |
| Plugins | 能力分发 | 团队规约与工具链打包共享 |

**源码级设计决策**（面试区分度，来自图解 Claude Code 源码解析）：

- **代码检索用 grep 而非 RAG**：精确匹配 + 结果可解释；RAG 有召回不确定性，不适合「差一行就错」的代码定位；
- **记忆用文件而非向量数据库**：可审查、可 diff、可版本化——记忆是规则不是检索；
- **Skill 按需加载**：元数据（何时用）→ 全文（怎么用）两级，避免全量塞上下文；
- **上下文压缩（Compact）**：长会话超限时摘要压缩，关键决策必须外置到记忆文件防丢。

### 2. 生产落地

**落地顺序**（按依赖排序，别跳步）：

```text
① 项目记忆 → ② Hooks 自动检查 → ③ Skills 团队知识 → ④ MCP 工具扩展 → ⑤ Subagents 并行
```

- **CLAUDE.md 内容清单**：项目是什么 / 技术栈与版本 / 目录结构与职责 / 构建测试命令 / 编码规约（命名/异常/日志）/ 明确禁区（不许改的目录/不许用的 API）；
- **SDD（规约驱动开发）**：先写规约（需求 + 验收标准）再让 AI 编码——把「AI 理解需求」的不确定性前置消灭；
- **AI 原生研发流六阶段**：需求 → 规约 → 编码 → 验证 → 评审 → 上线，Agent 参与每个环节但人类把关准入/准出；
- **老项目改造**：先让 Agent 产出「现状报告」（架构/调用链/风险点）→ 再定改造顺序 → 小步可回滚。

### 3. 踩坑规避

| 坑 | 后果 | 对策 |
|----|------|------|
| 无 CLAUDE.md 直接上 Agent | 每次会话重新猜项目背景，产出漂移 | 先写记忆文件，哪怕只 20 行 |
| 全量 Skill 进上下文 | 窗口浪费、注意力稀释 | 元数据触发 + 按需加载 |
| 危险命令无拦截 | Agent 执行 rm -rf / 删库 | Hooks + 命令白名单 + 人工确认 |
| 长会话靠压缩接力 | 关键决策在摘要中失真 | 决策写入记忆文件，压缩只省过程 |
| 文档与代码漂移 | 文档误导后续会话 | 文档同步纳入验收 Checklist |

### 4. 优化进阶

**Anthropic 40 万次会话研究的核心结论**：用好 AI 编程的关键不是「会写代码」，而是**会问问题、会审结果、会定标准**——专家经验（判断力）比编码速度更值钱。对应工程实践：把资深工程师的审查标准沉淀为 Hooks/Skills，让 Agent 在循环中自动执行。

**提示词趋势**：从「长篇 prompt 教模型做事」转向「结构化上下文 + 短指令」——上下文工程（Context Engineering）取代提示词工程，模型越强，越不需要冗长指令。

### 5. 选型对比

| 维度 | Claude Code | Codex |
|------|-------------|-------|
| 运行形态 | 终端 Agent | CLI / 云端沙箱 |
| 项目记忆 | CLAUDE.md | AGENTS.md |
| 上下文策略 | grep 检索 + Compact | 上下文管理 + 会话恢复 |
| 强项 | 代码库深度检索、长任务 | 沙箱隔离、批量任务、CI 集成 |
| 适用 | 复杂重构/深度开发 | 批量任务/流水线 |

## 模块二 · 中间件工程化交付范式（oneThread 案例）

### 1. 核心原理

**从业务开发思维脱离**：框架/中间件开发的核心是「对使用者隐藏复杂度，对运维者暴露可控性」。oneThread 的分层即范式：core（领域内核）+ starter（接入层，按配置中心可插拔）+ spring-base（框架集成）+ dashboard（展示层）。

### 2. 生产落地

- **Starter 化交付**：Spring Boot Starter 自动装配 + `spring.factories`/`AutoConfiguration.imports` 注册 + 条件装配（`@ConditionalOnClass`）——使用者一个依赖接入，零配置可用；
- **配置中心驱动**：Nacos/Apollo 监听 + 模板方法复用刷新逻辑——参数即运维界面；
- **可观测三件套**：Prometheus 指标（队列深度/活跃线程/拒绝次数）+ Grafana 看板 + 钉钉告警（阈值 + 持续时间窗口防风暴）。

### 3. 踩坑规避

- 动态改 `corePoolSize` 有 JDK 并发边界问题——先减后加或加锁；
- 队列容量动态改要保证 `remainingCapacity` 一致性；
- 告警不加持续时间窗口 → 抖动告警风暴。

### 4. 优化进阶

**自愈闭环**：告警 → 自动扩容（K8s HPA 或动态调大 maximumPoolSize）→ 事后复盘——监控的终点是自动化响应，不是人肉救火。

### 5. 选型对比

| 交付形态 | 接入成本 | 可控性 | 适用 |
|----------|----------|--------|------|
| 裸 JDK 线程池 | 零 | 无（改参要重启） | 参数稳定的内部任务 |
| Spring TaskExecutor | 低 | 弱 | 简单异步 |
| **Starter 化动态线程池** | 低（一个依赖） | **强（热更+监控+告警）** | 生产业务线程池 |
| 虚拟线程（JDK21） | 中 | 需新监控工具 | 高并发 IO 新范式 |
