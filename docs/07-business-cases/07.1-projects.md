### 2. 生产落地（学习路径建议）

1. **第一阶段（基础巩固）**：oneThread → 掌握线程池工程化 + 可观测，直接反哺日常工作；

### 3. 踩坑规避（通用）

- **Demo 玩具化**：只调 API 不算做过 RAG/Agent/秒杀——面试追问永远在：数据一致性、异常路径、压测数据、故障演练；

- **忽视工程化**：上线 Checklist、回滚、监控是项目完整度的重要组成。

### 4. 优化进阶

- **二刷策略**：第一遍跟做功能；第二遍专攻"生产级改造"（加监控/压测/容错/文档）；
- **简历映射**：每个项目提炼 3 个可量化成果（QPS、P99、成本降幅）+ 2 个深度技术决策。

## 模块二：Ragent AI — 企业级 Agentic RAG 深度案例

### 1. 核心原理

- **定位**：从 0 到 1 纯手工打造企业级 Agentic RAG，拒绝 Demo 玩具。开源：`github.com/nageoffer/ragent`。
- **v1 vs v2 双架构（核心设计决策）**：
  - **v1 Workflow 编排**：路径写死（检索→重排→生成），更快、更可控、成本低 → 问答类场景；
  - **v2 Agentic 架构**：ReAct 循环，路径由模型自主决定，可规划、可调用工具 → 复杂任务场景；
  - **两套并存按场景路由**，是"可控性与智能性权衡"的教科书实践。
- **七模块架构**：`infra-ai`（模型客户端/档位/路由/首包探测/降级）、`system`（认证审计）、`rag`（问答/知识库/入库 Pipeline/意图树/检索/会话）、`agent`（AgentScope ReAct 引擎 + MCP 工具 + 技能 + 记忆 + 人工确认）、`bootstrap`、`framework`（统一响应/幂等/分布式 ID/MQ/SSE/跨节点流式取消）、`mcp-server`。

### 2. 生产落地

- **混合检索链路**：向量 + 关键词 + 知识图谱 + 联网搜索**并行召回** → 去重 → **RRF 融合** → **Rerank** 精排；按召回数/Rerank/TopK 分层控制，**单通道失败不影响主链**。
- **问题理解层**：查询词映射（同义词/领域词典）→ 问题重写与拆分（多问题拆分）→ **树形意图识别**（注册表模式）→ 多知识库路由。
- **流量保护（Redis）**：ZSET 公平排队 + Lua 原子抢占 + 过期信号量 + Pub/Sub 唤醒——模型调用是昂贵资源，必须限并发。
- **模型容错**：多候选模型自动切换；首包超时/空响应/异常三级触发降级；**三态熔断**。
- **可观测**：Trace Run/Node 级耗时与输入输出；**Langfuse** 追踪推理、工具调用、Token 消耗。
- **流式体验**：SSE 分事件输出（思考/正文/来源/推荐问题），全局超时 + 客户端断开取消（跨节点）。
- **数据一致性**：RocketMQ 事务消息保障分块可靠执行 + 幂等；远程刷新 = 分布式锁 + 状态机。

### 3. 踩坑规避

1. **检索单点故障拖垮主链** → 多通道并行 + 单通道隔离降级；
2. **模型首包慢导致用户体验差** → 首包探测 + 超时切换候选模型；
3. **流式输出跨节点无法取消** → 框架层统一管理 SSE 生命周期（Pub/Sub 广播取消信号）；
4. **知识库更新期间的脏读** → 远程刷新加分布式锁 + 状态机（刷新中/完成/失败）；
5. **会话 Token 成本失控** → 最近 N 轮 + 持久化摘要 + 上下文压缩。

### 4. 优化进阶

- **设计模式实战地图**（每个模式对应具体问题，面试可展开）：
  策略（检索通道/结果后处理）、工厂（意图树/分块策略）、模板方法（并行检索/模型请求）、注册表（意图节点）、装饰器（向量写入同步关键词和图谱索引）、责任链（检索后处理/模型故障降级）、中间件（Agent 记忆注入/上下文压缩）、适配器（多模型方言/MQ 客户端）、状态机（远程文档定时刷新）、事件回调（SSE）、AOP（Trace/幂等/审计）。
- **四大常见误区（面试考点）**：① 调 API ≠ 会 RAG/Agent；② RAG ≠ 检索+生成（每环都有坑）；③ 接框架/MCP ≠ 企业级（增量更新/多租户/风控/可观测）；④ 只关注模型忽略工程（检索策略/分块/上下文管理决定效果）。

### 5. 选型对比

| 维度 | v1 Workflow | v2 Agentic |
|------|-------------|------------|
| 路径 | 人写死 | 模型自主 |
| 延迟/成本 | 低 | 高（多轮推理） |
| 可控性 | 高 | 中 |
| 能力上限 | 中 | 高（可规划/用工具） |
| 适用 | 标准问答 | 复杂任务 |
| **生产结论** | **按场景路由，二者并存** | 同左 |

## 模块三：oneThread — 动态可观测线程池框架

> 加工来源：nageoffer《oneThread动态线程池》（sources/nageoffer/onethread.md）。星球专属不开源，公开介绍页含架构与配置全貌。

### 1. 核心原理

- **定位**：基于配置中心的动态可观测 Java 线程池框架；作者前作 Hippo4j（3.8k+ Star）。技术栈：Spring Boot + JUC + Nacos/Apollo + Prometheus/Grafana；纯 Java 代码 4.99k 行。
- **解决的两大生产痛点**（美团 2020 经典问题）：
  1. **任务执行拒绝**：核心数设置偏小 → 大量 `RejectedExecutionException` 触发降级；
  2. **任务执行时间过长**：队列过长 → 最大线程数失效 → 任务堆积 → 下游超时。
- **根因**：JDK 线程池参数**运行期不可调**，只能重启；缺乏监控，问题暴露时已酿成故障。
- **项目结构**（「核心 + 接入 + 展示」三层）：`core`（动态线程池内核）/ `starter`（Nacos、Apollo、Tomcat 适配、dashboard 可插拔组件）/ `spring-base`（扫描/开关/Banner）/ `example` / `dashboard-dev`（可视化控制台：线程池列表、参数编辑、Grafana 监控页）。

### 2. 生产落地

```yaml
onethread:
  executors:
    - thread-pool-id: onethread-producer
      core-pool-size: 12
      maximum-pool-size: 18
      queue-capacity: 2000
      work-queue: ResizableCapacityLinkedBlockingQueue
      rejected-handler: CallerRunsPolicy
      keep-alive-time: 60
      allow-core-thread-time-out: false
      alarm:
        enable: true
        queue-threshold: 80      # 队列使用率超 80% 告警
        active-threshold: 80     # 活跃线程占比超 80% 告警
```

- **动态参数刷新**：模板方法模式复用刷新逻辑；统一注册处理 Nacos/Apollo 多种配置中心监听事件 → 参数热更新**无需重启**。
- **拒绝策略增强**：基于 JDK `InvocationHandler` 动态代理拦截拒绝任务事件并告警（拒绝 = 故障前兆，必须可见）。
- **监控告警**：Prometheus + Grafana 采集可视化 + 钉钉通知；队列深度/活跃线程/拒绝次数阈值告警。
- **工程结构**：core（内核）+ starter（Nacos/Apollo/dashboard 可插拔）+ spring-base（扫描/开关）+ example + dashboard-dev（可视化控制台）。

### 3. 踩坑规避

1. **动态改 corePoolSize 的线程安全**：JDK 原生 `setCorePoolSize` 有并发边界问题，框架内部需同步处理（先减后加/加锁）；
2. **队列容量动态伸缩**：`ResizableCapacityLinkedBlockingQueue` 改容量需保证 `remainingCapacity` 一致性；
3. **优雅关闭**：关闭时拒新 + 排空存量 + 超时强退，避免任务丢失（`shutdown` + `awaitTermination` + `shutdownNow` 兜底）；
4. **告警风暴**：阈值加持续时间窗口（持续 N 秒超限才告警）。

### 4. 优化进阶

- **参数标定方法论**：压测找到"队列深度 × 处理时长 × 消费速率"的临界点 → 告警阈值设在临界点 70~80%；
- **从监控到自愈**：告警 → 自动化扩容（K8s HPA / 动态调大 maximumPoolSize）→ 人工复盘，形成闭环。

### 5. 选型对比

| 方案 | 动态调参 | 监控告警 | 侵入性 | 场景 |
|------|---------|---------|--------|------|
| JDK 原生 | ❌ 需重启 | ❌ | 零 | 参数稳定的内部任务 |
| **oneThread/Hippo4j** | ✅ 热更 | ✅ | 低（starter） | **生产业务线程池** |
| Spring `ThreadPoolTaskExecutor` | 部分（Bean 重建） | 弱 | 低 | 简单异步任务 |
| 虚拟线程（JDK21） | 不需要（按需创建） | 需新工具 | 中 | 高并发 IO 型（新范式） |

## 模块四：高并发业务系统案例（牛券 / 12306 / Link）

### 1. 核心原理

- **牛券（~10万 QPS）**：兑换/秒杀优惠券两套模式 + 批量分发（平台推送/Excel 导入）+ 模板创建（责任链）+ 防重复提交（AOP 注解 → Starter 化）。
- **12306（1.5w⭐）**：购票领域模型是精髓——**座位分配算法**（查余票 → 遍历有余票车厢 → 优先相邻 → 次选同车厢不相邻 → 最后跨车厢）；**区间分段扣减**（北京南→南京南实际扣减"北京南-济南西、北京南-南京南、济南西-南京南"三段，任一不足即失败）。
- **Link 短链（12k TPS 创建 / 56k QPS 跳转）**：唯一短码生成（哈希/Base62/雪花 + 碰撞校验）→ 映射持久化（Redis + MySQL）→ 301/302 重定向 → 埋点统计。

### 2. 生产落地

- **牛券防重三层**：Web 端（Token 防重复提交）+ 服务端（分布式锁 Redisson）+ MQ 消费（去重表/唯一索引）；**同一套逻辑抽象为 SpringBoot Starter，AOP + 注解复用**。
- **牛券缓存策略**：缓存击穿（互斥锁重建/逻辑过期）+ 穿透（布隆过滤器 + 空值缓存）+ 雪崩（随机 TTL + 多级缓存）；Redis 内存淘汰策略按业务选型（`allkeys-lru` vs `volatile-lru`）。
- **12306 读扩散治理**：用户名/手机号/邮箱多方式登录无法确定分片键 → 登录维度的**映射表分片** + 读请求扩散到多库聚合；大规模数据分库分表（分片键选择 + 平滑上线 + 快速回滚）。
- **12306 车次查询误区（经典面试题）**：直觉上 ES，实际上海量并发下 **ES 并发能力与资源占用不适用** → 查询条件经 Redis 缓存 + 内存组装。
- **Link 海量存储**：冷热分层（热短码 Redis / 温 MySQL / 冷对象存储）+ 分库分表 + 布隆过滤器防无效查询穿透。
- **Link 压测（阿里云 PTS）**：创建 12k TPS、跳转 56k QPS——**压测数据是项目可信度的核心证据**。

### 3. 踩坑规避

| 项目 | 坑 | 对策 |
|------|----|------|
| 牛券 | 百万行 Excel 解析 OOM | EasyExcel 流式读（SAX 模式）；两个主流框架 100w 行性能对比选型 |
| 牛券 | 秒杀超卖 | 扣减原子性（Redis Lua / DB 乐观锁）+ 对账补偿 |
| 12306 | 恶意刷中间站票 | 站间配额规则 + 动态放票（大站期初多放、临近发车开放小站） |
| 12306 | 缓存穿透（Null 缓存有漏洞：短暂脏数据；布隆有误判） | 二者组合 + 布隆误判兜底走 DB 校验 |
| Link | 短码碰撞 | 生成后碰撞校验 + 重试；唯一索引兜底 |
| Link | 多租户数据串权 | 租户 ID 强制注入查询条件（MyBatis 拦截器/行级策略） |

### 4. 优化进阶

- **秒杀两模式对比**（牛券核心考点）：兑换（先到先得，纯原子扣减，无时间窗）vs 秒杀（时间窗 + 库存预热 + 令牌桶限流 + 异步下单）——适用场景与一致性要求不同。
- **预约提醒架构**：百万预约 → 分库分表 + XXL-Job 分片扫描 + RocketMQ 5.x 延时消息（比定时轮询更省资源）。
- **Link 风控**：频控（单租户 QPS）、防刷（IP+设备指纹）、黑白名单、二维码海报（品牌化）。

### 5. 选型对比

| 场景 | 方案 | 牛券/12306/Link 实践 |
|------|------|---------------------|
| 高并发扣减 | Redis Lua vs DB 乐观锁 | Redis 主扣 + DB 异步对账 |
| 海量查询 | ES vs Redis 组装 | **Redis 组装（ES 并发不适配）** |
| 防重 | 分布式锁 vs 唯一索引 | 锁挡并发 + 唯一索引兜底 |
| 定时任务 | 轮询 vs 延时消息 | RocketMQ 延时消息优先 |
| 分库分表 | ShardingSphere | 分片键 = 用户/租户维度 |

## 案例深挖：Ragent V2 企业级 Agentic RAG 架构

### 1. 核心原理

**定位**：面向 Agentic RAG 演进的生产级 Java AI 平台（GitHub 开源 nageoffer/ragent）。前后端分离**模块化单体**，7 个 Maven 模块按职责隔离——`infra-ai`（模型客户端/档位/路由/首包探测/降级）、`system`（认证审计）、`rag`（问答/知识库/入库 Pipeline/意图树）、`agent`（AgentScope ReAct 引擎 + MCP 工具 + 技能/记忆/人工确认）、`bootstrap`（启动装配）、`framework`（统一响应/幂等/分布式 ID/MQ/SSE）、`mcp-server`（独立 MCP 工具示例服务）。**分层目的：业务编排、AI 供应商差异、通用基础设施三方隔离**——换模型/向量库/存储，核心流程不重写。

**v1 vs v2**：v1 Workflow 路径写死（重写→意图→召回→生成线性）；v2 Agentic 路径由模型自定（ReAct 循环里决定查不查、查几次、接着干什么）。**两套并存**：问答类走 v1 快可控，要规划要动手的交给 v2。

### 2. 生产落地

| 特性 | 实现 |
|------|------|
| 流量保护 | Redis ZSET 公平排队 + Lua 原子抢占 + 过期信号量 + Pub/Sub 唤醒 |
| 模型容错 | 多候选模型自动切换；首包超时/空响应/异常降级；三态熔断隔离故障节点 |
| 检索稳定性 | 多通道并行，单通道失败不影响主链；召回/Rerank/TopK 分层控制规模 |
| 数据一致性 | RocketMQ 事务消息保障分块可靠执行；幂等；远程刷新用分布式锁+状态机 |
| 可观测 | Trace Run/Node 耗时/输入输出/异常；Langfuse 追踪推理/工具调用/Token |
| 流式 | SSE 分事件输出思考/正文/来源/推荐问题；全局超时 + 客户端断开取消 |
| Agent 保障 | 上下文按水位裁剪压缩；长期记忆跨会话；写操作人工确认；执行中断 |
| 安全 | Sa-Token 认证、数据归属校验、上传限流、参数校验、统一异常 |

**工程质量**：10 个专用线程池隔离负载 + TTL 上下文跨线程传递；模型档位/候选/检索漏斗**启动阶段一致性校验**（fail-fast 不静默降质）；测试覆盖模型路由/检索预算/会话摘要/入库 Pipeline/MCP/Agent 记忆。

**设计模式实战**：策略（检索通道/后处理）、工厂（意图树/分块策略）、模板方法（并行检索）、注册表（意图节点）、装饰器（向量写入同步关键词图谱索引）、责任链（后处理/故障降级）、中间件（记忆注入/上下文压缩/技能遮蔽/工具批处理）、适配器（模型方言/MQ 客户端）、状态机（文档定时刷新）、事件回调（流式/首包探测/SSE）、AOP（追踪/幂等/审计）。

### 3. 踩坑规避

- **错误配置静默降质**：启动阶段强制校验模型档位与检索漏斗一致性，直接失败；
- **写操作误执行**：MCP 写操作强制人工确认（先展示内容和原始参数）；
- **突发流量压垮模型服务**：Redis 公平排队 + 分布式并发控制，不用本地限流；
- **Token 成本失控**：最近 N 轮 + 持久化摘要；Agent 上下文按水位裁剪压缩；
- **单一模型故障**：多候选路由 + 三态熔断，单节点故障不传导主链。

### 4. 优化进阶

扩展点设计：模型实现 `ChatClient`/`EmbeddingClient`/`RerankClient` 接口进候选配置 → 新供应商复用首包探测/健康检查/降级；存储实现 `ObjectStorageClient`/向量存取可配置替换；检索实现 `SearchChannel` 注册为 Bean → 参与并行召回；入库实现 `IngestionNode` → 进 Pipeline。**改动收敛在新实现和配置，不复制主链路**。

### 5. 选型对比

| 维度 | 常见 RAG Demo | Ragent |

| 检索 | 单路向量 TopK | 向量/关键词/图谱/联网 + RRF 融合 + Rerank |
