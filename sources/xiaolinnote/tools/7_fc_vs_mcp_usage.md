# LLM 工具调用面试题 7：什么场景下使用 Function Calling，什么场景下使用 MCP？

## 核心答案

本质区别：**FC 的工具「内嵌」在应用代码里**（schema 和调用逻辑写在项目中，工具和应用绑定，应用换了重写）；**MCP 的工具「独立」**（封装成独立进程，生命周期和应用解耦，独立部署维护、一次实现到处复用）。判断核心问题只有一个：**这个工具会不会在这个应用之外被用到？**

## FC 适用：轻量、临时、不复用

1. **快速原型/Demo**：目标是跑通想法，直接代码里定义 schema 就行，搭 Server 的时间可能超过原型本身价值；
2. **工具只为单一应用服务**：内部私有数据库查询绝不会被别处用到，写在项目里更清晰；
3. **需要精细控制执行逻辑**：权限校验、参数二次处理、特殊错误处理、链路追踪直接嵌进调用代码——MCP Server 是独立进程，这类定制逻辑要额外传递或约定；
4. **部署环境受限**：某些云环境/Serverless 不允许启动子进程，stdio MCP Server 没法用，只能 FC。

## MCP 适用：工具不是「自己用、用一次就扔」

1. **跨项目/跨团队复用**：同一套 GitHub 工具 Claude Desktop、Cursor、CI/CD Agent 都要用——FC 三处各维护一份，接口一变同步改三处漏一个出 bug；MCP 封装成 Server，配置文件加几行接入，维护责任在 Server 侧所有客户端自动受益；
2. **社区有现成 Server**：GitHub/Slack/PostgreSQL/Puppeteer/Google Maps 都有官方或社区 Server，直接配置就能用，手写 FC 是重复造轮子；
3. **工具规模起来了**：不看绝对数字门槛（复杂度×团队规模×变更频率综合——「感觉到散乱」的拐点），schema 和调用逻辑散落代码各处，新加工具改应用代码、有 bug 也进应用代码，定位链路长；MCP 自动发现让主程序不感知具体工具只连 Server；
4. **构建 Agent 系统**：工具需求多样来源复杂（代码执行/文件系统/数据库/外部 API），全靠 FC 工具 schema 会成为 Agent 代码最难维护的部分；MCP 让工具来源模块化，核心逻辑和工具管理解耦。

## 判断流程

① 社区有没有现成 MCP Server？有就直接用；② 工具要不要跨项目/多人复用？要就 MCP；③ 综合看数量/复杂度/团队/变更频率，规模上来就 MCP 统一管理；④ 正式 Agent 系统还是 Demo 原型？⑤ 部署环境允许启动子进程吗？

**一句话：「只用自己、只用一次、不需要复用」才适合 FC，其他情况优先 MCP**。两者不是竞争——MCP 底层本来就靠 FC 驱动，选哪个取决于工程需求不是技术优劣。
