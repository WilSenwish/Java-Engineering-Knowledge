# LLM 工具调用面试题 20：Agent 接入工具时应该如何选择 CLI 或 MCP？

## 核心答案

**CLI 是执行入口，MCP 是接入协议——不同层次，可以组合不一定要互斥**。链路：Agent 宿主 → MCP 客户端 → MCP Server → CLI 或业务函数 → 实际资源。

- 单一可控宿主 + 已有稳定 CLI：直接适配更简单（宿主维护工具说明，模型参数转命令参数，解析执行结果）；
- 多兼容 MCP 宿主复用能力：MCP 更有价值（统一工具描述/参数结构/调用方式，减少重复接入）；
- 已有 CLI 可被 MCP Server 包装，业务逻辑继续复用；
- **本地/远程是独立部署选择**：MCP 能 stdio 连本地进程也能 Streamable HTTP 集中部署；CLI 也能访问远程 API——「本地用 CLI、远程用 MCP」的划分没依据。

## 执行入口与接入协议

- CLI 提供程序入口：指定可执行程序/子命令/参数，执行后交回输出和退出状态；
- MCP 规范客户端与服务端交互：`tools/list` 发现（名称/描述/输入 Schema），`tools/call` 调用；
- **JSON 是数据格式不是协议**：普通 CLI 输出 JSON ≠ MCP 消息；stdio MCP 要收发协议消息、处理发现调用，stdout 不能混日志；
- 模型支持工具调用 ≠ 宿主支持 MCP，分别判断。

## 直接调用 CLI 的适配工作

- 宿主提供工具名称/用途/参数说明；模型生成结构化请求；宿主做参数映射（文件标识→文件路径 + 范围检查）、启动 CLI、结果转换；
- CLI 同时产生结果/诊断日志/退出状态，宿主按约定解释，**不能把终端文字拼一起当业务结果**；
- 优势是链路短、已有程序直接用、同团队维护时一份清楚适配器就够；
- 普通 CLI 没有普遍遵循面向 Agent 的工具发现调用协议——怎么获取说明/转参数/理解结果要双方协商。

## 选型判断表

| 实际需求 | 更值得评估的方式 |
|---------|----------------|
| 单一宿主 + 已有稳定命令 + 环境可控 | 直接适配 CLI |
| 多个兼容 MCP 的宿主共享能力 | 提供 MCP 接入层 |
| 原命令还要服务终端/脚本/自动化 | 保留 CLI，再按需包装 MCP |
| 能力由常驻后台服务提供 | MCP Server 调业务接口，不绕 CLI |
| 依赖本机文件或设备 | 优先可访问这些资源的本地部署 |
| 需要集中更新与多用户访问 | 评估网络服务及运维、鉴权成本 |

注意：标注支持 MCP 的宿主也可能只支持部分功能/传输方式，身份配置/结果呈现/工具选择要在目标宿主验证。

## 用 MCP 包装已有 CLI

- 保留 CLI + 新增 MCP Server 层：声明业务工具 → 协议参数转 CLI 参数 → 启动原程序 → 按退出状态和业务结果构造 MCP 返回；
- 包装层统一对外接入、复用执行逻辑；**不能原样转发文本**——参数类型/结果内容/错误语义都要对齐（CLI 正常执行但无匹配记录 ≠ 程序启动失败，要保留区别）；
- 超时取消核对实际行为：停止等待≠底层进程终止，结束子进程≠远端任务取消；
- 组合增加维护：CLI 升级要查匹配；排障要区分协议层/参数转换/命令执行/业务后台；
- 已有业务函数方便直接调用就复用函数；能力在后台 API 就直连 API——包装 CLI 是保护既有实现的一种办法，不是 MCP 必须结构。

## 协议选择不替代权限、可靠性、上下文设计

- CLI 子进程能访问什么取决于执行身份和环境；MCP Server 能操作什么取决于实现和业务权限——**标注支持 MCP 不会自动获得更严格资源边界**；
- 工具出现在列表里只说明可被发现，不代表用户有权操作任何资源；工具描述的「只读」标注不替代对实际实现的检查；
- 可靠性：协议请求失败不一定外部写操作没发生，重复提交靠稳定标识/去重/查状态；
- Token 成本取决于宿主怎么向模型提供信息：CLI 可附很长帮助文字，MCP 也可只给当前需要的工具定义——暴露多少/描述多长/结果裁剪才直接影响上下文。
