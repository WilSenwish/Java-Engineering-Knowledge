# LLM 工具调用面试题 22：Agent 的 Skill 加载机制是如何实现的？

## 核心答案

**渐进式加载三层**：

1. **元数据目录**：宿主从目录/服务/内置包发现 Skill，解析 `SKILL.md` 顶部 YAML frontmatter 的 name + description，形成轻量目录；
2. **正文激活**：模型根据任务和描述选择（或用户指定），调用文件读取工具/专用加载工具把正文读进上下文；
3. **资源按需**：参考资料、模板、脚本留在包里，执行到需要的步骤再取用。

**加载改变的是当前上下文，不改模型参数，也不等于执行脚本**——脚本仍要经工具调用，宿主检查参数和权限后运行。安装 Skill ≠ 模型已读到 ≠ 操作已发生。

## 加载 Skill = 把工作方法交给模型

模型作判断只能用当前请求提供的材料 + 运行程序通过工具给它的信息。文件存在不会自动改变模型这次看到的内容——宿主要把相关指令送进上下文。Markdown 指令被读到不成为已执行代码，它影响后续决策，具体操作靠工具完成。

## 第一层：元数据建立能力目录

```yaml
---
name: table-cleaning
description: 清理已有表格中的重复行和字段格式，适用于数据整理，不负责生成业务统计口径。
---
```

- 宿主发现 Skill → 解析元数据 → 保存名称/描述/内容位置 → 提供目录给模型；
- 名称便于识别，**描述帮助选择**：只写「处理文件」无法区分表格清理/文档转换/图片压缩——要写处理对象与任务边界；
- **内容位置必须保留**：模型决定用 table-cleaning 后，宿主要知道去哪读正文，不能只有名字没来源；
- 发现 ≠ 正文已加载。宿主可预缓存全文到内存，但只有实际交给模型的部分占本轮输入——**程序缓存与模型上下文是两个位置**；
- 目录本身有成本：Skill 多时按可见范围/相关性筛选，但要保留找到所需能力的途径。渐进式减少的是无关正文资源预载，不是让所有能力信息零成本。

## 第二层：选中后正文才进上下文

- 常见做法：模型调文件读取工具打开 SKILL.md，内容作为工具结果返回；
- 模型无文件读取能力 → 提供专用加载工具（模型提交 Skill 标识，宿主查登记信息取正文）；
- 用户显式指定 → 宿主直接加载；
- **选择与内容交接必须接起来**：模型输出「使用某 Skill」只表达选择，只有正文真正进上下文才具备按它工作的材料；
- 正文要提供足够主流程（执行顺序/必要检查/交付要求），让模型知道从哪开始；只有「详见附件」等于没加载；
- 选择可能出错：描述相似范围不清会误选；任务缺关键要求要先澄清。自动匹配是选择机制，不是必然用对的保证。

```
宿主发现能力包 → 提供名称与描述 → 选择所需 Skill → 实际读取内容 → 正文进入上下文 → 后续模型按指令工作
```

## 第三层：正文与资源分层

```text
table-cleaning/
├── SKILL.md                   # 名称、描述和主流程
├── references/field_rules.md  # 特定字段的详细说明
├── assets/report_template.md  # 输出模板
└── scripts/clean.py           # 可执行的处理程序
```

| 层次 | 提供什么 | 解决什么问题 |
|------|---------|-------------|
| 元数据 | 名称与适用描述 | 当前任务该选哪个能力 |
| 操作正文 | 主流程与必要要求 | 选中后怎样开展工作 |
| 辅助资源 | 详细参考/模板/脚本 | 当前步骤需要哪些额外材料或实现 |

- 三层不是必须无条件读完的列表——包装了十个参考文件，不意味着每次激活全加进上下文；
- **引用相对路径从 Skill 根目录解析**，不落到用户项目同名文件；远程包要等价资源定位；
- 资源取用不总是送进模型：模板可能直接复制给处理程序，脚本由执行工具读取运行，图片按任务用——只有需要模型理解的内容才进上下文。

## 加载说明与执行脚本分离

- 正文写「运行 scripts/clean.py」是操作指令——读到不自动启动 Python、不改表格；
- 真正执行经工具调用：请求明确输入/输出/参数，宿主找程序、查执行条件、运行、回传实际结果；
- 脚本把适合固定实现的步骤交给程序，减少模型反复生成相同代码，但**不要求全部源码先放进上下文**；
- 包里其他程序不必连带执行——清理/检查/上传分别服务不同步骤，只有当前任务需要且获准的进执行链；
- **加载权限 ≠ 执行权限**：允许读手册 ≠ 允许改任意文件/访问外部服务；第三方 Skill 即使结构合法，仍按来源和操作影响判断可信；
- Skill 正文不能靠声明「需要更高权限」自行改变 OS 或业务接口限制。

## 「以前加载过」≠「当前仍能使用」

长任务整理上下文后正文可能不再完整保留。记录已激活的名称与来源帮助重新取回，但**加载标记不能代替丢失的具体规则**：当前需要的指令仍在上下文就不重复注入；关键细节丢了按来源重读，且重读核对实际内容版本（防正文一套流程、脚本换成不兼容实现）。

## 诊断「Skill 没生效」四检查

1. 目录没有暴露（没被发现/被筛选掉）；
2. 能力选错（描述相似误选）；
3. 正文没读到（只选了名没交接内容）；
4. 执行条件没满足（工具/权限/参数不满足）。
