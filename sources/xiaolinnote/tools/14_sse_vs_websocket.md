# LLM 工具调用面试题 14：SSE 和 WebSocket 有什么区别？什么场景用哪个？

> **来源站点**：小林面试笔记（xiaolinnote.com）
> **原文链接**：https://xiaolinnote.com/ai/tools/14_sse_vs_websocket.html
> **抓取日期**：2026-10-20
> **所属知识域**：域6 性能优化与架构演进（AI 前沿）
> **板块**：LLM 工具调用面试题（22 题）· 通信协议

## 核心答案

- **SSE（Server-Sent Events）**：基于 HTTP 的**服务端单向推送**，浏览器用 `EventSource` 一行接入；
- **WebSocket**：独立协议，握手升级后**全双工**双向通信。

LLM 场景的行业事实：**文字流式输出的标准是 SSE**——OpenAI、Anthropic、国内各家大模型的流式 API 全是 SSE。WebSocket 的主战场是实时交互（游戏、协同编辑、弹幕）。

## 详细对比

| 维度 | SSE | WebSocket |
|------|-----|-----------|
| 方向 | 单向（服务端→客户端） | 全双工 |
| 协议基础 | 原生 HTTP | 独立协议（ws/wss），101 Upgrade 握手 |
| 接入成本 | EventSource 自动重连，极简 | 需客户端库，自管心跳重连 |
| 数据格式 | 文本（UTF-8） | 文本 + 二进制帧 |
| 断线恢复 | 浏览器自动重连 + Last-Event-ID 续传 | 应用层自实现 |
| HTTP/1.1 限制 | **同域 6 条连接上限**（多页面标签互相挤占） | 单条连接走多路，无此问题 |

## SSE 的局限

1. **HTTP/1.1 每域 6 连接**：一个页面开多个 SSE 源（LLM 流 + 通知流 + 日志流）会占满配额——HTTP/2 多路复用缓解；
2. **只能传文本**：二进制要 Base64，体积膨胀 33%；
3. **双通道依赖**：客户端上行（如用户打断、追问）还得另开 HTTP 请求——「下行 SSE + 上行 POST」组合拳。

## WebSocket 的局限

1. **有状态难扩展**：连接粘在具体机器上，横向扩展要额外的连接层/消息总线（类似 IM 架构）；
2. **代理/防火墙拦截**：部分企业网络拦 Upgrade 头，SSE 走普通 HTTP 端口更容易过；
3. **无原生请求-响应配对**：SSE/HTTP 天然「一个请求对一个响应」，WS 上要自己设计消息 ID 做配对，复杂度上移应用层。

## 选型判断

| 场景 | 选择 | 理由 |
|------|------|------|
| LLM 文字流式输出 | SSE | 行业标准、实现最简、断线自动恢复 |
| 实时语音对话 | WebSocket / WebRTC | 全双工低延迟（见 Q15） |
| 协同编辑/游戏 | WebSocket | 高频双向小消息 |
| 服务端推送通知 | SSE | 单向足够、HTTP 友好 |
| 二进制流（音视频帧） | WebSocket（或 WebRTC） | SSE 只传文本且 Base64 膨胀 |

**核心原则：文字容忍乱序丢包所以 TCP 是朋友；语音容忍丢包但绝不容忍延迟，所以 UDP 才是朋友**——协议选型的本质是匹配业务的「能容忍什么、绝不能容忍什么」。
