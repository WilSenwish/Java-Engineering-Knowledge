## 核心答案

工具很多时不做全量塞 Prompt，而是**分层 Tool Routing**：先建统一的工具注册表（命名空间/标签/适用场景/Schema/权限/风险/状态），每次请求用产品范围、租户、角色、环境、任务状态做硬过滤；再做两级召回——一级规则/轻量分类判业务域，二级 BM25/Embedding/混合检索召回 Top-K；最后只把候选工具的完整描述和 Schema 动态绑定给 LLM 精选。

**Tool Routing 路由的是「工具候选集」，Multi-Agent Routing 路由的是「任务由哪个 Agent 接手」**——两层可配合不能混谈。

## 为什么不能把全部工具都塞进 Prompt

1. **Token 问题**：工具定义占输入，挤压任务和证据空间；Prompt Cache 降本但没让可见工具变少；
2. **选择混淆**：`order_get`/`order_search`/`order_detail`/`after_sale_query` 描述都写「查询订单信息」，模型在相似选项间选错——问题在工具边界没讲清；
3. **权限风险**：把 `payment_refund` 暴露给无退款权限的客服，即使执行层拒绝也扩大了误调用和注入攻击面；
4. **延迟问题**：输入更长预处理更久，候选空间更大判断更慢（但别说「路由一定更快」——额外分类检索也耗时，要比较端到端）。

## 完整链路五步

**第一步：可路由的工具注册表（工具卡片）**

| 信息 | 作用 | 示例 |
|------|------|------|
| 唯一名称与命名空间 | 避免同名，按业务分组 | `orders.get_detail` |
| 能做什么 | 理解工具能力 | 查询单个订单的实时详情 |
| 什么时候用/不用 | 正向边界，区分相似工具 | 已知订单号用详情；批量模糊查找不要用 |
| 输入输出 Schema | 约束参数与返回 | `order_id` 必填字符串 |
| 标签 | 规则和检索 | 订单、查询、只读 |
| 权限与风险 | 决定能否暴露、是否审批 | `order:read`、低风险 |
| 状态与环境 | 排除不可用 | 仅生产环境、当前健康 |
| 版本与成本 | 灰度和调度参考 | v2、预估高延迟 |

命名体现「业务域 + 动作」（`orders.search`/`orders.get_detail`/`orders.cancel`）；命名空间和标签提供稳定一级索引。

**第二步：先做确定性过滤**

- 静态过滤：Allowlist/Blocklist（客服 Agent 只允许客户/订单/知识库工具；开发环境禁真实支付；某版本只启用 v2）；
- 动态过滤：租户、用户角色、功能开关、地区、会话阶段、任务状态、工具健康状态、关键参数是否已收集；
- **安全原则：先鉴权，再做相关性召回**——检索器只能在「当前请求有权看到的工具集合」里搜，不能全库召回再指望 Prompt 告诉模型「这个不能用」；
- 隐藏工具只减少暴露，**执行时仍要服务端重新鉴权**（权限可能取决于具体参数和资源归属，如 `order_id` 属于哪个租户）。

**第三步：粗分类缩小业务域**

- 边界清楚的请求优先规则（出现订单号问物流 → 「订单+物流」类别；工作流进入付款确认节点 → 只开放支付查询类）；
- 规则难覆盖时用轻量分类模型/小参数 LLM（检索类/查询类/生成类/执行类，或订单/支付/审批域）；
- **粗分类要偏向高召回**：「查订单+取消订单」保留两个类别；不确定时跳过这层直接进更大范围检索。

**第四步：候选域里检索工具**

- BM25 适合产品名/接口名/字段名/缩写（「Jira」「SKU」「order_id」）；Embedding 适合语义（「包裹还在路上吗」→「查询物流轨迹」）；混合检索 + 分数融合/轻量 Rerank；
- 索引内容不止一句描述：名称、业务标签、适用场景、排除条件、参数名、少量调用示例；
- 工具检索追求「别漏掉正确工具」，**不是「排第一就直接执行」**——相似度只表达语义接近，不代表有权限、参数满足、能完成任务。

**第五步：只把候选动态绑定给 LLM**

- 模型做三件事：判断是否真需要工具、选一个或多个、填结构化参数；
- 「先召回后精选」把 LLM 从上百相似选项盲选变成小候选集判断；
- OpenAI/Anthropic 官方工具搜索都支持延迟加载（工具留目录中，需要时才加载进上下文）；
- 少数高频低风险工具可常驻（只读搜索、帮助工具），长尾按需加载；
- 动态绑定只决定「模型看见什么」，执行前仍要 Schema 校验、权限校验、风险策略、人工审批。

```python
def route_tools(query, context, registry):
    allowed = registry.filter(product=..., tenant=..., role=...,
                              environment=..., healthy_only=True)   # 硬过滤先行
    domains, confidence = classify_domains(query, context.task_state)
    if confidence >= 0.7:
        allowed = allowed.in_domains(domains)                      # 粗分类
    candidates = hybrid_retrieve(query=query, tool_cards=allowed, top_k=6)  # 召回不执行
    return bind_full_schemas(candidates)                           # 精选交给主模型
```

## Skill 渐进加载与 Tool Routing 配合

常见链路：**用户请求 → 匹配 Skill → 加载任务流程 → 根据当前步骤路由 Tool**。Skill 选中后可提示「先用 `orders.get_detail`，满足条件后用 `orders.cancel`」，把检索范围缩小到某命名空间。但 Skill 不能替代权限过滤和执行鉴权——Skill 里写了工具名，不绕过用户当前权限。

## 工具描述和 Schema 质量决定路由上限

- 名称具体，避免 `query_data`/`process` 泛化命名；
- 描述回答四问：做什么/何时用/何时不用/返回什么；相似工具直接写差异；
- Schema 收紧：能枚举不任意字符串、必填明确、日期 ID 范围写清；少量正反例；
- **Schema 约束解决格式合法性，业务合法性仍要在工具内部校验**；
- 两个工具总被混淆，先检查职责重叠能否合并/拆分——工具设计本身就是 Tool Routing 的一部分。

## 评估体系（三层拆开看）

| 层 | 指标 |
|----|------|
| 候选召回 | Recall@K（单工具）、多工具召回完整度、候选集大小、Schema Token |
| 模型精选 | 工具选择准确率、相似工具误选率、无工具拒选准确率、漏调率；参数 Schema 合法率/必填完整率/事实正确率 |
| 业务结果 | 任务成功率、执行失败率、端到端延迟、成本、澄清率、人工接管率；越权暴露率、越权拦截、高风险审批覆盖率 |

评测集要含 Hard Negative（相似工具）、多意图、不需要工具、缺参数、无权限、历史 Badcase；保留每层候选/分数/过滤原因/最终调用 Trace。

## 路由失败兜底

- 无候选或置信度低：改写查询扩大类别和 Top-K 再检索；仍不确定让用户补充信息，比猜工具可靠；
- 多相似工具分数接近：低风险只读让 LLM 精选；高风险（付款/删除/发信）进确定性规则或人工审批；
- 首选工具不可用：切备用工具/降级只读/转人工；**模型输出候选集之外的工具名，运行时必须拒绝**；
- 正确工具没进 Top-K：同一个 LLM 在错误候选里反思无意义，回召回层放宽类别/改写查询/走默认工具搜索入口。
