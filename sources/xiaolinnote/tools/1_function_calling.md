## 核心答案

Function Calling = 开发者用 JSON schema 描述工具传给模型，模型判断需要调工具时**不输出自然语言而输出结构化 tool_calls JSON**（「调哪个函数、参数是什么」），宿主代码解析执行，把结果塞回对话，模型再生成最终答案。**两轮对话 + 中间执行**的闭环。核心设计：**模型全程只做决策，执行一律由宿主代码完成**——模型没有直接执行代码和访问网络的权限。OpenAI 2023 年推出，现为主流模型标配。

## 三角色 = 任务委托

- **开发者 = HR**：写工具「职位说明书」（JSON schema）；
- **模型 = 经理**：读说明书决定调哪个工具、参数填什么，下达指令；
- **你的代码 = 员工**：真正跑函数、访问网络、查数据库，汇报结果。

## schema 设计关键

```python
{
  "name": "get_weather",
  "description": "查询指定城市的实时天气，包含气温、天气状况、风向风速，仅支持中国大陆城市",
  "parameters": {
    "properties": {"city": {"description": "城市名称，如「北京」「上海」，不要带省份前缀"}, ...},
    "required": ["city"]
  }
}
```

**description 是模型判断是否调用和参数填写的唯一依据**——写「获取天气」模型会瞎猜（带英文名的城市也照调、时间跨度不对也硬塞）；写清用途/范围/格式/示例/限制，模型选择才准确。

## 运行时流程

第一轮：工具列表 + 用户问题一起传给模型 → 模型判断需要工具则返回 `finish_reason == "tool_calls"`（明确信号：还没准备好给答案）→ 代码解析 tool_calls 执行 → 第二轮：结果以 `role: "tool"` + `tool_call_id` 塞回对话 → 模型给最终自然语言答案。

## 并行调用

用户一口气问多件事（「查北京、上海、广州天气」），模型一次响应输出多个 tool_calls，代码用 `asyncio.gather`/多线程同时执行，结果一次性塞回，**「两轮对话」压缩成「一轮对话 + 并行执行」**，省掉串行的多轮推理延迟。前提：工具间无依赖——查北京和查上海可并行；「先查订单号再用订单号查物流」只能串行，模型也会分两轮输出。
