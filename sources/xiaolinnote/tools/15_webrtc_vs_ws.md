## 核心答案

实时语音选 WebRTC 的根本原因：**语音容忍丢包，但绝不容忍延迟**。

- 丢几个音频包：插值补偿一下，人耳几乎无感；
- 慢 200ms：对话节奏被打断，体验崩坏。

**TCP 的重传机制在语音场景是灾难**——丢一个包等重传，延迟雪上加霜。所以 WebRTC 走 **UDP**，用「丢了就丢了、快速前进」的策略保延迟。WebSocket 基于 TCP，天生不适合实时语音主干（但可做它的信令通道）。

## WebRTC = UDP + 协议全家桶

WebRTC 不是单一协议，是一整套实时通信栈：

| 组件 | 职责 |
|------|------|
| **UDP** | 传输底座，不重传，保延迟 |
| **RTP** | 音频/视频数据打包传输（带序号/时间戳） |
| **RTCP** | 质量控制（丢包率/延迟/抖动反馈，驱动降码率） |
| **DTLS** | 密钥协商（加密握手） |
| **SRTP** | 加密媒体流传输 |
| **ICE** | 连接性探测（STUN/TURN 协同） |

## NAT 穿透：三层降级

两端设备多在 NAT 后没有公网 IP，WebRTC 的打通路径：

1. **STUN**：问公网服务器「我的公网地址是什么」——大多数场景直接打通（P2P 最优，延迟最低）；
2. **TURN 中继**：STUN 搞不定（对称型 NAT/企业防火墙）时，媒体流绕经 TURN 服务器转发——延迟增加但保证连通；
3. **完全失败**：降级为普通网络中继。

## 内置音频处理全家桶

浏览器原生提供，无需业务开发：

- **AEC**（回声消除）：防止对方声音从扬声器出来又被麦克风收回形成回声；
- **NS**（噪声抑制）：滤除环境噪声；
- **AGC**（自动增益）：说话远近自动调节音量；
- **ABR**（自适应码率）：网络差时自动降音质保流畅。

## WebSocket 在 WebRTC 中的角色

WebSocket 并不是没用——**它做信令（Signaling）通道**：

```
浏览器 A ←──WebSocket──→ 信令服务器 ←──WebSocket──→ 浏览器 B
       （交换 SDP：支持的编码/码率/ICE 候选地址）
                    ↓ 信令交换完成
        A ←============= UDP/RTP 直连 =============→ B
            （媒体流点对点传输，不再走服务器）
```

**SDP 交换必须借助一个双向通道完成，WebSocket 正好干这个；媒体流本身绝不走 WebSocket。**

## 行业事实

**OpenAI Realtime API（实时语音）选 WebRTC 而非 WebSocket**——延迟要求摆在那。面试一句话：**「WebSocket 是基于 TCP 的全双工通道，适合文字和小消息实时交互；WebRTC 是基于 UDP 的实时通信栈，为低延迟音视频而生，WebSocket 在 WebRTC 里只配当信使」**。
