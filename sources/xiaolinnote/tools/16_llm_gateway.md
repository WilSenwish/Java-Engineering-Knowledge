## 核心答案

**LLM 网关（LLM Gateway）是应用与各家模型 API 之间的中间层**——业务代码不直接调 OpenAI/Claude/通义，而是统一调网关，由网关负责路由、治理、观测。

解决的问题：多模型接入碎片化、API Key 散落各处、成本失控、限流无统一管控、缓存无从谈起。

## 六大核心能力

1. **多模型统一接口**：一套 SDK/协议调所有模型——OpenAI 格式转 Anthropic 格式、转国产模型格式；模型切换只改配置不改代码（防厂商锁定）；
2. **API Key 集中管理**：Key 存网关侧，业务系统不碰密钥；泄露面从「每个应用一份」缩到「网关一处」；支持按团队/应用分配虚拟 Key；
3. **限流与配额**：按应用/租户/模型维度限 RPM/TPM；预算熔断（本月额度用完自动停），防「一个脚本烧穿预算」；
4. **成本追踪**：按应用/用户/功能统计 token 消耗与费用，账单可拆解到人；
5. **Prompt 安全**：注入检测、敏感词过滤、PII 脱敏、输入输出审计——统一安全闸门；
6. **语义缓存（杀手级能力）**：对 query 做 embedding，与缓存中历史 query 算**向量相似度**，超过阈值（通常 0.85-0.95）直接返回历史答案，**完全跳过 LLM 调用**——省钱省延迟。相似问题（「怎么重置密码」vs「密码忘了咋办」）命中同一缓存。

## 语义缓存 vs 传统缓存

| | 传统精确缓存 | 语义缓存 |
|--|------------|---------|
| 命中条件 | 字符串完全一致 | 向量相似度 ≥ 阈值 |
| 命中率 | 低（用户表达千差万别） | 高（同义不同形也命中） |
| 代价 | 查 Redis | embedding 计算 + 向量检索 |
| 风险 | 无 | 阈值低了答非所问，需按业务调 |

## 主流选型

| 产品 | 定位 | 特点 |
|------|------|------|
| **LiteLLM** | 开源 Python 网关 | 100+ 模型统一 OpenAI 格式，社区活跃，自托管 |
| **One API** | 开源（国产） | 轻量、渠道管理、国内模型支持好 |
| **Bifrost** | 开源高性能（Go） | 低延迟高并发，Go 技术栈友好 |
| **PortKey** | 商业可自托管 | 可观测性强，治理功能全 |
| **Kong AI Gateway** | 基于 Kong | 复用已有 API 网关基础设施，企业级 |

**选型思路**：已有 Kong 网关设施 → Kong AI Gateway；Go 高并发团队 → Bifrost；快速起步 100+ 模型 → LiteLLM；国内模型渠道多 → One API。核心诉求就两个：**统一接入 + 可治理**。
