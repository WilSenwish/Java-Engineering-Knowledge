# AI 编程面试题 6：复杂开发需求如何拆分，才能让 AI 更可靠地完成？

## 核心答案

1. **先找行为**：结合需求和现有代码，找出要改变的行为、需保留的约定、还没弄清的部分；
2. **按可验证目标拆**：每任务说明依据、修改范围、依赖、完成标准；粒度以能理解、能检查为准，**一个任务可以跨多个文件**；
3. **相关实现 + 必要验证放一起**：筛选条件怎样进查询、怎样影响结果和总数作为同一项行为考虑——不能分别改完却没人检查一致性；
4. **顺序**：先确认共享接口和前置条件，优先打通一条能验证的链路再扩展；只有依赖已满足、修改范围不冲突才并行；
5. **tasks.md 维护**：执行中发现新依赖/需求变化/判断不成立，更新受影响的剩余计划；完成依据是实际改动和检查结果；最后对照总需求做集成和回归。

## 为什么列了步骤还做不好

按技术层拆（前端/后端/数据库各自一任务）会让每层自行决定接口——前端叫 `status`、后端叫 `state`、数据库叫 `order_status`，各自写完没人让它们互相认识。拆太细（一个函数一任务、加行校验也单开）反复恢复上下文交接结果，完整行为反而难核对。

**任务拆分的作用是让每步目标和依据更清楚，同时保留步骤之间的关系**——任务数量由关系决定，不预先规定拆几步。

## 从行为拆起，再定代码范围

先整理：要增加的行为、重要边界、必须保持的约定，再结合源码确认涉及哪些位置。订单列表状态筛选示例要求：状态未选保持原查询范围；选择后列表和总数用同一筛选条件；切换状态回第一页；非法状态按已有参数错误处理；保留原数据访问约束。

不能看到哪些文件就把每个文件安排一任务——范围来自要改变的行为及其关系。**暂时不清楚的部分先安排有输出的分析任务**（核对查询链路，记录参数传递/筛选位置/验证方式），完成依据是找到可核对的代码关系，不是运行过一次搜索。

拆完对照整体要求：「状态筛选有人实现、页面切换有人实现，但总数是否用相同条件没出现在任何任务里」= 计划有缺口。

## 粒度与验证配套

适合执行的任务：前置条件成立后，有明确输出和检查方法。接口任务可覆盖参数校验/条件传递/结果与总数查询/测试——跨请求入口、业务层、查询层，但共同完成一个可通过接口验证的行为。

「增加筛选条件」和「调整总数查询」分开却不明确两者必须同一条件 → 中间结果可能不一致；它们可以保留实现步骤，但应在同一行为目标下安排检查。

**相关验证跟着任务走**：接口完成时检查有效筛选/非法输入/分页结果；页面完成时检查参数发送与页码重置——不要等所有实现结束才第一次想正确结果是什么。

## 依赖与并行

- 计划写前置结果而非任务编号：「页面任务依赖筛选参数和响应结构已确认」让执行者理解为什么等、能否先用稳定约定开工；
- 共享约定确定后接口与页面可并行（同一参数语义、修改范围分开、局部检查有依据）；最终联调依赖两边实际结果；
- 并行考虑共享修改：两个任务改同一公共类型或同一份测试数据会互相覆盖；文件不同但共同改变一个接口约定也可能语义冲突；
- 独立目录/工作区减少文件干扰，但不自动保证接口一致——合并后要查实际差异和组合行为。

## tasks.md 结构示例

```markdown
## T1：确认现有链路与接口约定
- [ ] 核对请求入口、参数类型、结果与总数查询、页面调用和现有测试。
- [ ] 在 plan.md 记录状态参数、页码处理与错误响应的代码依据。
完成依据：能说明数据怎样传递，关键规则已有明确约定，未知事项已标出。

## T2：实现接口筛选与对应验证
前置：T1 接口语义已确认。
- [ ] 实现参数校验与筛选传递，使列表和总数使用相同条件。
- [ ] 验证有效筛选、非法状态、空结果以及筛选后分页与总数。
完成依据：实际接口结果符合约定，检查通过且不破坏原查询行为。

## T3：实现页面筛选与对应验证
前置：T1 已确认，页面修改不与 T2 冲突。
- [ ] 接入筛选交互，正确发送状态参数，切换状态重置页码。
完成依据：局部交互符合规则；明确此时是否仍使用测试替身。

## T4：连接真实接口并验证完整链路
前置：T2、T3 通过各自检查。
完成依据：页面到实际接口行为一致，没有仅在替身环境成立的假设。

## T5：核对总需求与相关回归
前置：T4 完成。
完成依据：总需求有对应证据，已有约定得到保留，未完成项如实列出。
```

T1 接口约定是共同输入让 T2/T3 有条件并行；T3 记录是否用测试替身，T4 再查真实连接——防把局部通过当整项完成。

## 执行中维护与整体验收

新信息（源码参数封装不同、公共接口有其他调用方、测试缺数据条件）→ 判断影响哪部分：只影响局部实现调当前任务；改变接口约定或前置结果→查后续任务是否仍成立；需求变化→同步更新要求和验收依据。

完成状态要证据：文件写入≠验收通过；构建环境起不来或仍用替身要记录限制。**接口单测和页面组件测试都过，真实请求可能没带状态参数**——局部正确还可能有单位转换/字段传递/执行顺序的组合错误，必须联调发现。计划更新保留有效步骤、补新依赖、更新受影响完成依据；已完成任务因新规则失效要明确重新验证什么。
