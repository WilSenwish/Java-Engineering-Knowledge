# AI 编程面试题 5：Vibe Coding 和 Spec 驱动开发有什么区别？分别适合什么场景？

> **来源站点**：小林面试笔记（xiaolinnote.com）
> **原文链接**：https://xiaolinnote.com/ai/coding/vibe_coding_vs_spec_driven.html
> **抓取日期**：2026-10-20
> **所属知识域**：域6 性能优化与架构演进（AI 前沿）
> **板块**：AI 编程面试题（14 题）· 开发方式

---

## 核心答案

- **Vibe Coding（严格含义）**：自然语言让 AI 生成修改代码，开发者主要看运行效果、继续反馈，对生成代码的理解和审查较少。推进：提出想法 → 生成实现 → 运行观察 → 反馈调整；
- **Spec 驱动开发**：先把已确认的行为、约束、验收条件写成规格，再组织实现和验证；需求变更同步更新受影响的文档和检查。

注意区分三件独立的事：**AI 是否生成代码 / 开发者怎样审查 / 有没有用规格组织开发**。用 AI 生成但认真读 diff、核对规则、跑检查 = 普通 AI 辅助开发，不必强行归类。

**选择逻辑**：想法没成形→原型探索（缩短试验等待、可丢弃）；规则明确、要兼容已有系统/多人协作/长期维护→规格组织（追踪要求、验证结果）。实际按任务阶段组合：先低成本原型确认方向，进入正式交付再明确规格、审查原型代码、补齐验证——**不因原型能跑就继承全部实现，不因文档厚就当质量保证**。

## Spec 的三份核心文档

| 文档 | 回答 | 待办功能示例 |
|------|------|-------------|
| `spec.md` | 应该有什么行为？怎样验收？ | 空名称不新增；切换/删除只影响指定记录；刷新后清空 |
| `plan.md` | 怎样在当前项目中实现？ | 沿用现有组件结构、内存状态、安排行为检查 |
| `tasks.md` | 按什么顺序执行、依赖什么？ | 状态处理 → 交互接入 → 边界验证与回归 |

目录结构（Spec Kit）：

```text
.specify/memory/constitution.md   # 项目共同原则（依赖/兼容性/验证要求）
specs/<功能目录>/spec.md           # 功能要求与验收条件
specs/<功能目录>/plan.md           # 技术实现方案
specs/<功能目录>/tasks.md          # 可执行任务与依赖顺序
```

复杂功能可加 `research.md`（调研）、`data-model.md`（实体状态）、`quickstart.md`（运行验证）、`contracts/`（接口约定）、`checklists/*.md`（需求质量核对——清单通过≠代码测试通过）。

## Spec Kit / OpenSpec 的 Skill 工作流

| Skill | 作用 | 产物 |
|-------|------|------|
| `/speckit-constitution` | 建立/更新项目原则 | constitution.md |
| `/speckit-specify` | 自然语言需求整理成规格 | spec.md + 质量检查材料 |
| `/speckit-clarify` | 歧义补齐（规划前） | 更新 spec.md |
| `/speckit-plan` | 设计实现 | plan.md + 调研/模型/接口材料 |
| `/speckit-tasks` | 拆分有依赖顺序的任务 | tasks.md |
| `/speckit-implement` | 按任务推进 | 代码、测试、任务进度 |
| `/speckit-analyze` | 交叉分析三份文档报冲突/遗漏/含糊（不改文件） | 分析报告 |
| `/speckit-converge` | 实现后对照规格检查遗漏 | 问题列表 + 追加待办 |

OpenSpec 围绕一次变更组织：`/opsx:propose`（proposal.md + specs/ + design.md + tasks.md）→ `/opsx:apply` → `/opsx:archive`（同步主规格）。**Skill 报告仍要核实，「没发现问题」≠ 证明所有要求满足**。

## 不确定性处理与转换

| 维度 | Vibe Coding | Spec 驱动 |
|------|------------|----------|
| 推进依据 | 运行效果与即时反馈 | 已确认的规格和当前执行结果 |
| 需求明确 | 尝试反馈中逐步形成 | 先确认规则再指导实现 |
| 代码审查 | 较少深入检查，易停留在可见效果 | 实现和检查对应到规格，仍需审查 |
| 变更处理 | 追加反馈继续修改 | 更新受影响的规格、实现和验证依据 |
| 主要代价 | 实现理解不足、规则不一致、后续返工 | 规格确认、维护与一致性检查投入 |

效果反馈回答问题的范围有限：页面符合预期≠异常分支、数据处理、依赖使用正确。反复对话修补还可能让不同轮次采用不同规则。

探索→交付转换：整理原型中已确认的行为、标出临时替代和未决规则；检查代码是否适合继续用（临时状态/模拟数据/绕过错误的处理要重新核对）；已确认规格也可调整——持续核对的依据要跟有效需求变化。
