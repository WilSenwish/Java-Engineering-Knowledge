## 核心答案

核心是**先缩小搜索范围，再沿代码关系补齐上下文**：

1. **需求转搜索线索**：业务描述和源码命名不一致，把接口路径、报错文本、日志、字段名、堆栈转成可搜索的锚点；
2. **缩小范围**：先读顶层目录/构建配置/模块入口了解划分；优先搜项目源码，减少依赖和生成文件干扰；
3. **选对工具**：有明确标识用文本搜索（带路径行号先筛再展开）；只有模糊描述用语义检索找候选；「这个调用指向哪个函数」用符号工具（跳转定义/查找引用）；
4. **读完整函数**：补类型和必要外围结构，防同名代码当同一实现；
5. **沿关系跨文件**：调用方/被调用方、数据读写、事件传递；核对配置和注册代码（决定实际用哪个实现）；
6. **定位到位标准**：新增功能确认职责与影响范围；排障还要结合日志/轨迹/最小复现验证原因。

## 命中文件 ≠ 找到相关实现

搜「订单」出几十个文件：类型定义、测试数据、旧接口、在用的逻辑——文件与问题有关不代表其中所有代码都要改。**代码定位要回答：哪段代码承担当前职责，哪些代码关系会影响这段实现**。定位结果通常是一组有关系的位置：关键函数 + 必要类型/配置 + 相关调用方。

**搜索和阅读要对应同一版本**：排查线上故障却读已修改的主分支会误判；预建索引要确认对应提交并回当前源码核验。

## 三类工具的证据差异

| 工具 | 适合 | 局限 |
|------|------|------|
| 文本搜索 | 已知名称/字符串（接口路径、错误文本、字段名） | 同名歧义（`save` 在多个类）；命中只说明文本存在 |
| 语义检索 | 缺少明确名称（「防止请求重复处理」→「幂等校验」） | 相似度高≠相关（注释/测试/旧实现可能更接近描述） |
| 符号工具 | 确认调用指向（`CustomerRepository.save` vs `InvoiceRepository.save`） | 动态调用/反射/运行时注册可能让分析不完整 |

确认符号后给模型足够阅读上下文：孤立一行 `status = SUCCESS` 看不出改哪个对象、什么条件下执行——读所属函数参数/分支/返回 + 状态类型。

## 沿代码关系连跨文件实现

- **调用关系**：调用方说明执行条件和传入参数；被调用方说明交了哪些工作；
- **数据关系**：谁写字段、谁读字段、中间有没有默认值/格式转换/重算——几个文件没有相似业务描述也可能通过同一数据对象联系；
- **事件关系**：`OrderPaid` 发布函数和消费函数可能连变量名都不同，要从事件类型/发送位置/订阅注册/处理函数查；
- **确认运行路径**：接口多实现由注入配置决定；消费者写好但订阅没启用——注册与配置也是定位范围。

这也是相似度检索替代不了关系分析的原因。**扩展关系要有具体问题**：确认输入是否校验就查来源与校验分支；确认结果为何没变就查写入条件和读取——不把整个依赖图搬进上下文。

## 定位到位标准

- 新增/修改：职责由哪个函数承担、输入输出约定、影响哪些调用方（相关测试帮助理解已有约定）；
- 排障：候选原因能否解释实际现象——源码说明路径可能发生，日志/轨迹判断这次是否经过，最小复现验证；
- 工具结果完整性：搜索被截断不能断言其他位置没实现；读取失败不当代码不存在；
- 完成后保留关键路径/函数名/关系/验证依据，已排除的文件不占上下文。
