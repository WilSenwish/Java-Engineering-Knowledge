## 核心答案

1. **复现清楚**：给 AI 明确的预期结果、实际结果、触发步骤、代码版本、运行环境、执行命令；报错保留异常信息和调用栈；日志筛出同一次请求/测试的关键过程；
2. **追踪数据来源**：沿报错位置追输入和数据来源，提出有依据的原因假设，说明下一步怎么区分假设；每轮先做能缩小范围的检查（读依赖契约/观察中间值/最小复现）；
3. **按约定修复**：确认原因后按原有业务约定修——遗漏异步等待就等结果回来，**不能靠返回默认值让报错消失**（「提示空值就补默认值」= 接口成功但用户名没了）；
4. **证明恢复**：用原复现条件检查，补能在旧实现中失败的回归用例，再查相关路径和最终差异；
5. **解释≠验证**：AI 的解释属于判断，实际执行结果才是验证依据；无法复现或未验证的部分单独说明。

## 三类证据各自回答什么

| 证据 | 主要帮助回答 | 还需补充 |
|------|-------------|---------|
| 异常信息与调用栈 | 在什么操作、什么位置失败 | 相关值怎样产生，外围有没有包装转换 |
| 关联日志 | 这次执行经过哪些步骤 | 是否覆盖关键位置、是否同一次执行 |
| 失败测试 | 哪个预期没满足 | 前置条件、断言、替身是否符合真实约定 |

没有固定高低顺序：接口直接返错误结果没异常时失败断言更有用；依赖偶发失败时关联日志提供单次执行看不到的线索。**时间接近的两条日志不一定属于同一个操作**——按同一次请求/同一条测试关联。

## 案例：getDisplayName 的 TypeError

```javascript
export async function getDisplayName(userId, userRepo) {
  const user = userRepo.findById(userId);   // 返回 Promise，没 await
  if (user === null) return null;
  return user.name.trim();                  // TypeError: reading 'trim' of undefined
}
```

错误链：仓库返回 Promise → 调用方按用户对象读取 → `name` 为 undefined → 读 `trim` 失败。**`async` 只是允许函数用异步写法并返回 Promise，内部某次调用的结果仍需按依赖约定等待**。补空字符串会保留错误的数据处理过程。

## 区分候选原因的实验设计

怀疑罗列（用户名缺失/响应多包一层/遗漏异步等待）后，说明什么观察能支持或排除：

```text
run=demo-17 check=lookup-return thenable=true      # 返回可 then 调用 → 异步线索
run=demo-17 check=lookup-resolved found=true nameType=string  # 等后是合法字符串 → 排除字段缺失
run=demo-17 check=original-call outcome=TypeError  # 原函数仍失败 → 正确数据没被按约定处理
```

- **诊断日志围绕具体疑问**：记录返回特征和完成后字段类型，比打印整份用户资料有用；不能只在入口出口写「开始」「结束」；
- **最小复现保留关键语义**：替身必须返回 Promise——换成同步返回用户对象，原函数就正常，复现反而把缺陷藏起来；
- **每轮检查验证一个明确判断**：一次同改返回结构+异常处理+测试预期，变了也不知道哪个改动有效。

## 修复与回归验证

```javascript
const user = await userRepo.findById(userId);  // 等查询完成
if (user === null) return null;
return user.name.trim();
```

验证三条路径：用户名正确返回（存在用户）、`null`（不存在）、错误继续抛出（查询失败）。**只检查「没有 TypeError」会让返回空字符串的错误修改也通过**。

旧测试为何全绿：旧替身同步返回用户对象，调用方没有等待的必要——**测试没模拟真实仓库的接口契约**。改 `async` 替身后，即使 Promise 很快完成也能区分两种实现，无需人为加延迟。

回归用例设计原则：**先确认用例在旧实现中失败，再验证修复后通过**——否则不能证明它检查到了这次缺陷。

## debug.md 排查记录

```markdown
## 已确认事实 / 已排除的候选原因 / 修复与验证 / 尚未验证
```

- 结论对应证据，避免下一轮重复猜已排除的原因；
- 连续几轮没缩小范围 → 检查方法：复现条件是否稳定、观察点是否覆盖关键步骤、有没有把修改前后输出混一起；
- 偶发问题保留出现/未出现时的差异（数据/环境/顺序）；证据不足时说清下一步缺什么，比贴「环境问题」标签有用；
- 修复后查最终改动范围：排查用的临时输出是否保留、测试预期有没有被放宽、无关接口是否变化。
