# AI 编程面试题 3：使用 AI 编程时，应该提供哪些代码上下文？

## 核心答案

围绕当前任务选上下文：先给目标、修改约束、验收标准（这次解决什么问题），再补实现需要的项目事实。

- **代码**：相关入口和目标函数，必要时补调用方、依赖接口、类型定义（只看一个函数不知道参数单位、数据经过什么转换、改返回值影响谁）；
- **测试 + 同类实现**：相关测试展示已有行为和测试方式；一个经过核对的同类实现帮助理解项目写法；
- **构建/运行问题**：依赖版本、相关配置、执行命令、关键报错；
- **工具可读仓库时**：先给路径/符号/错误文本让它按需补读——**能访问文件 ≠ 模型已拿到文件内容**。

筛选标准：**这份信息是否会影响当前实现或验证的判断**。不全仓库塞入（依赖/生成文件/旧实现混入），不为省长度截断关键分支和类型。

## 打开仓库 ≠ AI 知道所有代码

模型一次回答依据的是这次实际得到的信息：粘贴的代码、工具附加的文件、对话历史、搜索/读取/命令结果。告诉 AI「问题在 order_service.ts」只是给了线索——工具没读文件内容，它仍不知道实现。模型的通用编程知识也代替不了项目事实（安装的版本、封装过的接口、刚改过的代码）。

## 材料清单与各自补充的未知

| 材料 | 帮助核对什么 |
|------|-------------|
| 目标函数 + 完整边界 | 这行代码实际在做什么（参数/前置处理/返回路径） |
| 类型与接口定义 | 参数能否缺失、枚举值、返回结构 |
| 调用方 | 输入经过什么校验/转换/默认值（防重复处理或漏处理） |
| 依赖接口与下游 | 能否调整返回类型和异常方式 |
| 相关测试 | 已有行为、关键样例、测试组织方式（旧测试也可能有错） |
| 同类实现（经核对） | 项目怎样处理相同问题（错误封装/分层/替身组织） |
| 依赖清单/锁文件/配置 | 可用能力、启用条件、执行环境 |
| 输入/命令/报错/堆栈 | 实际怎样失败、失败在哪步 |

区分构建失败/测试断言失败/环境无法启动——指向不同检查方向。脱敏时替换身份凭据但保留影响判断的结构类型关联。

## 范围控制与逐步补充

先提供入口 + 任务约定 + 必要代码，让 AI 说明能确认什么；参数语义不清→补读类型和调用方；检查失败→补命令和错误。**每次增加材料解决一个具体信息缺口**。暂时无关的内容保留路径、符号和一句核对过的说明。阅读结果被截断要补读——「未出现在当前结果」不说明实现不存在。

## 来源与版本核对

- 代码片段保留文件路径和关键符号；已提交版本记录提交位置；**工作区未提交修改要考虑实际内容**；
- 文档和历史结论提供线索但区分来源：开发者「我怀疑某字段转换错了」= 待验证假设；源码明确执行一次转换 = 可核对事实；
- 需求说明规定期望行为、源码说明当前实现——两者不同可能正是要修的问题；
- 持续修改中 AI 前面读过的代码可能已变，重要修改前核对当前内容。

提示词要求：以当前工作区实际源码核对（注意未提交修改）；区分「源码已确认的事实/我的假设/仍缺少的信息」；材料冲突时指出冲突涉及的行为，不默默选一个版本。
