# AI 编程面试题 8：如何审查 AI 生成的代码，发现看起来合理但实际错误的实现？

## 核心答案

审查目标：**确认这份实际改动怎样改变了系统行为，以及这些改变有没有正确依据**。

1. **从实际 Diff 入手**：对照需求和必须保留的约定，确认改了哪些文件、增删了什么；审查范围含测试、依赖、检查配置（防「总结说精简判断实际删了用户范围限制」）；
2. **转成行为问题**：沿输入/判断/操作/结果读——哪些条件变了、数据从哪来到哪去、影响谁；关键位置补读调用方和依赖，重点查业务边界、权限范围、错误处理、接口兼容；
3. **疑点 → 确认缺陷**：找出具体触发条件，说明预期与实际差别，用源码推导或最小反例核验；先查外围是否已处理该条件，防把局部疑点当缺陷；
4. **测试也要审**：是否真触发目标路径、断言是否依据独立规则、有没有删断言/放宽预期/跳过用例；
5. **AI 辅助但逐条核实**：每条意见带位置/触发条件/违反的规则/预期与实际/证据；按影响处理；修复后重新审查最终差异和相关验证。

## 为什么看着合理却可能错

命名、结构、解释都顺能降低阅读难度，但正确行为要符合具体要求。函数写得简洁也可能把「需要同时成立的条件」变成「二选一」。语法完全合法、正常输入返回合理结果、测试没构造触发条件——构建和测试都能过。

AI 完成说明是摘要，可能只描述新增功能、省略同时删除的逻辑。**人写的代码也有同样问题；AI 产生修改更快，开发者更需要确认每项改动的行为含义**。

## Diff 审查要点

- 看完整文件变化范围：需求只涉查询筛选，实际却调公共类型/依赖版本/测试配置——范围扩大不一定错，但不能因完成说明没提就略过；
- **删除的代码尤其值得核对**：约束、异常处理、状态更新被删后可能没有明显报错——要知道删除前承担什么职责、现在由谁承担；
- 测试和检查配置属于实际改动：预期变化可能是合理需求更新，也可能是配合错误实现；
- Diff 几行上下文未必够：判断的输入可能在前半段经过转换、输出由其他模块使用——展开相关函数、类型、调用关系；
- 对比对应明确版本：审查哪份修改、依据哪个基线、是否含工作区其他变动。

## 行为推导与反例核验

错误实现示例（用户范围被状态分支替代）：

```javascript
function buildOrderFilter(ownerId, status) {
  if (status !== undefined) { return { status }; }   // 丢了 ownerId
  return { ownerId };
}
```

审查问题：「选择状态后，查询条件还保留用户范围吗？」触发条件：选已支付状态 + 存在其他用户同状态订单。反例：订单 101 属用户 7、102 属用户 8 都已支付；用户 7 按已支付筛选应只得 101，错误实现两条都匹配。未选状态或用例只有一个用户时测试都能过——**错误需要特定条件才显现**。

核验路径：读查询依赖——若下层始终补用户范围、或该函数仅用于管理入口，局部片段不足以证明越权。核对入口身份、实际查询条件、执行路径；能静态确认的给静态依据，依赖运行配置的要复现。修复方向：用户范围始终保留、状态追加叠加，并验证选择/未选择两种路径 + 多用户数据。

## 测试全绿时的审查

- 测试数据只有一个用户 → 无法区分「按用户+状态」和「只按状态」；用例名写权限校验也没建立能发现错误的条件；
- 断言只查返回数据状态对 → 错误实现仍满足；要同时观察结果归属范围；
- 测试自己调用过滤函数算预期 → 测试和实现一起接受错误；
- 替身返回预准备的本人订单 → 代码没传用户条件也得正确数据；查替身是否观察实际输入、是否需要真实查询路径补充验证。

## AI 审查意见的组织

给 AI 明确规则 + 实际差异，让它对照证据审查（防只复述生成时的解释）。每条意见：位置、触发条件、违反的规则、预期与实际结果、证据；缺依据的推断列待确认项；纯风格偏好单独列出不当功能缺陷。

```
请审查本次订单查询增加状态筛选的实际代码差异。
已确认要求：普通用户的查询始终限制在本人订单，状态作为附加条件。
先核对修改基线与完整文件列表，阅读新增、删除、测试和配置变化。
沿状态参数、用户身份与查询条件补读调用方和依赖。
本轮不修改业务实现；每个问题说明位置、触发条件、违反的规则、预期与实际、证据。
```

处理顺序按影响：数据范围扩大、结果错误、接口破坏优先；命名偏好作建议。**意见数量多 ≠ 审查质量高**。换模型增加视角，但多个模型可能继承同一份错误需求或都没读实际依赖；AI 没提出问题也不能替代对关键规则和实际改动的核验。

## 修复后确认关闭

修复围绕违反的规则（恢复用户范围+状态组合），不能通过禁掉功能或让测试只查状态绕过去。补能区分错误实现的回归用例（多用户同状态数据），核对最终查询执行真采用两项条件（不只对象里多了字段）。修复后重看实际差异确认无额外改动，用最终版本重新核对原触发条件。审查结论保留范围：已核对过滤逻辑/已验证真实接口/尚未覆盖某配置——记录清楚才能判断能否交付。
