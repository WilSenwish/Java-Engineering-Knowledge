# AI 编程面试题 12：Coding Agent 如何避免被过期的代码描述误导？

## 核心答案

代码描述（函数摘要/目录说明）是**派生信息**：帮 Agent 找相关实现，**关键判断仍回源码核验**。

1. **可维护的描述带来源**：仓库、文件路径、符号位置、源码版本（提交号）+ **内容指纹**（生成时输入内容的 Hash）；
2. **过期判断看输入变化不看日期**：昨天生成的描述可能已失效，一年前的可能仍适用；
3. **影响范围含依赖**：被调用函数改了，调用方的职责说明也失效（调用方文件没改）——记录「这条解释依据了哪些内容」（被调函数/类型/配置/路由注册），变更时反向查找受影响描述，**上层摘要跟着更新**；
4. **更新先失效后重建**：受影响描述标为待更新、检索屏蔽旧正文；新描述生成后确认对应输入没再变化（防迟到任务覆盖新结果）；
5. **检索与读取对齐目标版本**：提交号不代表工作区（未提交修改实际代码已变）；
6. **Agent 用描述后要核验**：摘要声称负责权限检查 → 读关键条件和调用位置；**描述与源码冲突时按源码和执行证据修正，并纠正上下文里已采用的旧结论**。

## 描述为什么会过期

压缩省略细节（「检查权限后保存数据」省略权限条件/异常分支/调用方式）。函数删除重命名容易暴露；**函数名路径都没变、职责已改最难发现**——旧描述仍把 Agent 带到真实文件，解释的却是过去的行为。**部分正确的描述反而更危险**（模块负责保存数据对，但「保存前做权限检查」的职责已迁走）。

## 来源与指纹设计

| 要素 | 作用 |
|------|------|
| 仓库 + 路径 + 符号 | 从摘要回到具体实现（行号会因增删漂移，不能只靠行号） |
| 源码版本（提交号） | 基于哪份快照（分支名不够，同一分支不断产生新提交） |
| 工作区检查 | 提交号相同 ≠ 实际代码没变（未提交修改） |
| 内容指纹（Hash） | 判断实际输入有没有变化；**指纹范围 = 生成器读取的全部输入**（只给函数主体算指纹，配置改了仍认为一致） |

新提交 ≠ 所有描述重写：输入没变的检查后复用。**「失效」指不能继续解释当前目标版本**，历史描述不必删除。

## 依赖传播与更新时序

`submit()` 描述「只允许管理员提交」，依赖 `checkPermission()`；后者改成允许普通用户，`submit()` 函数体没变但描述失效。依赖 = 「这条解释依据了哪些内容」，与调用关系有关但不同（文件摘要依赖多个函数、目录摘要依赖成员，没有函数调用也要在输入变化时检查）。

更新时序三关：

1. **先失效**：发现源码变化 → 受影响描述标待更新、检索屏蔽旧正文（否则空档期 Agent 仍按旧解释推理）；
2. **对齐版本生成**：按目标版本取输入生成；A 任务读版本 A 开始生成、期间代码变 B，A 的结果不能覆盖 B 的当前描述（带来源标识写入 + 版本条件控制）；
3. **正文/索引/来源一起更新**：只更新正文，检索缓存仍返回旧内容 = 没完成更新。

事件通知会漏 → 定期或查询时比对指纹补查。**更新期间允许 Agent 直接读源码**，不为等摘要继续依赖旧正文。

## 使用侧核验

- 版本匹配解决「来源一致」，**描述本身是否准确是另一项检查**（生成器可能漏看分支把「部分请求需要校验」写成「所有」）；
- 摘要声称某功能没启用 → 核对注册与配置，不凭一句话决定修改；
- **Agent 上下文里的旧结论不会因检索端停用而自动撤回**——前几轮读过的旧描述可能已写进计划/任务摘要；发现失效要把受影响旧结论标为不再适用、补最新源码依据、重查依赖它的计划。
