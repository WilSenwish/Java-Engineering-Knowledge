# AI 编程面试题 7：如何保证 AI 生成代码的质量？

## 核心答案

判断能不能交付看三点：**是否符合需求、是否破坏已有行为、能否安全接入项目**。代码能运行只是基础；模型的解释和自我审查不能代替实际验证。

1. **生成前**：明确输入输出、边界条件、不允许改变的行为（验收契约），提供相关源码、真实接口、项目约束，修改集中在必要范围；
2. **生成后**：构建/类型/静态检查 → 测试验证业务行为和真实调用链 → 已有测试相关回归；
3. **测试预期必须有独立的需求依据**（测试 Oracle），不能照着生成实现反推——否则实现和测试一起错；
4. **审查实际 Diff**：业务规则、权限边界、修改范围（含测试和检查配置——防删断言/跳过用例让结果变绿）；
5. **修复**：按规则修，不靠删断言跳过检查改绿；修后重新验证受影响部分；交付判断依据最终代码的检查结果，说明还有哪些重要条件没验证。

## 能运行为什么不够

程序语言只规定代码怎样表达执行，不知道业务希望它做什么。规则「数值至少 100」：`value >= 100` 和 `value > 100` 都合法，区别只在边界值。质量也不只看新增行为——改了错误码/返回格式/权限规则，已有调用方仍可能出问题。可维护性：为简单判断引入复杂框架、复制项目已有逻辑，增加后续成本。

**AI 可提出方案和待确认问题，标准来自需求、接口约定和项目规则**——不能因为模型生成了某种行为就反过来把它当需求。

## 测试预期不能跟着实现走

测试比较实际与预期，相等只说明两者一致。模型把 `>= 100` 写成 `> 100`，又按实现给 100 写出「应该拒绝」的预期，测试通过——验证的是错误实现与错误预期相互一致。更明显：测试再次调用待测函数算预期，实际值和预期值来自同一段逻辑，错了也可能相等。

**Oracle（判断正确结果的依据）不一定是另一个程序**：可以是人工确认的样例、接口规范、经审查的参考模型。重点是预期有需求依据。AI 可按确认规则生成测试、开发者核对关键预期；换模型审查增加视角，但两个模型继承同一份错误规则仍可能一致认可。

还要看测试观察了什么：只检查「没抛异常」验证不了数据正确保存；只检查「方法被调用」不证明最终状态对。断言要对应验收契约的结果。

## 不同检查各自发现什么

| 检查 | 能发现 | 不能发现 |
|------|--------|---------|
| 构建/类型/静态 | 语法、类型不匹配、接口引用错误、部分空值/危险调用 | 项目特有业务规则 |
| 单元测试 | 局部输入输出、边界分支，失败定位集中 | 调用方传错数据（毫秒/秒都整数类型查不出） |
| 集成验证 | 真实传递路径的协作问题、替身不具备的事务/约束/网络行为 | （覆盖范围外的问题） |
| 回归测试 | 修改是否破坏原有行为 | 需区分原有失败与本次引入，不能用原有失败掩盖新问题 |

验证强度围绕改动风险：改权限条件验允许/拒绝边界；改带状态重试查重复执行和失败后状态。**依据是这次可能改变什么行为，不是罗列工具**。

## 检查通过后还要审 Diff

测试在有限条件下运行，未构造路径可能仍有问题。Diff 直接看到新增/删除/修改——模型完成说明可能漏掉修改（说「精简了判断」实际删了用户范围限制）。**审查对象是实际差异**，按需补读周围调用与数据关系。

重点查测试和检查配置本身：删断言、放宽预期、跳过失败用例——检查调整可有合理原因，但要独立说明原标准为何不适用，不能只因新实现过不去。信任边界：代码能读一条记录≠当前用户有权读；参数格式正确≠资源属于该用户。可维护性：是否重复已有逻辑、异常是否按项目约定。

## 修复完成标准

保留失败条件/实际结果/预期依据 → 区分原因（实现违反规则改实现；测试预期错按独立规则修；环境不可用恢复环境或说明未完成）→ 修后重跑相关检查 + 按影响范围回归 → **验证结果必须对应最终交付代码**（通过后又改逻辑，先前结果不能证明新版本）。交付说明：实现了哪些规则、经过哪些实际运行的检查、哪些重要条件没验证。
