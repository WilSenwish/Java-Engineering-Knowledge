# AI 编程面试题 10：如何保证 AI 生成的测试用例覆盖关键业务场景？

## 核心答案

**先把业务规则对应到场景，再让 AI 生成测试**，而不是按函数数量分配用例：

1. **场景从规则推导**：输入范围（等价类 + 边界）、业务状态（操作前状态）、权限条件（登录 ≠ 有权访问资源）、流程失败点（第几步失败留什么状态）；重复请求/并发考虑操作顺序；
2. **每条用例有前置状态、执行操作、预期结果**，并确认测试真触发目标条件（重试要模拟失败并检查后续执行）；
3. **预期来自需求/已确认样例/可信参考模型**（Oracle），不照待测实现反推；
4. **生成后对应检查**：规则 ↔ 实际运行的测试 ↔ 断言观察的结果；哪些规则没用例、哪些只有正常路径；
5. **代码覆盖率是补充不是证明**——实现漏了权限检查，测试把现有代码全执行一遍覆盖率仍高（缺失规则没有代码可覆盖）；
6. **对重要规则做错误注入**：副本里故意破坏逻辑，看现有用例能否失败；变异测试辅助核验发现错误的能力。

## 数量与覆盖率为什么都不代表业务覆盖

同一成功请求换十组输入 = 十条相同流程的用例，验证同一项规则。业务动作跨多函数（检查资格→保存→通知），每函数单独测过 ≠ 组合起来中途失败/重复执行/状态变化符合要求。

**覆盖率不知道业务要求是否完整实现**：实现漏一个权限检查 → 没有对应代码 → 覆盖率没这部分可统计。只沿现有代码生成测试，容易把实现中的遗漏一起带进测试集。

## 从规则推导场景的方法

- **等价类划分**：相同处理要求的输入归一类选代表值。范围 1-100：0/1/100/101 边界内外——只用 10/20 中间值发现不了包含边界写成不包含的错误；
- **状态维度**：规则「已取消的任务不能完成」→ 分别测允许完成的状态和已取消状态，操作同、前置不同、预期不同；
- **权限维度**：「已登录」与「有权访问当前资源」是不同要求；只构造登录用户查不出资源归属限制；
- **失败点维度**：第一步失败 vs 第二步成功/第三步失败留下不同状态；**超时 ≠ 操作没完成**（请求可能没生效也可能已生效响应丢失，重试分别按规则验证）；
- **并发维度**：一次正确 ≠ 重复一次正确；串行正确 ≠ 交错正确——用同步屏障/测试钩子控制时序，**睡一会儿再查靠运气**。

优先覆盖：改变业务决策、造成越权或错误状态的条件、已发生过的故障。彼此独立不改变结果的输入变化减少重复。

## 触发与断言的有效性

- 前置条件隔离重置，**不依赖另一条用例碰巧留下的数据**；
- 替身制造的故障要落在目标步骤（别被前面输入校验拦截导致目标逻辑没执行）；
- **替身 ≠ 真实组件**：替身返回失败不自动模拟「事务已提交响应丢失」——要安排对应状态或集成验证；
- 断言观察规则要求的结果：检查返回成功 ≠ 数据已保存；检查写入方法被调用 ≠ 最终状态正确；
- **拒绝类场景查副作用**：无权限不得修改 → 还要查原有数据没变、没有不允许的后续动作（「虽然拒绝了但已改数据」靠错误响应查不出）。

## 覆盖缺口排查

规则-条件-用例-断言对应表 + 覆盖报告（未执行行/分支提示场景没触发或范围遗漏）+ **错误注入**（故意放宽边界/移除权限判断/跳过状态更新，看用例是否失败）+ 变异测试（等价变异不违反验证范围内的规则，仍通过不一定代表缺口）。需求变化或新故障时更新规则、预期与回归测试。
