# Loop Engineering 是什么？AI 编程从 Prompt 到 Loop 的范式转变

## 核心答案

**Loop Engineering = 把「亲自给 agent 写 prompt 的那个你」替换掉，转而去设计那个代替你做这件事的系统。**（Addy Osmani 定义）loop 可以理解为一个**递归式的目标**：你定义一个目的，AI 持续迭代，直到完成。你不再是 prompt 的作者，你是 prompt 生产系统的设计师。

## 概念背景：三个人在同一周说了同一件事

- **Peter Steinberger**（OpenClaw 作者，6 月 7 日推文，800 多万浏览）：「你不该再给 coding agent 打 prompt 了。你该去设计那个给 agent 打 prompt 的 loop。」
- **Addy Osmani**（Google Cloud AI 总监）：长文给出正式定义（见核心答案）
- **Boris Cherny**（Claude Code 创始人）：「我已经不 prompt Claude 了。是 loop 在运行着 prompt Claude、决定做什么。我的工作是写 loop。」

一个造工具的、一个定方法论的、一个每天泡在一线的产品创始人，同一周共振——值得认真看。

## Q1：四个 engineering，到底都在 engineering 什么？

每个新词的出现背后都是同一件事：**上一个瓶颈被解决了，新的瓶颈暴露出来了**。把这条线从头捋一遍，四个词一下就清楚：

| 阶段 | 时间 | 瓶颈 | 本质类比 |
|---|---|---|---|
| Prompt Engineering | 2023 起 | 「怎么说」 | 跟一个聪明但一根筋的**实习生说话**的技巧 |
| Context Engineering | 2025 | 「喂什么」 | 给实习生准备一桌**整理好的资料** |
| Harness Engineering | 2026 初 | 「环境跟不上」 | agent 的**驾驶舱**（工具/权限边界/沙箱/子 agent/上下文管理） |
| Loop Engineering | 2026 中 | 「人肉驱动」 | 设计**工单系统**，让「下一次回车」不再由你来按 |

关键公式：**Agent = 模型 + harness**。同一个模型，驾驶舱不一样，能力可以差出几倍。

**模型每变强一截，瓶颈就往外移一层**：从你说的那句话 → 你给的那堆材料 → 它干活的环境 → 最后落到你本人身上。整条流水线上唯一还需要人肉驱动的环节，就是你坐在屏幕前敲下一条 prompt。**你睡觉，它就停工。** loop engineering 瞄准的就是这最后一环。

四个词不是营销轮换，**是瓶颈迁移的路标**。

## Q2：Loop Engineering 到底是什么？

过去两年你跟 coding agent 的协作是**回合制**：你写一条 prompt，读它的输出，再写下一条——agent 是工具，你全程握着它，一回合都不能松手。

loop engineering 说：松手吧。你把「发现任务、布置任务、检查结果、决定下一步」这套流程设计成一个能自己运转的循环，让循环去握着 agent。

比喻：以前你是客服热线的接线员，每个电话亲自接亲自答；现在你升级成设计工单系统的人——电话怎么分流、哪类问题转给谁、办结标准是什么、办不了的怎么升级到你。规则定好，系统自己转。

**支点移动**：以前写一条好 prompt，收益是「这一次回答变好」；现在设计一个好 loop，收益是「之后每一次循环都变好」。投入从消耗品变成了资产。但设计 loop 比写 prompt 难得多：要考虑触发、并行、验证、状态、止损——从「说一句话」升级到「设计一套制度」。**杠杆变长了，对握杠杆的人要求也变高了。**

## Q3：一个 loop 由什么组成？

五大件，外加一个记东西的地方。每一件都对应一个「不装它就会翻车」的具体场景：

### 第一件：自动化——loop 的心跳

写个很完美的工作流脚本但每次手动启动，不算 loop，**只是一个你跑过一次的任务**。定时或事件触发（每天早上自动扫 CI 失败、每次 PR 合并自动跑检查）。心跳有了，循环才算活着。

### 第二件：worktree——让并行不变成打架

几个 agent 同时干活会撞上：两个 agent 同时改同一个文件（像两个工程师挤同一台电脑改同一行代码还不打招呼）。解法是 git worktree：每个 agent 独立工作目录和独立分支，共享同一份仓库历史，物理上互不干扰，各开各的 PR。

### 第三件：skill——治好 agent 的「金鱼记忆」

agent 天生缺陷：每个会话都是冷启动，项目规范/约定/坑一概不知，你不得不**像对金鱼一样每个会话把项目重新解释一遍**；更要命的是没解释到的地方它不会空着，**会用一个自信的猜测填上**。skill 把项目知识写成文件放仓库里，该用的时候自己读。对 loop 的意义比对单次会话大得多：没有 skill，loop 每个周期都从零重新推导你的项目；有了 skill，知识是**复利**的。

### 第四件：connector——让 loop 摸到真实世界

只能看见文件系统的 loop，撑死了算半个 loop。真实工作流不止代码：读 issue 工单、查监控、发消息、开 PR。connector（基于 MCP 协议的连接器）是接外部系统的桥。差别：一个 agent 只会告诉你「修复方案在这里」，一个完整的 loop 会**自己开好 PR、关联好工单，等 CI 变绿之后自己去频道里通知人**。

### 第五件：sub-agent——写的人和查的人必须分开

五大件里最有用的结构性设计：**把写代码的 agent 和检查代码的 agent 分开**。理由一句话：**写代码的那个模型，给自己的作业打分时，实在太手下留情了。** 让 A 出方案，让一个干净上下文的 B 来挑刺——B 没有「希望自己是对的」的包袱，挑出来的才是真问题。

### 第六件：记忆——loop 的命根子

模型在两次运行之间会忘掉一切：今天循环干了什么、哪些做完了、哪些卡住了，明天一概不知道。解法朴素到意外：**把记忆放在磁盘上，而不是上下文里**。一个 markdown 文件、一个任务看板，只要它活在单次对话之外，记录着「做完了什么、下一步是什么」。Osmani 的妙总结：

> **agent 会忘，但 repo 不会。**

**五大件让 loop 转得起来，磁盘上的记忆让它第二天还接得上。**

## Q4：拼起来之后，一个真实的 loop 长什么样？

Osmani 自己在用的「晨间 triage loop」——每天早上自动把项目里值得修的问题找出来、修好、提交审核：

1. 每天早晨自动化准时触发，调用负责分诊的 skill
2. skill 读昨天的 CI 失败记录、没关闭的 issue、最近的提交，把「哪些问题值得处理」写进状态文件
3. 对每个值得做的问题，开隔离的 worktree，派一个 sub-agent 进去起草修复
4. 第二个 sub-agent 对照项目 skill 规范和现有测试，把草稿审一遍
5. 审过了，connector 自动开 PR、更新对应工单
6. loop 搞不定的问题，不硬来，丢进待办收件箱等真人来看
7. 所有经过写回状态文件，明天早上的循环从今天停下的地方继续

**整个过程里你只设计了一次，中间任何一步都没写过 prompt。** 你的活从「每一步都出现」变成「只在两个地方出现」：设计循环的时候，和收件箱里有东西的时候。

> **一个好 loop 的标志：你只在设计时出现一次，之后只在收件箱前出现。**

## Q5：工具已经追上来了，现在就能搭

关键时间差：一年前搭 loop 意味着写一堆只有自己看得懂还要永远自己维护的 bash 脚本；现在五大件全部内置在主流产品里。

| 部件在 loop 里的职责 | Codex | Claude Code |
|---|---|---|
| 自动化（定时发现和分诊） | Automations 面板 + 分诊收件箱 | 计划任务、`/loop`、hooks |
| worktree（隔离并行任务） | 每个线程内置 worktree | `git worktree`、隔离配置 |
| skill（固化项目知识） | Agent Skills | Agent Skills |
| connector（连接外部工具） | 基于 MCP 的 Connectors | MCP servers |
| sub-agent（分头干活、写查分离） | 配置文件定义子 agent | 子 agent、agent teams |
| 记忆（追踪进度） | markdown 或接工单系统 | markdown 或接工单系统 |

两家还都有一个 `/goal` 类能力，和普通定时循环的区别很微妙但重要：普通循环是**按节奏重复跑**（每小时一次，跑完就完了，对不对另说）；`/goal` 是**跑到你写的条件为真才停**（如「目录下所有测试通过且 lint 干净」），且每一轮结束后由**独立的模型**判断条件是否达成——「写的人和查的人分开」这次用在了停止条件上，**连「我做完了」这句话，都不让干活的那个 agent 自己说**。

### 实操：30 秒搭出你的第一个 loop

场景：提了 PR 等 CI，挂了切回去看日志、改、推送、再等，一下午切八次窗口。Claude Code 里一条命令交出去：

```
/loop 10m 检查当前分支 PR 的 CI 状态：有失败的检查就读日志、修复、推送；
全部变绿后停下来，给我一句话总结改了什么
```

拆开看麻雀虽小五脏俱全：`10m` 是**心跳**（每 10 分钟自动醒来跑一轮，不用按回车）；中间段是**任务**；最后一句是**停止条件加汇报**。还有个更省心的玩法：省掉间隔直接 `/loop` 加任务，节奏由模型自己定（按「CI 一般跑多久」决定多久看一次）。

两个使用边界：① `/loop` 活在当前会话里，适合「今天盯着这件事」的轮询，关掉电脑就停；要睡觉时也在跑，用计划任务或云端 routines；② 最小 loop 只有心跳、任务、停止条件，没有 worktree 和写查分离——**这不是缺陷，是起点：部件是一件一件长出来的，不是一天配齐的**（不放心它自己改代码→加检查 sub-agent；想同时盯三个 PR→上 worktree）。

更大的事：两家产品部件几乎一一对应，**loop 的设计正在变得工具无关**——部件是同样的部件，差的只是商标。「选 Codex 还是 Claude Code」这种争论的重要性在下降；**值得积累的是图纸，不是对某家工具的肌肉记忆**。

## Q6：三盆冷水：loop 越好用，这三个问题越尖锐

泼得最狠的恰恰是给概念定名的 Osmani 本人：「现在还早，我是持怀疑态度的。」核心一句话：**loop 改变了工作，但没有把你从工作中删除。**

### 第一盆：验证仍然归你

无人值守运行的 loop，也是一个无人值守犯错的 loop——你睡觉时它在干活，也意味着你睡觉时它在犯错。就算配了负责检查的 sub-agent：**检查 agent 嘴里的「done」，只是一个声明，不是一个证明**。它说没问题，和真的没问题，中间还隔着你的眼睛。

### 第二盆：理解债，越顺滑涨得越快

loop 交付你没写过的代码越快，「仓库里实际存在的东西」和「你脑子里真正理解的东西」之间鸿沟越大。专门名字：**理解债（Comprehension Debt）**。和技术债不一样：技术债是代码烂，理解债是代码可能不烂，**但你不知道它为什么是对的**。出问题那天，你面对的是一片自己「拥有」但不「理解」的代码。顺滑的 loop 不会帮你还这笔债，只会让它涨得更快，除非你坚持去读 loop 产出的东西。

### 第三盆：认知投降，最舒服的姿势最危险

loop 自己转起来后有个特别舒服的姿势：不再对产出有自己的观点，它给什么就收什么。专门名字：**认知投降（Cognitive Surrender）**。Osmani 原话：

> 带着判断力去设计 loop，它是解药；为了逃避思考去设计 loop，它是助燃剂。同一个动作，相反的结果。

还有一笔现实的账：token 成本。loop 按循环烧 token，sub-agent 每多一个就多一份模型和工具开销。务实的花法是把 sub-agent 用在「值得买第二意见」的地方，而不是处处双保险。

**三盆冷水共同点：都不是 loop 的 bug，而是 loop 的代价，并且由你来付。**

## 总结三句话

1. 从 prompt 到 context 到 harness 再到 loop，四个词是一场瓶颈迁移：模型越强，瓶颈越往外移，最后移到了「亲自按回车的你」身上
2. 一个 loop = 五大件 + 一份磁盘记忆：自动化是心跳，worktree 防打架，skill 治金鱼记忆，connector 摸到真实世界，sub-agent 写查分离，状态文件让明天接得上今天
3. loop 把你的杠杆变长了，但验证、理解债、认知投降这三笔账也同时变大了，工具分不出你是在加速还是在逃避，你自己分得出

> 「两个人可以搭一模一样的 loop，得到完全相反的结果。一个用它在自己深刻理解的工作上加速，另一个用它彻底逃避理解工作。loop 分不出区别，你分得出。」——Addy Osmani
