# RAG 面试题 20：在实际落地中，你觉得 RAG 最难的地方是哪里？

> **抓取日期**：2026-10-20
> **所属知识域**：域6 性能优化与架构演进（AI 前沿）
> **板块**：RAG 面试题（23 题）· 工程实践

## 核心答案

最难的不是跑起来（Demo 一两天），是调好（生产质量要几周甚至几个月迭代）。三大难：① **文档预处理**（地基型瓶颈——进去的是垃圾出来的也是垃圾）；② **检索质量调优**（系统天花板，但问题来源多：Chunking/语义鸿沟/精确词召回交织，排查费劲）；③ **效果评估**（答案对不对难系统衡量，没指标体系优化就是瞎猜）。每个环节都可能是瓶颈且环环相扣，没有捷径。

## 第一难：文档预处理

现实文档格式五花八门。**PDF 解析**：pypdf 这类通用库定位不是复杂排版，遇表格/双栏/嵌套会把顺序搞乱——三列规格表（型号/内存/价格）解析成「型号内存价格iPhone 158GB5999」行列关系全没。这不是 pypdf「不行」是工具属性，表格和复杂版面该交给 pdfplumber/unstructured，高价值文档（合同/财报/专利）可用 GPT-4o Vision 理解 PDF 截图——代价比普通 Embedding 高几十到上百倍（按 token 单价），只适合单价高、复杂、数量可控的文档。还有扫描版（OCR）、多图片文档（图里关键信息文本提取不到）、代码文档（切割不当破坏逻辑）。**生产系统文档预处理代码量往往比 RAG 核心逻辑还多**。

## 第二难：检索质量调优

三个排查点交织：① **Chunking 策略**——用户问「退款流程」但文档按产品分类组织，相关内容切散在十几个 chunk，每个单独看相关度都不高；② **语义鸿沟**——用户口语「这个功能怎么用不了」vs 文档「系统故障排查指南」，向量相似度低；解法 Query 改写，或**入库时为每个 chunk 生成几个可能的提问形式一起存**（假设性问题增强）；③ **精确词召回差**——「Pro Max 256GB」、专有名词、缩写，纯向量往往不如 BM25，生产必须混合检索。

## 第三难：效果评估

人工判断成本高且标准不一；端到端指标（满意度/解决率）反馈周期长，出问题不知道是 Chunking 的锅、检索的锅还是 LLM 的锅。实用做法拆两层：检索层 Hit@K（自动化批量跑，快速定位检索是否瓶颈）→ 生成层 RAGAs 三维（Faithfulness 防瞎编/Answer Relevancy 防答非所问/Context Recall 看覆盖），结合定位检索层问题还是生成层问题。
