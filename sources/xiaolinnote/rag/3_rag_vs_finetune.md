# RAG 面试题 3：相比直接微调 LLM，RAG 解决了什么问题？微调和 RAG 各自的优劣势是什么？

## 核心答案

两者解决的不是同一层面的问题，**不是谁替代谁**。微调把知识烧进参数，适合改变行为风格、培养深度专业能力；RAG 推理时实时检索注入，适合知识频繁更新、需要溯源的场景。知识库问答首选 RAG（成本低可随时更新）；定制输出格式/行业语气微调更合适。**实际工程最常见的是组合：先微调再套 RAG**。

## 微调：把知识直接烧进模型

**优势**：效果彻底，模型从内部改变——专业词汇、输出格式、回答风格都能深度定制；推理无额外检索步骤，延迟低。

**痛点**：
1. 成本高：标注数据 + GPU + 训练周期；
2. 更新难：业务数据每周变，不可能每周重训（每次几小时到几天）；
3. 不透明：回答来自参数，不知道从哪条知识推出，出错难定位——**模型只是记住了训练数据里的模式，记住了什么、记错了什么无从得知**。

## RAG：不改参数，推理时现查

**优势**：知识库更新即加文档，无需重训；答案附来源 chunk，出错立刻知道哪条知识有问题；成本低（OpenAI Embedding + Chroma 小团队就能跑）。

**短板**：
1. 多一步检索，延迟增加几百毫秒到一秒；
2. **检索质量上限**：相关 chunk 没召回，LLM 再强也答不出。**生成层只是复述整理检索内容，上限被检索层卡死**——RAG 调优主战场永远是检索层，不是换更强 LLM（一上来就换更贵模型往往南辕北辙）；
3. 对复杂推理能力提升有限——需要领域深度推理仍得微调。

## 组合：微调解决「怎么说」，RAG 解决「说什么」

| 维度 | 微调 | RAG |
|------|------|-----|
| 知识更新 | 需重训，成本高 | 更新知识库即生效 |
| 推理延迟 | 低 | 较高（多一次检索） |
| 实现成本 | 高（GPU+标注） | 低（向量库+Embedding） |
| 可溯源 | 不支持 | 支持，追溯到 chunk |
| 适合场景 | 定制输出风格、深度专业能力 | 私有知识问答、动态数据 |
| 知识上限 | 训练数据质量和规模 | 检索质量和 context 长度 |

面试禁忌：二选一思维。
