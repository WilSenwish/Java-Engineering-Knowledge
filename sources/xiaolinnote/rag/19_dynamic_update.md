# RAG 面试题 19：RAG 知识库如何实现动态与持续更新？

## 核心答案

核心挑战：文档和向量库是**一对多**（一篇切几十上百 chunk），不能像数据库 UPDATE 一条记录那样局部更新。最可靠逻辑是**「先删后增」**：文档变更时先删掉旧文档对应所有 chunk，再按新内容重新切割入库。变更检测用**内容 hash**（MD5/SHA256，改一个标点 hash 都不同，漏不了）。生产推荐组合：**事件驱动 + hash 检测 + 先删后增**。

## 三种操作

- **新增**：完整走「切割→Embedding→写入」，无历史包袱；
- **修改**：**永远先删旧 chunk 再重新入库，不要尝试「局部更新」**——文档一改切割边界全变（原来第 3 个 chunk 的内容可能分散到第 3、4 个），旧新 chunk 没法一一对应，像拆墙重建不能指望原插座位置还对得上；
- **删除**：清除所有 chunk，不留「僵尸 chunk」否则用户还检索得到失效内容。

## 变更检测：内容 hash

入库时算文档内容 hash，与文档 ID、chunk ID 列表一起存（Redis/数据库）。检测到文档时重算对比：同则跳过，异则触发重处理。优化：先用「最后修改时间」轻量字段粗筛，只对时间戳变化的算 hash——上百万篇每晚真正改的几千篇，过滤 99%，开销降一个量级。

## chunk ID 设计

一开始就要设计好文档-chunk 关联，否则更新时很痛苦。两种方式：① chunk ID 带文档 ID 前缀（`product_manual_v3_chunk_001`）按前缀批量查找删除；② chunk metadata 存 `source_doc_id` 字段，向量库按 metadata 过滤批量删除。

## 两种变更感知

| 方案 | 延迟 | 复杂度 | 适用 |
|------|------|--------|------|
| 定时轮询 | 分钟-小时级 | 低，不依赖外部系统 | 内部知识库、产品文档（一周改几次） |
| 事件驱动（Kafka/Webhook） | 秒级 | 中高，需数据源支持发消息 | 客服知识库（运营改退款政策要求立刻生效）、新闻资讯 |

Confluence/Notion/语雀支持 Webhook，文档保存自动推 HTTP 请求，天然适合事件驱动，不用引入消息队列这么重的组件。

## 全量重建与灰度

全量重建只在两种情况下用：知识库极小（几十篇几分钟搞定）；或重大架构调整（换 Embedding 模型/改 Chunking 策略，新旧向量不兼容必须重建）。平时不推荐——消耗大量时间和 API 费用，重建期间服务不可用。

**灰度更新（类蓝绿部署）**：新版本 chunk 打 `version=new`，旧版保留 `version=old`；测试问题同时跑新旧两版对比质量；通过后检索版本过滤从 old 切 new，最后清理旧版。**出问题秒级回滚**（切回过滤条件），不需重新入库——金融医疗等高要求场景必要。
