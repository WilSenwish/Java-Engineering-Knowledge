## 核心答案

问题本质：语义被拆散后，**每一半都不够强，检索时全军覆没**（不是信息丢了，是信息拆散后两段相关度都不高）。两个方向：① 切的时候别截断（重叠切割/语义边界切割）；② 切完之后补上下文（句子窗口检索/父子切割/命题化切割/Contextual Retrieval）。工程上组合使用：重叠做兜底，语义边界保质量，高要求场景加父子或 Contextual Retrieval。

## 六种方案

| 方案 | 核心思路 | 适合 | 代价 |
|------|---------|------|------|
| 重叠切割 | 相邻 chunk 重叠 10%~20% | 所有场景，基础兜底 | 存储轻微增加 |
| 语义边界切割 | 在句子/段落边界切（spacy/nltk 识别句界，句子为单位填充） | 段落结构清晰的文档 | 需 NLP 工具 |
| 句子窗口检索 | 存储按单句向量化（细粒度精准检索），命中后返回前后各 N 句窗口 | 追求高召回精度 | 存储量大（记录数=句子总数） |
| 父子切割 | 小块检索、大块返回（ID 关联，提前存好父子关系） | 通用，效果均衡 | 存储翻倍、索引复杂 |
| 命题化切割 | LLM 把文档分解成独立自包含命题 | 高质量要求的重要知识库 | LLM 调用成本高 |
| Contextual Retrieval | 向量化前为每个 chunk 补背景说明 | 文档语境强、chunk 孤立感严重 | LLM 成本（Prompt Caching 可降 80-90%） |

**重叠不是万能药**：只能保证跨边界文字不丢失，解决不了「一个完整语义被拆散」。太大（40%）重复内容干扰 LLM 阅读；太小（5%）保护效果弱。

## 命题化切割示例

原文「企业用户享有优先客服通道，响应时间不超过 2 小时，并可申请专属技术顾问服务」→ 三条独立命题：「企业用户享有优先客服通道。」「企业用户的客服响应时间不超过 2 小时。」「企业用户可以申请专属技术顾问服务。」每条单独拿出来就能看懂，语义密度最高。

## Contextual Retrieval（Anthropic 2024）

两步：① LLM 看着整篇文档为每个 chunk 生成 1~2 句背景说明；② Context 前置拼 chunk，整体做 Embedding + BM25 索引。

示例：chunk「此条款自 2024 年 1 月 1 日起生效，适用于所有企业版订阅用户」+ Context「这段内容说明了企业用户专属客服和技术顾问服务条款的生效日期和适用范围」→ 向量里包含「企业用户」「客服条款」「生效日期」关键语义。

**成本控制靠 Prompt Caching**：完整文档是所有 chunk 请求的相同前缀——首次写入缓存按 1.25 倍计费，后续命中按 10% 计费。100 chunk 的文档，文档部分成本降到原来 10%~20%；8k token 文档 + 800 token chunk，百万文档 token 上下文化总成本约 1 美元出头。

**效果**：结合 BM25 混合检索，检索失败率（Top-20 未命中目标 chunk）降低约 49%。
