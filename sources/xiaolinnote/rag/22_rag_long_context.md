# RAG 面试题 22：上下文窗口很大时为什么还需要 RAG？

## 核心答案

**窗口决定「能读多少」，RAG 决定「该读哪些」——容量 ≠ 有效利用**。装得下全部资料，不代表每份都相关、都有效，也不代表模型能把分散的条件全部用对。RAG 的四重独立价值：① 生成前检索整理材料，减少无关输入；② 版本/权限/适用范围可控（全文输入也可以做，但 RAG 提供按问题取有效子集的机制）；③ 不必每次处理整个资料库，成本随问题缩小（30 万 token 库问题只相关 5 千 token）；④ 外部资料更新改内容+索引即生效，不用重训模型。

## 为什么材料多 ≠ 证据充分

- 无关内容不因为能放进去就有帮助，反而增加区分负担；重复/不同版本/相近主题让模型混用条件；
- **「中间信息利用不足」**：关键信息放中间比放开头/末尾更难被可靠利用，程度随模型/内容/任务变化，要在实际模型上验证；
- **定位一条信息 ≠ 结合多处信息完成判断**：通用规则「上传上限 20MB」+ 接口 B 特殊规则「5MB」都在上下文里，只找到通用规则或忽略范围关系就答错。RAG 也可能只检索出通用规则漏掉特殊规定——**筛选本身必须考虑证据完整性**。

## 真正的取舍

全文可能把无关和冲突内容一起带进来；检索可能把必要内容提前筛掉。不能仅凭输入长短判断谁更准确。

## 大窗口与 RAG 配合

**检索负责缩小查找范围，长上下文负责范围内完整阅读**：检索命中片段当位置线索 → 读所属完整章节 → 正文引用附件/另一规则时继续补齐，避免只拿孤立文字下结论。但读命中文档全文仍补不回完全没召回的另一份重要资料——检索后要检查当前证据能否回答问题，缺范围/条件/依据继续补查，不能因为有几段文字就认为足够。**对全量总结或检查所有例外的任务，Top-K 少量结果尤其不能代替完整范围**——相关性排名不证明没有遗漏。

## 任务选型

| 任务与资料特点 | 更适合 |
|----------------|--------|
| 少量资料，需通读/总结/整体比较 | 直接长上下文 |
| 大资料库，问题集中在局部事实 | 检索后组织证据 |
| 需跨段条件或文档关系 | 检索定位再扩大阅读范围 |

成本比较要包括资料准备、检索、模型处理与补读，不是只比一次请求 token 数。前缀缓存可减重复处理费用（取决于实现/命中/资料变化）。资料很少只处理一次时，建复杂检索链路未必划算。
