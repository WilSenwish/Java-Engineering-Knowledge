## 核心答案

向量数据库专门存储和检索高维向量，核心能力是 **ANN（近似最近邻搜索）**。与「MySQL 加向量字段」的本质区别：**MySQL 擅长精确匹配（WHERE id=123），向量数据库擅长语义相似（找意思最接近的）**。B-tree 只能处理一维有序索引，对高维「多维度同时考虑距离」基本失效——百万条暴力遍历算一百万次余弦，延迟不可接受。

## 两大索引算法

**HNSW（Hierarchical Navigable Small World）**：多层图结构，查询从最上层稀疏图导航逐层收窄，到底层找最近邻——像地图找餐厅，先全国→省→市→区。召回率高（同延迟下 95%+）、查询快；缺点是建索引内存消耗大，亿级规模内存可能扛不住。Qdrant/Milvus/Chroma 默认 HNSW。

**IVF（Inverted File Index）**：先聚类把相似向量分桶，查询只搜最相关的几个桶——像图书馆分类体系。内存小、适合超大规模；精度略低，需调 nlist（聚类数）/nprobe（搜桶数）。Milvus 超大规模用 IVF 系列。

## 生产级三能力

1. **Metadata 过滤（混合检索）**：先过滤再 ANN——若先 ANN 再过滤，Top-K 大部分不满足条件白白浪费名额；
2. **实时更新**：在线写入增量构建索引，不用停服重建；
3. **向量+BM25 关键词融合**：纯向量对精确词语（产品型号「GPT-4o」、专有名词）效果不好，混合召回更好。

## 选型对比

| 数据库 | 部署 | 适合规模 | 混合检索 | 优势 | 劣势 |
|--------|------|---------|---------|------|------|
| Chroma | 本地/Client-Server/云 | 中小 | 是（BM25/SPLADE） | 零配置上手极快、生态集成好 | 超大规模稳定性待验证 |
| Qdrant | 自托管/云（分布式） | 中大规模（亿级） | 是 | 性能好、API 简洁、Rust | 超大规模需调优 |
| Milvus | 自托管分布式 | 大规模（亿级） | 是 | 可水平扩展、索引类型全 | 部署运维复杂 |
| Pinecone | 全托管云 | 中大规模 | 是 | 无需运维 | 费用高、数据出境问题 |
| pgvector | PostgreSQL 插件 | 中小 | 是（配合全文检索） | 无需新组件、可 JOIN 业务数据 | 性能弱于专用向量库 |

选型三维度：数据规模、部署方式、是否需要混合检索。**常见路径：Chroma 做原型 → 生产切 Qdrant → 超大规模 Milvus**。千万别拿 GitHub Star 数量当选型依据。
