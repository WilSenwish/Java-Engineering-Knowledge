## 核心答案

原始文档必须先切成 chunk 再向量化入库。**每条 chunk 记录三部分：向量（负责「找到」）+ 原始文本（负责「阅读」）+ metadata（负责过滤和溯源）**——向量是索引卡，原文是书页，metadata 是书签。粒度 500~1000 token 是合理起点，但更要按文档类型选策略。

## 为什么不能整篇存

1. 向量模型有输入长度限制（几百到几千 token）；
2. 整篇压缩成一个向量，细节被「平均掉」——问「退款政策」检索回来的却是混着「配送时效」「积分规则」的整篇。

## 存储记录结构

```text
一篇文档 → 向量库多条记录（5000 字文档切 500 字/chunk = 10 条）
每条记录：{ 向量: [0.12, -0.87, ...], 原文: "...", metadata: { 来源文件, 页码, 章节 } }
```

查询流程：问题向量化 → 找相似 chunk → 取原文 → 塞 prompt → LLM 生成。**向量只在「找」时用，LLM 最终读的是原文**。

## 五种切割策略

| 策略 | 适用 | 优点 | 缺点 |
|------|------|------|------|
| 固定大小+重叠 | 纯文本无结构 | 实现简单、大小可控 | 可能在语义中间截断 |
| 语义边界切割 | 段落分明的文章 | 语义完整、召回质量好 | 实现稍复杂、大小不均 |
| 标题层级切割 | Markdown/HTML | 天然语义独立、带结构 metadata | 依赖清晰标题结构 |
| 代码按函数切割 | 代码文件 | 保留逻辑完整性 | 需 AST 解析、限定语言 |
| 父子切割 | 追求高质量 | 检索精准+上下文完整两全 | 存储翻倍、索引复杂 |
| Late Chunking | 各类文档 | chunk 向量保留全文上下文 | 需模型支持长输入 |

**重叠（overlap）= chunk_size 的 10%~20%**（如 800 配 150）——像扫描仪扫跨页内容特意扫两遍边缘，保证跨边界语义至少被一个 chunk 完整覆盖。

**语义边界切割实现**：分隔符优先级列表——先按段落切，太大按句子切，再太大按标点；Markdown/HTML 按标题层级切，metadata 自动带「产品手册 > 退款政策 > 申请流程」。

**代码按函数切**：函数是最小语义完整单元，用 AST 识别边界；**表格整块保留转 Markdown，不能按行截断**（「2 小时」单独看无意义，配列名「响应时间」才清晰）。

**父子切割**：小块（200 token）检索 + 大块（1000 token）返回，ID 关联——用目录卡定位某章某节，读的是完整一章。

**Late Chunking**（Jina AI 2024）：先编码后切分——整篇过长上下文 Embedding 模型一次前向得每 token 向量（注意力已让 token 互相感知），再按边界 mean pooling 成 chunk 向量。chunk 向量天然融入全文语境，跨块代词/背景/对比关系都保留；代价是要求模型支持长窗口（如 8192 token）且保留 token 级中间结果。
