## 核心答案：四组件

**LLM、工具、记忆、规划模块**。类比一家公司：**LLM 是老板**（所有决策经它拍板）、**工具系统是外包执行团队**（说「去搜这个」它们真正干活）、**记忆系统是公司档案室**（信息存档调档）、**规划模块是项目经理**（大目标拆解成任务单）。

## 1. LLM 核心

所有输入（用户指令、工具返回、记忆调出）最终都经 LLM 理解和决策：下一步做什么？继续思考、调工具、还是给出最终答案？

- **System Prompt（系统提示词）**：给老板的「岗位说明书」，定义角色、行为边界、输出格式。如客服 Agent 的「只回答产品相关问题，不确定要说不知道，不要编造」。**实际工程里 System Prompt 调优往往占开发时间相当大一部分**，是能最直接控制 Agent 行为的手段。
- **模型选型三要素**：
  1. **推理能力**：GPT-4o、Claude Sonnet 复杂推理比小模型好但成本高；o1/o3、DeepSeek-R1 等推理模型适合做 Agent 大脑，但延迟更高 token 消耗更大。常见工程做法：**推理强模型做核心决策（规划/关键判断），小模型做简单任务（意图分类/格式提取）**；
  2. **工具调用稳定性**：有些模型 JSON 格式经常出错、参数乱填，生产环境带来大量重试和 token 浪费；
  3. **上下文窗口大小**：复杂任务十几步，每步工具返回都塞上下文，窗口太小后面步骤「看不到」前面。

## 2. 工具系统

Agent 与外部世界交互的唯一入口。LLM 本身不能上网/读文件/执行代码，都靠工具突破。

- **工具定义格式**（OpenAI FC 格式）：name + description + parameters（JSON Schema）。**定义里没有一行执行逻辑，只有「说明书」**；模型决定调哪个、参数填什么，以 JSON 告诉你，你的代码真正执行，结果反馈给模型。
- **工具描述质量直接影响表现**：模型靠 description 判断什么时候该用。description 只写「查询数据」太宽泛（用户问天气也可能去查库）；写成「查询公司内部销售数据库，支持按日期、产品类别筛选」就能精确判断。**工具描述需要反复调优，重要性不亚于 prompt 工程**。
- **MCP 解决工具管理标准化**：基于 JSON-RPC，定义三类能力——**Tools**（会改变外部世界的操作，如发邮件）、**Resources**（只读数据源，如文件内容）、**Prompts**（预定义提示词模板）。三层架构 Host → Client → Server。

## 3. 记忆系统（分层）

- **短期记忆**：context window 里的 messages，存当前任务中间状态。像人的「工作记忆」，容量有限，任务结束清空。
- **长期记忆**：向量数据库，embedding 后存储，语义检索拿回。像「档案室」，容量大可跨天保留，需主动「回忆」。
- 认知科学类比（仅便于理解，工程实现通常都是向量检索 + metadata 过滤）：
  - **语义记忆**：事实性知识（「用户是做金融行业的」「某 API 限流每分钟 60 次」）；
  - **情景记忆**：具体经历（「上次用户问退款问题时查了订单系统，发现订单已过退款期」）；
  - **程序性记忆**：「怎么做事」的经验（「处理退款标准流程：先查订单状态再核实支付方式」）——把方法论沉淀下来，下次类似任务直接套用。
- **工程挑战**：
  - 短期：窗口有限 → 摘要压缩（前面步骤浓缩成关键信息）或滑动窗口（只留最近几步），都会丢信息，「记住够多」vs「不撑爆」是记忆工程最核心设计问题；
  - 长期：**什么该存、什么不该存**——存太多检索噪音干扰决策，存太少失去意义。好做法：**存入前做一轮重要性评估**，只持久化真正有价值的信息；
  - **记忆衰减（Memory Decay）**：给每条记忆加时间权重，越久远权重越低。相关性分数 = 语义相似度 × 时间衰减因子。衰减速度按业务调整（客服场景快，法律合规场景慢）。

## 4. 规划模块

决定 Agent 能否应对复杂任务。「写竞品分析报告」→ 拆解：搜索资料 → 整理数据 → 对比分析 → 撰写报告。

- **推理技术手段**：**CoT**（思维链，「Let's think step by step」，中间推理输出成为下一步输入，给模型更多思考空间）→ **ToT**（思维树，每个推理节点展开多个分支、评估质量选最优继续，创造性/复杂决策场景效果好但成本高）；
- **两种运作模式**：
  1. **先规划后执行（Plan-and-Execute）**：LLM 先输出完整步骤列表再逐步执行。好处：结构清晰、执行前可人工审核；缺点：中间结果与预期不符时原计划可能不合适，需重新调整；
  2. **边执行边规划（ReAct）**：每走一步根据当前结果重新思考下一步。好处：灵活性极高；缺点：每步局部最优容易「走偏」。**实际工程常结合：先粗略计划定大方向，执行中动态微调。**

## Agent 运行伪代码（四组件协作）

```python
def agent_run(user_goal: str):
    plan = llm.plan(user_goal)          # 规划模块：目标拆成步骤列表
    memory = []                          # 短期记忆：每步中间结果
    for step in plan:
        action = llm.decide(
            step=step,
            history=memory,                     # 短期记忆：知道之前做了什么
            long_term=vector_db.search(step)    # 长期记忆：捞出相关历史
        )
        if action.type == "tool_call":
            result = tools.execute(action.tool_name, action.args)  # 工具系统真正执行
            memory.append({"step": step, "result": result})
        elif action.type == "final_answer":
            return action.content
```

核心节奏：**规划 → 决策 → 执行 → 结果存入记忆 → 再决策**，循环往复直到任务完成。LangChain/LlamaIndex/AutoGen 都围绕这四个组件设计，只是封装方式不同。

## 面试翻车点

1. **漏组件**：只说 LLM 和工具，忘了记忆和规划——这两个恰恰是跑复杂任务的关键；
2. **记忆理解太浅**：「记忆就是上下文」不完整——短期在 context window（任务中间状态），长期用向量数据库（跨任务），机制和用途完全不同；
3. **工具分工理解偏差**：模型不执行工具，只输出「调哪个、传什么」的决策，真正执行是你的代码——「决策和执行分离」是易被追问的点。
