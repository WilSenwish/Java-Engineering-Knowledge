# Agent 面试题 6：ReAct、Plan-and-Execute、Reflection 三种范式的核心区别与选型

## 核心答案

三者核心区别在「**决策和执行的关系**」：
- **ReAct**：边想边干，走一步看一步，单步迭代实时调整，灵活度最高；
- **Plan-and-Execute**：先想全再干，先定完整计划再分步执行，适合长流程复杂任务，不容易跑偏；
- **Reflection**：不是独立完整流程，是给前两者加的「检查修正 buff」，提升输出质量。

**选型三维度**：任务复杂度、流程确定性、输出质量要求。口诀：**任务简单用 ReAct，流程长且复杂用 Plan-and-Execute，输出要求高再加 Reflection，别过度工程化。**

## 概念澄清：设计范式 vs 推理模式

- **设计范式**：搭 Agent 的「顶层做事流程框架」，定整个系统从头到尾按什么大逻辑跑（灵活夫妻店 vs 连锁标准流程）；
- **推理模式**：Agent 每步干活时「脑子里具体怎么思考」（CoT 稳扎稳打 / ToT 先想几个方案选最优）；
- 关系：**设计范式是公司的管理制度，推理模式是员工的干活方法**，一一对应。

## 一、ReAct 单步迭代范式

本质：「思考→行动→观察→再思考」循环，走一步看一步，每步行动完全基于上一步结果实时调整，没有提前定死的完整计划。

比喻：外卖骑手接了「把餐送到用户手里」，不提前定死全程，实时决策（先去商家取餐 → 导航去小区 → 用户在 3 号楼走西门更近 → 送达）。

- 与另两者区别：**没有「提前做完整规划」环节**，规划执行混在一起；循环里**没有专门自我检查环节**，只有行动后的结果观察；
- 优势：实现简单、灵活度高、逻辑透明、好排查，新手零门槛；
- 短板：长流程多步骤复杂任务容易跑偏（忘了最初目标、某步陷入无效循环）；
- 适用：流程不固定、复杂度适中的任务（信息搜索、简单问答助手、客服机器人）。

## 二、Plan-and-Execute 规划执行范式

针对 ReAct「长任务跑偏」：**把规划推理和执行推理完全拆开（解耦）**——一个 LLM 负责规划（大目标拆成执行清单），另一个负责执行，最后统一汇总。

比喻：项目经理接「做新产品」不上来写代码，先做完整规划（需求调研 → 原型设计 → 开发 → 测试 → 上线）。

- **隐藏优势：规划执行可用不同模型**。规划对推理要求高 → GPT-4/Claude 强模型；执行每步已很具体 → 便宜小模型（GPT-4o-mini / 7B）就够用。**「强模型规划、弱模型执行」可降总成本 70%~90%**（规划只调一次，执行要调很多次）；
- 优势：整体结构清晰、链路可控、复杂长任务不易跑偏、无依赖步骤可并行；
- 代价：灵活度不如 ReAct（计划外情况易卡住）、实现更复杂（维护两个模块）、token 增加；
- 适用：流程长、复杂度高的任务（竞品分析报告、全流程项目开发、多维度行业调研）。

## 三、Reflection 反思迭代范式

**关键定位：不是独立完整流程，而是叠加在 ReAct 或 Plan-and-Execute 之上的「锦上添花 buff」**——不改变原流程，只加一层「自我检查、自我修正」。

比喻：ReAct 是一道题一道题挨着做不回头看；Plan-and-Execute 是先定好整卷做题顺序和时间分配；Reflection 是做完一道题（或整张卷）回头检查，发现错了马上改。

- 核心循环：**生成 → 评估 → 改进**闭环；
- 优势：输出质量明显提升，幻觉/逻辑错误/细节遗漏减少，严谨性要求高的场景效果明显；
- 代价：至少多一次 LLM 调用，token 和延迟线性增加；无轮次限制易陷「为了改而改」死循环（一般设最多 2~3 轮）；
- 适用：生产环境代码、正式商业报告、法律文书等「出错就出大问题」的场景。

## 进阶机制

**动态 Replan**：解决「计划定死了中途遇意外」。每步执行完后把当前结果 + 剩余计划交回规划模块，判断「原计划还合理吗」，不合理则生成新剩余步骤计划。保留 P&E 结构优势又不因计划僵硬翻车。代价：每步多一次「评估计划」调用。

**Reflexion**：Reflexion 比普通 Reflection 多做一件关键事——**把每次失败原因总结成「经验教训」存进记忆，下次类似任务作为上下文传给 LLM**（错题本机制）。**HumanEval 上 GPT-4 pass@1 从 80% → 91%**。代码生成天然适合（可运行可测试，执行结果是最直接反馈信号）。这种「verbal reinforcement learning（语言强化学习）」让 Agent 不需要梯度更新就能从错误中学习。

## Token 消耗对比（5 步工具调用任务，每步约 2000 token）

| 范式 | 消耗估算 | 说明 |
|------|---------|------|
| ReAct | ~30000 token | 每步带完整历史（2000+4000+6000+8000+10000），线性增长 |
| Plan-and-Execute | ~14500 token | 规划一次 3000 + 每步带结果摘要 1500×5 + 汇总 4000，比 ReAct 低一半多 |
| + Reflection | 再 +30%~100% | 每个反思节点至少多一次调用；反思两轮该步消耗翻三倍 |

**实践建议**：先用 ReAct 快速验证效果，跑通后再根据 token/延迟实际数据决定是否切换 P&E 或叠加 Reflection。不要一上来就选最复杂方案。

## 选型指南

- 任务不复杂、流程不固定、需实时调整 → **ReAct**；
- 任务很长、容易跑偏、需整体结构清晰 → **Plan-and-Execute**；执行中常遇意外 → 加**动态 Replan**；
- 输出要求高、不能出错 → 叠加 **Reflection**；
- 需跨任务积累经验、避免重复犯错 → **Reflexion** 沉淀失败教训；
- **常见混合架构**：规划阶段用 P&E 定全局计划 → 每步执行用 ReAct 循环（单步可能也需多轮工具调用）→ 整体输出做一次 Reflection 检查。三层嵌套在 LangGraph 里实现自然，很多生产级 Agent 这么搭。

**最容易踩的坑**：学了范式就全堆一起（又要规划、又要反思、又要 Replan、又要积累经验），系统又复杂又慢还出怪 bug。工程永远是「够用就好」。

## 面试总结

最关键一步：**先把 Reflection 的定位说清楚（不是独立流程，是叠加在前两者上的质量增强 buff）**——这点很多人搞错。然后按维度对比：ReAct 边想边干灵活但长任务易跑偏；P&E 先规划再执行结构清晰但灵活不足；Reflection 专治输出质量但增成本。追问时可展开动态 Replan 和 Reflexion，补 token 消耗差异。收尾口诀 + 「别过度工程化」。
