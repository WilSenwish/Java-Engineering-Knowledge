# Agent 面试题 19：如何评估一个 Agent 的效果？评测集和指标怎么设计？

## 核心答案

分四层评估：**工具层**（该不该调用、选得对不对、参数和返回处理正不正确）→ **单步与轨迹层**（每步决策是否合理，漏步骤/重复调用/越权/绕流程）→ **端到端层**（任务最终是否完成，外部环境状态是否达标）→ **线上层**（真实业务成功率、接管率、延迟、Token、成本、安全事件）。

评测集来自真实用户请求、历史 Badcase、边界场景和对抗样本；**每条样本不只保存问题和参考答案，还保存目标状态、允许/禁止的动作、关键检查点和评分规则**。多条正确路径的任务不强行要求轨迹逐步一致。

评分：**确定性检查放最前面**（能用 Schema、数据库状态、单元测试、权限规则判断的不用大模型猜），开放式质量再交人工和 LLM-as-a-Judge（用人工样本校准裁判，防位置/篇幅/自我偏好偏差）。**安全和关键业务约束设成发布硬门禁**，其余指标按核心任务和场景切片与基线比较。上线后 Trace + 用户反馈 + 业务结果发现 Badcase → 回流离线集 → 持续回归闭环。

## 为什么只看最终答案会被骗

Agent 比普通问答多了一条执行链（理解目标 → 选工具 → 填参数 → 读结果 → 决定继续或停止），每步都可能把后面带偏。退款 Agent 回复「退款已经完成」至少三种可能：真的按规则完成；没调接口只是编了一句成功；完成了但没先核验身份。**三种输出文字可以很像，但产品结果和风险完全不同。**

最可信的任务成功信号是**可验证的外部结果**——订单状态真的变成已退款、日历里真的出现目标日程、代码真的通过测试，而不是 Agent 自己声称完成。

## 四层评测

| 层级 | 核心问题 | 常用指标 |
|------|---------|---------|
| **工具层** | 单个工具和调用参数可靠吗 | 工具选择准确率、参数 Schema 通过率、参数语义正确率、工具执行成功率、重试后成功率、幂等检查通过率 |
| **单步与轨迹层** | 决策过程合理吗 | 必需步骤覆盖率、禁止动作触发率、重复调用率、轨迹冗余、约束遵循率、总步数/无效调用/Token/时间 |
| **端到端任务层** | 事情真的做成了吗 | 任务完成率、阶段目标完成度、结果正确性、多次运行稳定性（pass^k） |
| **线上业务层** | 用户和业务真的受益吗 | 解决率、人工接管率、用户主动纠正/撤销率、延迟分位、每次成功任务成本、安全事件率 |

**要点**：
- 工具层：**Schema 合法只代表格式能解析，不代表业务含义正确**——选中 `refund_order` 但订单号填错仍是失败调用；有副作用工具要测幂等（同一支付请求重试两次不能真扣两次）；
- 轨迹层：**不能给所有任务准备「标准轨迹」逐步完全匹配**——Agent 往往有多条合理路径。定义三类约束：哪些步骤必须出现、哪些禁止出现、哪些有先后依赖，剩下的允许 Agent 自己选。效率在成功且合规的前提下比较（多一步验证可能换来更高安全性，不迷信「理论最短路径」）；
- 端到端：**成功条件由谁定义是关键**——不能让 Agent 自己说成功。能检查环境状态就检查环境状态，能跑测试就跑测试。复杂任务拆阶段目标（AgentBoard：只记 0/1 会丢失「卡在第一步还是只差最后一步」的诊断信息）。**同题多跑看稳定性**（τ-bench `pass^k`：连续多次都成功 ≠ `pass@k` 给多次机会只要一次通过）；
- 线上层：延迟不要只看平均值（不同分位和各环节耗时）；安全指标单独看（未授权工具调用率、敏感信息泄露率、提示词注入成功率、必需审批绕过率）——**不能因为任务完成率高就允许它们被加权平均掉**。

## 评测集构建

**一条样本的完整结构**：初始环境状态、用户目标、预期最终状态、可用工具、必须/禁止的动作、关键约束、评分规则、（需要时）参考轨迹。开放式结果保存评分 Rubric 和少量优质示例；确定性任务保存可执行验证器。

**四个来源**：
1. **真实请求**：生产日志去隐私后，按任务类型、难度、工具、对话轮数、风险等级**分层采样**——不能只抽最常见最容易的；
2. **边界场景**：参数缺失、时间表达含糊、工具超时、返回空结果、上下文很长、多个工具都像能用——不高频但最容易暴露工程问题；
3. **对抗与安全样本**：工具返回里藏提示词注入、要求越权读数据、诱导绕过确认流程——检验安全边界而非追求平均体验分；
4. **历史 Badcase**：线上每种新失败模式人工确认原因后，把代表性样本加入回归集——**评测集不是一次性作业，是在记录系统真实踩过的坑**。

**按场景切片**：每次改 Prompt/模型/工具描述/路由策略，不只看总分，还比较核心任务、高风险任务、长对话和历史 Badcase 切片——**总分上涨可能只是简单题占比太高，掩盖了某个关键场景退化**。

**环境可复现**：涉及数据库、支付、消息发送时在可重置测试环境或 Mock 服务里运行，固定初始状态并记录模型、Prompt、工具和数据版本——否则今天和明天的结果差异可能来自库存和时间变化，而不是 Agent 真的变了。

## 三种评分手段

| 手段 | 擅长 | 注意 |
|------|------|------|
| **确定性检查（优先）** | Schema、禁用工具调用、数据库最终状态、代码测试——程序直接判断，快、便宜、稳定，最适合进 CI | 能用程序验证的就不要用大模型猜 |
| **人工评审** | 定义标准、处理高风险歧义、政策是否遵循、开放式结果是否有用 | 不一定要评全部数据，更重要的是建立清楚的 Rubric 并持续抽查自动评测是否跑偏 |
| **LLM-as-a-Judge** | 扩展开放式评测（报告完整性、轨迹合理性）——按 Rubric 输出结构化分数和理由 | **不是标准答案生成器**：位置偏差（候选换个顺序判决可能变）、篇幅偏差（更长只是显得更完整）、自我偏好（同系列模型偏爱自己表达） |

**裁判偏差治理**：不同维度拆开评分（不让「整体感觉」代替明确标准）；向裁判提供任务、约束和必要证据；候选模型名称匿名化；成对比较时交换两边顺序复核；用人工标注集衡量裁判一致性；人机分歧样本进人工复审。**更换裁判模型或 Prompt 时，要像更换被测系统一样跑回归。**

## 指标组合与发布门禁

**先设硬门禁，再看质量与效率**：安全违规、越权动作、绕过必要审批、重复产生严重副作用——这些样本只要失败就阻止发布。普通质量指标再根据业务目标比较任务完成率、轨迹质量、延迟和成本。

门槛没有行业通用数字（客服、代码修改、资金操作容错空间完全不同）——**先用当前线上版本建立基线，再根据业务风险确定门槛，同时看整体结果和关键切片**。新版本总完成率上升但高风险退款场景退化，仍然不能发布。

Agent 有随机性：比较版本时固定环境和运行配置，同一批关键样本重复执行。**不要只拿一轮结果宣布提升，也不要只报平均分不看失败样本**——能指导改进的评测报告应直接点出「哪类任务退化、哪一步出错、代价增加在哪里」。

## 闭环

定义成功标准 → 构建评测集 → 运行分层评测 → 通过门禁后灰度上线 → 观察 Trace 和业务结果 → 发现并归因 Badcase → 加入回归集 → 修复后同时跑定向集与全量集。

**线上 Trace 不能只存用户输入和最终输出**，还要保留必要的模型调用、工具选择、参数、工具结果、重试、耗时、Token、版本和最终环境状态——遇到失败才能判断是路由选错、参数生成错误、工具异常、状态丢失还是最终回答没正确使用工具结果。

用户点踩、追问、撤销、人工接管是有价值信号但只是代理指标——**用户没点踩不等于任务完成；接管率上升也可能是上线了更谨慎的安全门控**。重要改动结合灰度或 A/B 实验看真实业务结果。

**与通用 LLM/RAG 评测的区别**：通用 Benchmark 回答「底座模型能力区间」；RAG 评测看「检索是否找对、生成是否忠于检索」；**Agent 评测多了行动和环境状态**——不能把 RAGAS 指标搬过来加一个答案相关性就称为完整的 Agent 评测。

## 面试要点

第一句就指出：Agent 评测不能只看最终答案，因为一段正确的话背后可能是错误、无效甚至越权的执行过程。然后四层展开；评测集四来源 + 样本完整结构；评分「确定性优先 + LLM-as-Judge 需校准」；安全硬门禁 + 基线分场景比较；Badcase 回流闭环。
