## 核心答案

反思机制：让 Agent 在完成一个步骤或整个任务后**自我评估输出质量**，判断有没有问题，不达标就重试或调整策略。

原因是 LLM 第一次输出不一定最优（逻辑跳跃/遗漏细节/事实错误/表达含糊），加一轮自我检查能显著提升质量——相当于人写完东西自己再看一遍。代价是多至少一次 LLM 调用（token 和延迟增加），**工程里通常只在质量要求高的关键节点启用，不是每步都做**。

## 核心循环：生成 → 评估 → 改进（Self-Refine, Madaan 2023）

类比「草稿 → 批阅 → 修改」：学生交草稿（生成），老师批阅指出问题（评估），学生拿批注修改（改进），改完再审阅直到通过。靠两个 prompt 驱动：

**评估 prompt**（让 LLM 扮演「检查者」专门找问题）：

```
任务：{task}
当前输出：{current_output}

请评估以上输出：
1. 有没有事实错误或逻辑问题？
2. 有没有遗漏重要内容？
3. 表达是否清晰准确？

如果输出已经足够好，回复「PASS」；
否则指出具体问题并给出改进建议。
```

**两个关键设计**：
1. **给出明确检查维度**（事实、逻辑、完整性、表达）——没有方向的评估流于表面，LLM 可能只说「输出看起来不错」；给出具体维度它才会针对性逐项审查；
2. **必须有 PASS 机制**——给 LLM 一个「够好了就停」的出口。没有这个，它会无限挑毛病，反而把原本对的东西改错。

**改进 prompt**（同时传入三样，缺一改进就盲目）：

```
原始任务：{task}
当前输出：{current_output}
评估意见：{reflection}

请根据评估意见改进输出：
```

- 只有任务没有原始输出 → 不知道在什么基础上改；
- 只有原始输出没有评估意见 → 不知道改哪里；
- 只有评估意见没有任务 → 可能改着改着偏离原始目标。

两个 prompt 循环调用直到 PASS 或超最大轮次强制退出——外层不过是普通 for 循环。

## 两个粒度：步骤级 vs 任务级

| | 步骤级反思 | 任务级反思 |
|---|-----------|-----------|
| 时机 | 每个工具调用/推理步骤后立即检查 | 整个任务执行完后整体评估一次 |
| 优势 | 错误早发现早纠正，不在后续步骤层层放大（多步检索第一步关键词不精准，后续全在错误信息上继续，到最后才发现全废） | 开销小（整个任务只多一次调用）；整体视角能发现步骤级看不到的问题（各步骤单独看都对，但整体结论前后矛盾/衔接不自然） |
| 代价 | 每步多一次调用，10 步任务实际调 20 次 LLM | 中途某步出大问题到最后才发现，前面执行浪费 |
| 适用 | 步骤间强依赖、前步错后面全错 | 步骤相对独立、最终输出整体质量更重要（如生成报告） |

## 多 Agent 互评：为什么「他人审视」更好

单 Agent 自我反思时，**评估者和生成者是同一个模型**——它在生成输出时形成的一套「内部逻辑」，做评估时也会沿用这套逻辑，对自己的错误不够敏感，容易陷入「自洽」（类比：自己写的代码自己看容易「视觉疲劳」，不自觉地补脑跳过问题）。独立的 **Critic Agent** 没有这种包袱，唯一职责就是找问题，视角更客观。

流程：执行 Agent 生成 → Critic 审查给批注 → 执行 Agent 修改 → Critic 再次确认。适用：质量要求非常高的场景（生成代码后独立测试 Agent 验证、分析报告后事实核查 Agent 交叉验证）。代价：又多一个 Agent 的调用成本，系统复杂度更高——普通场景自我反思就够了。

## 进阶：Reflexion 与 LATS

- **Reflexion（Shinn 2023）**：不仅反思当前输出质量，还把「失败经验」存下来，下次类似任务直接参考（通常通过把经验记忆塞到当前任务上下文让 LLM 自己参考，而非严格相似度检索）。Self-Refine 是「写完作文当场改」，Reflexion 是「把错记在笔记本上，下次写之前先翻一遍」。代码生成 Agent 第一次写 bug，反思后修好还把「这类 bug 成因和避免方法」记下来，下次不易犯同样错误；
- **LATS（Language Agent Tree Search, Zhou 2024）**：MCTS + 反思——同时探索多条路径，每条路径执行后评估反思，反思结果作为经验反馈给后续路径探索。既有多路径成本又有反思成本，目前主要是学术研究；
- **辩论式反思**：正方 Agent 提方案、反方 Agent 专门挑毛病，正方针对反对意见优化——对抗式比单方面审查更能暴露深层问题（反方「职责」就是找漏洞，会比「检查一下有没有问题」的 Critic 更积极挖掘）。用于重要商业决策分析、法律文本审查等。

## 工程权衡

- **值得开反思**：输出质量要求高、错误代价大的关键节点（最终报告生成、重要决策推理）、任务复杂 LLM 容易遗漏细节；
- **不值得开**：简单直接任务（格式转换、简单问答——纯浪费）；实时性要求高的场景（一次反思至少多一次完整调用，延迟可能从 1 秒涨到 3 秒）；
- **防死循环（最重要）**：**必须硬性设最大轮次，通常 2-3 轮，绝不能依赖 LLM 自己判断停止**。LLM 有时陷入「为了改而改」——每轮都觉得还有优化空间，改完又有新「问题」，每轮改动很小但实质无进步；
- **代价清醒认知**：每轮反思 = 一次评估 + 一次改进，3 轮反思 = 原始生成外额外 6 次调用。

## 面试要点

1. 最常见误区：把反思说成「不满意就重新生成」——它是「生成→评估→改进」有结构的闭环，不是随机重试；
2. 评估 prompt 两关键设计：具体检查维度 + PASS 出口；
3. 步骤级 vs 任务级的区别（错误发现早晚 vs 开销大小）；
4. 防死循环：硬性最大轮次 2-3 轮；
5. 加分点：多 Agent 互评更好及原因（同模型对自己输出有「自洽」偏见）。
