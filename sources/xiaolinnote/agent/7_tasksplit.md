# Agent 面试题 7：复杂任务怎么做的任务拆分？为什么要拆分？效果如何提升？

## 核心答案

任务拆分的原因：**LLM 的 context window 有限，任务越大中间状态越多，模型很难持续追踪子目标，容易「桌面太乱」出错**。拆成小步骤每步聚焦一件事，准确率明显提升，且每步可独立检查和验证（某步出错只重试那步）。

两种拆分思路：**静态拆分**（提前写死步骤，行为可预测）vs **动态拆分**（LLM 自己根据目标规划，灵活但难控制）。

拆完后**分析步骤依赖关系，能并行的并发跑，端到端延迟可降 40%~60%**。

## 失败案例（系统性问题）

让 LLM 一次完成「帮我写一份竞品分析报告」（需搜索多家竞品、整理功能对比、分析优缺点、写结论——其实是四件事混在一起），典型毛病：搜索阶段就掺杂分析意见、写对比表时突然引入新竞品、写一半忘掉前面关键数据点、输出结构混乱「什么都有、什么都不深」。

**根因**：context window 有上限，任务越大中间状态越多「桌面越乱」（搜索结果、分析意见、写了一半的段落全堆一起），LLM 难以持续追踪「我现在在做哪个子目标」。类比：让一个人同时记住十件事全做对，比每次只专注一件事出错率高得多。

## 两种拆分思路

**概念澄清**：CoT 是「一次生成里的内部拆分」（不涉及多步工具调用），ToT 允许同时探索多条推理路径再选优——这些是「LLM 内部怎么想清楚」；静态/动态拆分是「Agent 怎么把大任务切成多个独立执行的步骤」，粒度和目标不同，不要混为一谈。

### 静态拆分

提前把任务流程设计好固定成确定 Workflow（如「写技术博客」固定：搜索资料 → 整理大纲 → 逐段撰写 → 润色校对）。好处：行为完全可预测、问题好排查；坏处：灵活性低，遇到没设计进流程的情况容易卡住。

### 动态拆分（Plan-and-Execute 核心）

把「任务拆解」本身交给 LLM：给它目标 → 先输出执行计划 → 按计划逐步执行。类比：没经验的程序员接到「开发登录系统」直接写代码边写边想（易漏错误处理、密码加密）；有经验的工程师先写项目计划（需求分析 → 数据库设计 → 接口设计 → 编码 → 安全测试）。

**三阶段**：
1. **规划**（项目启动会）：LLM 像项目经理输出有序步骤列表，只规划不执行（如行业调研：行业现状和市场规模 → 头部公司产品和策略 → 技术趋势 → 结论建议 → 排版润色）；
2. **执行**（各部门干活）：按步骤列表逐步执行，**每步把前面所有步骤结果作为 context 传进去**，LLM 始终知道整件事做到哪里；每步只聚焦自己任务，不像 ReAct 走着走着被岔路吸引；
3. **汇总**（项目验收）：整合各步骤产出生成最终输出——不只是拼接，还要解决步骤间衔接问题，确保是连贯整体。

优势：灵活性强；劣势：规划质量不稳定，规划错了后续全建立在错误基础上。

## 依赖分析与并行优化

步骤之间有依赖：有些必须等前步完成，有些无依赖可同时进行。**识别可并行步骤是降低总耗时的关键**。

厨师做饭直觉：烧水、切菜、腌肉三件事——串行总时间是三件事之和；先烧水、烧水同时切菜腌肉，总时间由最长路径（烧水）决定。**并行降低的不是「每步时间」而是「关键路径总时间」。**

```python
import asyncio

async def execute_parallel_steps(independent_steps: list):
    tasks = [execute_step_async(step) for step in independent_steps]
    results = await asyncio.gather(*tasks)   # 多个步骤同时开始，不等某个完成再启动下一个
    return results

# 依赖图：步骤1、2 独立可并行；步骤3 依赖步骤1；步骤4 依赖步骤2和3
# 步骤1 ───────────┐
#                   ├──> 步骤3 ──┐
# 步骤2 ───────────┘             ├──> 步骤4（最终输出）
```

每步 3 秒：串行 12 秒 → 并行后关键路径「步骤1/2（并行）→ 步骤3 → 步骤4」= 9 秒。**步骤越多可并行越多节省越可观，实际项目降 40%~60% 端到端延迟很常见**（前提：依赖关系稀疏、工具 I/O 占主要耗时；全强依赖则并行空间为零）。

**落地前提**：先把依赖关系画成有向无环图（DAG）——节点是步骤、边是「依赖」，没有依赖的节点同时跑。

## 拆分粒度：原子操作标准

- **拆太细**：步骤多 → LLM 调用多 → token 上升；步骤太碎 LLM 看不到全局，产出衔接生硬；
- **拆太粗**：回到「桌面太乱」问题，出错无法定位责任；
- **标准：原子操作**——只做一件独立的事，边界清晰，做完有明确输出，与其他步骤不互相依赖；
- **判断方法**：能给它写一个清晰的函数签名吗？能 → 大概是原子的；函数里还要分几个阶段、处理几类情况 → 需要再拆。
- 例：「搜索竞品 A 的产品信息」是原子的；「整理竞品分析」不是（包含搜索、筛选、格式化三件事）。

## 自适应拆分：做不好就继续拆

不在开始时把所有步骤粒度定死，而是执行中根据每步实际难度动态调整：**先让执行器尝试，做得好就继续；明显做不好（超最大步数或质量不达标）就交给规划器拆成更小子任务，对每个子任务重复同样流程**。

竞品报告例子：执行器一口气写完质量差 → 规划器拆三步（搜集数据 / 功能对比 / 写总结）→ 「搜集数据」发现竞品太多一次搜不完 → 再拆成「搜集竞品 A/B/C 的数据」→ 每步足够简单顺利完成。**像一棵递归展开的任务树，只有真正做不好的节点才继续拆——计算开销与任务实际难度成正比，而非一刀切。**

## 执行中的 Replan 机制

每步执行完后，把当前步骤结果 + 剩余计划交规划模块判断「基于新信息，后面计划还合理吗」。合理继续，不合理生成新剩余计划。保证计划与实际情况同步，不死守过时计划。

**折中做法**：不是每步都触发 Replan（每步多一次调用），而是设触发条件——某步输出与预期差异很大、或步骤执行失败时才启动。

## 拆分结果的验证标准（三条件）

1. **完备性**：所有步骤加在一起覆盖原始任务全部要求，无遗漏。检查方法：把所有步骤描述拼起来与原始任务逐项对照；
2. **独立性**：每步职责边界清晰，无两步做同一件事、输出无重叠。反面例：步骤2「搜索竞品 A 产品功能」vs 步骤3「分析竞品 A 核心能力」边界模糊会搜到同样内容；更好拆法：步骤2 只「搜集」、步骤3「提炼加工」；
3. **可验证性**：每步执行完能用简单标准判断对错。**好做法：拆分每步时同时写好「验收标准」，步骤定义和验收标准成对出现**（如「输出必须包含价格数字和计费模式」，缺了自动触发重试）——像写单元测试的断言。

## 面试总结（三层次）

1. **为什么拆**：context window 有上限，任务大中间状态多易出错，拆开每步可独立验证重试；
2. **怎么拆**：静态适合流程固定，动态（P&E）灵活但规划质量不稳定；
3. **拆完还要做什么**：依赖分析 + 并行执行，关键路径时间降 40%~60%。补一句「粒度以原子操作为标准，不能太细也不能太粗」。
