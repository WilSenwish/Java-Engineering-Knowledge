## 核心答案

先确认慢的是 **TTFT**（用户多久看到第一个 Token）还是**总时延**（任务从接收到完成一共多久）——网关排队、上下文构建、首轮检索、模型服务排队和预填充影响 TTFT；生成速度、工具调用、Planner 决策、失败重试、反思次数和任务步数影响总时延。

按任务类型、模型版本、工具、租户和发布时间切分 P50/P95/P99，判断是整体变慢还是少量长尾出问题。**只看平均值容易被骗**（90 多个请求 2 秒、少数几十秒，平均值还可接受但命中慢请求的用户已很难受）。

用同一 Trace ID 串起网关、排队、上下文构建、检索、模型调用、工具调用、编排决策和最终生成，每环节独立 Span（记录耗时、状态、重试次数、输入输出规模、Token 数、错误类型，**但不记录密码、完整提示词等敏感内容**）。定位：先指标圈定异常范围 → 抽取慢 Trace 和正常 Trace 对比 → 瀑布图找**关键路径**。优化对症下药，修改后通过历史轨迹回放、灰度和分位数对比验证，同时守住任务成功率、答案质量、安全和成本。

## 一条 Agent Trace 的结构

普通接口可能只有一次 DB 查询一次下游调用；Agent 是一条**动态执行链**——同样一句用户请求，这次可能只调一次模型，下次可能经过检索、规划、三个工具和两轮反思。

- **根 Span** 表示整个 Agent 请求，下面拆出网关鉴权、调度排队、上下文构建、检索、模型调用、工具调用、状态存储、结果整理等子 Span；
- 同链路 Span 共享 Trace ID，各自 Span ID + 父子关系；调远程工具、MQ、子 Agent 时传播 Trace 上下文（跨进程跨服务才能知道这些操作属于同一次任务）；
- 业务任务 ID/会话 ID/调用 ID 作关联 ID 保留（方便从工单反查），但不能替代 Trace ID/Span ID 父子关系；
- **Span 记录内容决定以后能不能找到问题**：模型调用记模型名、输入输出 Token 数、首 Token 到达时间（TTFT）、结束原因；检索记 Query 类型、召回数量、各阶段耗时；工具记工具名、结果状态、错误类型、重试次数；编排记当前步骤、路由结果、计划版本、累计步数；
- **可观测性不是把所有内容原样塞进日志**：完整 Prompt、用户原文、数据库结果、工具凭证可能含敏感数据——记录长度、哈希、分类标签和脱敏后摘要，配合访问控制、保存周期和审计策略；
- **采样**：只在入口随机抽样，罕见的超慢请求和错误请求可能刚好被漏掉——结合错误状态、业务重要性和完成后的总耗时保留更有诊断价值的 Trace。

## 定位顺序（不能反）

1. **指标确认异常边界**：TTFT 和总时延从什么时候开始涨、是 P50/P95/P99 涨、成功率和超时率有没有一起变；按模型/工具/任务类型/发布版本切分找变化最明显的一组。延迟上涨正好和一次发布、模型切换或下游异常在时间上重合 → 重要线索；
2. **选慢 Trace**：从异常分组抽多条慢 Trace + 同类型同版本正常 Trace 做对照——判断慢请求共有的特征（都卡在某工具？都比正常多跑几轮模型？）；
3. **瀑布图看关键路径**：最长的 Span 值得关注，但真正决定总时延的是「从请求开始到任务完成的关键路径」。**两个工具并行各 3 秒，对总时延贡献接近 3 秒而不是 6 秒——不能把所有子 Span 耗时简单相加，也不能看到某个 Span 很长就认定它是根因**；
4. **下钻 Span 对应日志、错误和资源指标**：模型 Span 变慢要区分客户端连接/供应商排队/首 Token/生成速度/输出变长；工具 Span 变慢看下游接口/连接池/数据库/重试；应用内部变慢看 CPU/内存/线程池。**Trace 告诉你「哪一段可疑」，日志和指标解释「为什么可疑」。**

## 六类常见瓶颈

| 瓶颈 | Trace 特征 | 治理 |
|------|-----------|------|
| **排队** | 请求还没进真正的模型/工具调用，调度队列等待已变长（突发流量、并发上限、线程池耗尽、租户争抢、下游限流）。**没有单独 queue Span，排队时间很容易被算进模型耗时，把锅甩错地方** | 扩容、按优先级/租户隔离负载、并发上限、背压和准入策略、端到端截止时间 |
| **模型调用** | 区分网络连接、服务端等待、TTFT、持续生成：TTFT 涨但输出速率正常 → 服务排队/输入变长/预填充变慢；首 Token 快但总时延长 → 输出变长/生成速率下降/触发更多步骤。**流式输出只改善用户感受，不会自动缩短任务真正完成的时间** | 模型路由（简单任务给轻模型）、稳定前缀缓存、裁无关上下文、约束超长输出 |
| **检索** | 一次 RAG 含 Query 改写、Embedding、向量召回、关键词召回、Rerank、文档读取——只建一个 `retrieval` 大 Span，慢了也不知改哪 | 拆 Span；向量库长尾/Rerank 变慢/召回过多文档分别对症 |
| **工具** | 第三方接口、DB、浏览器、代码执行环境延迟特征不同；关注超时、错误码、重试次数、返回大小、冷启动。**同一工具连续调用多次，也可能不是工具慢，而是 Agent 没正确利用上次结果** | 连接复用、索引优化、字段裁剪、减少无意义大结果、超时熔断降级 |
| **编排** | 单个 Span 都不算慢但整条 Trace 很长——步骤膨胀：Planner 拆太细、反思反复推翻正确结果、路由绕路、无依赖工具被串行 | DAG 并行（仅无依赖步骤）、清楚的完成标准与停止条件、减少无效步骤 |
| **重试** | 失败调用本身 1 秒，默认重试多轮 + 每轮退避 → 总时延突然拉长。**每次尝试单独记录并保留属于同一逻辑调用的关系** | 按错误类型判断是否值得重试（网络抖动/临时限流才有界退避+随机抖动；参数错误/权限不足原样重试无意义）；副作用工具用幂等键 |

## 优化验证与护栏

- **上线前**：历史慢 Trace 和典型任务整理成回放集，相同输入环境下比较修改前后——除了端到端时延，还比较各阶段 Span 对关键路径的贡献，确认下降来自预期环节而不是某步骤被意外跳过；
- **上线时**：灰度/受控实验，同口径观察 TTFT、总时延、P50/P95/P99。**平均值降但 P99 涨说明尾部用户反而更差；TTFT 降但任务总时延和超时率涨不算完整成功**；
- **护栏**：任务成功率、答案质量、工具执行正确率、安全违规率、单任务成本不能出现不可接受退化——减少检索文档能提速但答案依据不够就走偏了；五轮验证砍成一轮可能放过错误结果；
- **沉淀**：把异常对应的任务切片、慢 Trace 特征和根因加入监控与回归集——一次性能优化真正留下来的不只是更快的代码，还应有可复现的证据和不会轻易反弹的守护机制。

## 面试易踩的坑

1. 一听到 Agent 慢就默认模型慢——排队、检索、工具、编排、重试都可能比模型更慢，**必须让 Trace 先给出证据**；
2. 只报平均响应时间——主动区分 TTFT、总时延和不同分位数；
3. 找到最长 Span 就认为找到根因——并行 Span 会重叠、父 Span 包含子 Span 时间，应沿关键路径判断；
4. 用并行解决所有问题——只有无依赖、共享副作用可控的步骤才适合并行，盲目并行可能压垮下游、产生状态竞争和重复操作；
5. 优化后只验延迟——必须与成功率、质量、安全和成本一起验收。
