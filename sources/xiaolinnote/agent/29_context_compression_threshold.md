# Agent 面试题 29：Agent 的上下文压缩阈值应该如何确定？

> **来源站点**：小林面试笔记（xiaolinnote.com）

> **抓取日期**：2026-10-20
> **所属知识域**：域6 性能优化与架构演进（AI 前沿）
> **板块**：Agent 面试题（30 题）· 运行机制与控制策略

---

## 核心答案

**没有通用的 80%**。阈值 = 从任务预算里算出来的边界：先把窗口里实际装的东西算清（指令/任务状态/工具定义/检索资料/工具结果，不只聊天记录），再预留**模型输出 + 下一步工具增长 + 安全余量**，剩余才是当前输入预算。阈值应随任务动态调整，压缩目标和触发时机分开定，最终靠实际任务回放验证。

## 上下文为什么越用越大

用户只说几句话，输入却很长——模型判断下一步需要当前任务全部相关信息，应用把指令、消息、工具调用及结果全量装配，历史只累积不筛选，下一轮输入必然更大。到容量边界接口拒请求或输出提前结束，任务被打断。压缩 = 把过程收敛成较短仍有用的信息。**但压缩是有损搬家**：摘要保留「发现连接池问题」，可能漏了具体环境、配置值和用户限制——越早压越可能丢后续还需要的细节。

## 预算推导（32k 窗口示例）

```text
输入预算 = 总窗口 - 输出预留 - 安全余量
32,000 - 4,000（输出） - 2,000（计数误差/意外增长） = 26,000
```

- 输出预留跟任务走：提取一个字段 ≠ 生成完整代码文件；
- **缓存降费 ≠ 扩容**：前缀缓存命中内容仍占着上下文窗口，费用下降不代表多出装材料的空间；
- 计数对象是**装配好的完整请求**：用服务计数接口或匹配模型的分词器估算，并结合实际返回用量校准；
- 真实接口可能有独立的输入/输出上限，要分别满足。

## 工具增长要提前算

当前输入 21,000 没到 26,000，但下一步预计新增 6,000 工具结果（跑整套测试返回几千行日志）：

```text
21,000 + 6,000 + 4,000（后续输出） + 2,000（余量） = 33,000 > 32,000
```

当前输入只占窗口约 2/3 却该提前处理。等价视角：给这次增长预留后，当前输入只能用 `32,000 - 6,000 - 4,000 - 2,000 = 20,000`——**这步的触发边界更低**。增长估计参考同类工具历史返回量分布（日志波动大，平均值低估异常），工具实际返回后重新计数，估计不能替代检查。工具能返回无限长内容时，降阈值也没用——**完整日志存外部，只回摘要/命中位置/部分内容，按需读取**。

## 容量边界 ≠ 唯一触发理由

材料装得下但当前步骤不再需要很多（已定位连接池参数，前面几十轮排查过程跟着走只增阅读负担）→ **阶段完成时提前整理**，比没找到原因时匆忙压缩更保有效信息。但看到模型重复调用就压是误判——可能是工具一直报错或任务缺信息。提前压缩也要比收益：任务还依赖日志精确字段时过早概括成「出现错误」，模型重读文件，总耗时成本未必降。

## 触发边界 vs 压缩目标

26,000 触发只降到 25,800 → 下一轮 +500 又触发 → 反复总结几乎相同的历史，每次花时间还逐次损细节。两者分开：26,000 附近触发，目标降到 20,000 左右。释放空间时**用户目标、硬约束、关键参数、当前进度必须保留**（「不能改接口字段」不能压成「尽量兼容」；工具超时结果未知不能总结成已失败）。消息协议有约束：工具请求和返回按调用编号关联，不能删请求留孤立结果。压缩后检查两件事：大小回到预算 + 任务所需信息与消息结构完整。**Token 降很多只证明变短，不证明摘要可用**。压缩本身也要空间——窗口满了再提交整段历史生成摘要，压缩调用同样可能失败。

## 验证方法

候选策略（早压/晚压/按增长动态触发）放实际任务比较：短查询、长代码修改、大日志分析，固定模型/资料/初始状态，每类重复跑。先看任务完成/约束违反/关键信息可用，再看输入大小/压缩次数/重复读取/延迟/费用。

| 现象 | 检查方向 |
|------|---------|
| 工具结果到达后经常超限 | 增长估计不足 / 返回缺上限 |
| 压缩后反复重读同一资料 | 关键细节丢失 / 触发过早 |
| 每一两步就再次压缩 | 压缩目标离触发边界太近 |
| Token 明显下降但任务失败增加 | 摘要破坏约束/进度/消息关系 |

结论往往是**按任务类型配置的一套策略**，不是所有 Agent 共用一个数字。模型容量/工具输出/任务分布变化后重新检查预算。
