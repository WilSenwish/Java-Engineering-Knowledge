👔面试官：你了解 Multi-Agent 吗，说说它是什么，为什么要用？

🙋‍♂️我：Multi-Agent 就是多个 AI 一起工作，可以提高效率，一个人搞不定的事情多个人一起做。

👔面试官：你说「一个人搞不定」，具体是哪方面搞不定？技术上的根本限制是什么？

🙋‍♂️我：就是……任务太复杂，一个 Agent 处理不过来，容易出错。

👔面试官：「处理不过来」太模糊了。单个 Agent 有一个非常具体的硬限制，你知道是什么吗？不是「容易出错」，是结构性的上限。

🙋‍♂️我：哦，是 context window 的大小限制，装不下太多内容。

👔面试官：对，这是第一个。那除了 context 限制，还有一个更深层的问题，跟专业能力有关，你能说出来吗？

## 简要回答

多智能体系统（Multi-Agent）就是多个 Agent 协作完成任务，每个 Agent 各有分工，有的负责搜索、有的负责写代码、有的负责做评审。

单个 Agent 主要受两个限制：一是 **context 窗口大小**，复杂任务信息量一多就撑爆；二是**单点能力**，什么都让一个 Agent 做，每件事都是泛才。

Multi-Agent 通过专业分工和并行执行，能处理更复杂、更长流程的任务。

## 详细解析

### 两个硬限制

**context window 上限**：LLM 处理任务时把当前能看到的所有内容（指令、自己的推理、工具返回结果、历史对话）全部摆在「工作台」上一起处理。工作台有大小上限（常见 12.8 万 ~ 100 万 token），塞满后早期内容开始「掉落」——三十分钟前确认的方案悄悄消失，Agent 开始「遗忘」。这是结构性限制，不是努力优化能绕过去的。

**专业度问题**：让一个 Agent 既搜信息、又写代码、又做测试、又写文档，每件事都兼顾，精力分散，互相干扰；且某环节出问题整条链路卡住，无隔离性，排查痛苦。

### 核心思路：团队作战代替单打独斗

把任务按职能拆开，每个 Agent 只负责一件事，做完把结果传给下一个。

**三种协作模式**：

1. **顺序流水线**（Sequential Pipeline）：A 做完交给 B，B 做完交给 C，像工厂流水线；
2. **并行扇出**（Fan-out）：调度者把多个独立子任务同时分发给不同 Worker Agent 并行执行，最后收集汇总；
3. **辩论/评审模式**（Debate/Review）：多个 Agent 对同一问题各出方案，裁判 Agent 或互相评审筛选最优——适合代码评审、方案选型等高质量决策场景。

**爬虫工具案例对比**：

- 单 Agent：一个 Agent 同时想需求文档、代码结构、测试策略，context 塞满，思路乱，哪块都不够好，任何一步失误从头来；
- Multi-Agent：「需求分析师」产出功能列表后退出（工作台干净）；「程序员」拿功能列表专注写代码；「测试工程师」拿代码专注写测试。且需求分析结束后程序员和测试可**并行**（测试框架搭建不等代码写完）——Orchestrator 识别无依赖子任务同时派出去。

**并行的隐藏好处**：每个 Worker 的 context 完全隔离，不被其他角色信息干扰，输出质量更高。

### 框架与组织方式

成熟框架：**CrewAI**（上层易用）、**LangGraph**（底层灵活）。微软 2025 年推出 **Microsoft Agent Framework（MAF）**，合并 Semantic Kernel（企业级）与 AutoGen（多 Agent 编排）为统一生产 SDK；原 AutoGen 继续以研究/原型身份迭代，社区 fork 出 AG2 保持兼容。微软技术栈生产场景优先 MAF。

组织方式：**中心化**（统一调度者分配任务、收集结果——工程主流，调度清晰、责任明确、易排查）vs **去中心化**（Agent 间自行协商——灵活但难排查）。

## 面试总结

核心在于说清「为什么需要 Multi-Agent」而不是泛泛说效率高。三个具体点：① context window 硬上限（结构性遗忘）；② 专业度问题（单 Agent 身兼数职不专注，分工后 context 干净、能力更强）；③ 并行执行带来实质效率提升。
