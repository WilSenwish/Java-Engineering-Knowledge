# Agent 面试题 20：Agent 为什么会出现路径震荡、重复调用和死循环？怎么检测和治理？

## 核心答案

常见原因：目标和停止条件模糊；工具失败后只返回空结果；任务状态没有随执行结果更新；多 Agent 职责边界不清，交接时形成 A→B→A 循环。

**检测**：调度层记录每步的 Agent、工具、标准化参数、结果摘要和执行前后状态；结合**动作指纹、输出相似度、状态变化和 Agent 调用图**检测，用步数、时间、Token、成本和交接次数作全局预算。**单纯动作重复只是预警，「状态长时间没有向完成标准推进」才是更可靠的循环信号**。

**治理**：预警后先区分临时性错误和无进展循环——临时性错误走有界重试和退避；参数/权限错误直接修正或询问用户；执行路径无进展时禁用当前失败路径、改用其他参数或工具、必要时从检查点重新规划。预算耗尽或风险越界后停止自动执行，把已完成结果、卡点和可选方案交给用户或人工。

## 三个程度与判断标准

- **重复调用**：同一工具和近似参数多次出现；
- **路径震荡**：Agent 在几条路径间来回切换（搜索→总结→再搜索，或 A→B→A）；
- **死循环**：系统缺少有效出口，在外部预算耗尽前无法自己停下。

**三者有关联但不能只凭「动作又出现了」下结论**：搜索 Agent 分页拉数据，工具名每次相同但页码和已收集证据在变——任务有进展；接口第一次返回限流，按错误类型等待后再试——合理容错。

**无进展循环的关键特征：新一轮没有带来新证据、没有完成新子任务、也没有缩小与成功标准的差距。检测时要同时看「做了什么」和「状态变了什么」。**

订会议室例子：Agent 发现 A 会议室被占用，又查了一遍 A；查不到新结果便交给日程 Agent；日程 Agent 认为订会议室该归会议室 Agent 又送回去。日志不断增长、工具一直在调，但「订好一间可用会议室」始终没推进。

## 四类根因（沿执行链排查）

1. **「什么算完成」定义不清**：用户说「帮我查一下合适的会议时间」，系统没定义要返回几个可用时段、是否需要所有人有空、查不到怎么退出——Checker 没有可执行的验收标准，只能不断让 Executor「再试一下」；
2. **工具反馈不可操作**：超时、限流、参数错误、权限拒绝都被包装成一句「调用失败」，模型不知道失败是否值得重试、该改参数/换凭据/换工具——最容易继续输出上一个动作；
3. **状态没写回**：工具明明成功了，系统却没把已完成步骤、新证据和外部副作用写回状态，下一轮模型仍以为「这事还没做」。**邮件发送、扣款、建群这类有副作用的工具缺少幂等键，重复调用会再次改变外部系统——风险比多花 Token 大得多**；
4. **路由成环**：多 Agent 都只看局部任务，客服认为需风控批准、风控认为资料不齐该交回客服补充，两边都没有全局决策权。Planner/Executor 之间同样：原计划已被工具结果证明不可行，Planner 没改计划版本，Executor 一直执行过时步骤。

## 检测：四角度同时看

1. **动作指纹**：当前子任务 + Agent 名 + 工具名 + **标准化后的参数**组合哈希。标准化很重要——参数键顺序变了、搜索词多一个空格，不该被当成全新动作。指纹在近期窗口反复出现 → 打预警标记；
2. **输出相似度**：文本工具比较结果摘要的完全一致性或语义相似度；结构化工具直接比较关键字段；
3. **状态差分**：已完成步骤是否增加、待办集合是否缩小、是否拿到新证据、阻塞原因是否变化。**动作相似 + 输出相似 + 状态没推进，循环判断才有足够证据**；
4. **调用图**：调用链画成有向图（节点=Agent/工具，边=调用/Handoff）。A→B→A 只说路径上出现环，还要检查回到 A 时任务状态有没有更新——审核 Agent 要求修改、执行 Agent 修改后再交回审核，这条环可能正常；审核意见没有新内容、文档也没变，这条环才需要被打断；
5. **全局预算（保险丝）**：最大步数、执行时间、Token、成本、单工具重试、Handoff 次数。**不是循环根因诊断，而是防止问题无限放大**。简单查询和深度研究不能共用一组数字，阈值通过离线轨迹回放和线上数据按任务类型校准。

## 治理四步

1. **先读懂失败**：工具返回结构化错误——错误码、错误类型、是否可重试、建议等待时间、可行的下一步。网络抖动/限流等临时性错误按退避策略重试（加随机抖动避免同一时间集中重试）；**参数错误、权限不足、资源不存在需要换参数、请求授权或补充信息，继续原样重试没有意义**；
2. **换路**：当前动作可改参数时，说清楚上次为什么失败，要求新动作和旧动作有实质差异；工具能力边界不匹配时换备选工具或降级到能完成部分目标的路径。一个工具连续多个任务失败，调度层可暂时打开**熔断器**快速拒绝后续调用，避免每个 Agent 都在同一故障上浪费预算；
3. **Replan**：换参数换工具仍无法推进，问题往往在原计划本身。从最近 checkpoint 恢复，把原始目标、已完成结果、当前阻塞和已尝试路径交给 Planner 生成新剩余计划。**新计划应该有新版本，并把已证明无效的路径写入约束——否则 Replan 只是用更多 Token 再生成一遍旧计划**；
4. **Orchestrator 介入 Handoff 环**：读取各 Agent 职责、已访问路径和全局任务状态，决定改派给有处置权的 Agent 还是暂停请用户补充信息。Agent 的交接目标和接收条件要写进路由规则，不能让两个角色随意把任务踢给对方。

## 循环发生前的预防（最省成本）

1. **每个子任务同时定义输入、预期输出、完成标准和失败出口**——「查找有用信息」没办法验收，改成「找到支持结论的可核验证据，若指定来源无结果则返回缺失项」；
2. **状态更新成为执行协议的一部分**：工具成功后调度层在一个事务中记录结果标识、已完成步骤和对外部系统的影响；有副作用的工具用任务 ID + 动作 ID 生成幂等键，业务系统按幂等键识别重复请求——即使 Agent 因超时没拿到响应而重试，同一动作也不会反复产生副作用；
3. **路由层限定职责边界**：每个 Agent 写清接收条件、可交接对象和交接前必须附带的事实；能用确定性状态机表达的主流程由代码控制路由，只把没有固定规则的边缘决策交给模型；
4. **Trace 记录每步的输入、输出、错误、状态增量、路由决策和预算消耗**——线上告警只说「某类任务开始空转」，完整 Trace 才能说明是工具反馈、状态写回还是路由规则出了问题；修改策略后把失败轨迹加入回归集，检查新策略能否打断循环、会不会误伤正常长任务。

## 面试要点

先说判断标准：**动作重复不等于死循环，任务状态长时间没有向完成标准推进才是需要治理的无进展循环**。成因沿执行链排查（停止条件可验收性/工具错误可操作性/状态写回/计划版本/交接环）；检测四信号（指纹/相似度/状态差分/调用图）+ 全局预算止损，阈值按任务类型设；治理先分错误类型（临时错误才有界退避重试，无进展换参数/换工具/Replan）；到边界后停止自动执行、保留 checkpoint 和失败原因交人工——而不是只返回一句「超过最大步数」。
