## 核心答案

Single-Agent 适合任务流程清晰、复杂度适中的场景，实现简单好维护；Multi-Agent 适合需要专业分工、任务量大或需要并行的复杂场景。架构上两种拓扑：**中心化 Orchestrator 模式**（主 Agent 统一调度 Worker）/ **去中心化 Peer-to-Peer**（Agent 间直接通信）。**工程里几乎都选中心化**——好控制、好调试、出问题链路清晰。

## Single-Agent 的边界（三类任务力不从心）

本质 = 一个 LLM + 一套工具跑决策循环。核心优势不只是架构简单，而是**整条任务链路完全在掌控之内**（怎么走、用什么工具、何时结束都写在一个地方，链路短好排查）。类比：一个人独立完成「写博客」（自己查资料、想大纲、写下来），单人反而高效、沟通成本为零。

开始力不从心的三类任务：
1. **任务太长、信息量太大**，context 撑爆，Agent 开始遗忘；
2. **不同步骤需要完全不同的专业能力**，什么都塞进一个 Agent，每件事都不够专注；
3. **有多个独立子任务可并行**，但单 Agent 只能一个个来。

**不属于这三类就不要强行上 Multi-Agent**——系统变复杂变难维护但不带来对应收益。

## Multi-Agent 中心化：Orchestrator 模式

**Orchestrator（总调度员/项目经理）不做任何具体工作**，只负责三件事：读懂用户大目标拆成子任务 → 判断每个子任务交给哪个 Worker → 收集产出拼成最终答案。

**三种变体**（按复杂度递进）：
1. **静态路由（Static Router）**：拆分和分配规则预先定义（「代码任务给 Coder，搜索任务给 Researcher」）——简单可预测；
2. **动态规划（Dynamic Planner）**：Orchestrator 本身是 LLM，根据用户输入动态生成任务计划，计划执行中可调整——**大多数场景用这个就够**；
3. **自适应编排（Adaptive Orchestration）**：不仅动态规划，还根据 Worker 执行结果实时调整后续计划（Researcher 搜回信息不够 → 追加一轮搜索）——更强大但调试复杂度高很多。

**Worker Agent**：只关注自己那块，不需要知道整体任务和其他 Worker 在做什么，拿到属于自己的指令做完返回结果就退出。**context 是干净的，只装和自己职责相关的信息**。

**排查优势**：报告内容不准 → Researcher 搜的信息不够好；分析逻辑有问题 → Analyst 对比维度不对；格式不符 → Writer 输出问题。**每个 Agent 职责清晰，顺着 Orchestrator 的调度记录一步步追就能找到根源。**

## 去中心化为什么生产不可用

没有总调度，多 Agent 通过共享消息队列/状态空间自行协商。实际问题（三个 Agent 场景：A、B 都在搜类似信息，C 负责汇总，无人统筹）：
1. **任务分配没协调**：没人告诉 A 和 B 各搜什么范围 → 大量重叠重复工作；
2. **执行顺序没保证**：C 需要等 A 和 B 都搜完，但没人告诉 C「什么时候算搜完」——不知道等多久、有没有漏掉某个 Agent 的结果；
3. **失败没有感知**：A 中途出错，没有中央调度者收到错误通知，B 和 C 还在正常运行，最后汇出不完整结果而系统不知道出了问题。

类比没有项目经理的团队：每个人都很能干，但没人协调时间节点和接口，交出互不兼容的结果，且没人知道整体进度。**所以去中心化主要停留在学术研究，生产环境几乎所有正经项目都选 Orchestrator 模式。**

## 选型决策与渐进式演进

两个问题搞定选型：① 任务 Single-Agent 能搞定吗？（流程明确、不太长、不需专业分工 → Single，架构简单维护成本低链路透明）② 能接受系统行为不可控的风险吗？（生产答案一定是「不能」→ Orchestrator）。

**渐进式演进（实用策略）**：先用 Single-Agent 把系统跑起来 → 发现某环节确实成为瓶颈（context 经常撑满、某类子任务质量不行）→ 再把那个环节拆出来交给专门 Worker。**不要一上来就设计五六个 Agent 的复杂系统**——可能连真正的瓶颈在哪都还没搞清楚。从 Single 演进到 Multi 是自然过程，不是一开始就做的架构决策。

## 三方案对比

| 维度 | Single-Agent | Multi（中心化） | Multi（去中心化） |
|------|-------------|----------------|------------------|
| 架构复杂度 | 低 | 中 | 高 |
| Context 压力 | 全压一个 Agent | 各 Agent 独立管理，Orchestrator 只维护高层状态 | 独立管理但需额外共享协调状态 |
| 专业能力 | 泛才 | 专才分工 | 专才分工 |
| 并行 | 不支持 | 支持 | 支持 |
| 可控性 | 高 | 高（Orchestrator 统管） | 低 |
| 调试难度 | 容易 | 中（按调度链路追踪） | 难（行为不可预测） |
| 工程实用性 | 高 | 高 | 低（学术研究） |

**A2A 协议**（Google 2025.4 → 2025.6 捐 Linux 基金会，IBM ACP 已并入）：让不同团队/框架开发的 Agent 在协议层面互相发现和调用，思路很像微服务。目前仍在较早期，生产级跨框架互操作仍在演进，长远会深刻改变 Multi-Agent 构建方式。

## 面试翻车点

1. 选型标准只说「任务复杂就用 Multi」——要说出三类具体场景（context 撑爆/需专业分工/子任务可并行）；
2. 不提中心化 vs 去中心化，或说不出工程里几乎都选 Orchestrator 的原因（可控、可追踪、可排查）；
3. 说不出中心化的具体问题（任务分配没协调、执行顺序没保证、失败没感知）。
