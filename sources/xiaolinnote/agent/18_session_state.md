## 核心答案

先把信息分成四类，而不是把所有内容都塞进 messages：

| 信息类型 | 主要内容 | 典型生命周期 | 主要用途 |
|---------|---------|-------------|---------|
| **对话历史** | 用户原话、模型回复、工具返回 | 当前会话 | 还原语义、指代、语气和决策原因 |
| **业务状态** | 日期、金额、目标群、审批结果等已确认事实 | 当前业务任务，部分可更久 | 给业务规则和工具提供可信参数 |
| **任务状态** | 核心目标、当前子任务、待办、步骤状态、错误信息 | 一次任务执行 | 控制流程、重试、暂停与恢复 |
| **长期记忆** | 用户偏好、稳定背景、可复用经验 | 跨会话跨任务 | 个性化与历史经验召回 |

当前任务显式维护 `core_intent`、`current_subtask`、`pending_tools`、`completed_steps`、`context_snapshot`。每轮先判断用户输入是**补充、纠错、回答澄清问题、还是明确切换任务**，再更新结构化状态。

**对话历史是证据，结构化状态才是当前结论**——前者告诉我们事情怎么聊到这的，后者直接告诉执行器现在做到哪里。

## 任务状态核心字段

| 字段 | 记录什么 | 更新原则 |
|------|---------|----------|
| `core_intent` | 归一化后的核心目标、范围、约束、完成标准 | **模型不能自行覆盖**，用户明确改需求时版本化更新 |
| `current_subtask` | 当前正在处理的子任务 | 步骤开始或切换时更新 |
| `pending_tools` | 未完成的工具调用及编号、参数摘要、状态 | **先登记再执行**，拿到结果后改为 succeeded/failed/unknown |
| `completed_steps` | 已完成步骤的结论、证据引用、产物位置 | 只记可复用结论，不复制整段原始日志 |
| `context_snapshot` | 当前有效的用户、时间、地点、文件、订单号等实体 | 新信息校验后合并，保留来源与版本 |

外加 `session_id`/`thread_id`（一段连续交互）、`task_id`（会话中某个具体任务——一个会话可能先做报告又临时查天气，只拿会话编号当任务编号两个任务会搅在一起）、`state_version`（**乐观锁**：用户连发两条补充消息或两个 Worker 同时处理同一任务时，避免较晚写入的旧状态覆盖新状态）。

## 每轮输入的四分类处理

| 输入类型 | 示例 | 状态处理 |
|---------|------|---------|
| 补充约束 | 「语气正式一点」 | 更新 `context_snapshot`，原目标不变 |
| 纠错 | 「不是技术群，是产品群」 | 覆盖目标群槽位，**并让依赖旧群名的待执行步骤失效** |
| 澄清回复 | 回答「请告诉我群名」 | 解除 `WAITING_USER`，继续原任务 |
| 新任务 | 「刚才的任务先暂停，改成帮我订明天的票」 | 暂停旧 `task_id` 创建新任务；用户要求继续时恢复旧任务 checkpoint |

**用户切题最容易误判**：不能只靠与第一轮输入的向量相似度低就认定跑偏——用户可能切换任务也可能只是补充信息。意图锚点更适合作为**预警信号**而非最终裁判；结合当前步骤、待澄清问题、指代关系和「暂停/改成/另外」等表达，把新输入分四类，**置信度不够时就问一句**，不擅自改状态。

**纠错一个误区**：`core_intent` 的「锁定」不是永远保存第一句话——第一轮需求可能含糊也可能被用户合法修改。合理做法：先归一化为目标、约束和验收条件（必要时让用户确认）；之后禁止模型静默改写，用户明确修改时生成新意图版本并记录修改来源。**防跑偏不是不许用户换任务，而是不允许系统在用户没有授权时悄悄改目标。**

## 状态机与自然语言历史分工

- **自然语言历史负责理解**（用户说「还是按上周那个风格来」，需结合近几轮消息和相关记忆才能明白指什么）；
- **状态机负责执行**：任务处于 `WAITING_CONFIRMATION` 时，即使模型突然建议调用发送工具，执行器也应拒绝，只有收到有效确认才能进入 `EXECUTING`。**付款、发送、删除这类高风险动作，合法状态转换应该由确定性代码校验，不能只靠 Prompt 约束**。

```text
IDLE -> PLANNING -> EXECUTING -> CHECKING -> DONE
                    |              |
                    v              v
               WAITING_USER      ERROR
```

模型可以提议「更新哪些字段、下一步去哪」，但输出必须经过 **Schema 校验、权限校验和状态转换校验**——最终提交状态的是编排层，不是模型自己。

每轮上下文不必把数据库所有内容拼进去：系统规则 + `core_intent` + 当前子任务 + 关键状态快照 + 最近相关对话 + 上一步工具结果 + 按需召回的长期记忆。旧聊天可摘要，原始工具大结果落外部存储只留引用。

## 防跑偏三道防线

Agent 跑偏通常不是突然忘掉整项任务，而是在多次小偏差中慢慢发生（工具返回无关内容模型顺着展开、用户插入临时问题回答完忘了主线、摘要反复压缩后验收条件被压没）：

1. **结构化 `core_intent`**：不只是任务标题，还包含最终产物、必须满足的约束和完成标准；每次规划或检查前把它和 `current_subtask` 一起提供给模型；
2. **进度核对**：每完成关键步骤，Checker 问两个问题——这个结果是否推进了核心目标？下一步是否仍来自未完成计划？连续步骤与目标弱相关、重复修改同一状态、新计划无故丢验收条件 → 进入重新规划或人工澄清；
3. **保留事实来源和状态版本**：工具结果出错时不应让后面摘要把错误结论包装成确定事实；`context_snapshot` 关键字段带来源、置信度、更新时间；用户纠正后让依赖旧值的步骤失效，从受影响位置重新规划。

**摘要触发条件**：Token 预算、任务阶段变化、关键状态更新和偏航风险——短任务没必要机械摘要，长任务也不能等到固定轮次才检查（固定每五轮摘要、超二十轮强制重对齐只能作为工程策略，不是普适定律）。

## 中断恢复：checkpoint 三问与幂等

Checkpoint 至少要回答三个问题：① 这是哪个用户的哪个任务？② 保存的是哪一个一致状态？③ 恢复后哪一步可以安全执行？

**外部写操作的稳妥边界：执行前登记意图，执行后记录结果**。准备发群消息时先把工具调用记为 `planned`，生成稳定的 `operation_id`；真正发送成功后再保存平台返回的 `message_id`，把状态改成 `succeeded`。

**恢复顺序**：
1. 可信身份校验 `session_id`/`thread_id` → 定位 `task_id`（防读取别人的任务）；
2. 加载最近一次完整提交的 checkpoint，校验状态版本和工作流版本（不能把旧结构直接喂给新代码）；
3. 查看 `pending_tools`：`succeeded` 跳过 / `failed` 按策略重试 / **`unknown` 先去外部系统核对**；
4. 重新组装最小必要上下文；
5. 从合法状态继续执行，记录恢复来源、次数和结果（审计排障）。

**为什么有 unknown**：群消息已发出但工具响应还没写回状态时进程崩了——系统只知道调用开始过不知道结果。若恢复后直接重试，用户可能收到两条一样的消息。**跨网络跨系统时不存在「恰好执行一次」，更实际的办法是让副作用可幂等**：
- 稳定的业务幂等键，外部接口支持按键去重；
- 数据库写入用唯一约束或 upsert；
- 发送类动作保存去重记录，优先按 `operation_id` 查询执行结果。

外部系统既不能查询也不支持幂等 → 恢复程序不该盲目重发，把状态转入人工确认，明确告诉用户「上次发送结果无法确认」。

## 线上实现细节

| 维度 | 实践要点 |
|------|---------|
| 状态存储分层 | 活跃会话放 Redis 低延迟存储；关键 checkpoint 和审计记录落持久化数据库/对象存储 |
| TTL 策略 | 可清理已结束、可重建的会话缓存；但不能让仍在等待审批的长期任务因半小时没人说话就消失 |
| 多实例并发 | 按 `task_id` 加租约或分布式锁 + `state_version` 比较后更新 |
| 请求去重 | 每条用户请求带 `request_id`，重复提交直接返回之前的结果 |
| 敏感信息 | 不长期保存所有原始工具结果；密码令牌不入状态 |
| 大结果管理 | 存外部，只保留摘要、哈希和引用 |
| 日志追踪 | 脱敏，按租户和用户访问隔离 |

**观测指标**：意图改写次数、澄清率、非法状态转换次数、恢复成功率、重复副作用次数、中断到恢复耗时、恢复后结果与不中断基线的一致性。

## 面试要点

1. 先分类：对话历史、业务状态、任务状态、长期记忆分开管（解决不同问题）；
2. 再显式记录：`core_intent` 锚定目标 + `current_subtask`/`pending_tools`/`completed_steps`/`context_snapshot` 记录进度；
3. 每轮判断输入性质：补充/纠错/澄清回复/新任务；
4. 模型提议、系统放行：模型可提出状态更新，状态机和确定性校验最终放行；
5. 防跑偏不是死守第一句话：`core_intent` 防模型静默改目标，用户明确修改时版本化更新或创建新 `task_id`；
6. 中断恢复说到 checkpoint + session/task ID + 幂等：先加载最近一致状态再核对未决工具调用；付款、发消息、创建订单等外部副作用用稳定幂等键和结果查询，**绝不能看到步骤没写成成功就直接重跑**。
