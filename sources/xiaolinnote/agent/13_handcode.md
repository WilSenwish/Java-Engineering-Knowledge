# Agent 面试题 13：为什么有时候选择「手搓」Agent 而不是用成熟框架？

## 核心答案

框架用起来快，但有几个实际痛点：① **抽象层太多**，调试时不知道哪步出了问题，得一层层往下扒；② **版本升级经常有破坏性变更**，线上稳定性难保证；③ **通用设计和具体业务需求有偏差**，定制起来反而更费劲。

手搓的代码完全在自己掌控之内：可观测性好、出问题好排查、方便性能优化。**策略：核心逻辑手写，只在边缘功能上用框架的工具。**

## 框架的价值（真实，不要一开口就否定）

从零搭 Agent 的重复工作：定义工具格式让 LLM 理解、解析工具调用结果、维护对话历史（不丢消息顺序对）、处理工具失败重试、接向量库做检索——每个 Agent 项目都得做一遍且大同小异。框架把这些全封装好（LangChain 一个 `@tool` 装饰器注册工具、`AgentExecutor` 封装整个 ReAct loop，还内置 tracing/callback/记忆管理）。**POC 阶段两周的工作缩短到两天，快速验证 idea 阶段框架几乎没有明显副作用。**

## 框架的三个痛点（随项目推进逐渐浮现）

1. **抽象层太多，排查困难**：代码只有五十行，报错 stack trace 四十层，追到框架内部——不知道问题出在自己写的五十行、框架某版本逻辑变化、还是 callback 触发时机。类比：老式车打开引擎盖能看到哪根管子漏油；现代豪华车打开引擎盖是一堆看不懂的电子设备，只能去 4S 店接诊断仪。**框架的抽象层是排查问题的认知负担**。（LangSmith 等 tracing 能追踪调用链，但解决不了 breaking change 和隐性性能开销）
2. **版本升级 breaking change**：线上跑几个月，一次依赖升级框架改了接口，代码直接报错，要么回滚要么改十几处兼容。（LangChain 后来采用 semver 稳定性有改善，但早期教训让很多团队对框架依赖保持警惕；`AgentExecutor` 在新版已被废弃、官方推荐迁移 LangGraph 即是例证）
3. **隐性性能开销**：profile 发现某步 LLM 调用本身很快但总耗时超预期——框架内部每次调用做着你不需要的事：序列化中间结果、触发一堆 callback、记录详细日志。**这些是框架为通用性设计的，对你的场景没用但每次都在跑**，高流量下累积成真实可见的延迟增加和费用浪费。

## 手搓的本质优势：完全掌控

1. **链路透明、可观测性好**：每行代码都知道在干什么，任意位置加日志/打断点/插监控，没有黑盒。线上问题靠日志复现最快，链路清晰定位根因快——生产环境里真实的时间和成本节省；
2. **精确裁剪、无多余开销**：只写确实需要的逻辑，不带通用性包袱，性能优化空间完全在自己手里；
3. **稳定可控**：自己写的接口不会突然变，没有外部 breaking change，依赖只有底层 LLM SDK，生产可长期运行。

**Anthropic 官方 Agent 构建指南同样建议**：不要一上来就用框架，先用最少的抽象把核心逻辑跑通——「框架的抽象层会让你离底层更远，一旦出了问题，调试成本比你省下的开发时间还高」。

**类比**：框架是「租房」（装修好直接住，但结构改不了、房东可能调整政策）；手搓是「自建」（建起来慢，但结构都熟悉、改什么都能改、住着踏实）。

## 代码对比：框架 vs 手搓（带工具调用的 Agent loop）

```python
# 框架版（LangChain）：三四行跑起来，但内部调用链十几层
agent = create_openai_tools_agent(llm, tools, prompt)
executor = AgentExecutor(agent=agent, tools=tools)
result = executor.invoke({"input": "帮我查一下今天的天气"})

# 手搓版：代码量多一些，但每一步都在眼前
messages = [{"role": "system", "content": system_prompt},
            {"role": "user", "content": user_input}]
for i in range(max_turns):
    response = client.chat.completions.create(model="gpt-4", messages=messages, tools=tool_schemas)
    msg = response.choices[0].message
    messages.append(msg)
    if not msg.tool_calls:
        break                      # LLM 认为任务完成
    for tc in msg.tool_calls:
        result = execute_tool(tc.function.name, tc.function.arguments)
        messages.append({"role": "tool", "tool_call_id": tc.id, "content": result})
        logger.info(f"工具 {tc.function.name} 返回: {result}")   # 随意加日志/监控/重试
```

消息列表怎么拼的、工具怎么选的、循环什么时候退出，每个细节都摆在明面上——**「完全掌控」的具体含义**。

## 什么时候用框架，什么时候手搓（不是非此即彼）

- **框架适合**：POC 阶段快速验证 idea（目标是跑通不是优化）；团队刚接触 Agent 开发（少踩基础坑）；周边工具（文档解析、向量检索）依赖框架生态且核心逻辑复杂度不高；
- **手搓适合**：准备上生产（稳定性是核心关切）；流量上来（性能和成本敏感）；业务逻辑高度定制与通用设计偏差大；团队需要高可观测性；
- **折中方案（最常见最务实）：核心手写，周边借用**。控制边界：**工具调用循环、对话历史管理、错误处理重试、任务状态维护是 Agent 的「心脏」，直接决定系统行为，必须百分百理解百分百掌控 → 手写**；LangSmith tracing、LlamaIndex 文档解析、向量库客户端是「工具性」周边，出了问题一眼能看出来，不会带来黑盒困境 → 用外部工具。类比盖房子：核心结构承重墙必须自己掌控，门锁插座水龙头可以买现成的。

## 判断信号

**如果你能清楚说出「框架在某个地方替我做了什么、我用的这个方法内部发生了什么」，说明你理解它；如果你只是调了一个方法但完全不知道里面发生了什么，出了问题就是一个不透明的黑盒——这才是需要警惕的信号。框架本身不是问题，「不理解就依赖」才是。**

典型演进轨迹：先用框架快速跑通验证方向 → 遇到第一批线上问题后把排查困难的关键部分替换为手写 → 流量上来后把性能敏感的核心逻辑全部手写 → 最后框架只保留做得好的周边工具。

## 面试要点

1. 先承认框架的价值真实（POC 省时）；
2. 痛点说具体：抽象层多排查难 / breaking change / 隐性性能开销——泛泛说「框架有缺点」没说服力；
3. 手搓核心价值「完全掌控」：可观测、稳定、可精确裁剪；
4. 主动说折中方案：核心手写 + 周边借用——面试官通常很认可；
5. 金句收尾：框架不是问题，「不理解就依赖」才是。
