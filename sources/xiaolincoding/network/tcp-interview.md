# TCP 三次握手与四次挥手面试题

> 任 TCP 虐我千百遍，我仍待 TCP 如初恋。
> 本文不涉及 TCP 流量控制、拥塞控制、可靠性传输（见《TCP 重传、滑动窗口、流量控制、拥塞控制》）。

## TCP 基本认识

### TCP 头格式有哪些？

**序列号**：建立连接时由计算机生成的随机数作为初始值，通过 SYN 包传给接收端主机，每发送一次数据就「累加」该「数据字节数」的大小。**用来解决网络包乱序问题。**

**确认应答号**：指下一次「期望」收到的数据的序列号，发送端收到这个确认应答后可以认为该序号以前的数据都已被正常接收。**用来解决丢包的问题。**

**控制位**：

- **ACK**：为 `1` 时「确认应答」字段有效，TCP 规定除最初建立连接时的 SYN 包之外该位必须置 `1`。
- **RST**：为 `1` 时表示连接中出现异常必须强制断开。
- **SYN**：为 `1` 时表示希望建立连接，并在「序列号」字段进行初始值设定。
- **FIN**：为 `1` 时表示今后不会再有数据发送，希望断开连接。

### 为什么需要 TCP 协议？TCP 工作在哪一层？

IP 层是「不可靠」的：不保证网络包交付、不保证按序交付、不保证数据完整性。保障可靠性需要由上层（传输层）TCP 负责。TCP 是工作在**传输层**的**可靠**数据传输服务，确保接收端收到的网络包是**无损坏、无间隔、非冗余和按序的**。

### 什么是 TCP？

TCP 是**面向连接的、可靠的、基于字节流**的传输层通信协议。

- **面向连接**：一定「一对一」，不能像 UDP 一个主机同时向多个主机发消息（一对多做不到）。
- **可靠的**：无论链路如何变化，TCP 都保证一个报文一定能够到达接收端。
- **字节流**：用户消息可能被操作系统「分组」成多个 TCP 报文；若接收方程序不知道「消息的边界」就无法读出有效用户消息。TCP 报文有序，前一个报文没收到时即使先收到后一个也不能扔给应用层；重复报文自动丢弃。

### 什么是 TCP 连接？

RFC 793 定义：用于保证可靠性和流量控制维护的某些状态信息的组合，包括 Socket、序列号和窗口大小称为连接。建立连接即双方对以下三信息达成共识：

- **Socket**：由 IP 地址和端口号组成
- **序列号**：解决乱序问题
- **窗口大小**：流量控制

### 如何唯一确定一个 TCP 连接？

TCP 四元组唯一确定一个连接：

- 源地址、目的地址（32 位，IP 头部）
- 源端口、目的端口（16 位，TCP 头部）

**服务端单机最大 TCP 连接数**：客户端 IP 最多 2^32，端口最多 2^16，理论值约为 **2^48**。实际远达不到，受以下因素限制：

- **文件描述符限制**（每个连接是一个文件）：
  - 系统级：`cat /proc/sys/fs/file-max`
  - 用户级：`cat /etc/security/limits.conf`
  - 进程级：`cat /proc/sys/fs/nr_open`
- **内存限制**：每个连接占用一定内存，占满后 OOM。

### UDP 和 TCP 有什么区别？分别的应用场景？

UDP 不提供复杂控制机制，利用 IP 提供面向「无连接」的通信服务。头部只有 8 字节（64 位）：

- 目标和源端口：告诉 UDP 协议把报文发给哪个进程
- 包长度：UDP 首部长度 + 数据长度
- 校验和：防止收到传输受损的 UDP 包

**TCP 和 UDP 区别**：

| 维度 | TCP | UDP |
|------|-----|-----|
| 连接 | 面向连接，传输数据前先建立连接 | 无连接，即刻传输 |
| 服务对象 | 一对一两点服务 | 一对一、一对多、多对多 |
| 可靠性 | 可靠交付：无差错、不丢失、不重复、按序 | 不可靠，丢了就丢了（可基于 UDP 实现可靠传输，如 QUIC） |
| 拥塞/流量控制 | 有 | 无，网络拥堵也不影响发送速率 |
| 首部开销 | 20 字节起，有「选项」字段时变长 | 8 字节固定 |
| 传输方式 | 流式传输，无边界，保证顺序可靠 | 一个包一个包，有边界，可能丢包乱序 |
| 分片 | 大于 MSS 在**传输层**分片，丢一个分片只重传该分片 | 大于 MTU 在 **IP 层**分片，丢一个分片整个报文重传 |

**应用场景**：

- TCP：FTP 文件传输、HTTP/HTTPS
- UDP：包总量较少的通信（DNS、SNMP）、视频音频多媒体、广播通信

> **为什么 UDP 头部没有「首部长度」字段，TCP 有？**
> TCP 有可变长的「选项」字段，UDP 头部长度固定不变，无需记录。
>
> **为什么 UDP 有「包长度」字段，TCP 没有？**
> TCP 负载长度可通过「IP 总长度 - IP 首部长度 - TCP 首部长度」算出，UDP 同理也可算出，所以 UDP 的「包长度」看似冗余。两种靠谱说法：① 为硬件设计处理方便，首部长度需为 4 字节整数倍，去掉该字段后 UDP 首部就不是 4 的整数倍；② 早期 UDP 可能基于不提供报文长度/首部长度的网络层协议，故需要该字段。

### TCP 和 UDP 可以使用同一个端口吗？

**可以。** 传输层端口用于区分同一主机上不同应用程序。TCP 和 UDP 在内核是两个完全独立的软件模块，IP 包头的「协议号」字段决定送给哪个模块，各自根据「端口号」确定应用程序，端口号相互独立。如 TCP 有 80 端口，UDP 也可以有 80 端口，并不冲突。

延伸问题（见《TCP 和 UDP 可以使用同一个端口吗？》）：

- 多个 TCP 服务进程可以同时绑定同一个端口吗？
- 重启 TCP 服务进程为什么出现 "Address in use"？如何避免？
- 客户端端口可以重复使用吗？
- 客户端 TIME_WAIT 过多会导致端口资源耗尽吗？

## TCP 连接建立

### TCP 三次握手过程？

1. 客户端和服务端都处于 `CLOSE`。服务端主动监听某端口，进入 `LISTEN`。
2. 客户端随机初始化序号 `client_isn`，置于 TCP 首部「序号」字段，`SYN=1`，发送 SYN 报文（不含应用层数据），进入 `SYN-SENT`。
3. 服务端收到后，随机初始化 `server_isn` 填入「序号」，「确认应答号」填 `client_isn + 1`，`SYN=1, ACK=1`，发回 SYN+ACK（不含应用层数据），进入 `SYN-RCVD`。
4. 客户端收到后回最后一个应答报文：`ACK=1`，「确认应答号」填 `server_isn + 1`。**该报文可以携带客户端到服务端的数据**，客户端进入 `ESTABLISHED`。
5. 服务端收到该应答后也进入 `ESTABLISHED`。

**要点：第三次握手可以携带数据，前两次不可以**（面试常考）。完成后双方即可互相发送数据。

### 如何在 Linux 中查看 TCP 状态？

`netstat -napt`

### 为什么是三次握手？不是两次、四次？

常回答"保证双方具有接收和发送的能力"没问题但片面。**核心在于：为什么三次握手才可以初始化 Socket、序列号和窗口大小并建立 TCP 连接。** 三个原因：

#### 原因一：阻止重复历史连接的初始化（**主要原因**）

RFC 793 指出的首要原因：

> *The principle reason for the three-way handshake is to prevent old duplicate connection initiations from causing confusion.*

场景：客户端发 SYN（seq=90）后宕机，SYN 被网络阻塞；客户端重启后发新 SYN（seq=100）。

三次握手如何阻止：

- 旧 SYN 先到达服务端 → 服务端回 SYN+ACK，确认号 91（90+1）；
- 客户端发现期望的确认号应为 101 而非 91 → 回 **RST**；
- 服务端收到 RST 释放连接；
- 新 SYN 到达后正常完成三次握手。

**TIP**：若服务端先收到「旧 SYN」再收到「新 SYN」，会对新 SYN 回 [Challenge Ack](https://xiaolincoding.com/network/3_tcp/challenge_ack.html)（ack 仍是上一次的确认号 91），客户端发现不匹配仍回 RST。

**两次握手为何无法阻止？** 两次握手下服务端收到 SYN 即进入 ESTABLISHED，没有中间状态给客户端阻止历史连接的机会。若是历史连接，服务端在收到 RST 前已可发送数据，白白浪费资源。**因此必须在服务端发送数据前阻止历史连接，这需要三次握手。**

**TIP**：第三次握手（ACK）后客户端即可发数据，此时服务端还是 SYN_RCVD 状态，若 ACK 丢了数据是否白费？——不是，数据报文中含 ACK 标识和确认号（确认第二次握手），服务端收到数据报文可正常建立连接并接收该数据包。

#### 原因二：同步双方初始序列号

序列号的作用：

- 接收方去除重复数据；
- 按序接收；
- 标识哪些数据已被对方收到（通过 ACK 中的序列号）。

双方都必须可靠同步初始序列号：客户端发 SYN 需服务端 ACK 确认，服务端发 SYN 也需客户端 ACK 确认，**一来一回才能确保双方 ISN 可靠同步**。四次握手也能同步，但第二、三步可合并成一步，故为三次。两次握手只保证一方 ISN 被对方收到。

#### 原因三：避免资源浪费

两次握手时，客户端 SYN 阻塞后重发，服务端因不知客户端是否收到 ACK，**每收到一个 SYN 就只能先建一个连接**，消息滞留时会建立多个冗余无效连接，浪费资源。

#### 小结

三次握手能防止历史连接建立、减少双方资源开销、同步初始化序列号。序列号保证数据包不重复、不丢弃、按序传输。

- 两次握手：无法防历史连接、浪费资源、无法可靠同步序列号；
- 四次握手：三次已是理论上最少可靠连接建立。

### 为什么每次建立连接初始化的序列号要求不一样？

两个原因：

1. **防止历史报文被下一个相同四元组的连接接收**（主要）：若 ISN 都从 0 开始，旧连接中被阻塞的数据包可能在新连接的接收窗口内被正常接收，造成数据错乱。ISN 不同则大概率落在窗口外被丢弃（非完全避免，序列号会回绕，需时间戳机制判断，见《TCP 如何避免历史报文》）；
2. **安全性**：防止黑客伪造相同序列号的 TCP 报文被接收。

### 初始序列号 ISN 如何随机产生？

RFC793 算法：**ISN = M + F(localhost, localport, remotehost, remoteport)**

- `M`：计时器，每 4 微秒 +1，转一圈 4.55 小时；
- `F`：Hash 算法，根据源 IP、目的 IP、源端口、目的端口生成随机值，不能被外部轻易推算（MD5 是好选择）。

### 既然 IP 层会分片，为什么 TCP 层还需要 MSS？

- **MTU**：一个网络包的最大长度，以太网一般 1500 字节；
- **MSS**：除去 IP 和 TCP 头部后，一个网络包能容纳的 TCP 数据最大长度。

若把 TCP 整个报文交给 IP 层分片：**一个 IP 分片丢失，整个 IP 报文所有分片都得重传**（IP 层无超时重传，丢失后接收方无法组装完整 TCP 报文，不回 ACK，发送方超时后重发整个 TCP 报文），效率极差。

TCP 建立连接时协商双方 MSS，数据超 MSS 时在 TCP 层先分片，形成的 IP 包不大于 MTU，无需 IP 分片；一个 TCP 分片丢失只需重传该分片，大大提高重传效率。

### 第一次握手丢失会发生什么？

客户端发 SYN 后进入 `SYN_SENT`，收不到第二次握手（SYN-ACK）触发超时重传，**重传的 SYN 序列号不变**。

- Linux 中最大重传次数由 `tcp_syn_retries` 控制（默认 5）；
- 重传间隔翻倍：1s → 2s → 4s → 8s → 16s，第五次后再等 32s；
- 总耗时 1+2+4+8+16+32 = **63 秒**（约 1 分钟）。

### 第二次握手丢失会发生什么？

第二次握手 SYN-ACK 有两个目的：确认第一次握手的 ACK + 服务端发起连接的 SYN。丢失后**双方都重传**：

- 客户端：认为自己的 SYN 丢了，重传 SYN（`tcp_syn_retries`，默认 5）；
- 服务端：收不到第三次握手 ACK，重传 SYN-ACK（`tcp_synack_retries`，默认 5）。

### 第三次握手丢失会发生什么？

第三次握手 ACK 是对第二次握手的确认，丢失后**服务端重传 SYN-ACK**（由 `tcp_synack_retries` 控制），直到收到或达到最大次数。注意：**ACK 报文本身不会重传，ACK 丢了由对方重传对应报文**。

### 什么是 SYN 攻击？如何避免？

攻击者短时间伪造不同 IP 的 SYN 报文，服务端每收一个 SYN 进入 `SYN_RCVD`，但回应的 SYN+ACK 得不到 ACK 应答，**占满半连接队列**，无法为正常用户服务。

**两个队列**：

- **半连接队列（SYN 队列）**：收到 SYN 创建半连接对象加入，发 SYN+ACK 等待 ACK；
- **全连接队列（Accept 队列）**：收到 ACK 后从 SYN 队列取出半连接对象，创建新连接放入；应用通过 `accept()` 取出。

超过队列长度限制默认丢弃报文。SYN 攻击打满半连接队列，后续 SYN 被丢弃。

**四种防御方式**：

1. **调大 netdev_max_backlog**：网卡接收速度大于内核处理速度时的队列，默认 1000，可调至 10000：
   ```bash
   net.core.netdev_max_backlog = 10000
   ```
2. **增大半连接队列**（需同时调三个参数）：
   - `net.ipv4.tcp_max_syn_backlog`
   - `listen()` 的 backlog
   - `net.core.somaxconn`
3. **开启 tcp_syncookies**：SYN 队列满时不丢弃 SYN，而是计算 cookie 值放到第二次握手的序列号里；客户端 ACK 合法则放入 Accept 队列。**队列满时仍能正常建立连接**。
   - 0 关闭；1 仅当半连接队列满时启用（**应对 SYN 攻击设 1**）；2 无条件开启。
   ```bash
   $ echo 1 > /proc/sys/net/ipv4/tcp_syncookies
   ```
4. **减少 SYN+ACK 重传次数**：加快处于 SYN_RCVD 状态的连接断开：
   ```shell
   $ echo 2 > /proc/sys/net/ipv4/tcp_synack_retries
   ```

## TCP 连接断开

### TCP 四次挥手过程？

双方都可以主动断开：

1. 客户端发 `FIN=1` 报文，进入 `FIN_WAIT_1`；
2. 服务端回 `ACK`，进入 `CLOSE_WAIT`；
3. 客户端收到 ACK，进入 `FIN_WAIT_2`；
4. 服务端处理完数据后发 `FIN`，进入 `LAST_ACK`；
5. 客户端回 `ACK`，进入 `TIME_WAIT`；
6. 服务端收到 ACK 进入 `CLOSE`，完成关闭；
7. 客户端经过 `2MSL` 自动进入 `CLOSE`。

每个方向需要**一个 FIN 和一个 ACK**，故称四次挥手。**注意：只有主动关闭连接的一方才有 TIME_WAIT 状态。**

### 为什么挥手需要四次？

客户端 FIN 只表示不再发数据但还能接收；服务端收到 FIN 先回 ACK，可能还有数据要处理发送，等服务端不再发数据时才发 FIN。服务端的 ACK 和 FIN 一般分开发送，故需四次。**特定情况下可变成三次挥手**（见《TCP 四次挥手，可以变成三次吗？》）。

### 第一次挥手丢失会发生什么？

客户端迟迟收不到 ACK 触发超时重传 FIN，重发次数由 `tcp_orphan_retries` 控制；超过次数后再等 2 倍超时时间收不到第二次挥手，直接进入 `close`。

### 第二次挥手丢失会发生什么？

ACK 报文不会重传，客户端收不到第二次挥手就重传 FIN，直到收到或达到最大次数（`tcp_orphan_retries`）。

**FIN_WAIT_2 时长**：`tcp_fin_timeout` 控制，默认 60 秒。close 关闭的连接若 60 秒内收不到 FIN 则直接关闭。但若是 shutdown 只关发送方向，可一直处于 FIN_WAIT_2（`tcp_fin_timeout` 管不了 shutdown 关闭的连接）。

### 第三次挥手丢失会发生什么？

服务端处于 CLOSE_WAIT 时**内核无权代替进程关闭连接，必须由进程调用 close**，之后内核发 FIN 进入 LAST_ACK。收不到第四次挥手 ACK 则重发 FIN（`tcp_orphan_retries`）。客户端侧若 `tcp_fin_timeout` 内没收到第三次挥手也会断开。

### 第四次挥手丢失会发生什么？

客户端收到服务端 FIN 后回 ACK 进入 TIME_WAIT（持续 2MSL）。服务端没收到 ACK 前处于 LAST_ACK，会重发 FIN（`tcp_orphan_retries`）。客户端 TIME_WAIT 期间再次收到 FIN 会**重置 2MSL 定时器**。

### 为什么 TIME_WAIT 等待 2MSL？

MSL（Maximum Segment Lifetime）报文最大生存时间，超过则被丢弃。MSL 单位是时间，TTL 是路由跳数，**MSL ≥ TTL 消耗为 0 的时间**。TTL 一般 64，Linux MSL = 30 秒。

2MSL 的合理解释：一来一回两个方向的数据包都需时间自然消亡，相当于**至少允许报文丢失一次**。若 ACK 在一个 MSL 内丢失，被动方重发的 FIN 会在第 2 个 MSL 内到达，TIME_WAIT 可应对。为何不是 4/8 MSL：丢包率 1% 的糟糕网络连续两次丢包概率万分之一，忽略比解决更划算。

Linux 2MSL 固定 60 秒，定义在内核 `TCP_TIMEWAIT_LEN`：

```c
#define TCP_TIMEWAIT_LEN (60*HZ) /* how long to wait to destroy TIME-WAIT state, about 60 seconds */
```

修改需改内核代码并重新编译。2MSL 从**客户端收到 FIN 后发 ACK 开始计时**，期间收到重传 FIN 会重新计时。

### 为什么需要 TIME_WAIT 状态？

主动关闭方才有。两个原因：

1. **防止历史连接中的数据，被后面相同四元组的连接错误接收**：序列号和 ISN 是 32 位会回绕，无法据此判断新老数据。若 TIME_WAIT 过短，旧连接被延迟的数据包（如 SEQ=301）可能在新连接接收窗口内被正常接收，造成数据错乱。2MSL 足以让两个方向的数据包都自然消失。
2. **保证被动关闭方被正确关闭**（RFC 793）：确保最后的 ACK 能让被动方收到。若客户端发完 ACK 直接 CLOSE，ACK 丢失后服务端重传 FIN，客户端已关闭只能回 RST，被服务端解释为错误（Connection reset by peer），不够优雅。TIME_WAIT 保证客户端还在，收到重传 FIN 时重置 2MSL 计时。

### TIME_WAIT 过多有什么危害？

- **占用系统资源**：文件描述符、内存、CPU、线程；
- **占用端口资源**：可开启端口一般 `32768~61000`（`net.ipv4.ip_local_port_range`）。

客户端与服务端 TIME_WAIT 过多影响不同：

- **客户端过多**：占满端口后无法对「目的 IP+目的 PORT」都一样的服务端发起新连接，但已用端口仍可连其他服务端（连接定位靠四元组，端口可复用）；
- **服务端过多**：服务端只监听一个端口，端口不受限，但连接过多占用系统资源。

### 如何优化 TIME_WAIT？

1. **`net.ipv4.tcp_tw_reuse = 1`**（配合 `net.ipv4.tcp_timestamps=1`，默认即 1）：复用 TIME_WAIT 超过 1 秒的 socket 给新连接。**仅能用客户端（连接发起方）**，因为 `connect()` 时内核随机找一个 time_wait 超 1 秒的连接复用。有 TCP 时间戳后 2MSL 问题不复存在（重复数据包因时间戳过期被丢弃）。
2. **`net.ipv4.tcp_max_tw_buckets`**（默认 18000）：超过该值的 TIME_WAIT 连接状态被重置，比较暴力。
3. **SO_LINGER**：`l_onoff=1, l_linger=0` 时 close 后立即发 RST，跳过四次挥手和 TIME_WAIT。危险行为，不提倡。

《UNIX 网络编程》：**TIME_WAIT 是我们的朋友，不要试图避免，而应弄清楚它。如果服务端要避免过多 TIME_WAIT，就永远不要主动断开连接，让客户端断开，由分布在各处的客户端承受 TIME_WAIT。**

### 服务器大量 TIME_WAIT 的原因？

TIME_WAIT 是主动关闭方状态 → 服务器主动断了很多连接。三个场景：

1. **HTTP 没有使用长连接**：
   - HTTP/1.0 默认关闭 Keep-Alive，需请求/响应 header 均带 `Connection: Keep-Alive`；HTTP/1.1 默认开启；
   - 任一方 header 带 `Connection: close` 就无法使用长连接，变成短连接（建立 → 请求 → 响应 → 释放）；
   - **按大多数 Web 服务实现，无论哪方禁用 Keep-Alive，都是服务端主动关闭**：
     - 客户端禁用：请求带 `Connection: close`，不重用的时机只能在服务端（请求-响应周期末端）；
     - 服务端禁用：服务端 close 一次 syscall 搞定；若让客户端关，需把 socket 放 readable 队列 + epoll 等待 + read 确认，两次 syscall 且 socket 保持更久；
   - **排查**：客户端和服务端是否都开启了 Keep-Alive。
2. **HTTP 长连接超时**：nginx `keepalive_timeout`（如 60 秒），客户端超时不发新请求则 nginx 主动关闭。大量"建连后长时间不发数据"时优先排查网络问题。
3. **HTTP 长连接请求数达上限**：nginx `keepalive_requests` 默认 100，高 QPS 场景（>10000 QPS）频繁关闭连接产生大量 TIME_WAIT。**解决：调大该参数**。

### 服务器大量 CLOSE_WAIT 的原因？

CLOSE_WAIT 是**被动关闭方**状态，若服务端程序不调用 close 就发不出 FIN，无法转入 LAST_ACK。**大量 CLOSE_WAIT 说明服务端程序没有 close，需排查代码。**

普通 TCP 服务端流程：① 创建 socket → bind → listen；② 注册到 epoll；③ epoll_wait 等连接，accept 获取 socket；④ 已连接 socket 注册 epoll；⑤ 等事件；⑥ 对方关闭时调用 close。

四种未 close 的原因：

1. 第 2 步没做：服务端 socket 没注册 epoll，无法感知新连接（明显 bug，review 阶段能发现）；
2. 第 3 步没做：有新连接时没 accept，客户端断开后服务端没机会 close（可能 accept 前代码卡住或抛异常）；
3. 第 4 步没做：accept 后的 socket 没注册 epoll，无法感知 FIN（注册前卡住或抛异常，参见《一次 Netty 代码不健壮导致的大量 CLOSE_WAIT 连接原因分析》）；
4. 第 6 步没做：发现客户端关闭后没执行 close（漏处理或 close 前卡住，如死锁）。

**方向：服务端为什么没有调用 close。**

### 连接建立后客户端突然故障怎么办？

客户端宕机/断电时若服务端一直不发数据，永远感知不到，连接一直 ESTABLISHED 占用资源。TCP **保活机制**：一段时间无连接活动则每隔一定间隔发探测报文，连续几个无响应则认为连接死亡，通知上层。

Linux 参数（默认值）：

```shell
net.ipv4.tcp_keepalive_time=7200    # 2 小时无活动启动保活
net.ipv4.tcp_keepalive_intvl=75     # 探测间隔 75 秒
net.ipv4.tcp_keepalive_probes=9     # 探测 9 次无响应判定不可达
```

最少 **2 小时 11 分 15 秒**才发现死亡连接。应用需设置 `SO_KEEPALIVE` 才生效。三种情况：

1. 对端正常：正常响应，保活时间重置；
2. 对端宕机重启：可响应但无该连接信息，回 **RST**，很快发现连接被重置；
3. 对端宕机或报文不可达：探测报文石沉大海，达次数后判定连接死亡。

注意：**进程崩溃时操作系统回收资源会发 FIN，主机宕机才需要保活探测。** 应用层可自实现心跳（如 nginx keepalive_timeout 定时器）。

### 连接建立后服务端进程崩溃会发生什么？

TCP 连接信息由**内核**维护。进程崩溃后内核回收其所有 TCP 连接资源，**发第一次 FIN，后续挥手都在内核完成，无需进程参与**。kill -9 实验证实：进程被杀后服务端仍与客户端完成四次挥手。

## Socket 编程

### TCP 如何 Socket 编程？

1. 服务端和客户端初始化 socket，得到文件描述符；
2. 服务端 `bind`，绑定指定 IP 和端口；
3. 服务端 `listen`，监听；
4. 服务端 `accept`，等待客户端连接；
5. 客户端 `connect`，向服务端地址端口发起连接；
6. 服务端 `accept` 返回用于传输的 socket fd；
7. 客户端 `write` 写数据，服务端 `read` 读数据；
8. 客户端断开调用 `close`，服务端 `read` 读到 `EOF`，处理完数据后 `close`。

**注意**：accept 成功返回的是**已完成连接 socket**；监听 socket 与传输 socket 是「两个」socket。

### listen 时 backlog 的意义？

内核维护两个队列：

- 半连接队列（SYN 队列）：收到 SYN，处于 SYN_RCVD；
- 全连接队列（Accept 队列）：完成三次握手，处于 ESTABLISHED。

```c
int listen(int socketfd, int backlog)
```

- 早期 Linux 内核 backlog 是 SYN 队列大小；
- Linux 2.2 之后 backlog 是 **accept 队列**大小，**上限为内核参数 `somaxconn`：accept 队列长度 = min(backlog, somaxconn)**。

### accept 发生在三次握手的哪一步？

- 客户端协议栈收到服务端 ACK 后，**connect 调用返回（第二次握手时）**，客户端到服务端单向连接建立成功，同时客户端对服务端 SYN 应答（server_isn+1）；
- ACK 到达服务端后，服务端连接进入 ESTABLISHED，**accept 阻塞调用返回（三次握手成功后）**。

结论：**客户端 connect 成功返回在第二次握手，服务端 accept 成功返回在三次握手成功之后。**

### 客户端调用 close 后的断开流程？

1. 客户端 close → 发 FIN，进入 FIN_WAIT_1；
2. 服务端收到 FIN，TCP 协议栈向接收缓冲区插入文件结束符 `EOF`（**排在已排队数据之后**），应用通过 read 感知；服务端进入 CLOSE_WAIT；
3. 服务端处理完数据读到 EOF，调用 close 发 FIN，进入 LAST_ACK；
4. 客户端收到 FIN 回 ACK，进入 TIME_WAIT；
5. 服务端收到 ACK 进入 CLOSE；
6. 客户端 2MSL 后进入 CLOSE。

### 没有 accept，能建立 TCP 连接吗？

**可以。** accept 不参与三次握手，只负责从全连接队列取出已建立连接的 socket，供用户层读写。

### 没有 listen，能建立 TCP 连接吗？

**可以。** 客户端可以自己连自己（**TCP 自连接**），或两个客户端同时向对方发请求（**TCP 同时打开**），共同点是**没有服务端 listen 也能建立连接**。
