# HTTP 常见面试题

> 6 大类常问题目：HTTP 基本概念 / Get 与 Post / HTTP 特性 / HTTP 缓存技术 / HTTPS 与 HTTP / HTTP 1.1、2、3 演变。

## HTTP 基本概念

### HTTP 是什么？

HTTP 是超文本传输协议（HyperText Transfer Protocol）。拆解：

- **协议**：两个以上参与者 + 行为约定和规范；
- **传输**：两点之间搬运数据，是**双向协议**，允许中间人中转接力（A <-> N <-> M <-> B）；
- **超文本**：文字、图片、视频等的混合体，关键是有超链接能跳转。HTML 是最常见超文本。

准确表述：**HTTP 是一个在计算机世界里专门在「两点」之间「传输」文字、图片、音频、视频等「超文本」数据的「约定和规范」**。

> "HTTP 是用于从互联网服务器传输超文本到本地浏览器的协议"说法不正确——也可以是服务器↔服务器。

### 常见的状态码

- `1xx`：提示信息，中间状态，实际用得少；
- `2xx`：成功。`200 OK`（最常见，非 HEAD 请求有 body）；`204 No Content`（成功但无 body）；`206 Partial Content`（分块下载/断点续传）；
- `3xx`：重定向。`301 Moved Permanently`（永久，资源不存在需换 URL）；`302 Found`（临时）；都会带 `Location` 字段；`304 Not Modified`（缓存重定向，可用本地缓存）；
- `4xx`：客户端报文有误。`400 Bad Request`（笼统错误）；`403 Forbidden`（禁止访问，非请求出错）；`404 Not Found`；
- `5xx`：服务端内部错误。`500 Internal Server Error`；`501 Not Implemented`；`502 Bad Gateway`（网关/代理访问后端出错）；`503 Service Unavailable`。

### 常见字段

- **Host**：指定服务器域名（`Host: www.A.com`），同一服务器不同网站；
- **Content-Length**：回应数据长度（字节）。**HTTP 通过回车换行符作为 header 边界 + Content-Length 作为 body 边界，解决 TCP 粘包问题**；
- **Connection**：最常用于要求长连接（`Connection: Keep-Alive`），任意端未明确断开则保持 TCP 连接。**HTTP Keep-Alive ≠ TCP Keepalive**；
- **Content-Type**：回应数据格式（`text/html; Charset=utf-8`）；请求用 `Accept` 声明可接受格式；
- **Content-Encoding**：数据压缩方法（`Content-Encoding: gzip`）；请求用 `Accept-Encoding` 声明。

## GET 与 POST

### 区别

- **GET 语义**（RFC）：从服务器**获取指定资源**。参数写在 URL 中，URL 只支持 ASCII；浏览器对 URL 长度有限制（HTTP 协议本身没规定）；
- **POST 语义**（RFC）：根据请求负荷（body）**对指定资源做出处理**。数据在 body 中，任意格式（双方协商），浏览器不限制 body 大小。

### 安全与幂等

- **安全**：请求方法不破坏服务器资源；**幂等**：多次执行结果相同。
- GET 安全且幂等（只读）→ **可缓存**（浏览器/代理）、可存书签；
- POST 不安全且非幂等（新增/提交）→ 一般不缓存、不可书签。

| 方法 | 语义 | 安全 | 幂等 | 可缓存 |
|------|------|------|------|--------|
| GET | 获取资源 | 是 | 是 | 是 |
| POST | 对资源做处理 | 否 | 否 | 大部分不可 |

**注意**：实际开发不一定按 RFC 语义实现（GET 做删除、POST 做查询都可能）。经典事故：删除博客用 GET 且无鉴权，被爬虫爬完全站。

**GET 能带 body 吗？** RFC 未禁止，理论上任何请求都能带 body，只是 GET 语义不需要。URL 查询参数也不是 GET 独有。

## HTTP 缓存技术

两种实现方式：**强制缓存 + 协商缓存**。

### 强制缓存

浏览器判断缓存未过期就直接用本地缓存，主动性在浏览器。用两个响应头实现：

- `Cache-Control`（相对时间）；
- `Expires`（绝对时间）。**同时存在时 Cache-Control 优先级更高**（选项多、精细，推荐）。

### 协商缓存

服务端告知是否可用缓存（304）。两种实现：

1. `If-Modified-Since`（请求头）+ `Last-Modified`（响应头，资源最后修改时间）；
2. `If-None-Match`（请求头）+ `ETag`（响应头，资源唯一标识）。

**ETag 优先级更高**，解决 Last-Modified 的缺陷：① 内容没改但修改时间可能变；② 秒级内修改检查不到（粒度秒级）；③ 有些服务器不能精确获取修改时间。

**协商缓存字段必须配合强制缓存的 Cache-Control 使用**——只有未命中强制缓存才发带协商字段的请求。

## HTTP 特性

### 优点

1. **简单**：报文格式 `header + body`，key-value 文本，易理解；
2. **灵活易扩展**：请求方法/URI/状态码/头字段都可自定义扩充；工作在应用层，**下层可随意变化**（HTTPS 加 SSL/TLS 层、HTTP/3 改 UDP）；
3. **应用广泛跨平台**。

### 缺点

1. **无状态双刃剑**：好处是服务器不用记状态、减轻负担；坏处是关联操作（登录→购物车→下单→支付）每次都要验身份 → **Cookie 技术**解决（服务器下发"小贴纸"，后续请求带上）；
2. **明文传输双刃剑**：调试方便 vs 信息裸奔易被窃听；
3. **不安全**：① 明文可能被窃听；② 不验证身份可能被伪装；③ 无法证明完整性可能被篡改 → HTTPS 解决。

### HTTP/1.1 性能

1. **长连接（持久连接）**：改善 HTTP/1.0 每请求新建 TCP 的开销；任意端未明确断开则保持；
2. **管道（pipeline）**：同一 TCP 连接可连续发多个请求不必等回来 → 减少整体响应时间。**但服务器必须按接收顺序响应**，前请求阻塞会阻塞后续（**响应队头阻塞**）。
   > 实际上 HTTP/1.1 管道化**不是默认开启且浏览器基本未支持**，后续讨论均建立在无管道化前提。
3. **队头阻塞**：请求-应答模式下，前序请求阻塞导致后续排队请求一同阻塞。

## HTTP 与 HTTPS

### 区别

- HTTPS 在 TCP 与 HTTP 之间加 SSL/TLS 安全协议，加密传输；
- HTTP 三次握手后即可传报文；HTTPS 还需 TLS 握手；
- 默认端口：HTTP 80 / HTTPS 443；
- HTTPS 需向 CA 申请数字证书。

### HTTPS 解决三类风险

- **窃听** → 混合加密（机密性）；
- **篡改** → 摘要算法（哈希指纹，完整性）；
- **冒充** → 数字证书（CA 证明公钥身份）。

#### 混合加密

- 通信建立前用**非对称加密**交换「会话密钥」，后续全程**对称加密**。原因：对称加密快但密钥无法安全交换；非对称加密解决交换问题但慢。

#### 摘要算法 + 数字签名

- 摘要算法（哈希）计算内容"指纹"，比对即验完整性。但只有"内容+哈希值"无法防中间人整体替换 → 需证明来源；
- **数字签名**：私钥加密（内容哈希值），公钥解密验证 → 证明来源持有私钥一方。

#### 数字证书

- 公钥可能是伪造的 → CA 把「持有者信息 + 公钥 + CA 私钥签名」打包成**数字证书**；
- **客户端校验流程**：用相同 Hash 算法算证书得 H1 → 用 CA 公钥解 Certificate Signature 得 H2 → 比对 H1/H2；
- **证书信任链**：申请的证书一般由中间证书签发（如百度证书三级：baidu.com ← GlobalSign G2 ← GlobalSign Root CA）。客户端逐级向上验证到预置根证书；
- **为什么 Root CA 不直接签发**：根证书隔离越严越好，根证书失守则整个信任链崩溃。

#### TLS 握手（基于 RSA，四次通信）

1. **ClientHello**：TLS 版本、客户端随机数、支持的密码套件；
2. **ServerHello**：确认版本、服务器随机数、确认密码套件、**服务器数字证书**；
3. **客户端回应**：验证证书 → 取出公钥 → 发送 `pre-master key`（公钥加密）+ 算法变更通知 + 握手结束通知（带摘要）；
4. **服务器最后回应**：算出会话密钥 + 算法变更 + 握手结束通知。

三个随机数（Client Random + Server Random + pre-master key）→ 各自生成**会话密钥**。

> **RSA 的前向安全问题**：服务端私钥泄露则历史全部密文可破解 → ECDHE 算法（大多数网站现用）。

#### 记录协议（应用数据完整性）

TLS 分握手协议 + 记录协议两层。记录协议：消息分片 → 压缩 → **加 MAC（消息认证码，防篡改+防重放）** → 对称加密 → 加报头（类型/版本/长度）→ 交 TCP。

#### HTTPS 一定安全吗？

中间人攻击成立的前提：**用户点击接受伪造证书**或**电脑被恶意导入根证书**。HTTPS 协议本身无漏洞，被监听本质是利用了客户端漏洞。抓包工具（Fiddler/Charles）原理即中间人 + 客户端导入其根证书。**彻底防护：HTTPS 双向认证**（服务端也验客户端）。

## HTTP/1.1、HTTP/2、HTTP/3 演变

### HTTP/1.1 vs 1.0

改进：长连接、管道。仍有瓶颈：① 头部未压缩；② 发送冗长相同头部；③ 服务端按序响应（队头阻塞）；④ 无请求优先级；⑤ 只能客户端发起。

### HTTP/2 优化

1. **头部压缩（HPACK）**：客户端服务端维护头信息表，相同字段只发索引号；
2. **二进制格式**：头信息帧（Headers Frame）+ 数据帧（Data Frame）；如状态码 200 从 3 字节 '2''0''0' 变为 1 字节 `10001000`；
3. **并发传输**：**Stream 概念**，多个 Stream 复用一条 TCP 连接；不同 Stream 帧可乱序发送，Stream ID 组装。客户端 Stream 奇数号，服务端推送偶数号；
4. **服务器主动推送**：如客户端请求 HTML 时服务端直接推送 CSS，省一次往返。

**HTTP/2 的缺陷**：Stream 并发解决了 HTTP 层队头阻塞，但**底层 TCP 仍有队头阻塞**——TCP 必须保证字节完整连续，丢一个包（packet 3）即使后续包（4-6）到了，应用层也读不到，所有请求等待重传。

### HTTP/3 优化

- **把下层 TCP 换成 UDP**，基于 UDP 的 **QUIC 协议**实现可靠传输：
  1. **无队头阻塞**：某流丢包只阻塞该流，其他流独立；
  2. **更快连接建立**：QUIC 内部包含 TLS（用 TLS 1.3），1 RTT 完成连接+密钥协商；会话恢复可 **0-RTT**（数据与握手信息同包发）；
  3. **连接迁移**：不用四元组绑定，用**连接 ID** 标记端点 → 4G 切 WIFI（IP 变）也能无缝复用连接。
- **普及障碍**：很多网络设备不认识 QUIC，当普通 UDP 丢弃 → 普及缓慢。

### 读者问答要点

- HTTPS vs HTTP：① 建立连接多 TLS 握手；② 传输内容对称加密；
- **SSL 与 TLS 是同一东西的不同阶段**（SSL 网景 90 年代设计 → 1999 IETF 标准化改名 TLS），文章常并列称 SSL/TLS；
- TLS 1.2 需 4 次握手（2 RTT）；TLS 1.3 优化为 1 RTT（3 次）。
