# 什么是缓存雪崩、击穿、穿透？

> **来源**：小林coding（xiaolincoding.com）
> **原文链接**：https://xiaolincoding.com/redis/cluster/cache_problem.html
> **抓取日期**：2026-10-18
> **所属知识域**：域2 后端技术组件工程化
> **板块**：图解Redis · 缓存异常三难题

---

## 一、总览

引入 Redis 缓存层后面临三类缓存异常：**缓存雪崩、缓存击穿、缓存穿透**。

- 雪崩与击穿：数据不在缓存 → 大量请求打到数据库；数据重新载入缓存后压力骤降；
- 穿透：数据**既不在缓存也不在数据库** → 无法构建缓存，方案与前两者不同。

## 二、缓存雪崩

**定义**：大量缓存数据**同一时间过期**或 **Redis 故障宕机**时，大量请求全部打到数据库，压力骤增甚至宕机，连锁反应致系统崩溃。

### 诱因1：大量数据同时过期

1. **均匀设置过期时间**：过期时间加随机数，避免同一时刻失效；
2. **互斥锁**：缓存未命中时加锁，保证同一时间只有一个请求构建缓存（读库→回写），其余请求等待锁释放后重读缓存或返回空值/默认值。**必须设锁超时**，防持锁线程异常不释放导致全局无响应；
3. **后台更新缓存**：缓存"永久有效"，后台线程定时更新。注意：内存紧张时缓存仍可能被淘汰 → 两种补救：① 毫秒级高频检测失效并立即重建（间隔不能太长，体验一般）；② 业务线程发现失效后发**消息队列**通知后台线程更新（更新更及时，体验好）。
   - 附带能力：**缓存预热**——业务上线前提前把数据缓存起来，不等用户访问触发。

### 诱因2：Redis 故障宕机

1. **服务熔断或请求限流**：熔断=暂停业务访问缓存服务直接返回错误，保数据库；限流=只放少部分请求到数据库，其余入口拒绝，等 Redis 恢复并预热完再解除；
2. **构建高可靠集群**：主从节点部署，主节点故障从节点顶上，从根上避免雪崩（事前防护优于事后熔断）。

## 三、缓存击穿

**定义**：某个**热点数据过期**（如秒杀商品），大量请求同时访问该 key，缓存全部未命中直击数据库。可视为雪崩的子集（单个热点 key 版）。

方案：互斥锁（同雪崩）；热点数据不设过期时间，后台异步更新；或在过期前提前通知后台线程更新并重置过期。

## 四、缓存穿透

**定义**：访问的数据**既不在缓存也不在数据库**，无法构建缓存服务后续请求；大量此类请求使数据库压力骤增。

成因：① 业务误操作缓存与库数据都被删；② 黑客恶意访问不存在的数据。

三种方案：

1. **非法请求限制**：API 入口校验参数合理性（非法值、字段缺失），识别恶意请求直接返回错误，不碰缓存和数据库；
2. **缓存空值或默认值**：针对查不到的数据在缓存写空值/默认值（需设较短 TTL 防正常数据长期被挡），后续请求读空值返回，不再查库；
3. **布隆过滤器**：写库时在布隆过滤器做标记；请求先查布隆过滤器判断存在性，不存在就直接返回，不查库。即使发生穿透，大量请求也只查 Redis + 布隆过滤器，不碰数据库。Redis 自身支持布隆过滤器。

### 布隆过滤器原理

- 组成：**初始全 0 的位图数组 + N 个哈希函数**；
- 标记三步：① N 个哈希函数分别计算得 N 个哈希值；② 对位图长度取模得位置；③ 对应位置置 1；
- 查询：N 个位置**全为 1 才认为存在**；有一个为 0 则**一定不存在**；
- **误判特性**：哈希冲突 → 说"存在"不一定真存在（假阳性），但说"不存在"则一定不存在（无假阴性）。

## 五、对比总结

| 问题 | 直接原因 | 数据库中是否有数据 | 核心方案 |
|------|----------|-------------------|----------|
| 雪崩 | 大量 key 同时过期 / Redis 宕机 | 有 | 随机过期时间、互斥锁、后台更新、熔断限流、高可用集群 |
| 击穿 | 单个热点 key 过期 | 有 | 互斥锁、热点不过期、后台异步更新 |
| 穿透 | key 在缓存和 DB 均不存在 | 无 | 入口参数校验、缓存空值、布隆过滤器 |
