## 一、AOF 日志原理

- 每执行一条**写操作命令**，以追加方式写入 AOF 文件；重启时读取文件命令并执行 → 恢复数据；
- 读命令不记录；默认关闭，需改 `redis.conf`；
- **先执行命令、后记录日志**，两个好处：① 不用额外做语法检查（记录的都是可执行命令）；② 不阻塞当前写命令；
- 两个风险：① 命令写入硬盘前宕机 → 数据丢失；② 写日志与执行命令都在主进程同步完成，硬盘 I/O 压力大时阻塞**下一个**命令。

## 二、写入流程（三步）

1. 命令执行完追加到 `server.aof_buf` 缓冲区；
2. `write()` 系统调用将 aof_buf 写入 AOF 文件——数据到**内核缓冲区 page cache**，未落盘；
3. 内核决定何时把 page cache 写回硬盘——**由 `fsync()` 调用时机控制**。

## 三、三种写回策略（appendfsync）

| 策略 | 机制 | 可靠性 | 性能 |
|------|------|--------|------|
| **Always** | 每次写入后立即 `fsync()` | 最高，几乎不丢数据 | 最低，每条写命令都同步落盘 |
| **Everysec** | `write()` 后由 **BIO 后台线程**每秒异步 `fsync()` | 折中，最多丢 1 秒 | 高 |
| **No** | 永不调 `fsync()`，交由操作系统决定 | 最低，丢失量不定 | 最高 |

选型：高性能选 No；高可靠选 Always；允许少量丢失又要性能选 Everysec（生产常用）。

## 四、AOF 重写机制

- 问题：写命令越来越多 → 文件越来越大 → 重启恢复（顺序重放命令）越来越慢；
- 原理：读取当前数据库**所有键值对**，每个键值对用**一条命令**写入新 AOF 文件，完成后替换旧文件；
- 例：`set name xiaolin` + `set name xiaolincoding` 两条命令 → 重写后只保留 `set name xiaolincoding`；
- **先写新文件再覆盖**：重写失败直接删新文件，不污染现有 AOF（避免无法恢复）。

## 五、AOF 后台重写（bgrewriteaof）

- 重写要遍历全量数据，耗时长，不能放主进程 → **fork 子进程 bgrewriteaof**；
- 好处：① 重写期间主进程继续处理命令；② 子进程用**数据副本**，无需加锁（线程共享内存才需要锁）；
- **fork + 写时复制（COW）**：fork 时操作系统复制**页表**（虚拟→物理映射）而非物理内存，父子共享物理内存且权限只读；任一方写时触发**写保护中断**，OS 复制该物理页并改为可读写；
- **两个阻塞点**：① fork 复制页表（页表越大阻塞越久）；② COW 拷贝物理页（修改 bigkey 时拷贝耗时，阻塞主进程）；
- **AOF 重写缓冲区**：子进程重写期间主进程把写命令**同时**写入 AOF 缓冲区 + AOF 重写缓冲区；子进程完成后发信号，主进程信号处理函数把重写缓冲区内容追加进新 AOF 文件（保证新旧文件数据库状态一致），再改名覆盖；
- 除 COW 外，信号处理函数执行时也会短暂阻塞主进程。

## 六、Redis 7.0 Multi Part AOF（MP-AOF）

重构 AOF 重写机制，AOF 拆成多个文件：

- `manifest` 清单文件：记录当前 AOF 由哪些文件组成；
- `base` 基础文件：**RDB 格式**保存重写开始那一刻的全量内存数据；
- `incr` 增量文件：**AOF 格式**记录重写开始后新产生的写命令。

重写流程：① 主进程打开新 incr 文件，新写命令直接追加（不再写重写缓冲区）；② 子进程把内存状态以 RDB 格式写入新 base 文件；③ 完成后**原子更新 manifest** 指向新 base + 新 incr，旧文件安全删除。

收益：无需父子进程管道同步增量命令、无需主进程维护重写缓冲区、减轻主进程内存/CPU 压力、过程更健壮。

## 七、总结

- AOF 记录写命令，恢复时顺序重放；**AOF 恢复慢**（单线程逐条执行，文件大时重放久）；
- 三策略在可靠性与性能间权衡，核心是 `fsync()` 调用时机；
- 重写压缩命令数量；后台化靠 fork+COW+重写缓冲区保证一致性。
