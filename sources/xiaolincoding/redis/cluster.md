## 1. 为什么我们需要 Redis Cluster？

### 1.1 单机 Redis 能扛多久？

一开始 Redis 都是单机部署，一台机器跑起来就能用，但有两个天生的坑：

- **第一个坑是可用性**：机器一旦宕机，整个服务 GG，所有依赖 Redis 的业务全都歇菜。
- **第二个坑是容量**：一台机器内存总有上限。且 Redis 内存越大，持久化时 fork 子进程耗时越长，阻塞主线程风险越高，甚至出现「内存够用但 Redis 已经带不动」的情况。

**解决第一个坑的演进：**

1. **主从复制**：一个主节点带若干个从节点，数据从主同步到从。主挂了，从还能兜读请求。但主挂了后谁来把从切换成新主？只能人肉搞，不够自动。
2. **哨兵（Sentinel）**：一群「看门大爷」7x24 小时盯着主节点，发现主节点挂了就自动从从节点里挑一个接班，全程无需人工介入。到这一步，Redis 的**高可用**问题基本解决。

**但请注意，只解决了第一个坑，第二个坑还在。**

### 1.2 哨兵解决不了的问题

**核心问题**：哨兵模式下，主节点和从节点保存的数据是完全一样的。从节点是主节点的复制品，主有什么它就有什么。

- 这意味着不管挂多少个从节点，整个系统能存下的数据量**还是一台机器的内存上限**。
- 例如主节点 64G，配 5 个从节点，总集群内存不是 `64 * 6 = 384G`，而是**仍然只有 64G**。其余机器只做冗余备份，存的是**同一份数据**。
- 如果业务数据要存 200G，哨兵完全无能为力。

**解决办法：切片集群（Sharding）**

> 核心思想：把一个大数据集切成多份，分别存到多台机器上，让整个集群的容量随机器数量线性扩展。

切片集群是通用概念，实现方案有：

- 客户端自己分片
- 用代理分片（如 Codis、Twemproxy）
- **Redis Cluster**：Redis 官方从 3.0 版本开始提供的切片集群方案，属于「亲儿子」级别。

**Cluster 要解决的核心问题**：怎么把数据分散到多台 Redis 上，同时还要保证这些 Redis 合起来用起来像一台一样顺手。

## 2. 数据怎么分？哈希槽到底是个什么东西

最核心的问题：**给你一个 key，怎么决定它该存到哪台机器上？**

### 2.1 最朴素的办法：key 直接对机器数取模

假设有 3 台 Redis，对 key 算哈希值，然后除以 3 取余：

- 余数 0 → 第一台
- 余数 1 → 第二台
- 余数 2 → 第三台

**致命问题**：假设集群 3 台机器，`user:100` 哈希值为 6，`6 % 3 = 0`，存在第一台。扩容到 4 台后，`6 % 4 = 2`，客户端跑去第三台找，发现没有——因为数据还在第一台。

> **结论**：每次加机器或减机器，几乎所有 key 的位置都要重新计算，意味着几乎要把整个集群数据重新搬一遍，成本高得离谱。

### 2.2 升级一下：引入一个「中间层」

**哈希槽（Hash Slot）设计思想**：不让 key 直接对应机器，而是在 key 和机器中间加一层「槽」。

- 预设固定数量的「槽」，**16384 个，写死，永远不变**。
- key 不再直接映射到机器，而是先映射到某个槽。
- 机器不再直接装 key，而是「认领」一批槽，装在这批槽里的 key 归它管。

**文本示意图**：

```text
key  →  哈希槽（固定 16384 个，永不变）  →  机器（可增可减）
```

**好处**：扩容增加一台机器时，只需要**从已有机器里匀一部分槽出来给新机器**，槽里面装的 key 根本不用动。因为对 key 来说，它只认自己属于哪个槽，至于这个槽归哪台机器管，是集群内部的事。

> **本质**：扩缩容时迁移的粒度从「一个个 key」变成了「一批批槽」，槽数量固定，迁移可控。这就是 Redis Cluster 哈希槽的设计思想，说白了就是在 key 和机器之间加了一层「解耦」。

### 2.3 那 key 是怎么算出槽号的？

Redis Cluster 使用 **CRC16** 哈希算法。每个 key 先用 CRC16 算出哈希值，然后对 16384 取模：

```text
slot = CRC16(key) % 16384
```

取值范围是 `0 ~ 16383`。

> 为什么是 16384 而不是 65536 或 8192？文章第 7 节会专门解答。

### 2.4 槽是怎么分给各个节点的

在**集群初始化**时就安排好。Redis 会把 16384 个槽尽量平均分给每个主节点。

**示例：3 个主节点 A、B、C**

| 节点 | 负责槽范围 |
|------|-----------|
| 节点 A | 0 ~ 5460 号槽 |
| 节点 B | 5461 ~ 10922 号槽 |
| 节点 C | 10923 ~ 16383 号槽 |

合起来正好覆盖全部 16384 个槽，一个不多一个不少。

集群里每个节点都会在本地维护一份完整的「哪个槽归谁管」的映射表，节点之间也会不停地互相同步这份信息（通过 Gossip，后面会讲）。

## 3. 客户端是怎么知道该访问哪台机器的？

这是 Redis Cluster 里最容易让初学者迷糊的地方。

### 3.1 最笨的办法：每次都让服务端告诉我

客户端随便挑一台节点发请求，发错了就让服务端返回「你应该去找哪个节点」，然后重新发。

**评价**：能用，但性能太差，每次请求最坏都要走两趟，实际生产没人这么干。

### 3.2 真实方案：客户端自己缓存一份「槽 → 节点」的地图

**真正做法**：客户端启动时，主动去任意一个节点拉一份「哪个槽归哪台节点管」的映射表，缓存在本地。

可以把这份表想象成一张地图，写着「0 ~ 5460 号槽在 A 节点」「5461 ~ 10922 号槽在 B 节点」等。

**客户端每次访问 key，本地做三件事**：

1. 用 CRC16 算出这个 key 属于哪个槽；
2. 查本地地图，看看这个槽归哪个节点；
3. 直接发请求给那个节点。

整个过程**全是本地计算**，一次请求就能命中，效率非常高。

这种带着本地缓存地图的客户端叫 **Smart Client（智能客户端）**。Java 的 Jedis、Lettuce，Go 的 go-redis，以及 `redis-cli -c`（加了 `-c` 参数）都是 Smart Client 行为。

### 3.3 地图过期了怎么办？MOVED 重定向出场

**问题**：地图是启动时一次性拉下来的，万一集群扩容/缩容，槽归属变了，本地地图不就过期了？

**解决方案：MOVED 重定向**

假设客户端本地地图记的是「槽 100 在 A 节点」，但因扩容槽 100 已迁到 B 节点。客户端按老地图发给 A，A 一看这槽不归自己管，**不处理请求，返回 MOVED 错误**：

```text
(error) MOVED 100 192.168.1.2:6379
```

含义：「槽 100 已经搬到 192.168.1.2:6379 那儿去了，你去找它」。

**客户端收到 MOVED 后做两件事**：

1. **立刻更新本地地图**，把槽 100 的归属改成 B 节点；
2. 重新把请求发给 B 节点，完成操作。

**关键点**：因为更新了本地地图，下次再访问槽 100 的 key 就能一次命中。所以 MOVED 错误偶尔出现，但客户端会「越跑越聪明」。

### 3.4 正在搬家中的槽怎么办？ASK 重定向

**更微妙的情况**：槽不是已经搬完了，而是正在搬的过程中。

**场景**：把槽 100 从 A 迁到 B，迁移是 key 一个 key 搬的。当前状态是槽 100 里一部分 key 已搬到 B，另一部分还在 A。

客户端按旧地图发请求去 A 访问 `key1`，A 一查：

- 如果 `key1` 还在自己这里 → 正常处理返回结果；
- 如果 `key1` 已被搬到 B → **A 不能返回 MOVED**。

**为什么不能返回 MOVED？**

MOVED 的语义是「这个槽**永久**归 B 了」，但实际情况是槽 100 还有 key 没搬完，这个槽**整体上**还是归 A 管。如果让客户端更新地图把整个槽 100 改到 B，客户端下次访问留在 A 的那些 key 就全部找错地方。

**解决方案：ASK 重定向**

```text
(error) ASK 100 192.168.1.2:6379
```

含义：「这个 key **这一次**你去 B 节点问问看，但这只是临时的，不要更新你的地图」。

**客户端收到 ASK 后做两件事**：

1. **不更新本地地图**，槽 100 的归属还是 A；
2. 先给 B 发一个特殊命令 **`ASKING`**，然后再发真正的请求。

**为什么要先发 `ASKING`？**

因为此时 B 还没正式接管槽 100，如果直接发请求，B 反而会返回 MOVED 让你回去找 A（B 认为这个槽此刻不归自己）。`ASKING` 告诉 B：「我知道这个槽你还没正式接管，但我是从 A 那边被 ASK 过来的，你就破个例给我处理一下这次请求吧」。B 收到 `ASKING` 后会临时处理一次，仅此一次。

**MOVED 和 ASK 的核心区别**：

> **MOVED 是「永久搬家通知」，客户端要更新地图；ASK 是「临时借道通知」，客户端这一次跳过去，地图不动。**

这个区别是 Redis Cluster 能够在**不停机**情况下完成数据迁移的关键。

## 4. 节点之间怎么同步信息？聊聊 Gossip 协议

Cluster 是一堆节点组成的，节点之间需要互相通信。集群状态动态变化：

- 有新节点加入
- 有节点挂掉下线
- 有槽在节点之间迁移
- 有主从切换发生

这些变化必须让每个节点都知道，不然就乱套了。

### 4.1 两种思路：中心化 vs 去中心化

| 思路 | 说明 | 问题 |
|------|------|------|
| **中心化** | 专门搞一个（或一小撮）「管理员」，所有节点向它汇报状态，也从它读最新状态。哨兵模式本质如此。 | 管理员自己挂了呢？架构复杂，维护成本高。 |
| **去中心化** | 不要管理员，节点之间直接互相聊天，各自把自己知道的告诉别人，最终信息同步一致。 | 天生没有单点，不需要额外组件。 |

**Redis Cluster 选的是第二种，使用的协议叫 Gossip（流言）协议。**

### 4.2 Gossip 协议：一个八卦传播的故事

Gossip 本意「八卦、流言」，工作方式与八卦传播一模一样。

**生活例子**：公司 100 号人，你知道一个爆炸性八卦，不会一个一个跑去跟全公司每个人讲，只会随机找 2、3 个同事聊一下，这 2、3 个同事又各自去找 2、3 个同事，一传十十传百，不久整个公司都知道了。

**Gossip 协议工作方式**：每个节点**不需要跟所有节点通信**，只要周期性地随机挑几个节点聊聊，把自己知道的集群状态告诉它们。这几个节点收到后又把信息传给自己挑的几个邻居。经过若干轮，整个集群所有节点都会收敛到一致的状态。

- **好处**：实现简单、没有单点。
- **坏处**：信息传播有一定延迟，不像中心化那样「一喊全都知道」。但对 Redis Cluster 这种对一致性要求没那么极致的场景，这点延迟完全可以接受。

### 4.3 Cluster 里的几种消息

节点之间互相发送的 Gossip 消息主要有：

| 消息类型 | 作用 |
|---------|------|
| **ping** | 节点每秒向随机选出的其他节点发 ping，顺便把自己当前知道的集群状态（哪些节点活着、哪些槽归谁）塞在消息里带过去。 |
| **pong** | 节点收到 ping 后回复 pong 作为确认，pong 里同样带上自己所知道的集群状态。 |
| **meet** | 往集群加新节点时，让某台老节点主动给新节点发 meet 消息，「打个招呼，欢迎加入」。新节点收到后与发消息方建立连接，顺着 Gossip 网络把其他节点也「认识」一遍。 |
| **fail** | 某节点被判定为彻底挂了，会有节点向整个集群广播 fail 消息，告诉大家「这家伙真不行了，把状态更新成下线吧」。 |

每次「闲聊」都在交换情报，慢慢地整个集群的视图就统一了。

### 4.4 集群总线和 16379 端口

**节点间通信不走业务端口**（如 6379），而是一个专门的**集群总线端口**，叫 cluster bus，约定是「业务端口 + 10000」。

- 如果 Redis 端口是 6379，节点间通信端口就是 **16379**。
- 部署 Cluster 时，防火墙上**两个端口都要放行**。忘了放 16379 是新手常踩的坑，会出现节点之间看起来谁也连不上谁的诡异现象。

### 4.5 Gossip 不是没有代价

**主要代价**：Gossip 的消息量会随节点数量增长而急剧增长，大概是**平方级**关系。

**原因**：每个节点都要跟其他节点通信，且每条消息里还要携带一份自己所知道的集群状态。节点越多，每条消息体越大，每秒发出消息总数越多，带宽开销很夸张。

**因此 Redis 官方建议 Cluster 主节点数量不要超过 1000 个**。超过这个规模，光是节点间「打招呼」的流量就足够把网络搞得很紧张，甚至影响正常业务请求。

## 5. 节点挂了怎么办？聊聊故障转移

实际生产环境里，机器挂掉是家常便饭。号称高可用的集群方案必须能在节点挂掉时**自动恢复服务**，这就是故障转移（failover）。

### 5.1 先铺垫一下：Cluster 里的主从关系

**Redis Cluster 里每个主节点都可以配一个或多个从节点。**

- 从节点是主节点的「影子」，通过主从复制不断同步数据，保证数据和主节点尽量一致。
- **从节点默认不对外提供读写服务**。直接连上从节点 GET 一个 key，它会返回 MOVED 让你回去找主节点。（后面会讲 `READONLY` 命令可改变此行为。）
- 可以把从节点理解为「热备」：平时待命，主节点出事立马顶上去。

**这就是「3 主 3 从」是 Redis Cluster 最小推荐部署规模的原因**：3 个主节点分摊 16384 个槽负责读写，每个主节点各配一个从节点做热备。任何一个主节点挂了，对应从节点立刻顶上。

### 5.2 怎么发现一个节点挂了？pfail 和 fail 两阶段

节点之间不断互相发 ping。如果某个节点发出去的 ping 在约定时间（参数 `cluster-node-timeout` 控制，默认 15 秒）内没收到回复，它就会心里嘀咕：「这哥们是不是挂了？」

**两阶段判定**：

1. **pfail 状态（主观下线）**：单个节点单方面的判断。有可能只是网络闪了一下，别的节点其实还连得上。
2. **fail 状态（客观下线）**：pfail 状态随 Gossip 传到别的节点，如果集群里**半数以上**持有槽的主节点都认为这个节点处于 pfail（大家都觉得它挂了，不是我一个人闹脾气），状态升级为 fail。此时才有节点广播 fail 消息，告诉整个集群：「这家伙真没了，启动故障转移吧。」

**为什么要搞两阶段？** 为了**防止误判**。网络抖动常有，单靠一个节点判断就把别人拉下马太草率。多个节点达成共识后再下线，稳妥得多。

### 5.3 选出一个新主：Cluster 的选举机制

挂从节点没啥大事，顶多少个备胎。挂主节点问题严重：它负责的那部分槽没人管，客户端访问那些槽都会失败。这时候要从它的从节点里**选一个当新主**。

Redis Cluster 用类似 Raft 的投票机制，流程如下：

**第一步，资格检查**

不是所有从节点都有资格参选。如果一个从节点跟主节点已失联太久（数据可能很陈旧），就没资格参与选举。Redis 根据 `cluster-replica-validity-factor` 参数判断「失联多久算太久」。

**第二步，排队等发起选举**

有资格的从节点不会一股脑跳出来，而是按自己和主节点的**数据同步进度**排队：**复制得越新的从节点，等待时间越短**。这样数据最新的从节点优先发起选举、最可能当选，把故障切换后**数据丢失风险降到最低**。

**第三步，发起选举，请求投票**

等待时间到了，从节点向集群里所有持有槽的主节点拉票：「我想竞选槽 X 的新主，请投我一票」。

**第四步，收集选票**

- **只有持有槽的主节点才有投票权**，从节点和不持有槽的节点没有投票权。
- 每个主节点在一轮选举里只能投一票，投给第一个来拉票的合格候选人。

**第五步，成为新主**

如果某个候选从节点拿到**半数以上**主节点的票（如 5 个主节点里 3 票），就当选。当选后把自己从「从节点」升级成「主节点」，通过 Gossip 广播一条消息告诉整个集群：「这些槽现在归我管了」。其他节点更新本地信息，客户端下次访问这些槽时通过 MOVED 重定向被纠正到新主节点，故障转移完成。

### 5.4 一个必须要提的「但是」：Cluster 会丢数据吗？

**Redis Cluster 的主从复制是异步的，所以故障转移过程中有可能丢数据。**

**异步含义**：主节点处理完写命令后，**立刻**返回成功给客户端，**然后**才慢悠悠地把写命令同步给从节点。中间有一个极小时间窗口。

**极端丢数据场景**：

1. 客户端向主节点写入一条数据，主节点写完内存，返回 OK；
2. 主节点还没来得及同步给从节点，就突然宕机；
3. 从节点被选举成新主，但它手里根本没有这条数据；
4. 客户端再来查，发现数据不见了。

**CAP 定位**：Redis Cluster 在 CAP 理论里**偏向 AP**，为了可用性和分区容忍性，牺牲了一部分强一致性。

- 对绝大多数缓存场景，这点损失完全可以接受。
- 对一定要强一致的场景（如钱的扣款、库存扣减），需另想办法，如配合数据库做最终一致，或上 ZooKeeper、etcd 这类强一致协调服务。

## 6. 初学者最容易踩的两个坑

原理懂了不代表动手就能顺利用起来，以下两个坑第一次用 Cluster 就会撞到。

### 6.1 多 key 操作报 CROSSSLOT 错误

单机 Redis 上写得好好的代码：

```text
MSET user:1:name xiaolin user:1:age 18
```

换到 Cluster 环境直接报错：

```text
(error) CROSSSLOT Keys in request don't hash to the same slot
```

**原因**：`user:1:name` 和 `user:1:age` 算出的 CRC16 值完全不一样，很可能落在不同槽，不同槽又很可能归不同节点管。一个命令要同时操作两个节点上的数据，Cluster 做不到，只能报错。

**官方解决办法：Hash Tag**

在 key 里用花括号 `{}` 括起一段，**只有花括号里的部分会参与 CRC16 计算**：

```text
MSET {user:1}:name xiaolin {user:1}:age 18
```

这两个 key 计算槽号时只看 `user:1`，算出的槽号**一定一样**，一定会落在同一个节点，MSET 正常工作。

**同样适用于**：事务（MULTI/EXEC）、Lua 脚本、pipeline 等多 key 场景。如果希望这些操作在 Cluster 下正确工作，记得给相关 key 加统一 Hash Tag，让它们绑在一个槽里。

### 6.2 从节点默认不提供读服务

很多小伙伴听说 Cluster 有从节点，以为可以把读请求打到从节点做读写分离，结果连上从节点 GET 一个 key，直接被 MOVED 回主节点。

**原因**：Cluster 里从节点**默认不处理读请求**，唯一任务是等主节点挂了顶上去。

**如果确实想让从节点分担读压力**：客户端侧先对从节点发 **`READONLY`** 命令，告诉它：「我知道从这里读可能读到稍微旧一点的数据，我能接受」。发过 `READONLY` 后，后续读请求就在这个从节点上正常处理。

**提醒**：从节点数据是异步同步过来的，和主节点之间可能有短暂延迟。对数据新鲜度要求高的业务，还是老老实实走主节点。

## 7. 加餐：为什么哈希槽的数量是 16384？

这个问题当年在 GitHub 上有人问过 Redis 作者 antirez。

**antirez 的理由主要跟网络传输效率有关。**

Gossip 每秒通过 ping/pong 交换集群状态，其中重要内容是「我这个节点负责哪些槽」。这个信息在节点里用**位图（bitmap）**存储：每个槽占一个 bit，1 表示归我管，0 表示不归我管。

**如果槽数量是 65536**：

```text
65536 bit / 8 = 8192 字节 = 8 KB
```

每发一次 ping 都要带一个 8KB 位图到处跑。

**如果槽数量是 16384**：

```text
16384 bit / 8 = 2048 字节 = 2 KB
```

从 8KB 降到 2KB，省 6KB。Gossip 每秒都在跑，集群节点越多差距越放大，带宽压力明显小很多。

**那为什么不用更小的 8192？**（8192 对应位图才 1KB）

这涉及另一个约束：**槽数量要大于集群中主节点数量**，且要有足够**富余度**保证负载均衡。CRC16 结果并非绝对均匀，槽太少容易出现有的节点分到的 key 多、有的少的情况。

antirez 认为 Redis Cluster 最多支撑约 1000 个主节点，16384 个槽平均分给 1000 个节点，每个节点约 16 个槽，足以保证负载均衡；8192 就有点紧。

**综合「带宽消耗」和「负载均衡」，antirez 最终选择 16384**。它恰好覆盖常见集群规模，位图 2KB 带宽开销可接受，是工程上的折中。

**源码细节**：Redis 源码里实际计算槽号用**位运算**：

```text
slot = CRC16(key) & 16383
```

因为 `x % (2^n)` 等价于 `x & (2^n - 1)`，16384 是 2 的 14 次方，16383 是 `2^14 - 1`，用 `&` 比 `%` 快。这也是为什么槽数量要选 2 的幂次方。

## 8. 总结一下

**Redis Cluster 要解决的核心问题**：单机 Redis 内存有上限，必须把数据分散到多台机器上。这是它存在的根本理由。

**数据怎么分？** 通过在 key 和机器之间加一层「哈希槽」：`key → CRC16 → 16384 个槽 → 节点`。好处是扩缩容时只搬槽不搬 key，迁移成本可控。

**客户端怎么找到数据？** Smart Client 本地缓存一份「槽 → 节点」地图，先本地算槽号再直接发请求，一次命中。地图过期时，服务端通过 **MOVED** 通知「永久搬家」；槽正在迁移中则通过 **ASK** 做「临时借道」。

**节点之间怎么同步状态？** 用 **Gossip 协议**，每个节点周期性跟其他节点「八卦」自己知道的集群状态，最终集群信息收敛到一致。代价是消息量随节点数平方级增长，规模不建议超过 **1000 主节点**。

**节点挂了怎么办？** 通过 **pfail、fail** 两阶段判断是否真的下线，然后从故障主节点的从节点里按**数据新鲜度优先级**发起选举，半数以上主节点投票赞成即可当选新主。注意主从是异步复制的，故障转移有丢数据风险，Cluster 整体偏 **AP** 而不是 CP。

**动手前的两个坑**：
- 多 key 操作要用 **Hash Tag** 把 key 绑到同一个槽；
- 从节点读要先发 **`READONLY`**。
