## 一、RDB 定位

- **RDB = 某一瞬间的内存数据二进制快照**；AOF = 操作命令流；
- 恢复速度：**RDB 远快于 AOF**（直接读入内存 vs 逐条重放命令）。

## 二、两个命令

```bash
save    # 主线程生成 RDB，写盘太久阻塞主线程（生产禁用）
bgsave  # fork 子进程生成，不阻塞主线程（生产用这个）
```

RDB 加载在服务器启动时自动执行，无专门加载命令。

## 三、自动触发配置

```text
save 900 1        # 900 秒内至少 1 次修改
save 300 10       # 300 秒内至少 10 次修改
save 60 10000     # 60 秒内至少 10000 次修改
```

名为 save 实则 bgsave（fork 子进程）。满足任一条件即触发。

**全量快照的固有矛盾**：频率高 → 性能损耗（fork + 全量写盘）；频率低 → 宕机丢数据多（最多丢一个周期）。通常至少 5 分钟一次，即最多丢 5 分钟。

## 四、bgsave 与写时复制（COW）

- `fork()` 时复制**页表**而非物理内存，父子**共享物理内存**（只读）；
- 主线程修改共享数据 → 触发**写保护中断** → 复制该物理页 → 主线程在副本上改；
- 子进程继续把**原数据**写入 RDB → 快照期间主线程的修改**进不了本次 RDB**，只能等下次快照；
- **极端情况**：共享内存全被修改 → 内存占用翻倍。**写多场景必须预留内存**，防止快照期间 OOM；
- fork 本身阻塞主线程（复制页表），内存越大页表越大、阻塞越久——监控 `latest_fork_usec`。

## 五、混合持久化（Redis 4.0+）

```text
aof-use-rdb-preamble yes
```

- 工作于 **AOF 重写过程**：重写子进程先把内存数据以 **RDB 格式**写入 AOF 文件，重写期间的增量命令以 **AOF 格式**追加；
- AOF 文件 = **前半 RDB 全量 + 后半 AOF 增量**；
- 恢复：先快速加载 RDB 段，再重放 AOF 段——**兼顾 RDB 的恢复速度与 AOF 的少量丢失**；
- 生产推荐组合：**AOF everysec + 混合持久化 + 定期 bgsave 冷备**。

## 六、RDB vs AOF 决策表

| 维度 | RDB | AOF |
|------|-----|-----|
| 内容 | 二进制全量快照 | 命令流（重写后为 RDB+AOF 混合） |
| 恢复速度 | 快 | 慢（重放） |
| 丢失量 | 一个快照周期（分钟级） | everysec 最多 1 秒 |
| 性能影响 | fork + COW 内存翻倍风险 | 写盘竞争（重写期） |
| 适用 | 冷备、灾难恢复、主从全量同步 | 主力持久化 |
