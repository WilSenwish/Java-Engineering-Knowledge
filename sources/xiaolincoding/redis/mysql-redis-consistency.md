## 更新顺序的四种组合分析

### 「更新缓存」方案（均存在并发问题）

**先更新数据库，再更新缓存**：请求 A 更新 DB 为 1，请求 B 更新 DB 为 2 并更新缓存为 2，A 再更新缓存为 1 → DB=2、缓存=1 不一致。

**先更新缓存，再更新数据库**：对称问题 → DB=1、缓存=2 不一致。

结论：无并发控制时两个方案都不一致。缓解手段：
- 更新缓存前加**分布式锁**（串行化，牺牲写性能）；
- 缓存加**较短过期时间**兜底；
- 适用场景：对缓存命中率要求极高（更新缓存不产生未命中）。

### 「删除缓存」方案（Cache Aside 旁路缓存）

**写策略**：更新数据库 → 删除缓存。**读策略**：命中直接返回；未命中读 DB → 写缓存 → 返回。

**先删缓存，再更新数据库**：读+写并发时——A 删缓存，B 读 DB 旧值写缓存，A 更新 DB → 缓存旧值、DB 新值不一致。缓解：**延迟双删**（删缓存 → 更新 DB → sleep N → 再删缓存），sleep 需大于 B 的「读 DB + 写缓存」耗时，但时长是玄学，只能尽可能保证。

**先更新数据库，再删除缓存**：理论上也有不一致窗口（A 读 DB 旧值未写缓存，B 更新 DB 删缓存，A 才写缓存），但实际概率极低——**缓存写入通常远快于数据库写入**，B 几乎总是先于 A 完成删除。**生产推荐方案**。

## 核心问题的完整方案矩阵

| 问题 | 方案 | 评价 |
|------|------|------|
| 删除缓存失败导致长期不一致 | 缓存加过期时间兜底 | 最终一致 |
| 保证「更新 DB + 删缓存」两步都成功 | 消息队列重试 | 代码入侵强 |
| 保证两步都成功（低侵入） | **Canal 订阅 binlog + MQ + 重试删除** | 阿里方案；先删成功再 ACK，否则消息丢失无法重试 |
| 先删缓存方案的一致性窗口 | 延迟双删 | 睡眠时长玄学，仅尽可能保证 |

## 为什么是删除缓存而不是更新缓存？

1. **轻量**：删除比更新出问题的概率小；
2. **聚合数据**：缓存可能来自多表/多系统聚合（商品详情关联商品表、价格表、库存表），更新代价极高；
3. **Lazy Loading**：不是所有缓存都频繁访问，删除后下次命中再填充，节省计算资源。

## 生产结论

1. **首选「先更新数据库，再删除缓存」+ 过期时间兜底**；
2. 高要求场景：**Canal + MQ 异步删缓存**（先删成功再 ACK）；
3. 命中率敏感场景：更新缓存 + 分布式锁/短过期时间；
4. 任何方案都是**最终一致性**，强一致需分布式锁串行化。
