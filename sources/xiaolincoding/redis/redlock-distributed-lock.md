## 1. 加锁：从 SETNX 到工业级

**最简模型**：`SETNX lock_key value` 成功=加锁，`DEL` 释放。生产不可用，需逐层加固：

### 等待与重试

- **轮询等待**：失败后 sleep 100ms 重试，总等待超时 ≈ 锁平均持有时间（如 P99 业务 800ms → 设 1s）；
- **事件监听**：订阅 lock_key 的 DEL 事件（Pub/Sub 或 Keyspace Notifications），实时性更好。**注意**：「检测锁存在」与「发起订阅」必须原子化/严密有序，否则间隙中锁被释放会错过通知；
- **重试幂等**：`SETNX` 超时后不能盲目重试。value 用**全局唯一 ID（UUID）**，重试前 `GET` 判定：
  - 返回 nil → 上次没成功，可重新 SETNX；
  - 返回本客户端 UUID → 上次已成功，重置过期时间即可；
  - 返回别的 UUID → 锁已被他人拿走，本轮失败。

### 过期与续约

- **原子加锁+过期**：`SET lock_key unique_value EX 30 NX`（SETNX+EXPIRE 两步非原子会死锁）；
- **过期时长**：按业务 P999 + buffer（99.9% 请求 5s 完成 → 设 10-20s）；过期时间主要防宕机死锁，正常应由业务主动 DEL，设长些（30s/1min）通常安全；
- **看门狗续约**：加锁成功启动后台线程，周期检查（如 50s/60s 周期）重置 TTL；预留窗口期容忍单次续约失败；
- **续约失败策略**：保守（推荐）——归属权已丢，立即中断业务回滚抛异常；激进——继续执行（可能数据不一致，慎用）；
- **业务中断**：锁框架只能发信号（volatile 标志位 / interrupt），**中断逻辑依赖业务代码配合**——大循环每轮检测、多步骤步骤间检测。业界无银弹。

## 2. 释放锁：原子化查删

**误删场景**：A 的锁过期 → B 加锁成功 → A 业务结束执行 `DEL` → 删掉 B 的锁。

**方案**：Lua 脚本原子查删（Redis 执行 Lua 原子）：

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

## 3. Redlock 与争议

### 为什么主从不够

主从复制是**异步**的：A 在 Master 加锁 → Master 未复制即宕机 → Slave 升主 → B 在新主加锁成功 → **两客户端同时持锁**。

### Redlock 算法（antirez）

部署 N 个（如 5 个）独立主库（无主从），**多数派原则**：

1. 记录起始时间戳；
2. 依次在所有实例 `SET ... EX ... NX`，每个实例设很短超时（如 50ms）防止宕机节点浪费时间；
3. **超过半数成功**且总耗时 < 锁有效时间 → 加锁成功；
4. **锁真正有效时间 = 初始过期时间 - 加锁总耗时**。

释放：向所有实例发 Lua 释放脚本（无论当时是否成功），清理僵尸锁。

### Martin Kleppmann vs antirez 之争（2016）

**Martin 质疑**：① 时钟会跳变（NTP/手动调整），基于时间的锁无法保证互斥；② 进程暂停（GC/Swap/缺页）恢复后客户端不知锁已过期；③ 网络延迟同样导致"自以为持锁"。

**Martin 结论**：基于时钟的分布式锁无法提供严格互斥，必须由**被保护资源配合单调递增 fencing token**（版本号校验，丢弃迟到请求）。

**antirez 回应**：混淆了故障模型，实际场景 Redlock 对时钟漂移要求合理；fencing token 需改造资源服务器，非银弹。

**生产建议**：资金扣款/库存强一致 → ZooKeeper/etcd + fencing token；性能去重类"尽力而为"互斥 → 单实例 Redis 锁或 Redlock 足够。

## 4. 性能优化

| 方案 | 原理 | 评价 |
|------|------|------|
| **Singleflight** | 同一 key 的加锁请求实例内只放 1 个线程去 Redis 竞争，其余本地等结果 | 竞争越激烈收益越大；Guava/Go 有实现 |
| 本地锁交接 | T1 持锁执行完不 DEL，本地把"锁凭证"转交等待的 T2 | 省一次 DEL+SETNX；但引入本地状态依赖，实例崩溃锁泄漏，违背集中仲裁哲学，生产少用 |
| 分布式锁替换 | **数据库乐观锁**（version 字段，UPDATE 影响行数=0 则重试）；**一致性哈希**（同 ID 请求固定路由到同实例，退化为单机 ReentrantLock） | 从根源消除锁需求 |
