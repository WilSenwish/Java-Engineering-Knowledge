# 索引常见面试题

> 索引定义：帮助存储引擎快速获取数据的一种数据结构，**索引是数据的目录**，以空间换时间。

## 什么是索引？

数据库索引位于存储引擎层。存储引擎 = 如何存储数据、如何建立索引、如何更新查询数据的实现方法。MySQL 常见引擎：MyISAM、InnoDB（5.5+ 默认）、Memory。

## 索引的分类（四个角度）

1. **按数据结构**：B+Tree 索引、Hash 索引、Full-text 索引；
2. **按物理存储**：聚簇索引（主键索引）、二级索引（辅助索引）；
3. **按字段特性**：主键索引、唯一索引、普通索引、前缀索引；
4. **按字段个数**：单列索引、联合索引。

### 聚簇索引的选取规则（InnoDB）

- 有主键 → 主键作为聚簇索引键；
- 无主键 → 第一个不含 NULL 的唯一列；
- 都没有 → 自动生成隐式自增 id 列。

### B+Tree 存储与查询

- 多叉树，**叶子节点才存数据**，非叶子节点只存索引；节点数据按主键顺序存放；
- 父节点索引值出现在子节点中；叶子节点双向链表连接；
- 查询过程（`where id=5`）：根节点 (1,10,20) → 二层 (1,4,7) → 三层叶子 (4,5,6) → 命中。**3 次磁盘 I/O**；
- **B+Tree 存千万级数据只需 3-4 层高度** → 最多 3-4 次磁盘 I/O。

### 二级索引与回表 / 覆盖索引

- 主键索引 B+Tree 叶子存**实际数据**；二级索引 B+Tree 叶子存**主键值**；
- `where product_no='0002'`（SELECT *）→ 先查二级索引拿主键 → 再查主键索引 → **回表（查两棵 B+Tree）**；
- `select id from product where product_no='0002'` → 数据在二级索引即可得 → **覆盖索引（只查一棵 B+Tree）**。

### 为什么选 B+Tree

1. **vs B 树**：B+Tree 只在叶子存数据 → 节点更小 → 相同 I/O 下查询更多节点；叶子双向链表**适合范围顺序查找**（B 树做不到）；
2. **vs 二叉树**：B+Tree 搜索复杂度 `O(log_d N)`，d>100 → 千万级高度仍 3-4 层；二叉树 `O(log N)` 磁盘 I/O 次数多得多；
3. **vs Hash**：Hash 等值查询 O(1) 快，但**不适合范围查询** → B+Tree 适用场景更广。

### 各类索引定义与创建

- **主键索引**：`PRIMARY KEY(index_column) USING BTREE`，一表最多一个，不允许 NULL；
- **唯一索引**：`UNIQUE KEY(...)`，可多个，值唯一但允许 NULL；
- **普通索引**：`INDEX(...)`；
- **前缀索引**：`INDEX(column_name(length))`，对字符类型前几个字符建索引，减少存储空间提升查询效率。

### 联合索引与最左匹配

- `(product_no, name)` 联合索引：非叶子节点用两字段值作 key；先按 product_no 排，product_no 相同再按 name 排；
- **最左匹配原则**：`(a,b,c)` 可匹配 `a=1` / `a=1 and b=2` / `a=1 and b=2 and c=3`；`b=2` / `c=3` / `b=2 and c=3` 失效；
- **a 字段在 where 子句的顺序不重要**（查询优化器会重排）；
- 失效根因：**b 和 c 是全局无序、局部相对有序**——利用索引的前提是索引 key 有序。

### 联合索引范围查询（关键细节）

最左匹配**遇到范围查询（>、<）就停止匹配**，范围查询字段本身可用索引，但其后字段不可用。**但 `>=`、`<=`、`BETWEEN`、`like 前缀匹配` 不会停止匹配**。

- **Q1** `where a > 1 and b = 2` → 只有 a 用索引；a>1 范围内 b 无序；
- **Q2** `where a >= 1 and b = 2` → a 和 b 都用索引。`a>=1` 被拆成 `a>1`（b 不走索引）+ `a=1`（ab 都走），扫描从 `a=1 and b=2` 第一条开始；
- **Q3** `where a BETWEEN 2 AND 8 AND b = 2` → MySQL 的 BETWEEN **含边界值**（类似 >= and <=），a 和 b 都用索引；
- **Q4** `where name like 'j%' and age = 22`（联合索引 (name, age)）→ 前缀匹配范围 ['j','k')，name 和 age 都用索引。

**key_len 判定法**：执行计划 key_len 表示用了多少个字段的查询条件形成扫描区间。a、b 都是 int 非 NULL：Q1 key_len=4（仅 a），Q2 key_len=8（a+b）。

> key_len 中变长字段长度说明：执行计划在 server 层生成，**不管实际存储用几字节，变长字段一律按 2 字节**表示。

### 索引下推（ICP，MySQL 5.6+）

`where a > 1 and b = 2` 只有 a 能索引定位，但**可在联合索引遍历过程中先判断 b=2，过滤后再回表**，减少回表次数。执行计划 Extra 出现 `Using index condition` 即使用了 ICP。

### 索引区分度

区分度 = `COUNT(DISTINCT col) / COUNT(*)`。**区分度高 ≠ 适合放联合索引最前，也不 ≠ 写入成本低**：

- 性别字段区分度低，优化器发现某值占比高会忽略索引走全表；
- UUIDv4 区分度高但随机插入 → 页分裂/随机 IO；作主键还会让所有二级索引变大；
- MySQL 8.0 `UUID_TO_BIN(uuid, 1)` 可交换时间字段改善 UUIDv1 局部性，但 **UUIDv4 无法变递增**；
- 是否走索引最终由优化器成本估算决定，**没有固定"30%"判断线**。

### 联合索引排序优化

`select * from order where status = 1 order by create_time asc`：单独给 status 建索引 → 过滤后还要 filesort；**给 (status, create_time) 建联合索引** → 按 status 筛完即按 create_time 有序，避免文件排序。

## 什么时候需要 / 不需要创建索引？

### 适用索引

- 字段有唯一性限制（商品编码）；
- 经常用于 WHERE 条件（多字段建联合索引）；
- 经常用于 GROUP BY / ORDER BY（利用索引有序性免排序）。

### 不需要索引

- WHERE/GROUP BY/ORDER BY 用不到的字段（占空间）；
- **大量重复数据**（性别——分布均匀时搜哪个都返回约一半，优化器会忽略索引走全表）；
- 表数据太少；
- **经常更新的字段**（余额——频繁维护 B+Tree 有序性影响性能）。

## 优化索引的方法

### 前缀索引优化

减小索引字段大小 → 一页存更多索引值 → 查询更快。局限：**order by 无法用前缀索引；无法作覆盖索引**。

### 覆盖索引优化

query 的所有字段在索引 B+Tree 叶子都能找到 → 免回表 → 减少大量 I/O。如「商品ID、名称、价格」联合索引。

### 主键索引最好是自增的

- 自增主键：新数据追加到当前索引节点位置，页满开新页 → **无页分裂、无数据移动**；
- 非自增主键：随机插入可能插到数据页中间 → **页分裂**（数据移动 + 内存碎片 + 空间利用率降）；
- **主键长度不要太大**：二级索引叶子存主键值，主键越小二级索引越小。

### 索引最好设置为 NOT NULL

1. NULL 使索引选择、统计、值比较更复杂（count 会省略 NULL 行）；
2. NULL 占物理空间——行格式中至少 1 字节存 NULL 值列表。

### 防止索引失效（常见场景）

- 左模糊或左右模糊匹配：`like '%xx'` / `like '%xx%'`；
- 对索引列做计算、函数、类型转换；
- 联合索引不遵循最左匹配；
- OR 前后条件列（前索引后非索引）。

### 执行计划（EXPLAIN）关键字段

- `possible_keys`：可能用到的索引；
- `key`：实际用的索引，**NULL = 没用索引**；
- `key_len`：索引长度；
- `rows`：扫描行数；
- `type`：扫描类型。效率从低到高：**All（全表）< index（全索引）< range < ref（非唯一索引）< eq_ref（唯一索引）< const（主键/唯一索引常量）**。**至少要到 range**；
- `Extra`：`Using filesort`（文件排序，避免）、`Using temporary`（临时表，避免）、`Using index`（覆盖索引，优）。
