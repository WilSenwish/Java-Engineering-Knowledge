# 秒杀系统架构与库存扣减设计

## 秒杀系统核心挑战分析

秒杀活动将大量用户请求集中在极短时间窗口内释放，对系统承载能力形成巨大冲击。

## 流量层层过滤架构

**核心理念：逐层削减流量**，让绝大多数请求在到达核心服务前被过滤掉：

| 层级 | 过滤策略 |
|------|----------|
| 客户端层 | 前端随机丢弃逻辑，服务端压力大时直接返回"系统繁忙" |
| CDN | 秒杀页静态资源提前推送 CDN，就近获取降源站压力 |
| Nginx 接入层 | IP 限流（单 IP 每秒最多 5 次）、黑白名单、频率控制 |
| 应用网关层 | Sentinel 动态限流（按负载实时调阈值）+ 业务校验（登录状态/活动窗口） |
| 缓存层 | 商品/库存热点数据预加载本地缓存（Caffeine）+ Redis |

## 热点数据处理策略

秒杀商品天然是热点，读写高度集中：

### 数据拆分策略

单个热点商品库存拆成多个子库存分散到不同缓存节点。例：1000 件拆 10 个子库存各 100 件，请求均匀路由到不同子库存扣减。

### 多级缓存预热

1. **Redis 预热**：活动前将商品详情、库存写入 Redis 集群；
2. **本地缓存预热**：应用启动或定时任务加载热点数据；
3. **多副本部署**：Redis 热 Key 在不同节点建多副本。

## 库存扣减核心设计

库存扣减是秒杀系统最关键的环节，必须同时满足**原子性**和**有序性**，否则超卖或少卖。

### 超卖问题根源分析

超卖指实际销售数量超过可售库存。典型场景：并发下"查库存→判断充足→扣减"三步非原子，两个线程同时读到剩余 1 件，都通过判断，都扣减成功 → 库存变 -1。
