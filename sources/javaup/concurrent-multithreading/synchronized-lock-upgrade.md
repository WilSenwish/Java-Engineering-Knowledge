# Synchronized 锁升级与优化策略

## 锁升级机制概述

JDK 1.6 之前，Synchronized 直接使用重量级锁，每次加锁需操作系统介入，性能开销巨大。从 JDK 1.6 开始，HotSpot 引入锁升级机制，根据竞争情况动态调整锁状态。

### 四种锁状态（Mark Word 低3位标识）

- **无锁**：标志位 `001`
- **偏向锁**：标志位 `101`
- **轻量级锁**：标志位 `00`
- **重量级锁**：标志位 `10`

## 无锁状态

对象创建时处于无锁状态，Mark Word 存储哈希码、GC 分代年龄等信息。第一个线程访问同步代码块时锁状态开始变化。

## 偏向锁机制

### 设计理念

基于观察：**大多数情况下，锁不存在多线程竞争，且总是由同一个线程多次获得**。

### 工作流程

1. **首次获取**：线程首次进入同步块，CAS 将 Thread ID 写入对象头；
2. **再次进入**：检查 Mark Word 中 Thread ID 是否匹配——匹配直接执行，无任何同步操作；不匹配则偏向锁失效；
3. **偏向撤销**：检测到其他线程竞争时，等待安全点（Safe Point）→ 暂停持有线程 → 检查是否还在同步块 → 撤销并升级。

### JDK 15 废弃偏向锁的原因（JEP 374）

1. **维护成本高**：实现复杂，与其他组件交互复杂；
2. **收益递减**：现代应用大量使用 ConcurrentHashMap 等并发集合，不依赖 Synchronized；
3. **撤销开销**：竞争场景下频繁撤销（等安全点+暂停线程）反而降低性能；
4. **场景变化**：HashTable/Vector 已被高性能并发容器替代。

## 轻量级锁机制

### 适用场景

**线程交替执行同步块，无长时间竞争**。通过 CAS 避免互斥量开销。

### 加锁流程

1. **创建锁记录**：线程栈帧中创建 Lock Record 空间；
2. **保存原始信息**：对象头 Mark Word 复制到 Lock Record（Displaced Mark Word）——解锁时恢复，保证 hashCode/GC 年龄不丢失；
3. **CAS 操作**：尝试将对象头 Mark Word 更新为指向 Lock Record 的指针——成功获得锁，失败进入自旋或升级；
4. **自旋等待**：CAS 失败后空循环等待，避免线程切换开销。

### 解锁流程

CAS 将 Displaced Mark Word 替换回对象头：成功则无竞争解锁完成；失败说明锁已膨胀，需释放重量级锁并唤醒等待线程。

## 重量级锁机制

### 膨胀触发条件

轻量级锁 CAS 多次失败（自旋超阈值）/ 自旋时间过长浪费 CPU / 等待线程过多。

### 工作机制

通过操作系统互斥量（Mutex）实现：未获得锁线程进入 BLOCKED 状态，需 OS 调度（用户态↔内核态切换），开销大但避免 CPU 空转。

## 锁降级的真相

**常见误解**：认为锁可从重量级降级回轻量级——**不正确**。HotSpot 中锁状态只能升级不能降级。

**特殊的"降级"场景——Monitor 回收（Deflation）**：发生在 STW 阶段，JVM 检查所有 Monitor，回收空闲 Monitor，对象头恢复初始状态。这不是真降级，下次加锁仍从偏向/轻量级开始。

**JRockit 虚拟机**：支持真正的锁降级——最后一个竞争线程释放重量级锁时，若判断受益可降为轻量级。

## 锁优化技术

### 自旋锁优化

共享数据锁定状态通常只持续很短时间，为此挂起恢复线程不值得。优点：避免线程切换开销；缺点：占用 CPU，不适合长锁持有。

### 锁消除优化

逃逸分析检测到加锁对象不会被多线程访问时，JIT 自动消除锁。典型：`StringBuffer` 局部变量不逃逸，其 append 的 synchronized 被消除。

### 锁粗化优化

检测到一系列连续操作对同一对象反复加锁解锁，将锁范围扩大到整个操作序列外。与"减小锁粒度"不矛盾：减小粒度强调锁内不做无关操作；锁粗化强调同一对象连续操作合并。

类比：减小粒度=办业务前备好资料；锁粗化=5 个业务在同一窗口一次办完。

### 适应性自旋

自旋次数不固定，根据前一次自旋成功率动态调整。

## 核心要点总结

1. 锁升级单向：无锁→偏向锁→轻量级锁→重量级锁，不可逆；
2. 偏向锁 JDK 15 废弃（维护成本高、收益递减）；
3. 轻量级锁 CAS+自旋，适合竞争不激烈；
4. 重量级锁 Monitor 机制，适合高竞争；
5. HotSpot 无锁降级，但 Monitor 对象可回收（Deflation）；
6. JIT 提供锁消除/锁粗化/自适应自旋；
7. JDK 1.6 后 Synchronized 性能接近甚至超过 ReentrantLock，是首选同步机制。
