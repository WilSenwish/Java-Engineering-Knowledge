## 1. 项目定位

12306 铁路购票服务是与生活和出行相关的关键系统，包括**会员、购票、订单、支付和网关**等服务。旨在让学习者快速掌握分布式系统设计技巧，尤其适合对高并发、分布式感兴趣的同学。项目中包含**缓存、消息队列、分库分表、设计模式**等代码。

**双版本设计**：
- **SpringBoot 聚合服务版本**：适合测试和部署，直接启动 `aggregation-service` 聚合服务 + 网关；
- **SpringCloud 微服务版本**：适合学习微服务设计，支付、订单、用户、购票、网关分别启动。

**技术架构**：JDK 17 + SpringBoot 3 + SpringCloud（Alibaba）微服务架构，构建高并发、大数据量下高效可靠的购票服务。前端 Vue3。

## 2. 用户服务五大设计难题（面试核心）

1. **信息真实性校验**：注册新账号/添加乘车人时，如何验证用户提交信息的真实性和准确性？如何有效预防虚假信息、保障购票安全？
2. **大规模数据分库分表**：大规模用户和乘车人数据如何选择分库分表？**选择哪个字段作为分片键**？如何在老业务上**平滑上线**分库分表？出现问题如何**快速回滚**？
3. **读请求扩散**：系统支持用户名、手机号、邮箱等多种方式登录，**登录时无法确定用户的分片键**，造成的"读请求扩散"问题如何解决？
4. **缓存穿透治理**：高并发会员注册场景下绝对会出现缓存穿透。"网上鼓吹的对不存在 Key 缓存值设为 Null，以及布隆过滤器等**都存在漏洞**，如何解决？"
5. **敏感信息防泄露**：姓名、手机号、邮箱、证件号码、住址，如何防止数据库被攻击时造成的敏感信息泄露？

## 3. 购票服务：座位分配算法（完整逻辑）

**场景**：用户购买两个乘车人的高铁一等座票且没有选座时，座位分配逻辑：

1. **余票校验**：首先检查当前列车的一等座余票是否足够。余票不足 → 直接返回购票失败；
2. **候选车厢筛选**：获取所有车厢中有两个座位余票的车厢，对这些车厢进行遍历；
3. **第一优先级——相邻座位**：检查所有车厢中是否存在一等座车票的相邻座位。如果所有车厢都没有相邻座位，进入下一步；
4. **第二优先级——同车厢不相邻**：检查是否有车厢包含两个不相邻的一等座座位（同车厢两座位相邻的没有，就退而找同车厢不相邻）；
5. **第三优先级——跨车厢不相邻**：如果以上都无法满足，最后选择分配不同车厢的不相邻座位。由于已确认一等座余票充足，因此一定能够成功完成购票。

**设计目标**：在余票充足情况下合理分配座位，确保乘车体验；余票不足时优先满足乘车人顺利购票。

## 4. 12306 购票三大误区（经典面试题）

**背景**：一列列车途径 北京南、济南西、南京南、杭州东、宁波。

**误区一：车次查询用 ElasticSearch？**
- 你以为：通过 ES 解决，因为涉及大量查询条件（车次、车组、出发车站、到达车站、出发时间等）；
- 实际上：**当海量并发查询时，ES 的并发能力以及资源占用并不适用**。仔细思考发现这些查询条件都可以通过类似 Redis 的缓存技术存储，**并在内存中进行组装**。

**误区二：北京南→南京南只扣单趟？**
- 你以为：只扣减北京南到南京南单趟的票；
- 实际上：会扣减 **北京南-济南西、北京南-南京南、济南西-南京南三趟车票**。其中任意条件不满足都不会购买成功。

**误区三：恶意刷中间站票？**
- 你以为：如果通过软件恶意刷票，只买济南西-南京南的票，是不是北京南-杭州东就买不到了？
- 实际上：**每个站数之间的数量都有规则**。虽然放票时间一致，但优先大站之间的票量，避免大量用户购买中间站车票导致始发站和终点站购票困难。**通过动态放票解决**：刚开始放票时对小站之间仅开放少量票，大站之间放多数票；接近发车时间再开放小站间车票。
