告警刚响，排查很容易被监控页面上最显眼的那条曲线带着走。看到 CPU 高就抓线程栈，看到 Full GC 就查堆，发布刚结束就准备回滚。可这些现象经常互相传导：慢 SQL 会占住数据库连接，连接池等待又会拖住业务线程，最后可能同时看到延迟、错误率和 CPU 上升。单看其中一项，很难定根因。

## 收到告警后先确认什么？

1. 先看用户侧有没有异常：单个实例 CPU 高但请求仍被其他实例正常承接 ≠ 整个服务错误率上升；
2. 排除监控误报、指标采集延迟、下游超时把线程堵在本服务；
3. 把告警前后十几分钟的请求量、错误率、P95/P99、CPU、内存、GC、线程池、连接池曲线**放在一起看**，对照发布、配置变更、定时任务、流量突增的时间点；
4. 数据库、Redis、MQ、外部接口的告警一起拉进来，沿时间线确认**哪个指标最先变化**；
5. 平均响应时间正常 ≠ 请求都正常——少量超慢请求可能卡在登录/下单/支付关键链路，看 P95/P99、超时率、业务成功率。

## 止血和留证怎么取舍？

故障扩大时先按预案止血：回滚版本、摘除异常实例、关闭问题定时任务、限流、熔断、降级非核心、扩容。每项都有副作用：扩容可能压垮数据库，重试放大下游流量，回滚未必兼容已变更数据。

重启/回滚前保留：告警前后监控截图、应用/访问/GC 日志、**一到三份间隔数秒的线程栈**（不是一份）、Trace 慢调用、进程 CPU/RSS/堆/线程数/fd/连接状态、DB 慢查询/锁等待/连接池状态、Redis 慢命令、MQ 积压。

实例摘流量后也不要马上做 Heap Dump——转储大堆需要磁盘空间和 I/O。**提前配置 OOM 自动转储**：

```bash
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/path/with/enough/space
```

## 现象 → 排查入口速查表

| 现象 | 优先检查 |
|------|----------|
| CPU 高，接口同时变慢 | 热点线程、死循环、序列化、锁竞争、频繁 GC |
| CPU 不高，Load 很高 | 磁盘 I/O、不可中断睡眠、网络存储、容器 CPU 限额 |
| RSS 持续上涨，Java 堆稳定 | 直接内存、线程栈、Metaspace、JNI、本地库、内存映射 |
| Old 区回收后仍持续上涨 | 长生命周期对象、无界缓存、集合持有、监听器、ThreadLocal |
| 线程数和队列长度上涨 | 下游变慢、锁等待、任务变慢、线程池隔离不足 |
| 数据库连接池等待上涨 | 慢 SQL、长事务、连接泄漏、DB 容量 |
| Redis RT 上涨 | 慢命令、大 Key、热 Key、网络抖动、连接池等待 |
| MQ Lag 持续上涨 | 消费变慢、分区不均、异常消息重试、下游容量 |

**跨层传播警示**：慢 SQL 占连接 → 业务线程阻塞在连接池 → 线程池队列堆积 → 上游超时重试 → CPU/延迟/错误率齐升。

## CPU 飙高排查

```bash
jps -l                          # 找 Java 进程
top -H -p <pid>                 # 进程内各线程 CPU
pidstat -t -p <pid> 1           # 按线程看一段时间 CPU
printf '%x\n' <tid>             # top 十进制 tid → 十六进制
jcmd <pid> Thread.print > /tmp/thread-dump.txt   # 线程栈对照 nid
```

线程栈**连续抓几份**：某线程只在一份里做 JSON 序列化可能只是采样巧合；多份都停在同一段代码才值得深查。常见原因：无法退出的循环/递归、大对象序列化/正则回溯/加解密、大量分配引发频繁 GC、锁竞争伴随上下文切换、流量上涨或重试放大。

CPU 接近打满时不要同时启动多个高开销诊断任务。

## CPU 不高但 Load 很高

Load Average 统计运行中 + 不可中断睡眠任务。磁盘/网络存储/内核 I/O 等待严重时 CPU 不高 Load 仍涨。

```bash
vmstat 1        # 运行队列、I/O 等待、阻塞任务
iostat -xz 1    # 设备利用率、等待时间、队列
pidstat -d -p <pid> 1
```

## 接口慢但 CPU 不高

多为等待：等 DB 连接、等下游响应、等锁、等线程池、等磁盘 I/O。线程栈常见状态：

- 大量线程停 `getConnection()` → 连接池等待、活跃连接、慢 SQL、长事务；
- 大量线程停 HTTP 客户端读响应 → 下游延迟、超时配置、重试次数；
- 大量线程 `BLOCKED` → 锁持有者与临界区慢操作；
- 业务线程空闲但队列堆积 → 消费者线程、任务提交方式、执行器状态。

**耗时对账**：一次慢请求总耗时应能和各阶段对上；Trace 只记业务方法耗时时，连接池等待/线程池排队/DNS/TLS 会出现「无法解释的空白」——补埋点。

## 内存持续上涨与 OOM

先分清 Java 堆 / 进程 RSS / 容器总内存。`-Xmx` 只限堆，还有 Metaspace、Code Cache、线程栈、直接内存、GC 结构、本地库内存。

```bash
jcmd <pid> GC.heap_info
jcmd <pid> VM.flags
jcmd <pid> VM.native_memory summary   # 依赖启动参数 -XX:NativeMemoryTracking=summary，不能故障后补开
```

OOM 信息对照：

| OOM | 排查方向 |
|-----|----------|
| `Java heap space` | 大对象、对象持有、无界集合、缓存、一次查询返回过多 |
| `GC overhead limit exceeded` | 堆接近耗尽，GC 耗时但回收很少 |
| `Metaspace` | 动态类生成、类加载器泄漏、上限过小 |
| `Direct buffer memory` | NIO 直接内存、Netty Buffer、释放延迟 |
| `unable to create native thread` | 线程数过多、进程限制、容器内存不足、栈过大 |

Heap Dump 分析（MAT/VisualVM）：先看占用最大对象、Dominator Tree、到 GC Roots 的引用链、可疑类加载器。

手动转储：`jcmd <pid> GC.heap_dump filename=/path/heap.hprof`（有明显影响，摘流量后执行）。`jmap -dump:live` 可能触发 Full GC，**不是无风险命令**。

**泄漏 vs 正常增长**：看完整 GC 后的堆占用——流量和数据规模稳定时，Old 区多次完整回收后仍持续抬升才怀疑泄漏。缓存预热、类加载、流量增长导致的逐步上升不一定是泄漏。Map 大只说明占内存，要沿引用链找到**无界缓存/静态集合/监听器/ThreadLocal/错误的会话生命周期**才能确认修复点。

## Young GC 频繁

分配速率快或年轻代不足。`jstat -gcutil <pid> 1000 10` + `jcmd <pid> GC.heap_info`。常见原因：一次查询加载大量对象、接口返回超大结果、日志/序列化大量临时对象、批处理无批次控制。调参只改变节奏，**修复不了无界查询和高分配代码**。

## Full GC 频繁

从 GC 日志确认触发原因（不是所有 Full GC 都是「老年代满了」）、回收前后占用、停顿时间。重点看：Old 区回收后能否明显下降、大对象/晋升是否过多、Metaspace 是否接近上限、是否有显式 `System.gc()`、堆与容器限额是否匹配、GC 前是否有流量上涨/批任务/缓存刷新。**加大堆只会延后下一次故障**。

## 线程池队列堆积

不能只看活跃线程数，至少监控：core/maximum/当前线程数、活跃线程/队列长度/队列容量、任务提交速率/完成速率/等待时间/执行时间、拒绝次数与策略。

排查顺序：① 确认哪些业务任务混用该池；② 比较提交/完成速率与排队/执行时间；③ 抽运行中任务线程栈确认在计算还是等待；④ 检查 DB/HTTP/Redis 连接池是否同步耗尽；⑤ 按任务重要性限流/降级/扩容/隔离/丢弃。

`CallerRunsPolicy` 让提交线程自己执行——Web 请求线程被长任务占住后接口延迟也升，需结合调用方判断。

## 数据库连接池耗尽

看活跃/空闲连接、等待线程、获取耗时。三个方向：SQL 慢（连接长时间不还）、事务范围过大（含远程调用/文件处理/大量计算）、连接泄漏（分支未关）。DB 侧：`SHOW PROCESSLIST`、慢日志、Performance Schema、`EXPLAIN`、InnoDB 锁信息。**测试库走索引 ≠ 生产相同**（执行计划来自当前 SQL/参数/数据分布）。

扩容前确认 DB 承受力：实例数 × 单实例池上限 = DB 总连接数。

## Redis 变慢

先区分客户端等待 vs 服务端执行（连接池耗尽/网络/DNS 都会让调用变慢）。服务端看：命令延迟与慢日志（`SLOWLOG GET` 只记服务端执行时间，不含排队和网络）、CPU/内存/网络/连接数、大 Key/热 Key/过期删除/持久化、主从延迟与集群状态。

大 Key 排查 `redis-cli --bigkeys` 需扫描键空间——低峰期/从节点/受控采样，**禁止线上 `KEYS *`**。热 Key 要看访问频率 + 节点负载（体积小但读取次数极高）。

## MQ 积压

比较生产/消费速率，定位 Topic/队列/分区。常见原因：流量超设计容量、某类消息变慢拖住整个分区、异常消息重试风暴、分区分配不均/Rebalance、提交位点失败重复消费、下游成瓶颈。

Kafka 有效并行度受**分区数**限制——加消费者没有分区可分配不提升吞吐。处理积压要保幂等，跳异常消息需留内容和失败原因后续补偿。

## 下游接口超时

把一次调用时间拆开：连接池等待、DNS、TCP 建连、TLS 握手、发送、服务端处理、响应读取——不同阶段要不同超时配置。多层重试放大：网关/服务/SDK 各重试 3 次，最坏请求量远超一次调用——**先限重试层级和总预算**，再按幂等性决定能否重试。

## 面试怎么回答线上排查

> 先确认影响范围、流量和最近变更，判断是否摘实例/限流/回滚；条件允许保留监控、日志和多份线程栈。CPU 确实来自 Java 进程后，用 `top -H`/`pidstat -t` 找热点线程，tid 转十六进制对照线程栈 `nid`；连续采样确认线程长期停留位置，结合 GC/Trace/流量判断计算热点、死循环、锁竞争还是频繁 GC。修复后同场景验证，补监控和回归测试。

没处理过真实故障就说测试环境演练过什么、参考过什么案例，**不要把读过的文章说成亲自负责的事故**。

## 常用工具速查

| 工具 | 用途 | 提醒 |
|------|------|------|
| `top`/`pidstat` | 进程/线程 CPU、I/O | 先确认容器和宿主机观察口径 |
| `vmstat`/`iostat` | 运行队列、内存、磁盘 | 结合一段时间趋势 |
| `jcmd` | 线程栈、堆信息、JFR、类直方图 | 部分命令开销高 |
| `jstat` | GC 与各内存区变化 | 连续采样比单点有用 |
| JFR/JMC | CPU、分配、锁、I/O 事件 | 采集配置结合线上开销 |
| MAT/VisualVM | Heap Dump 分析 | 重点看引用链和 GC Roots |
| Arthas | 方法耗时、线程、类、运行时诊断 | 高流量方法 Trace/Watch 限制范围 |
| Trace/监控平台 | 请求链、错误率、延迟、依赖 | 关注采样率、脱敏、时间同步 |
