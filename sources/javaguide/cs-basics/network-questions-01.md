## 一、计算机网络体系结构

### 1.1 OSI 七层模型

由国际标准化组织提出，**概念清楚、理论完整**。**缺点**：比较复杂且不实用，有些功能在多个层中重复出现。核心思想：每一层专注做一件事情，并使用下一层提供的功能。

### 1.2 TCP/IP 四层模型

目前被广泛采用的模型，可看作 OSI 七层的**精简版本**：应用层、传输层、网络层、网络接口层。不能与 OSI 完全精确匹配，但可简单对应。

### 1.3 为什么网络要分层？

1. **各层之间相互独立**：只需知道如何调用下层功能（类似接口调用）；
2. **提高灵活性和可替换性**：每层可用最适合的技术，接口不变即可独立修改替换（高内聚低耦合）；
3. **大问题化小**：复杂问题分解为界线清晰的小问题。

> 结论：计算机科学领域的任何问题都可以通过增加一个间接的中间层来解决。

## 二、各层协议与相关设备

### 2.1 应用层常见协议

| 协议 | 说明 | 传输层基础 | 关键特性 |
|------|------|-----------|----------|
| **HTTP** | 超文本传输协议 | TCP（1.x/2）；QUIC/UDP（3） | Web 客户端与服务器通信 |
| **SMTP** | 简单邮件发送 | TCP | 只负责发送不负责接收 |
| **POP3/IMAP** | 邮件接收 | TCP | IMAP 更新更强，支持搜索/标记/多设备同步 |
| **FTP** | 文件传输 | TCP | 屏蔽 OS 差异；**不加密**，建议 SFTP |
| **Telnet** | 远程登录 | TCP | 明文（含密码），已很少使用 |
| **SSH** | 安全网络传输 | TCP | 加密 + 认证 |
| **RTP** | 实时传输 | 通常 UDP | 端到端实时，不保证质量 |
| **DNS** | 域名系统 | 通常 UDP（53）；响应过大/区域传送用 TCP | 域名 → IP 映射 |

**涉及设备/实体**：DNS 服务器、Web 服务器、代理、网关。

### 2.2 传输层

- **TCP**：面向连接、可靠传输；
- **UDP**：无连接、尽最大努力，简单高效。

### 2.3 网络层协议与设备

- **IP**：数据包格式、路由寻址（IPv4/IPv6）；
- **ARP**：IP → MAC 地址解析；
- **ICMP**：网络状态和错误消息（Ping）；
- **NAT**：LAN → WAN 地址转换，共享公网 IP；
- **OSPF**：内部网关协议，链路状态算法（带宽/延迟）；
- **RIP**：内部网关协议，距离向量（固定跳数）；
- **BGP**：边界网关协议，域间交换可达性信息（NLRI）。

**相关设备**：路由器、NAT 设备、防火墙、负载均衡器。

## 三、输入网址到网页显示全过程

1. 浏览器输入 URL；
2. 通过 **DNS** 获取域名对应 IP；
3. 根据 IP + 端口发起 **TCP** 连接；
4. 在 TCP 连接上发送 **HTTP** 请求报文；
5. 服务器处理并返回 HTTP 响应报文；
6. 浏览器解析 HTML 渲染，再对图片/CSS/JS 等资源发起 HTTP 请求直至加载完成；
7. 浏览器主动关闭 TCP 连接或等待服务器关闭。

> 路由过程可能涉及 **OSPF** 等路由选择协议。

## 四、HTTP 缓存

### 缓存相关字段

| 字段 | 说明 |
|------|------|
| `Cache-Control` | 指定缓存机制遵守的指令（如 `no-cache`） |
| `If-Modified-Since` | 资源自指定日期未修改则返回 304 |
| `If-None-Match` | ETag 未变化则返回 304 |
| `If-Match` | 客户端实体与服务器匹配才操作 |
| `If-Unmodified-Since` | 实体自某时间未修改才回应 |
| `If-Range` | 未修改则发缺少部分，否则发整个新实体 |
| **ETag** | HTTP/1.1 引入的缓存判断标准 |

**版本差异**：HTTP/1.0 用 `If-Modified-Since`、`Expires`；HTTP/1.1 引入 ETag、`If-None-Match`、Range 头域（206 Partial Content）。

**GET 幂等可缓存；POST 不适合缓存**。

## 五、HTTP 状态码

常见：`100 Continue`（发送大请求体前确认）、`101 Switching Protocols`（WebSocket 升级）、`206 Partial Content`（范围请求）、`304 Not Modified`（用本地缓存）、`409 Conflict`、`410 Gone`。

## 六、GET 与 POST 的区别

| 方面 | GET | POST |
|------|-----|------|
| **语义（主要区别）** | 获取/查询资源 | 创建/修改资源 |
| **幂等性** | 幂等 | 不幂等 |
| **参数格式** | URL 查询字符串，长度受限 | body，无明确限制，多种编码 |
| **缓存** | 可缓存 | 不适合 |
| **安全性** | 参数在 URL 更易泄露 | body 相对不易泄露 |

> 实际使用中也有项目所有请求都用 POST，项目组达成共识即可。

## 七、关键结论

### HTTP/1.1 与 HTTP/2.0 的队头阻塞对比

| 方面 | HTTP/1.1 | HTTP/2.0 |
|------|----------|----------|
| **层级** | 应用层（协议本身限制） | 传输层（TCP 限制） |
| **根本原因** | 无法多路复用，按顺序传输 | TCP 按序交付，丢包阻塞整个连接 |
| **受影响范围** | 单个请求/响应阻塞后续 | 单个 TCP 包丢失影响所有流 |
| **缓解** | 多个并行 TCP 连接 | 减少掉包或用 QUIC |

### HTTPS 握手里 RSA 和 ECDHE 区别

- **RSA（TLS 1.2 静态）**：客户端生成 PreMasterSecret，用服务器证书 RSA 公钥加密后发，服务端私钥解密。**无前向安全**——私钥泄漏可解历史会话；
- **ECDHE**：双方各自生成临时密钥对，交换临时公钥本地算出共享秘密；证书私钥只用于签名认证，**不用来解密会话密钥**。支持前向安全，现代 HTTPS 主流。

### 有了 HTTP，为什么还要 RPC？

- HTTP 和 RPC 不是谁取代谁；
- **HTTP**：适合对外接口（Web/App/第三方），通用、好调试、接入成本低；
- **RPC**：适合公司内部服务互调，可一并处理服务发现、超时、重试、负载均衡、链路追踪；
- 一句话：HTTP 没那么弱，RPC 也没那么神，看哪个能用更低成本解决现在的问题。

### 其他速记

- **URI vs URL**：URI 是统一资源标志符（唯一标识资源）；URL 是统一资源定位符（具体 URI，还指明如何 locate）；
- **保存用户状态**：Cookie + Session（主流，Session 可存内存/DB/Redis）；URL 重写（Cookie 禁用时，安全性低）；Token 认证（JWT，适合前后端分离和微服务）；
- **Ping 通不代表 TCP 连通**：ICMP 与 TCP 由中间设备按协议/端口/策略分别处理。排查顺序：DNS → ping → nc 测端口 → curl/openssl s_client 看 TLS；
- **DNS 根服务器**：逻辑上 13 个标识（a~m.root-servers.net），由 12 个独立运营组织负责，背后通过 Anycast 部署多个物理实例。
