## 一、操作系统基础

### 1.1 什么是操作系统

通过以下四点概括：

1. **操作系统（OS）是管理计算机硬件与软件资源的程序**，是计算机的基石。
2. 本质上是一个运行在计算机上的软件程序，所有应用程序都通过它调用内存、磁盘等硬件。
3. **屏蔽了硬件层的复杂性**，操作系统是硬件使用的负责人。
4. **内核（Kernel）是操作系统的核心部分**，负责内存管理、硬件设备管理、文件系统管理以及应用程序管理，是连接应用程序和硬件的桥梁。

**Kernel vs CPU 的区别**：
- Kernel 属于操作系统层面，CPU 属于硬件。
- CPU 提供运算、处理指令的能力；Kernel 负责系统管理（如内存管理），屏蔽对硬件的操作。

### 1.2 操作系统主要功能（从资源管理角度，共 6 大功能）

1. **进程和线程的管理**：进程的创建、撤销、阻塞、唤醒，进程间的通信等。
2. **存储管理**：内存的分配与回收、地址转换、进程隔离、页面回收，以及外存空间管理等。
3. **文件管理**：把底层存储块组织成文件和目录，负责文件读写、创建、删除、权限控制和崩溃恢复等。
4. **设备管理**：完成设备的请求或释放，以及设备启动等功能。
5. **网络管理**：管理计算机网络的配置、连接、通信和安全等。
6. **安全管理**：用户身份认证、访问控制、文件加密等。

## 二、用户态与内核态

### 2.1 什么是用户态和内核态

用户态和内核态描述的是 **CPU 执行代码时的特权级别**。

| 状态 | 权限与能力 |
|------|-----------|
| **用户态（User Mode）** | 权限较低，不能直接执行特权指令，不能随意访问内核地址空间或操作硬件。应用读文件、收发网络数据需通过系统调用请求内核服务。 |
| **内核态（Kernel Mode）** | 权限较高，可执行管理页表、中断、设备等特权操作。系统调用、中断或同步异常进入内核后，运行的是内核代码，而非把用户进程变成"内核进程"。 |

> **结论**：用户态/内核态切换需要经过架构规定的入口、保存状态并执行权限检查，比普通函数调用更重。但它**不等于线程上下文切换**——只有调度器换成另一个执行实体时，才发生线程切换。

### 2.2 为什么要有用户态和内核态

主要是为了**安全**和**稳定**：

- **限制特权操作**：修改页表、控制中断、访问设备寄存器等影响整个系统的操作，只能由内核执行。
- **隔离故障和权限**：若应用都能以内核权限运行，一个越界写或恶意程序就可能破坏其他进程和内核数据，进程隔离失去基础。

### 2.3 用户态和内核态是如何切换的

让 CPU 从用户态进入内核态的事件主要有三类：

1. **系统调用（Trap）**：应用主动执行 `syscall`、`ecall` 等指令，请求内核完成 `read()`、`send()` 等。由当前指令触发，属于**同步事件**。
2. **硬件中断（Interrupt）**：由定时器、网卡、磁盘等外部硬件触发，与当前指令无直接关系，属于**异步事件**。
3. **同步异常（Exception）**：由当前指令触发，如除零、非法指令或 Page Fault。异常不一定代表程序出错，懒分配、COW 和从文件调页也会触发可恢复的 Page Fault。

> **补充**：信号（Signal）是内核通知进程/线程的一种**软件机制**。例如非法内存访问先触发 Page Fault，内核判断无法修复后，再向当前线程投递 `SIGSEGV`。

## 三、中断与异常（专题提炼）

原文将"中断与异常"融合在"用户态/内核态切换"中，核心要点如下：

- **硬件中断（Interrupt）**：异步事件，由外部硬件触发（定时器、网卡、磁盘等），与当前执行指令无直接关系。
- **同步异常（Exception）**：同步事件，由当前指令触发（除零、非法指令、Page Fault）。Page Fault 不一定是错误，也可能是懒分配、COW、文件调页等可恢复场景。
- **系统调用（Trap）**：虽也是同步事件，但属于用户主动请求内核服务的受控入口，与"异常"的被动触发有所区别。

## 四、系统调用

### 4.1 什么是系统调用

系统调用是**内核向用户程序提供的受控服务接口**。应用不能直接操作磁盘、页表、网卡等受保护资源，需通过系统调用让内核代为完成。

按功能分类：

- **设备管理**：设备请求/释放、启动等。
- **文件管理**：文件读、写、创建、删除。
- **进程管理**：进程创建、撤销、阻塞、唤醒、通信。
- **内存管理**：内存分配、回收、获取占用内存区大小及地址。
- **网络通信**：创建 Socket、建立连接、收发数据。

> **系统调用 vs 库函数**：不是同一层概念。普通函数调用始终在用户态执行；glibc 等运行库提供的 `read()` 包装函数会按 ABI 准备系统调用号和参数，再执行特殊指令进入内核。

### 4.2 系统调用的过程（以 Linux x86-64 `read(fd, buf, count)` 为例）

1. glibc 包装函数按调用约定，把**系统调用号和参数放入指定寄存器**，执行 `syscall`。
2. CPU 切换到内核特权级和对应入口；内核入口代码**保存寄存器状态**，按系统调用号分发到 `read` 处理逻辑。
3. 内核**检查文件描述符、用户缓冲区、访问权限和文件状态**，进入 VFS、文件系统、网络协议栈或设备驱动。
4. 数据就绪则完成读取并返回；数据未就绪则**当前线程可能进入等待**，调度器转而运行其他任务。
5. 返回值通过寄存器交回用户态；出错时 glibc 通常把内核错误码转换成 `-1` 和 `errno`。

### 4.3 系统调用一定会发生上下文切换吗

**不一定**。

- 若内核很快处理完并返回原线程，整个过程只有**用户态/内核态切换**，没有切换线程。
- 只有当系统调用需要等待 I/O、锁等资源导致线程阻塞，调度器选择另一个可运行任务时，才会发生**线程上下文切换**。
- 反过来，时钟中断进入内核后，若调度器仍让原线程继续运行，也不会发生线程切换。

## 五、进程管理

### 5.1 进程和线程的区别

进程和线程是并发执行的两个核心概念，关系可理解为**工厂和工人**：

- **进程（Process）像工厂**：是**资源分配和隔离的基本单位**，拥有独立虚拟地址空间、文件句柄等，进程间严格隔离。
- **线程（Thread）像工人**：是**CPU 调度和执行的基本单位**，共享进程资源，但有自己的栈和任务清单。

从 JVM 角度：一个进程中多个线程**共享堆和方法区（元空间）**，但每个线程私有**程序计数器、虚拟机栈、本地方法栈**。

**关键对比表**：

| 维度 | 进程 | 线程 |
|------|------|------|
| **基本定位** | 资源分配和隔离的基本单位 | CPU 调度和执行的基本单位 |
| **地址空间** | 默认拥有独立虚拟地址空间 | 同一进程内的线程共享进程地址空间 |
| **私有内容** | PID、地址空间、打开文件表、权限信息等进程级资源 | 线程 ID、栈、寄存器、程序计数器、线程本地存储等执行现场 |
| **通信方式** | 需要 IPC（管道、消息队列、共享内存、Socket） | 可直接读写共享内存，但必须处理同步和线程安全 |
| **创建/切换成本** | 通常更高，可能涉及地址空间切换、TLB 失效 | 通常更低，同进程线程切换一般不需要切换地址空间 |
| **故障影响** | 隔离性更好，一个进程崩溃通常不影响其他进程 | 一个线程出错可能导致整个进程退出 |

### 5.2 有了进程为什么还需要线程

核心原因：**在单个应用内实现低开销、高效率的并发**。

- 多进程共享状态麻烦，通信要走 IPC，资源占用高。
- 多线程可直接共享堆内存和连接，协作成本低。
- 提高资源利用率：单核 CPU 上 I/O 阻塞时其他线程可运行；多核 CPU 上可并行执行。
- **注意**：线程不是越多越好。过多会带来栈内存占用、调度开销、锁竞争和缓存失效等问题。

### 5.3 多线程一定能提高性能吗

取决于任务类型、CPU 核数和共享资源竞争：

- **I/O 密集型**：一个线程等待磁盘/网络/锁时，其他线程可用 CPU，能隐藏部分等待时间。
- **CPU 密集型**：可拆分且独立的计算可多核并行，但受串行部分、数据依赖、缓存和调度开销影响。
- **线程过多**：可运行线程远多于 CPU 核数后，上下文切换、缓存失效和锁竞争增加，吞吐量和延迟都可能变差。

### 5.4 线程间的同步方式

线程同步是避免共享关键资源冲突的机制，常见方式：

1. **互斥锁（Mutex）**：只有拥有互斥对象的线程才能访问公共资源。如 Java `synchronized`、各种 `Lock`。
2. **读写锁（Read-Write Lock）**：允许多线程同时读，但只允许一个线程写。
3. **信号量（Semaphore）**：允许同一时刻多个线程访问资源，但控制最大并发数量。
4. **屏障（Barrier）**：等待多个线程到达某点再一起继续。如 Java `CyclicBarrier`。
5. **条件变量（Condition Variable）/事件通知**：条件不满足时等待，条件变更后通知。通常需配合互斥锁避免丢通知。如 Java `Object.wait()/notify()`、`Condition.await()/signal()`，Windows Event。

### 5.5 PCB 与 TCB

**PCB（Process Control Block，进程控制块）**：每个进程对应一个独立 PCB，是进程的大脑。包含：

- **标识信息**：PID、父进程 ID、用户 ID。
- **进程状态和调度信息**：就绪/运行/阻塞、优先级、时间片、CPU 时间统计。
- **CPU 上下文**：程序计数器、栈指针、通用寄存器、PSW。
- **内存管理信息**：虚拟地址空间、页表、内存映射等。
- **资源信息**：打开文件、文件描述符、I/O 状态、工作目录、信号处理信息等。

**TCB（Thread Control Block，线程控制块）**：保存线程级控制信息（线程 ID、状态、寄存器现场、栈信息、调度优先级、TLS 等）。

> **Linux 特殊之处**：不严格拆分 PCB/TCB，把进程和线程都看成 task，用 `task_struct` 描述调度实体，通过资源结构是否共享来区分。关键是分清：**地址空间、文件表属于资源边界；栈、寄存器、PC 属于执行现场**。

### 5.6 进程状态

一般分为 5 种：

- **创建状态（new）**：正在被创建，尚未到就绪。
- **就绪状态（ready）**：获得除处理器外的一切资源，等 CPU 即可运行。
- **运行状态（running）**：正在处理器上运行（单核 CPU 任意时刻只有一个）。
- **阻塞状态（waiting）**：等待某事件（资源可用、I/O 完成）而暂停，即使 CPU 空闲也不能运行。
- **结束状态（terminated）**：正在从系统中消失。

**状态转换重点**：就绪态拿到 CPU 进入运行态；运行态时间片用完回就绪态；运行中发起阻塞 I/O、等锁或等事件进入阻塞态；阻塞事件完成后通常先回就绪态等调度。

**挂起状态**：强调进程暂时不在内存中或被暂停；与"阻塞"（等待事件）不是一回事。进程可以阻塞但仍在内存，也可以被换出到外存后处于阻塞挂起。

### 5.7 进程间通信（IPC）

进程默认拥有独立虚拟地址空间，不能直接访问彼此内存，需要 IPC。按场景回答：

- **父子进程传少量字节流**：匿名管道。
- **无亲缘关系进程本机通信**：命名管道、Unix Domain Socket。
- **小型结构化消息**：消息队列。
- **本机大块数据交换**：共享内存（需配合信号量、互斥锁、`futex`、`eventfd` 等同步）。
- **异步事件通知**：信号。
- **跨机器通信**：TCP/UDP Socket 或更上层 RPC 框架。

### 5.8 fork、exec、wait

Unix/Linux 进程创建和程序替换的三个核心动作：

- **`fork()`**：创建子进程。父子进程从同一位置继续执行，但返回值不同。
- **`exec()`**：在当前进程中装入另一个程序，**不新建进程**，而是替换当前进程的用户态代码和数据。
- **`wait()`/`waitpid()`**：等待子进程状态变化，回收子进程退出后留在内核里的状态信息。

> **Shell 启动外部命令链路**：Shell `fork()` 出子进程 → 子进程 `exec()` 成目标程序 → 父进程 `wait()` 回收退出状态。父进程一直不回收已退出子进程会产生**僵尸进程**。

### 5.9 什么是上下文切换

上下文切换指 **CPU 从一个执行实体切到另一个执行实体**。操作系统保存当前实体的寄存器、PC、栈指针等现场，再恢复下一个实体的现场。

- **进程切换通常更重**：涉及页表切换、TLB 失效、缓存局部性下降。
- **同进程线程切换**：通常只需换线程自己的栈、寄存器、PC 等执行现场，不换地址空间。
- **与用户态/内核态切换的区别**：系统调用、Page Fault、硬件中断都会进入内核，但只要内核处理后仍返回原线程，就没有发生线程上下文切换。

### 5.10 进程的调度算法

调度器需要在**吞吐量、周转时间、响应时间、公平性**和切换开销之间权衡。

**非抢占式调度**：

1. **先到先服务（FCFS）**：按到达顺序运行。长任务排在前面会出现**护航效应**。
2. **短作业优先（SJF）**：优先运行预计时间短的任务，降低平均等待；但难预测长度，长任务可能饥饿。

**抢占式调度**：

- **时间片轮转（RR）**：轮流运行一个时间片。太短放大切换开销，太长接近 FCFS。
- **优先级调度（Priority）**：优先高优先级任务，需处理低优先级饥饿。

**多级反馈队列（MLFQ）**：设置多个优先级队列，按运行行为调整。新任务先进高优先级队列；经常用完时间片的 CPU 密集型任务逐步降级，经常主动等 I/O 的交互任务保留较高优先级。

> **真实 Linux 实现**：普通任务长期由 **CFS** 按权重和 `vruntime` 分配 CPU；Linux 6.6 开始在 fair 调度类引入 **EEVDF**，用 lag 和虚拟截止时间改进任务选择。

### 5.11 谁负责调度 / load average 与 CPU 使用率

- **调度器（Scheduler）**：内核中负责"选择下一个任务"的组件。触发调度的情况包括：当前任务阻塞、主动让出 CPU、时间片/额度耗尽、优先级变化、更合适任务被唤醒。
- **分派程序（Dispatcher）**：负责把调度决定落到 CPU——保存当前进程上下文到 PCB，加载下一进程上下文，移交控制权。现代 Linux 不严格拆成两个组件，理解两项职责即可。

**load average vs CPU 使用率**：

- **load average**：反映一段时间内**可运行任务（R）和不可中断睡眠任务（D）**的数量。load 高可能是 CPU 争抢，也可能是等待块设备/网络存储/Swap（此时 CPU 可能仍空闲）。
- **CPU 使用率**：描述 CPU 时间花在用户态、内核态、I/O wait、中断、空闲或 steal 等位置。
- **判断 load 要结合逻辑 CPU 数**：load 8 对 1 核和 64 核压力完全不同。
- **排查工具**：`uptime`、`top`、`vmstat 1`、`pidstat`、`mpstat`。

## 六、死锁

### 6.1 什么是死锁

死锁描述的是：**一组进程/线程互相等待对方释放资源或完成动作，等待关系形成闭环**，导致所有参与者都无法自行继续执行。

- 普通阻塞可能等锁释放、I/O 返回后继续；死锁的等待链绕成了环，**无外力介入不会自然解开**。
- **经典例子"交叉持锁"**：线程 1 先拿锁 A 再尝试拿锁 B；线程 2 先拿锁 B 再尝试拿锁 A，形成等待环。

### 6.2 产生死锁的四个必要条件

死锁必须**同时满足**以下四条件：

1. **互斥**：资源一次只有一个进程使用。
2. **占有并等待**：进程至少占有一个资源，并等待另一被其他进程占有的资源。
3. **非抢占**：资源不能被抢占，只能等持有者完成任务后释放。
4. **循环等待**：存在等待进程集合 `{P0, P1, ..., Pn}`，`P0` 等 `P1` 占有的资源，`P1` 等 `P2` 的，…，`Pn` 等 `P0` 的。

> **结论**：只满足其中一两个不一定会死锁；只要能稳定**破坏其中任意一个**，就可以从结构上预防死锁。

### 6.3 模拟死锁代码（Java 交叉持锁）

```java
public class DeadLockDemo {
    private static final Object resource1 = new Object();
    private static final Object resource2 = new Object();

    public static void main(String[] args) {
        new Thread(() -> {
            synchronized (resource1) {
                System.out.println(Thread.currentThread() + "get resource1");
                try { Thread.sleep(1000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                System.out.println(Thread.currentThread() + "waiting get resource2");
                synchronized (resource2) {
                    System.out.println(Thread.currentThread() + "get resource2");
                }
            }
        }, "线程 1").start();

        new Thread(() -> {
            synchronized (resource2) {
                System.out.println(Thread.currentThread() + "get resource2");
                try { Thread.sleep(1000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                System.out.println(Thread.currentThread() + "waiting get resource1");
                synchronized (resource1) {
                    System.out.println(Thread.currentThread() + "get resource1");
                }
            }
        }, "线程 2").start();
    }
}
```

**Output**：

```text
Thread[线程 1,5,main]get resource1
Thread[线程 2,5,main]get resource2
Thread[线程 1,5,main]waiting get resource2
Thread[线程 2,5,main]waiting get resource1
```

> `Thread.sleep(1000)` 不是死锁原因，只是拉大交错窗口，让死锁更容易复现。

### 6.4 解决死锁的方法

四类思路：**预防、避免、检测、解除/恢复**。

- **预防**：提前破坏四个必要条件之一。工程中最常见是**固定加锁顺序、缩小锁范围、避免持锁做慢操作**。
- **避免**：分配资源前判断系统是否仍处于安全状态，典型代表**银行家算法**。偏教材，普通业务系统很少直接实现。
- **检测**：允许等待发生，再检查等待图/资源分配图是否有环。Java 可用 `jcmd <pid> Thread.print -l`、`jstack -l <pid>` 或 `ThreadMXBean.findDeadlockedThreads()`；数据库也会检测事务等待环。
- **解除/恢复**：发现死锁后打破等待环，如终止进程、回滚事务、抢占资源或应用层重试。数据库事务天然支持回滚，更适合检测+恢复。
