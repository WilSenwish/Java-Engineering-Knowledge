# Redis 常见面试题总结（上）

> 覆盖 Redis 基础、应用、数据类型、持久化、线程模型、内存管理六大部分。

## Redis 基础

### 什么是 Redis？

Redis（REmote DIctionary Server）是一个基于 C 语言开发的开源 NoSQL 数据库（BSD 许可）。与传统数据库不同的是，Redis 的数据保存在内存中（内存数据库，支持持久化），因此读写速度非常快，被广泛应用于分布式缓存。Redis 存储的是 KV 键值对数据。

为了满足不同业务场景，Redis 内置了多种数据类型（String、Hash、Sorted Set、Bitmap、HyperLogLog、GEO），还支持事务、持久化、Lua 脚本、发布订阅模型、多种开箱即用的集群方案（Redis Sentinel、Redis Cluster）。

### ⭐️ Redis 为什么很快？

1. **纯内存操作**：数据读写都发生在内存中，访问速度纳秒级，传统数据库磁盘访问毫秒级，相差数个数量级；
2. **高效的 I/O 模型**：单线程事件循环配合 I/O 多路复用，单个线程同时处理多个网络连接上的 I/O 事件，避免多线程的上下文切换和锁竞争；
3. **优化的内部数据结构**：多种数据类型内部采用高度优化的编码（ziplist、quicklist、skiplist、hashtable 等），根据数据大小和类型动态选择最合适的编码；
4. **简洁高效的通信协议**：RESP 协议实现简单、解析性能好、二进制安全，序列化/反序列化开销小。

为什么不直接用 Redis 当主数据库？内存成本太高，且持久化仍有数据丢失风险。

### 除了 Redis，你还知道其他分布式缓存方案吗？

- **Memcached**：分布式缓存最开始兴起时常用，现在基本没有项目使用。
- **Tendis**（腾讯开源）：基于 RocksDB，100% 兼容 Redis 协议和 Redis4.0 数据模型。但开源版几乎已无人维护，不建议使用。
- **Dragonfly**：针对现代应用负荷构建的内存数据库，完全兼容 Redis 和 Memcached API，迁移无需改代码。
- **KeyDB**（Snapchat）：Redis 的高性能分支，专注多线程、内存效率和高吞吐量。

**分布式缓存首选 Redis**——经过多年考验，生态优秀，资料全面。

### 说一下 Redis 和 Memcached 的区别和共同点

**共同点**：都是基于内存的数据库，一般都用来当缓存；都有过期策略；性能都非常高。

**区别**：

1. **数据类型**：Redis 支持更丰富的数据类型（list、set、zset、hash 等）；Memcached 只支持最简单的 k/v；
2. **数据持久化**：Redis 支持持久化（重启可加载）；Memcached 全部存在内存中，没有灾难恢复机制；
3. **集群模式**：Memcached 没有原生集群模式，靠客户端分片；Redis 自 3.0 起原生支持集群；
4. **线程模型**：Memcached 是多线程非阻塞 IO 复用；Redis 使用单线程多路 IO 复用（6.0 后网络读写引入多线程）；
5. **特性支持**：Redis 支持发布订阅、Lua 脚本、事务，Memcached 不支持；
6. **过期数据删除**：Memcached 只用惰性删除；Redis 同时使用惰性删除与定期删除。

### ⭐️ 为什么要用 Redis？

1. **访问速度更快**：传统数据库数据在磁盘，Redis 基于内存，内存访问速度比磁盘快很多，高频数据放 Redis 中可提升几十倍甚至上百倍；
2. **高并发**：MySQL QPS 大概 4k 左右（4 核 8g），使用 Redis 缓存后很容易达到 5w+，甚至 10w+（单机 Redis）；
3. **功能全面**：缓存之外还可用于分布式锁、限流、消息队列、延时队列等。

### ⭐️ 为什么用 Redis 而不用本地缓存呢？

| 特性 | 本地缓存 | Redis |
|------|----------|-------|
| 数据一致性 | 多服务器部署时存在不一致问题 | 数据一致 |
| 内存限制 | 受限于单台服务器内存 | 独立部署，内存空间更大 |
| 数据丢失风险 | 服务器宕机数据丢失 | 可持久化，不易丢失 |
| 管理维护 | 分散，管理不便 | 集中管理，工具丰富 |
| 功能丰富性 | 通常只提供简单键值对 | 多种数据结构和功能 |

### 什么是 Redis Module？有什么用？

Redis 从 4.0 开始支持通过 Module 扩展功能，以动态链接库（so 文件）形式加载。官方推荐的 Module：RediSearch（搜索引擎）、RedisJSON（JSON 数据）、RedisGraph（图形数据库）、RedisTimeSeries（时间序列）、RedisBloom（布隆过滤器）、RedisAI（深度学习/机器学习）、RedisCell（分布式限流）。

## ⭐️ Redis 应用

### Redis 除了做缓存，还能做什么？

- **分布式锁**：通常基于 Redisson 实现；
- **限流**：Redis + Lua 脚本，或 Redisson 的 `RRateLimiter`（Lua + 令牌桶）；
- **消息队列**：List 可作简单队列；Redis 5.0 的 Stream 更适合（类似 Kafka，有主题和消费组概念，支持持久化和 ACK）；
- **延时队列**：Redisson 内置（基于 Sorted Set）；
- **分布式 Session**：String/Hash 保存 Session，所有服务器可访问；
- **复杂业务场景**：Bitmap 统计活跃用户、Sorted Set 维护排行榜、HyperLogLog 统计 UV/PV。

### Redis 可以做消息队列么？怎么实现？

**结论**：业务简单、量小、追求极致性能且能容忍极小概率数据丢失，用 Redis Stream 最优（省去部署维护 MQ 成本）；金融级业务、海量数据、严格不丢消息，必须选 Kafka、RabbitMQ 等成熟 MQ。

### 如何基于 Redis 实现延时任务？

两种方案：

1. **Redis 过期事件监听**：时效性差、丢消息、多服务实例下重复消费，**不被推荐**；
2. **Redisson 内置延时队列**：消息持久化（Redis 宕机也只丢一点，可配数据库扫描补偿）；每个客户端从同一目标队列获取任务，不存在重复消费。

## ⭐️ Redis 数据类型

### Redis 常用的数据类型有哪些？

- **5 种基础类型**：String、List、Set、Hash、Zset；
- **3 种特殊类型**：HyperLogLog（基数统计）、Bitmap（位图）、Geospatial（地理位置）；
- 其他：Bloom filter（布隆过滤器）、Bitfield（位域）。

### String 的应用场景有哪些？

二进制安全，可存储任何类型数据（字符串、整数、浮点数、图片 base64、序列化对象）。常见场景：常规数据缓存（Session、Token、序列化对象、图片路径）；计数（用户请求数限流、页面访问数）；分布式锁（`SETNX key value`）。

### String 还是 Hash 存储对象数据更好呢？

- **对象存储方式**：String 存序列化后的整个对象，操作简单；Hash 对每个字段单独存储，可获取/修改部分字段，节省网络流量。字段经常变动或需单独查询个别字段时 Hash 非常适合。
- **内存消耗**：Hash 通常更省内存（字段多且短时），小型 Hash 用 ziplist 优化。
- **复杂对象**：String 处理多层嵌套更方便。
- **性能**：String 操作 O(1) 整体读写好；Hash 字段多且常变动时有额外开销。

**总结**：绝大多数情况 String 更适合；需要频繁操作部分字段或节省内存时 Hash 更好。

### String 的底层实现是什么？

Redis 的 String 底层不是 C 字符串（`\0` 结尾），而是自己编写的 **SDS（Simple Dynamic String，简单动态字符串）**。

Redis 7.0 SDS 有五种实现：sdshdr5（未用到）、sdshdr8、sdshdr16、sdshdr32、sdshdr64，Redis 根据初始化长度决定使用哪种类型，减少内存使用：

| 类型 | 长度位 |
|------|--------|
| sdshdr5 | < 1，< 8 |
| sdshdr8 | 1，8 |
| sdshdr16 | 2，16 |
| sdshdr32 | 4，32 |
| sdshdr64 | 8，64 |

后四种都包含 4 个属性：`len`（已使用字节数）、`alloc`（可用字符空间）、`buf[]`（实际存储数组）、`flags`（低三位类型标志）。

**SDS 相比 C 字符串的提升**：

1. **避免缓冲区溢出**：修改时先检查 len 是否满足空间，不满足先扩展；
2. **获取长度复杂度低**：直接读 len 属性 O(1)，C 字符串需遍历 O(n)；
3. **减少内存分配次数**：空间预分配 + 惰性空间释放；
4. **二进制安全**：用 len 判断结束，可保存含 `\0` 的二进制数据。

### 购物车信息用 String 还是 Hash 存储更好呢?

**建议 Hash**（商品频繁修改变动）：

- 用户 id 为 key，商品 id 为 field，商品数量为 value；
- 添加商品 = 往 Hash 增加 field 与 value；查询 = 遍历 Hash；改数量 = 修改 value；删商品 = 删除 field；清空 = 删除 key。

### 使用 Redis 实现一个排行榜怎么做？

Sorted Set 常用于排行榜（直播间礼物榜、微信步数榜、段位榜、话题热度榜）。相关命令：`ZRANGE`（从小到大）、`ZREVRANGE`（从大到小）、`ZREVRANK`（指定元素排名）。

### Redis 的有序集合底层为什么要用跳表，而不用平衡树、红黑树或者 B+ 树？

- **平衡树 vs 跳表**：插入删除查询都是 O(log n)，范围查询平衡树也可中序遍历达到效果。但平衡树每次插入删除都要保证绝对平衡，不平衡就要旋转，过程耗时。**跳表使用概率平衡而非严格强制平衡，插入删除算法比平衡树简单得多、快得多。**
- **红黑树 vs 跳表**：跳表实现更简单，不需要旋转和染色保证黑平衡；按区间查找数据跳表效率更高。
- **B+ 树 vs 跳表**：B+ 树核心思想是通过最少 IO 定位尽可能多的索引，适合磁盘数据库。Redis 是内存数据库，不可能存储大量数据，不需要 B+ 树维护索引，按概率随机维护即可，节约内存，实现更简单。

### Set 的应用场景是什么？

无序集合，元素唯一，类似 Java HashSet：

- 数据不能重复的场景：网站 UV 统计（数据量巨大用 HyperLogLog 更合适）、文章点赞、动态点赞；
- 交集并集差集场景：共同好友/粉丝/关注（交集）、好友推荐（差集）、音乐推荐（差集）、订阅号推荐（差集+交集）；
- 随机获取元素：抽奖系统、随机点名。

### 使用 Set 实现抽奖系统怎么做？

- `SADD key member1 member2 ...`：添加元素；
- `SPOP key count`：随机移除并获取（不允许重复中奖）；
- `SRANDMEMBER key count`：随机获取不移除（允许重复中奖）。

### 使用 Bitmap 统计活跃用户怎么做？

Bitmap 存储连续二进制数字（0/1），一个 bit 表示一个元素的值，8 个 bit 组成一个 byte，极大节省空间。可看作存储二进制数字的数组，每个元素下标叫 offset。

用日期（精确到天）作为 key，用户 ID 为 offset，当日活跃设为 1：

```bash
SETBIT 20210308 1 1
SETBIT 20210308 2 1
SETBIT 20210309 1 1

# 统计 20210308~20210309 总活跃用户数（交集）
BITOP and desk1 20210308 20210309
BITCOUNT desk1

# 统计 20210308~20210309 在线活跃用户数（并集）
BITOP or desk2 20210308 20210309
BITCOUNT desk2
```

### HyperLogLog 适合什么场景？

HLL 是概率性数据结构，用极小内存估算集合中不重复元素数量（基数）。核心权衡：**用一点精确度损失换巨大内存节省**，Redis 中默认标准误差 0.81%。

适合场景：① 数据量巨大、内存敏感（亿级日活 App 的 UV 统计，用 Set 需几 GB，HLL 只需固定 12KB）；② 对精确度要求不是 100%（产品看数量级和趋势）。

具体应用：网站/App UV 统计、搜索引擎关键词搜索人数统计、社交网络互动统计（微博被多少不同用户转发）。Redis 内部会在稀疏矩阵（更小空间）和稠密矩阵（固定 12KB）之间自动切换。

命令：`PFADD key element...`、`PFCOUNT key1 key2`。

### 如果我想判断一个元素是否不在海量元素集合中，用什么数据类型？

**布隆过滤器**。告诉你一个元素一定不存在或可能存在：有极高的空间效率和一定误判率，但绝不会漏报。说存在，小概率误判；说不存在，一定不在。

原理：字符串加入时由多个哈希函数生成不同哈希值，将位数组对应下标置 1；判断时再次哈希计算，位数组中每个元素都为 1 则存在（可能误判），有一个不为 1 则一定不在。

## ⭐️ Redis 线程模型

### Redis 单线程模型了解吗？

**Redis 基于 Reactor 模式设计开发了一套高效的事件处理模型**（Netty 线程模型也基于 Reactor），对应 Redis 中的**文件事件处理器（file event handler）**。由于文件事件处理器单线程方式运行，所以一般说 Redis 是单线程模型。

文件事件处理器使用 I/O 多路复用程序同时监听多个套接字，并根据套接字执行的任务关联不同的事件处理器。当被监听的套接字准备好执行连接应答（accept）、读取（read）、写入（write）、关闭（close）等操作时，对应文件事件产生，调用之前关联好的事件处理器处理。

**单线程怎么监听大量客户端连接？** 通过 IO 多路复用程序监听多个 socket，将感兴趣的事件及类型注册到内核并监听每个事件是否发生。好处：不需要额外创建多余线程监听客户端的大量连接，降低资源消耗（类似 NIO 的 Selector）。

文件事件处理器 4 个部分：多个 socket（客户端连接）、IO 多路复用程序、文件事件分派器（将 socket 关联到事件处理器）、事件处理器（连接应答/命令请求/命令回复处理器）。

### Redis6.0 之前为什么不使用多线程？

Redis 4.0 后已加入多线程支持，但主要针对大键值对删除操作（异步处理）：`UNLINK`（DEL 异步版）、`FLUSHALL ASYNC`、`FLUSHDB ASYNC`。

**6.0 之前不使用多线程的原因**：① 单线程编程容易且更容易维护；② Redis 性能瓶颈不在 CPU，主要在内存和网络；③ 多线程存在死锁、线程上下文切换等问题，甚至影响性能。

### Redis6.0 之后为何引入了多线程？

**为了提高网络 IO 读写性能**（Redis 的瓶颈主要受限于内存和网络）。多线程只在网络数据读写这类耗时操作上使用，**执行命令仍然是单线程顺序执行，不需要担心线程安全问题。**

默认禁用，只使用主线程。修改 redis.conf：

```bash
io-threads 4        # 4 核建议 2 或 3 个线程，8 核建议 6 个
io-threads-do-reads yes  # 开启多线程 IO 读取（官网描述提升不大，一般不建议）
```

注意：io-threads 个数一旦设置不能动态修改；设置 ssl 后 io-threads 不工作。

### Redis 后台线程了解吗？

虽然主逻辑单线程，但还有一些后台线程执行耗时操作：

- `bio_close_file`：释放 AOF/RDB 过程中产生的临时文件资源；
- `bio_aof_fsync`：调用 fsync 将系统内核缓冲区还未同步到磁盘的数据强制刷到磁盘（AOF 文件）；
- `bio_lazy_free`：释放大对象（已删除）占用的内存空间。

## ⭐️ Redis 内存管理

### Redis 给缓存数据设置过期时间有什么用？

内存有限，不设置过期时间会一直增长最终 OOM。设置合理过期时间，Redis 自动删除暂时不需要的数据。另外业务场景本身就需要数据只在某时间段存在（短信验证码 1 分钟、Token 1 天）。

```bash
expire key 60    # 数据 60s 后过期
setex key 60 value  # 设置值并 60s 后过期
ttl key          # 查看还有多久过期
persist key      # 移除过期时间
```

注意：除字符串有独有 `setex` 外，其他类型都依靠 `expire` 命令设置过期时间。

### Redis 是如何判断数据是否过期的呢？

通过**过期字典**（可看作 hash 表）保存数据过期时间。过期字典的键指向 Redis 数据库中的某个 key，值是 long long 类型整数（毫秒精度 UNIX 时间戳）。存储在 redisDb 结构中：`dict *expires` 保存键的过期时间。查询 key 时先检查是否在过期字典中（O(1)），在的话判断是否过期，过期直接删除返回 null。

### Redis 过期 key 删除策略了解么？

常用策略：**惰性删除**（取出 key 时才检查，CPU 最友好但可能太多过期 key 没删）、**定期删除**（周期性随机抽查一批，内存友好 CPU 不友好）、**延迟队列**（保证每个过期 key 都被删除但维护麻烦）、**定时删除**（立即删除，CPU 压力最大）。

**Redis 采用定期删除+惰性删除结合的策略。** 定期删除是随机的（周期性地随机从设置了过期时间的 key 中抽查），不保证所有过期键立即删除。Redis 7.2 版本：执行时间阈值 25ms，过期 key 比例设定值 10%；每次随机抽查 20 个 key（ACTIVE_EXPIRE_CYCLE_KEYS_PER_LOOP）。

定期删除频率由 **hz** 参数控制，默认 10（每秒执行 10 次），范围 1~500，官方建议不超过 100。**dynamic-hz** 默认开启，会动态计算 hz 值。

**为什么定期删除不是把所有过期 key 都删除？** key 数量庞大时挨个遍历检查非常耗时，严重影响性能。策略目的是平衡内存和性能。

### 大量 key 集中过期怎么办？

可能导致：请求延迟增加（CPU 占用升高影响其他请求）、内存占用过高（过期 key 未及时清理甚至溢出）。

解决方案：

1. **尽量避免 key 集中过期**：设置过期时间时尽量随机一点；
2. **开启 lazy free 机制**：`lazyfree-lazy-expire yes`，后台异步删除过期 key，不阻塞主线程。

### Redis 内存淘汰策略了解么？

内存淘汰策略只有在运行内存达到 `maxmemory` 配置的最大内存阈值时才触发。64 位操作系统下 `maxmemory` 默认为 0（不限制），32 位默认 3GB。

6 种基础策略：

1. **volatile-lru**：从设置了过期时间的数据集中挑选最近最少使用的淘汰；
2. **volatile-ttl**：从设置了过期时间的数据集中挑选将要过期的淘汰；
3. **volatile-random**：从设置了过期时间的数据集中任意选择淘汰；
4. **allkeys-lru**：从数据集中移除最近最少使用的淘汰；
5. **allkeys-random**：从数据集中任意选择淘汰；
6. **no-eviction**（默认）：禁止驱逐数据，内存不足时新写入报错。

4.0 后增加两种：

7. **volatile-lfu**：从设置了过期时间的数据集中挑选最不经常使用的淘汰；
8. **allkeys-lfu**：从数据集中移除最不经常使用的淘汰。

`allkeys-xxx` 从所有键值中淘汰，`volatile-xxx` 从设置了过期时间的键值中淘汰。通过 `config set maxmemory-policy` 立即生效（重启失效），修改 redis.conf 重启后生效。
