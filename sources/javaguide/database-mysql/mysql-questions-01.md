# MySQL 常见面试题总结

> 覆盖 MySQL 基础、字段类型、基础架构、存储引擎、索引、查询缓存、事务、锁、性能优化九大部分。

## MySQL 基础

### 什么是关系型数据库？

关系型数据库（RDB，Relational Database）建立在关系模型基础上。关系模型表明了数据库中所存储的数据之间的联系（一对一、一对多、多对多）。数据被存放在各种表中，表中每一行存放着一条数据。大部分关系型数据库使用 SQL 操作数据，并支持事务的四大特性（ACID）。

常见的关系型数据库：MySQL、PostgreSQL、Oracle、SQL Server、SQLite（微信本地聊天记录存储用的就是 SQLite）。

### 什么是 SQL？

SQL 是结构化查询语言（Structured Query Language），专门用来与数据库打交道。几乎所有主流关系数据库都支持 SQL，一些非关系型数据库也兼容 SQL 或类似查询语言。可做：新建数据库/表/字段、增删改查、视图/函数/存储过程、简单数据分析、搭配 Hive/Spark SQL 做大数据、搭配 SQLFlow 做机器学习等。

### 什么是 MySQL？

MySQL 是一种关系型数据库，主要用于持久化存储系统中的数据（如用户信息）。开源免费、成熟，被大量使用。GPL 许可下可下载并按需修改。**默认端口号 3306。**

### ⭐️ MySQL 有什么优点？

**1. 生态和成本角度：**
- 开源免费：广泛普及的基石，降低技术门槛和初期成本。
- 社区庞大、生态完善：遇到问题几乎都能找到解决方案；主流编程语言、框架、ORM、监控系统都有完美支持。

**2. 核心技术功能：**
- 强大的事务支持：InnoDB 默认的 REPEATABLE-READ 隔离级别通过 MVCC 和 Next-Key Lock 机制，很大程度上避免了幻读，兼顾性能和一致性。
- 优秀的性能和可扩展性：经过海量互联网业务考验，围绕水平扩展形成成熟方案（主从复制、读写分离、分库分表）。

**3. 运维和使用：**
- 开箱即用、上手简单：安装配置日常使用简单直观，学习曲线平缓。
- 维护成本低：运维人才和解决方案相对容易找。

### 数据库表设计规范要点（字段类型）

MySQL 字段类型分三类：数值类型（整型 TINYINT/SMALLINT/MEDIUMINT/INT/BIGINT、浮点 FLOAT/DOUBLE、定点 DECIMAL、位字段 BIT）、字符串类型（CHAR、VARCHAR、TINYTEXT/TEXT/MEDIUMTEXT/LONGTEXT、BINARY、BLOB 系列，最常用 CHAR 和 VARCHAR）、日期时间类型（YEAR、TIME、DATE、DATETIME、TIMESTAMP）。

### ⭐️ 整数类型的 UNSIGNED 属性有什么用？

表示不允许负值的无符号整数，可以将正整数的上限提高一倍（不需要存储负数值）。例如 TINYINT UNSIGNED 范围 0~255（普通 TINYINT 是 -128~127）。**对于从 0 开始递增的 ID 列非常适合。**

### CHAR 和 VARCHAR 的区别是什么？

- **CHAR 是定长字符串，VARCHAR 是变长字符串。**
- CHAR 存储时右边填充空格以达到指定长度，检索时去掉空格；VARCHAR 存储时需要用 1 或 2 个额外字节记录字符串长度，检索时不需要处理。
- CHAR 适合长度较短或长度都差不多的字符串（Bcrypt/MD5 加密后的密码、身份证号）；VARCHAR 适合长度不确定或差异较大的字符串（用户昵称、文章标题）。
- CHAR(M) 和 VARCHAR(M) 的 M 都代表能保存的字符数最大值，无论字母、数字还是中文，每个都只占用一个字符。

### VARCHAR(100)和 VARCHAR(10)的区别是什么？

二者存储相同的字符串，占用磁盘的存储空间其实是一样的（容易误解的一点）。但 **VARCHAR(100) 会消耗更多的内存**——VARCHAR 在内存中操作时通常分配固定大小的内存块（按定义的长度），例如排序时 VARCHAR(100) 按 100 这个长度进行，消耗更多内存。VARCHAR(100) 有更好的业务拓展性。

### DECIMAL 和 FLOAT/DOUBLE 的区别是什么？

DECIMAL 是定点数，FLOAT/DOUBLE 是浮点数。**DECIMAL 可以存储精确的小数值，FLOAT/DOUBLE 只能存储近似的小数值。** DECIMAL 用于存储有精度要求的小数（如货币数据）。Java 中 DECIMAL 对应 `java.math.BigDecimal`。

### 为什么不推荐使用 TEXT 和 BLOB？

| 类型 | 可存储大小 | 用途 |
|------|-----------|------|
| TINYTEXT | 0-255 字节 | 一般文本字符串 |
| TEXT | 0-65,535 字节 | 长文本字符串 |
| MEDIUMTEXT | 0-16,772,150 字节 | 较大文本数据 |
| LONGTEXT | 0-4,294,967,295 字节 | 极大文本数据 |
| TINYBLOB | 0-255 字节 | 短文本二进制字符串 |
| BLOB | 0-65KB | 二进制字符串 |
| MEDIUMBLOB | 0-16MB | 二进制形式的长文本数据 |
| LONGBLOB | 0-4GB | 二进制形式的极大文本数据 |

数据库规范通常不推荐 BLOB 和 TEXT：不能有默认值；使用临时表时只能用磁盘临时表；检索效率低；不能直接创建索引（需指定前缀长度）；可能消耗大量网络和 IO 带宽；可能导致表上 DML 操作变慢。如果预期长度可以用 VARCHAR 满足，建议避免 TEXT。

### ⭐️ DATETIME 和 TIMESTAMP 的区别是什么？如何选择？

- DATETIME 没有时区信息；TIMESTAMP 和时区有关。
- TIMESTAMP 只用 4 字节，DATETIME 用 8 字节；但 TIMESTAMP 时间范围更小：
  - DATETIME：'1000-01-01 00:00:00' 到 '9999-12-31 23:59:59'
  - TIMESTAMP：'1970-01-01 00:00:01' UTC 到 '2038-01-19 03:14:07' UTC
- TIMESTAMP 核心优势是内建时区处理（UTC 存储 + 会话时区自动转换），适合多时区应用（注意 2038 问题）。
- 不涉及时区转换、需要表示 2038 年后的时间时，DATETIME 更稳妥。

### NULL 和 '' 的区别是什么？

- **NULL 代表缺失或未知的数据，'' 表示一个已知存在的空字符串。**
- NULL 不等于任何值（包括自身）：`SELECT NULL = NULL` 结果是 NULL。判断必须用 `IS NULL`/`IS NOT NULL`。
- 比较运算：任何值与 NULL 比较结果都是 NULL；'' 可以正常比较（`'' = ''` 为 true）。
- 聚合函数：SUM/AVG/MIN/MAX 忽略 NULL；`COUNT(*)` 统计所有行（含 NULL），`COUNT(列名)` 只统计非 NULL 行；'' 会被计算在内（SUM 视为 0）。

### ⭐️ Boolean 类型如何表示？

MySQL 中没有专门的布尔类型，BOOL/BOOLEAN 是 TINYINT(1) 的同义词，通常 0 表示 false、非 0 表示 true。BIT(1) 也可以存 0/1，但不是 BOOL/BOOLEAN 的实际映射。

### ⭐️ 手机号存储用 INT 还是 VARCHAR？

**强烈推荐 VARCHAR。** 原因：

1. **格式兼容性与完整性**：手机号可能含前导零、国家代码前缀（'+'）、分隔符；INT/BIGINT 会丢失这些信息。
2. **非算术性**：手机号本质是标识符，不做数学运算。
3. **查询灵活性**：VARCHAR 配合 `LIKE '138%'` 前缀查询直观高效；数字类型需 CAST/SUBSTRING 或范围查询，难用索引。
4. **加密存储**：手机号属敏感信息必须加密，密文是字符串，INT/BIGINT 无法存储。

长度选择：不加密 VARCHAR(20)~VARCHAR(32)；加密按密文最大长度计算（如 VARCHAR(128/256)）。

## MySQL 基础架构

MySQL 主要由以下几部分构成：

- **连接器**：身份认证和权限相关（登录时）。
- **查询缓存**：执行查询语句时先查缓存（MySQL 8.0 版本后移除，功能不太实用）。
- **分析器**：先看 SQL 要干嘛，再检查语法是否正确。
- **优化器**：按照 MySQL 认为最优的方案去执行。
- **执行器**：执行语句，从存储引擎返回数据；执行前先判断权限。
- **插件式存储引擎**：负责数据存储和读取，支持 InnoDB、MyISAM、Memory 等。**InnoDB 是默认存储引擎，绝大部分场景使用 InnoDB 就是最好的选择。**

## MySQL 存储引擎

### MySQL 支持哪些存储引擎？默认使用哪个？

通过 `SHOW ENGINES` 查看所有存储引擎。当前默认存储引擎是 **InnoDB**，且只有 InnoDB 是事务性存储引擎。MySQL 5.5.5 之前 MyISAM 是默认引擎，之后 InnoDB 是默认引擎。

### MySQL 存储引擎架构了解吗？

**插件式架构**，支持多种存储引擎，可以为不同的表设置不同的存储引擎。**存储引擎是基于表的，而不是数据库。** InnoDB 刚开始也是一个第三方存储引擎，后被 Oracle 收购。

### ⭐️ MyISAM 和 InnoDB 有什么区别？

1. **是否支持行级锁**：MyISAM 只有表级锁，一锁锁整张表；InnoDB 支持行级锁和表级锁，默认为行级锁。并发写时 InnoDB 性能更好。
2. **是否支持事务**：MyISAM 不支持；InnoDB 提供事务支持，实现了四个隔离级别，具有提交和回滚能力。默认 REPEATABLE-READ 可解决幻读（基于 MVCC 和 Next-Key Lock）。
3. **是否支持外键**：MyISAM 不支持；InnoDB 支持。外键有助于数据一致性但有性能损耗，**阿里《Java 开发手册》明确规定禁止使用外键**，建议在业务代码中约束。
4. **崩溃后安全恢复**：MyISAM 不支持；InnoDB 支持，依赖 redo log。
5. **是否支持 MVCC**：MyISAM 不支持；InnoDB 支持。
6. **索引实现不一样**：两者都用 B+Tree，但 InnoDB 数据文件本身就是索引文件（聚簇索引），MyISAM 索引文件和数据文件分离。
7. **性能**：InnoDB 比 MyISAM 更强大，随 CPU 核数增加读写能力呈线性增长；MyISAM 读写不能并发，处理能力跟核数没关系。
8. **数据缓存**：InnoDB 用缓冲池（Buffer Pool）缓存数据页和索引页；MyISAM 用键缓存（Key Cache）仅缓存索引页。

### MyISAM 和 InnoDB 如何选择？

大多数时候使用 InnoDB。某些读密集场景 MyISAM 也合适，前提是不介意不支持事务、崩溃恢复。《MySQL 高性能》：不要轻易相信"MyISAM 比 InnoDB 快"，很多时候 InnoDB 速度可以让 MyISAM 望尘莫及，尤其是用到聚簇索引或数据可放入内存的应用。**日常业务系统老老实实使用默认的 InnoDB。**

## ⭐️ MySQL 索引

### 索引是什么？

**索引是一种用于快速查询和检索数据的数据结构，其本质可以看成是一种排序好的数据结构。** 索引的作用相当于书的目录。底层结构常见有 B 树、B+ 树、Hash、红黑树，MySQL 中 InnoDB 和 MyISAM 都使用 B+ 树。

**优点**：① 查询速度起飞（减少扫描数据量，减少磁盘 I/O）；② 保证数据唯一性（唯一索引）；③ 加速排序和分组（利用索引已排序特性避免额外排序）。

**缺点**：① 创建和维护耗时（大表创建慢，DML 操作需同步维护索引）；② 占用存储空间；③ 可能被误用或失效（设计不当或 SQL 写得不好时优化器不走索引）。

**用了索引一定能提高查询性能吗？不一定。** 例外：数据量太小（全表扫描可能更快）；查询结果集占比过大（超过 20%-30%，回表随机 I/O 成本高于顺序全表扫描）；索引维护不当或统计信息过时导致优化器误判。

### 索引为什么快？

核心原因是**大大减少了磁盘 I/O 的次数**：① B+树"矮胖"，千万数据的表索引树高度可能只有 3-4 层，最多 3-4 次磁盘 I/O 即可定位；② B+树叶子节点用链表连起来，找到开头后可顺序读下去，对磁盘友好，还能触发预读。

### MySQL 索引底层数据结构是什么？

MyISAM 和 InnoDB 都使用 B+Tree。

### 为什么 InnoDB 没有使用哈希作为索引的数据结构？

> 注意区分存储引擎：MEMORY 引擎就同时支持哈希和 B 树。

哈希索引底层是哈希表，精确等值查询理论 O(1)，但有致命缺点：

1. **不支持范围查询**：哈希函数把相邻输入值映射到不相邻位置，`WHERE age > 30` 或 `BETWEEN` 只能退化为全表扫描；
2. **不支持排序**：哈希值无序，无法优化 ORDER BY；
3. **不支持部分索引键查询**：联合索引必须使用所有索引列；
4. **哈希冲突问题**：需要额外链表或开放寻址，降低性能。

### 为什么 InnoDB 没有使用 B 树作为索引的数据结构？

B+树是 B 树的增强版，针对数据库场景做了关键优化：

1. **I/O 效率更高**：B+树只有叶子节点存数据，非叶子节点只存索引键，可容纳更多键，"扇出"更大，树更矮，磁盘 I/O 次数更少；
2. **查询性能更稳定**：B+树任何查询都必须从根走到叶子，路径长度固定；B 树可能在非叶子节点就找到（运气好）也可能走到叶子（运气不好）；
3. **对范围查询极其友好**：叶子节点间通过链表连接，范围查询只需找到起点后沿链表顺序扫描，无需回溯上层节点。

### 什么是覆盖索引？

**覆盖索引（Covering Index）**：一个索引包含（覆盖）所有需要查询的字段的值。InnoDB 非主键索引的叶子节点包含主键的值，用非主键索引查询时需要先找主键值再回表。**如果查询字段正好是索引字段，直接根据该索引即可查到数据，无需回表。**

### 请解释一下 MySQL 的联合索引及其最左前缀原则

联合索引（组合索引）使用表中多个字段创建：

```sql
ALTER TABLE `cus_order` ADD INDEX id_score_name(score, name);
```

**最左前缀匹配原则**：MySQL 根据索引中的字段顺序从左到右依次匹配查询条件。如果查询条件与索引最左侧字段匹配，MySQL 就会使用索引过滤数据。会一直向右匹配直到遇到范围查询（>、<）为止；对于 >=、<=、BETWEEN 以及前缀匹配 LIKE 的范围查询，不会停止匹配。

创建 1 个联合索引 `(column1, column2, column3)` 相当于创建了 3 个索引：`(column1)`、`(column1, column2)`、`(column1, column2, column3)`。

**可以将区分度高的字段放在最左边，过滤更多数据。**

常见面试题：联合索引 `(a, b, c)`：

1. `a=1 AND c=1`：仅在 `a=1` 上使用索引，然后对结果过滤 `c=1`。
2. `c=1`：不含最左列 a，整个索引无法使用。
3. `b=1 AND c=1`：整个索引都不会使用。
4. `b=1 AND a=1 AND c=1`：可以用到索引——优化器会对查询条件重排序为 `a=1 AND b=1 AND c=1`。

MySQL 8.0.13 引入索引跳跃扫描（Index Skip Scan），可在某些不满足最左前缀的场景避免全表扫描，但功能比较鸡肋（8.0.31 曾报 bug #109145），知道有即可。

### SELECT * 会导致索引失效吗？

不会直接导致索引失效（不走索引大概率是因为 where 查询范围过大），但可能带来其他性能问题：网络传输和数据处理浪费、无法使用索引覆盖。

### 哪些字段适合创建索引？

- 不为 NULL 的字段（NULL 字段数据库较难优化，避免不了时用 0/1/true/false 替代）；
- 被频繁查询的字段；
- 被作为 WHERE 条件查询的字段；
- 频繁需要排序的字段（利用索引已排序）；
- 被经常频繁用于连接的字段（外键列，不一定建外键）。

### 索引失效的原因有哪些？

1. 创建了组合索引，但查询条件未遵守最左匹配原则；
2. 在索引列上进行计算、函数、类型转换等操作；
3. 以 % 开头的 LIKE 查询（`LIKE '%abc'`）；
4. 查询条件中使用 OR，且 OR 前后条件中有一个列没有索引；
5. IN 的取值范围较大时（NOT IN 相同）；
6. 发生隐式转换。

## MySQL 查询缓存

执行查询语句时先查缓存，命中则直接返回。匹配条件非常严格：任何字符差异（查询语句本身、当前数据库、客户端协议版本号等）都会导致不命中。包含用户自定义函数、存储函数、用户变量、临时表、系统表的查询不被缓存。缓存建立后，涉及的表（数据或结构）发生变化，相关缓存全部失效。

MySQL 5.6 开始查询缓存默认禁用，**MySQL 8.0 开始不再支持查询缓存。**

## ⭐️ MySQL 日志

MySQL 三大日志（binlog、redo log、undo log）详见 [MySQL 三大日志详解](https://javaguide.cn/database/mysql/mysql-logs.html)：分别解决复制、崩溃恢复和事务回滚问题。

## ⭐️ MySQL 事务

### 什么是事务？

**事务是逻辑上的一组操作，要么都执行，要么都不执行。** 最经典的例子是转账：小明给小红转 1000 元涉及"小明余额减少 1000"和"小红余额增加 1000"两个操作，必须都成功或都失败。

### 什么是数据库事务？

数据库事务保证多个对数据库的操作（SQL 语句）构成一个逻辑上的整体，遵循**要么全部执行成功，要么全部不执行**。

```sql
START TRANSACTION;  -- 开启事务
-- 多条 SQL 语句
COMMIT;            -- 提交事务
```

关系型数据库事务都有 **ACID** 特性：

1. **原子性（Atomicity）**：事务是最小执行单位，不允许分割，要么全部完成，要么完全不起作用；
2. **一致性（Consistency）**：执行事务前后数据保持一致；
3. **隔离性（Isolation）**：并发访问时一个用户的事务不被其他事务干扰；
4. **持久性（Durability）**：事务提交后对数据的改变是持久的，即使数据库故障也不应影响。

🌈 **只有保证了事务的持久性、原子性、隔离性之后，一致性才能得到保障。A、I、D 是手段，C 是目的！** DDIA 作者：原子性、隔离性和持久性是数据库的属性，而一致性（ACID 意义上）是应用程序的属性。

### 并发事务带来了哪些问题?

#### 脏读（Dirty read）

一个事务读取数据并修改，这个修改对其他事务可见（即使当前事务未提交）。另一个事务读取了还未提交的数据，但第一个事务突然回滚，第二个事务读到的就是脏数据。

#### 丢失修改（Lost to modify）

一个事务读取一个数据时另一个事务也访问该数据，第一个事务修改后第二个事务也修改，第一个事务的修改结果丢失。

#### 不可重复读（Unrepeatable read）

一个事务内多次读同一数据，在这个事务还没结束时另一个事务也访问该数据并修改，导致第一个事务两次读取的数据不一样。

#### 幻读（Phantom read）

一个事务读取了几行数据，接着另一个并发事务插入了一些数据，随后的查询中第一个事务发现多了一些原本不存在的记录。

### 不可重复读和幻读有什么区别？

- **不可重复读**：同一事务内，同一条记录被其他事务修改或删除，导致再次读取时记录内容或存在性变化。
- **幻读**：同一事务内，同一个范围条件查询多次执行时，符合条件的记录集合发生变化（新增或消失）。

幻读是不可重复读的特殊情况，单独区分的原因是**解决方案不一样**：delete/update 可以直接对记录加锁；insert 时记录锁（Record Lock）只能锁住已存在的记录，需要间隙锁（Gap Lock），即 Next-Key Lock（Record Lock + Gap Lock）来避免幻读。

### 并发事务的控制方式有哪些？

**锁**和 **MVCC**。锁是悲观控制模式，MVCC（Multiversion concurrency control）是乐观控制模式。

**锁**：通过读写锁实现并发控制。

- **共享锁（S 锁）**：读锁，多个事务可同时获取（锁兼容）；
- **排他锁（X 锁）**：写锁/独占锁，不允许多个事务同时获取，与任何锁都不兼容。

读写锁可以读读并行，但无法写读、写写并行。按锁粒度分为表级锁和行级锁。InnoDB 支持表级锁和行级锁，默认为行级锁。

**MVCC**：对一份数据存储多个版本，通过事务可见性保证事务能看到应该看到的版本。MySQL 中实现依赖：**隐藏字段、read view、undo log**。

- undo log：记录某行数据的多个版本；
- read view 和隐藏字段：判断当前版本数据的可见性。

### SQL 标准定义了哪些事务隔离级别?

- **READ-UNCOMMITTED（读取未提交）**：允许读取尚未提交的数据变更，可能脏读、幻读、不可重复读。实际应用很少使用。
- **READ-COMMITTED（读取已提交）**：允许读取并发事务已提交的数据，阻止脏读，但幻读或不可重复读仍可能发生。Oracle、SQL Server 的默认级别。
- **REPEATABLE-READ（可重复读）**：对同一字段多次读取结果一致，阻止脏读和不可重复读，幻读仍可能发生。**MySQL InnoDB 默认隔离级别**，通过 MVCC 和 Next-Key Locks 在很大程度上解决了幻读。
- **SERIALIZABLE（可串行化）**：最高隔离级别，所有事务依次执行，完全防止脏读、不可重复读和幻读。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|------|-----------|------|
| READ UNCOMMITTED | √ | √ | √ |
| READ COMMITTED | × | √ | √ |
| REPEATABLE READ | × | × | √(标准)/≈×(InnoDB) |
| SERIALIZABLE | × | × | × |

### MySQL 的默认隔离级别是什么?

**REPEATABLE READ**。MySQL 8.0 之前用 `SELECT @@tx_isolation;`，8.0 及之后用 `SELECT @@transaction_isolation;`。

### MySQL 的隔离级别是基于锁实现的吗？

**基于锁和 MVCC 共同实现。** SERIALIZABLE 通过锁实现；READ-COMMITTED 和 REPEATABLE-READ 基于 MVCC。但 SERIALIZABLE 之外的隔离级别也可能用到锁，如 REPEATABLE-READ 在当前读情况下需要使用加锁读来保证不出现幻读。

## MySQL 锁

### 表级锁和行级锁了解吗？有什么区别？

- **表级锁**：MySQL 中锁定粒度最大的锁（全局锁除外），针对非索引字段加的锁，对当前操作的整张表加锁。实现简单，资源消耗少，加锁快，不会出现死锁；但触发锁冲突概率最高，高并发下效率极低。与存储引擎无关，MyISAM 和 InnoDB 都支持。
- **行级锁**：MySQL 中锁定粒度最小的锁，**针对索引字段加的锁**，只针对当前操作的行记录加锁。大大减少数据库操作冲突，并发度高；但加锁开销最大，加锁慢，会出现死锁。在存储引擎层面实现。

### 行级锁的使用有什么注意事项？

InnoDB 的行锁是针对索引字段加的锁。执行 UPDATE、DELETE 时，如果 WHERE 条件字段没有命中唯一索引或者索引失效，会导致扫描全表对表中的所有行记录加锁。**日常工作开发中经常会遇到，一定要多多注意！** 很多时候即用了索引也可能走全表扫描，这是 MySQL 优化器的原因。

### InnoDB 有哪几类行锁？

InnoDB 行锁通过对索引数据页上的记录加锁实现，支持三种行锁定方式：

- **记录锁（Record Lock）**：单个行记录上的锁；
- **间隙锁（Gap Lock）**：锁定一个范围，不包括记录本身；
- **临键锁（Next-Key Lock）**：Record Lock + Gap Lock，锁定一个范围且包含记录本身，主要解决幻读。

**在默认隔离级别 REPEATABLE-READ 下，行锁默认使用 Next-Key Lock。但如果操作的索引是唯一索引或主键，InnoDB 会对 Next-Key Lock 优化，降级为 Record Lock。**

### 共享锁和排他锁呢？

不论是表级锁还是行级锁，都有共享锁（S 锁）和排他锁（X 锁）：

- **共享锁（S 锁）**：读锁，读取记录时获取，允许多个事务同时获取；
- **排他锁（X 锁）**：写锁/独占锁，修改记录时获取，不允许多个事务同时获取，与任何锁都不兼容。

|  | S 锁 | X 锁 |
|--|------|------|
| S 锁 | 不冲突 | 冲突 |
| X 锁 | 冲突 | 冲突 |

由于 MVCC 的存在，对于一般的 SELECT 语句，InnoDB 不会加任何锁。可通过以下语句显式加锁：

```sql
SELECT ... LOCK IN SHARE MODE;  -- S 锁（MySQL 5.7 和 8.0）
SELECT ... FOR SHARE;           -- S 锁（MySQL 8.0）
SELECT ... FOR UPDATE;          -- X 锁
```

### 意向锁有什么作用？

如果需要用到表锁，如何判断表中的记录没有行锁？一行行遍历性能太差。**意向锁**用于快速判断是否可以对某个表使用表锁，是表级锁，共有两种：

- **意向共享锁（IS 锁）**：事务有意向对表中的某些记录加 S 锁，加 S 锁前必须先取得该表的 IS 锁；
- **意向排他锁（IX 锁）**：事务有意向对表中的某些记录加 X 锁，加 X 锁之前必须先取得该表的 IX 锁。

意向锁由数据引擎自己维护，用户无法手动操作。**意向锁之间互相兼容**；意向锁与表级别的 S 锁和 X 锁互斥（不与行级的互斥）。

### 当前读和快照读有什么区别？

**快照读**（一致性非锁定读）就是单纯的 SELECT 语句（不包括 `SELECT ... FOR UPDATE`、`SELECT ... LOCK IN SHARE MODE`、`SELECT ... FOR SHARE`）。快照即记录的历史版本，每行记录可能有多个历史版本。快照读情况下，如果读取的记录正在执行 UPDATE/DELETE，读取操作不会等待 X 锁释放，而是读取行的一个快照。

只有在 RC 和 RR 隔离级别下，InnoDB 才会使用一致性非锁定读：

- RC 级别：总是读取被锁定行的最新一份快照数据；
- RR 级别：总是读取本事务开始时的行数据版本。

**当前读**（一致性锁定读）就是给行记录加 X 锁或 S 锁：

```sql
SELECT...FOR UPDATE           -- 对读的记录加 X 锁
SELECT...LOCK IN SHARE MODE   -- 对读的记录加 S 锁
SELECT...FOR SHARE            -- 对读的记录加 S 锁
INSERT.../UPDATE.../DELETE... -- 对修改的记录加 X 锁
```

### 自增锁有了解吗？

InnoDB 中自增主键涉及一种特殊的表级锁——**自增锁（AUTO-INC Locks）**。不仅仅是自增主键，AUTO_INCREMENT 的列都会涉及。配置项 `innodb_autoinc_lock_mode`（MySQL 5.1.22 引入）：

| 模式 | 介绍 |
|------|------|
| 0 | 传统模式 |
| 1 | 连续模式（MySQL 8.0 之前默认） |
| 2 | 交错模式（MySQL 8.0 之后默认） |

交错模式下所有"INSERT-LIKE"语句都不使用表级锁，使用轻量级互斥锁，多条插入语句可并发执行，速度更快。但如果有主从同步需求且 Binlog 格式为 Statement，不要设置为交错模式，否则并发下插入语句执行顺序无法保障，会有数据不一致问题。

## ⭐️ MySQL 性能优化

### 能用 MySQL 直接存储文件（比如图片）吗？

可以但不建议，会严重影响数据库性能、消耗过多存储空间。建议使用云厂商文件存储服务或基于 FastDFS、MinIO 自建文件服务，**数据库只存储文件地址信息**。

### MySQL 如何存储 IP 地址？

将 IP 地址转换成整形数据存储，性能更好、占用空间更小。MySQL 提供：

- `INET_ATON()`：把 IP 转为无符号整型；
- `INET_NTOA()`：把整型的 IP 转为地址。

### 如何分析 SQL 的性能？

使用 `EXPLAIN` 命令分析 SQL 的执行计划。`EXPLAIN` 不会真的执行语句，而是通过查询优化器分析找出最优查询方案。适用于 SELECT、DELETE、INSERT、REPLACE、UPDATE 语句。

```sql
mysql> EXPLAIN SELECT `score`,`name` FROM `cus_order` ORDER BY `score` DESC;
+----+-------------+-----------+------------+------+---------------+------+---------+------+--------+----------+----------------+
| id | select_type | table     | partitions | type | possible_keys | key  | key_len | ref  | rows   | filtered | Extra          |
+----+-------------+-----------+------------+------+---------------+------+---------+------+--------+----------+----------------+
|  1 | SIMPLE      | cus_order | NULL       | ALL  | NULL          | NULL | NULL    | NULL | 997572 |   100.00 | Using filesort |
+----+-------------+-----------+------------+------+---------------+------+---------+------+--------+----------+----------------+
```

各字段含义：

| 列名 | 含义 |
|------|------|
| id | SELECT 查询的序列标识符 |
| select_type | SELECT 关键字对应的查询类型 |
| table | 用到的表名 |
| partitions | 匹配的分区（未分区表为 NULL） |
| type | 表的访问方法 |
| possible_keys | 可能用到的索引 |
| key | 实际用到的索引 |
| key_len | 所选索引的长度 |
| ref | 使用索引等值查询时与索引作比较的列或常量 |
| rows | 预计要读取的行数 |
| filtered | 按表条件过滤后留存记录数的百分比 |
| Extra | 附加信息 |

### MySQL 性能怎么优化？（面试回答框架）

按"**点-线-面**"思路展开：

**1. 抓住核心：慢 SQL 定位与分析**——监控工具（慢查询日志、Performance Schema）+ EXPLAIN 命令（执行顺序、索引使用、全表扫描）。

**2. 由点及面：索引、表结构和 SQL 优化**——索引创建原则、覆盖索引、最左前缀匹配；字段类型选择、避免冗余、范式与反范式；避免 SELECT *、用具体字段、连接代替子查询、合理分页、批量操作。

**3. 进阶方案：架构优化**——读写分离、分库分表（权衡复杂性和维护成本）、数据冷热分离、缓存机制（Redis，性价比极高）。

**4. 其他手段**——连接池配置（大小、超时）、硬件配置（高性能服务器、增加内存、SSD）。

**5. 总结优先级**：慢 SQL 定位 → 索引优化 → 表结构设计 → SQL 优化；架构层面优化（读写分离、分库分表、冷热分离）作为最后手段，因其引入的复杂性会带来额外维护成本。
